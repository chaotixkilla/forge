# pull-request (`--pr=<number>`)

Activated by `--pr=<number>`, referenced from [scope-the-review](../phases/01-scope-the-review.md).

The base review reads the local working-tree diff — ambient, no capability needed. This module changes *where the change comes from*: instead of the local diff, fetch a remote pull request's diff **and** its surrounding context through the vcs capability, so review can run against a change that isn't in the local tree. Deletion test: remove this module and review still runs on the local diff; it is genuinely optional, which is why it is a module and not part of the scope phase.

## The delta

- **Fetch the PR's diff** by number, through the vcs capability; the dispatch resolves to whichever provider is configured. This diff replaces the working-tree diff as the change under review, and its **declared base..head** — the base the PR was opened against, carried in the fetched metadata — *is* the review window. Do **not** re-derive the base here as a merge-base against the repository's default branch: that derivation belongs to the local `--changed` path in [scope-the-review](../phases/01-scope-the-review.md) and gives the wrong window for a PR opened against a non-default base (a stacked PR whose base is another feature branch). For `--pr`, the PR's declared base wins.
- **Fetch the PR's description and context** — the title, body, and any linked intent — and hand them to [build-the-mental-model](../phases/02-build-the-mental-model.md) as first-class evidence of *intent*. A PR description often states the goal more explicitly than the diff does, which sharpens the standard the change is judged against ([respect-author-intent](../rules/respect-author-intent.md)).
- **Materialize the change to file-state at the PR head.** The fetched diff carries the changed *lines*, but [scope-the-review](../phases/01-scope-the-review.md)'s "load surrounding code" and [read-the-diff-in-its-blast-radius](../rules/read-the-diff-in-its-blast-radius.md) require reading definitions, call sites, and invariants *as they stand at the PR revision* — content the diff does not carry. So, through the vcs capability, check the PR out at its **current head** into an **isolated working copy** (a worktree), and run the mental-model, hunt, and craft passes against *that* tree — not against whatever branch the user happens to have checked out, and not against a stale local copy of the PR branch. Materialize into an isolated worktree so review never disturbs the user's working tree; discard it when the review completes. (This materialization is intrinsic to `--pr` — it always happens, it is not a user-chosen flag.)
- **Cross-check the materialized change against the PR metadata as a scope tripwire.** After materializing, compare the file count and hunk/line counts of the checked-out change against the counts the PR metadata reports (e.g. the provider's `changedFiles`). A mismatch means the head you materialized is *not* the current PR head — a force-push moved it, or a fetch grabbed a stale ref. Do not review a mismatched tree: re-fetch the current head and re-materialize, and if the counts still disagree, report the discrepancy rather than silently reviewing the wrong revision. (basis: this is the one place `--pr` can silently review the wrong change — a stale/force-pushed head produces a confident, clean report scoped to code that is no longer the PR; the count cross-check is the cheapest tripwire that catches it.)

Everything downstream of scoping is unchanged in *procedure*: the hunt, craft, triage, and delivery passes run identically — now over the materialized checkout and its fetched diff, rather than the local working tree.

## Prerequisite and degrade

`--pr` is the reason review reaches the vcs capability at all. A remote PR cannot be fetched without it, so invoke the vcs capability (served by the `vcs` skill, which dispatches to the configured provider). If it reports the backend unavailable — `tools.vcs` unconfigured — degrade by reporting plainly that the PR could not be fetched (the `vcs` skill owns guiding the user through `init:vcs`); do **not** silently review the local diff instead, which would answer a different question than the caller asked. review itself declares no vcs prerequisite — the `vcs` skill owns `tools.vcs` (doer-owns-prerequisites), and review's base path is ambient, running without any configured backend. This is the one path in review where a missing vcs capability blocks the requested work rather than merely narrowing it.
