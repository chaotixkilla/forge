# Respect author intent

Every change sets out to do something, and a review's job is to judge whether it does *that* well — not whether it does what the reviewer would have done instead. The failure this rule prevents is the review that redefines the task: the author added a cache, and the review critiques the caching strategy they never proposed, or folds "you should also refactor the surrounding module" into the verdict as if it were a defect in the change. That review is unactionable, because it holds the change to a goal it never had. This rule keeps the review anchored to the change's own intent and handles genuine scope problems as their own, separate finding.

## Review what the change set out to do

First, establish the intent — the mental-model pass ([build-the-mental-model](../phases/02-build-the-mental-model.md)) exists partly for this: what is this change trying to accomplish, per its diff, its description, and its context? When those sources disagree — the description promises one thing, the diff does another — the divergence is itself a finding to surface, not a call to make silently ([build-the-mental-model](../phases/02-build-the-mental-model.md) pins how). Then judge against the stated goal. A change that achieves its stated goal correctly and cleanly is a good change, even if you would have solved the underlying problem differently. "I'd have used a different approach" is not a finding unless the author's approach is actually *wrong* ([separate-correctness-from-taste](separate-correctness-from-taste.md)) or breaks a local convention ([judge-against-the-surrounding-code](judge-against-the-surrounding-code.md)).

## Scope creep is a finding, not a verdict modifier

Two scope problems are real and worth surfacing — but as their own findings, never folded into the correctness or craft verdict:

- **The change does more than it set out to** — an unrelated refactor rides along, a drive-by edit touches a different concern. Flag it as a scope finding ("this diff bundles an unrelated change to X; consider splitting it"), so the author can separate concerns. Do not let the extra scope silently raise or lower your judgment of the intended change. A scope finding is an **ungraded boundary note — no severity, no confidence** ([severity-scale](severity-scale.md), [deliver-findings](../phases/06-deliver-findings.md)); it says something is *outside* the review, not how bad a defect is. (If the bundled change is itself *wrong*, that wrongness is an ordinary correctness finding on it, graded normally — separate from the scope note that it doesn't belong here.)
- **The change does too little to be correct** — it sets out to fix a bug but leaves a case unhandled, or its stated goal genuinely requires more than it delivers. This *is* a correctness finding, framed against the change's own goal: "the change aims to handle empty input but the null case remains."

The discriminator between these and mere preference: **does the gap trace to the change's *own* stated intent, or to a goal the reviewer is importing?** A gap against the change's own intent is a finding; a gap against the reviewer's larger ambitions for the code is out of scope. Such an imported-ambition suggestion is *not* a scope finding — it is at most an ordinary `info`-severity craft suggestion if a thoughtful author would be glad to see it, and dropped otherwise ([weight-by-impact-not-count](weight-by-impact-not-count.md)). Keep the two distinct: a **scope finding** flags a change that *is present but doesn't belong* (ungraded boundary note); an **imported-ambition suggestion** flags work *not present that the reviewer wishes were* (graded `info`, or dropped).
