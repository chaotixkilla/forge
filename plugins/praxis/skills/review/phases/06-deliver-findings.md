The ranked list is the review's substance; this phase gets it to where the author will act on it, in a shape they can read the same way every time. Two reviewers who reach the same findings must also produce reports of the same character — so the output shape is pinned here, not left to each run to invent. The sink is chosen by flag; the default is a local report, and a report is *always* produced as the record even when another sink also fires.

## The default sink: a structured report

Render the findings as a report with a fixed shape, so two runs are comparable and an author knows where to look:

- **A scope line** — what was reviewed: the resolved diff window (the base and endpoint that [scope-the-review](01-scope-the-review.md) settled on) and anything deliberately excluded. This makes the review's coverage legible — the author sees exactly what window the findings, and the silence, cover.
- **A verdict line** — the outcome at a glance: a single combined count by severity across both sections, each count led by its pinned severity marker ([severity-scale](../rules/severity-scale.md)) so the worst is visible without reading — e.g. **🟠 1 high · 🟡 2 medium · 🔵 3 low** — highest severity first, or plainly **"no findings"** when the list is empty. The tally is combined; the correctness/craft split lives in the sections below, not in the verdict line. Silence is a real verdict, not an empty section ([weight-by-impact-not-count](../rules/weight-by-impact-not-count.md)).
- **A fitness verdict** — a top-line judgment of whether the change *does what it set out to*: **satisfies** / **partially satisfies** / **does not satisfy** the requirement it is held to — the stated intent from [build-the-mental-model](02-build-the-mental-model.md), or the linked ticket/spec when one is in hand. For *partially* or *does not*, name the gap — the acceptance the change leaves unmet. The boundaries: **satisfies** when every stated acceptance is met (a remaining nit that touches no acceptance is a low/info finding, not a fitness demotion); **partially satisfies** when the change's *central* goal is met but a stated acceptance is not; **does not satisfy** when the central goal itself is unmet. This is distinct from the defect list: a change can be defect-free yet not satisfy its goal (it built the wrong thing), or carry nits yet fully satisfy it. Judge against the *stated* requirement; never re-litigate whether the requirement itself is right (that is `spec`'s job). When no requirement is stated at all — no ticket, no described goal — say so and judge against the change's own apparent intent, rather than inventing a requirement to grade against. (basis: the review role's own "does it achieve its goal" question, made an explicit verdict; the central-goal-vs-stated-acceptance split is what separates the three, and the no-stated-requirement case names its basis of judgment so a cold run never fabricates a requirement.)
- **Correctness findings**, then **craft findings**, in two separate sections — the reader must be able to tell a must-fix defect from an optional cleanup at a glance ([separate-correctness-from-taste](../rules/separate-correctness-from-taste.md)).
- **Each finding, in rank order within its section**, as a fixed record led by its severity marker: `<🔴/🟠/🟡/🔵/⚪> severity · confidence · file:line — what is wrong — the failing scenario or concrete cost — the smallest suggested fix` (the marker is the pinned one for that severity, paired with the word — [severity-scale](../rules/severity-scale.md)). The location and scenario are mandatory ([anchor-every-finding-to-evidence](../rules/anchor-every-finding-to-evidence.md)); the suggestion is the least-invasive one that resolves it ([prefer-the-smaller-suggestion](../rules/prefer-the-smaller-suggestion.md)).
- **Scope findings**, if any, in their own short section — the bundled-but-unrelated changes, kept out of the verdict. A scope finding **carries no severity and no confidence grade**: it is a boundary note, not a graded defect — one line naming *what* is out of scope and *why* (bundled and unrelated to the change's intent, so not reviewed here), optionally with "consider splitting it." Do not put it on the severity scale or fold it into the verdict tally. (basis: severity grades a defect *in the change under review* by its consequence; a scope finding states something is *outside* that review, so it has no consequence-in-the-change to grade — a run that reaches for the general scale invents a rung the scale never defined. If a bundled change is itself *wrong*, that wrongness is a normal correctness finding on that change, not a "severe" scope note.)

That record shape is the pinned output; do not vary the fields run to run. (basis: the field set is the minimum an author needs to act — grade, certainty, location, why, and the fix — mirroring the finding shape a review output conventionally carries, as the harness's own review channel does; pinning it is what makes two cold reviewers format identically.)

## The alternate and additional sinks

The sinks are independent and composable; the report above is always the record, and a flag adds or redirects delivery on top of it:

- **`--comment`** publishes the findings back onto the change through the vcs capability instead of returning them only locally — see [publish-to-vcs](../modules/publish-to-vcs.md). `--inline` modifies that module to anchor each finding to its exact line rather than posting one summary; it does nothing without `--comment`. If the vcs capability reports the backend unavailable, degrade — fall back to the local report and say the findings were not posted (the `vcs` skill owns guiding the user through `init:vcs`).
- **`--fix`** applies the accepted findings to the working tree as edits and re-checks each at its site — see [apply-fixes](../modules/apply-fixes.md).
- **`--gate`** computes a pass/fail status from the findings at or above the floor and exits accordingly — see [gate-mode](../modules/gate-mode.md).

## How the sinks compose

The interactions are defined, not left to chance:

- **`--gate` with `--comment`** — both fire: post the findings *and* set the pass/fail status. The gate reads the same floored list the report shows; commenting does not change the verdict. Here the posted review's **stance** follows the gate verdict — a pass posts as an approval, a fail as a request-for-changes ([publish-to-vcs](../modules/publish-to-vcs.md)); `--comment` *without* `--gate` posts comment-only, never casting an approval on the caller's behalf.
- **`--fix` with `--comment`** — apply what can be auto-fixed, then comment on what remains (the findings not auto-fixable, e.g. a design-level correctness issue). Do not comment "fixed" as a finding; report the applied fixes in the summary.
- **`--fix` with `--gate`** — apply fixes first, then compute the gate status against what *remains* after fixing, so a fully-fixed change can pass.

(These combinations are the resolution of the sinks' interaction question — independent sinks over one shared floored list, each reading the same triaged findings; no combination redefines severity or the floor.)

Whatever sinks fire, return the record of what was delivered — the findings, and for `--fix`/`--comment`/`--gate`, what was applied, posted, or gated — so the run's outcome is auditable.
