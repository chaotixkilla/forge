The ranked list is the review's substance; this phase gets it to where the author will act on it, in a shape they can read the same way every time. Two reviewers who reach the same findings must also produce reports of the same character — so the output shape is pinned here, not left to each run to invent. The sink is chosen by flag; the default is a local report, and a report is *always* produced as the record even when another sink also fires.

## The default sink: a structured report

Render the findings as a report with a fixed shape, so two runs are comparable and an author knows where to look. The report has two parts, in this order: **the reader's brief**, then **the findings sections**.

### The reader's brief

The brief is the report's head: the orientation a reader needs to judge the change *before* reading a single finding, and to pick the thread back up in a later session without re-deriving it. Emit it when `output.brief` is true — its default, and the value that applies whenever the setting cannot be read ([report-style-settings](../../init/rules/report-style-settings.md) defines the four keys, their domains, and what to do with a value it does not define). When it is false, skip the brief and put the fitness, verdict, and scope lines back directly above the findings sections: those three are the report's record and are never dropped, only relocated. `(basis: derived — the maintainer's cost is a reader parsing a whole report to learn what a change means for them, so the brief is placed and pinned as the head rather than offered as a tail summary; the false case relocates rather than removes the three record lines because dropping a review's coverage statement to honor a style setting would trade legibility for silence.)`

The fields are pinned in this order; do not vary them run to run:

- **A fitness verdict** — a top-line judgment of whether the change *does what it set out to*: **satisfies** / **partially satisfies** / **does not satisfy** the requirement it is held to — the stated intent from [build-the-mental-model](02-build-the-mental-model.md), or the linked ticket/spec when one is in hand. For *partially* or *does not*, name the gap — the acceptance the change leaves unmet. The boundaries: **satisfies** when every stated acceptance is met (a remaining nit that touches no acceptance is a low/info finding, not a fitness demotion); **partially satisfies** when the change's *central* goal is met but a stated acceptance is not; **does not satisfy** when the central goal itself is unmet. This is distinct from the defect list: a change can be defect-free yet not satisfy its goal (it built the wrong thing), or carry nits yet fully satisfy it. Judge against the *stated* requirement; never re-litigate whether the requirement itself is right (that is `spec`'s job). When no requirement is stated at all — no ticket, no described goal — say so and judge against the change's own apparent intent, rather than inventing a requirement to grade against. (basis: the review role's own "does it achieve its goal" question, made an explicit verdict; the central-goal-vs-stated-acceptance split is what separates the three, and the no-stated-requirement case names its basis of judgment so a cold run never fabricates a requirement.)
- **A verdict line** — the outcome at a glance: a single combined count by severity across both sections, each count led by its pinned severity marker ([severity-scale](../rules/severity-scale.md)) so the worst is visible without reading — e.g. **🟠 1 high · 🟡 2 medium · 🔵 3 low** — highest severity first, or plainly **"no findings"** when the list is empty. The tally is combined; the correctness/craft split lives in the sections below, not in the verdict line. Silence is a real verdict, not an empty section ([weight-by-impact-not-count](../rules/weight-by-impact-not-count.md)).
- **What a user will notice** — the change's effect at the product's outer boundary: something a person *using* the running software can observe without reading code — a screen or rendered output, a message, a flow that behaves differently, a response they consume, a delay they would feel. The discriminator is **who bears it**: this field is for someone who uses the product and never reads this repo; anything only a person writing code against this repo would notice belongs to the next field. A codebase with no runtime surface of its own — a library, an internal package — legitimately has **none** here, its whole effect landing in the developer-facing field. State the none-case as **"no user-observable change"**; it is a real outcome, not an omitted section. `(basis: derived — the two impact fields split by *who bears the change* rather than by artifact type, because a type-based split collapses on a library (whose users are developers) and forces a cold run either to invent a user-facing effect or to drop the field silently; the who-bears-it test stays answerable for every codebase.)`
- **What another developer must know** — which of a colleague's correct assumptions this change invalidates: a signature, return shape, error mode, or default that moved; a config key or environment expectation; an invariant the code used to guarantee; a build, test, or release step that now runs differently; a business-logic assumption someone working elsewhere would reasonably still hold. The discriminator: **could another developer's correct code or correct mental model become wrong because of this change, without their file being touched?** If yes, it belongs here. Read this from the contracts [build-the-mental-model](02-build-the-mental-model.md) already mapped rather than re-deriving them. Explicit none: **"nothing outside the diff changes for other developers."** `(basis: derived — this field is the contracts read from [build-the-mental-model](02-build-the-mental-model.md) turned outward, so its discriminator is that phase's own contract-change test applied to a third party: a change is developer-facing exactly when it can invalidate correct code the diff never touched. Anchoring it there keeps one definition of a contract change in this skill instead of two.)`
- **Assumptions the change rests on** — the load-bearing ones only, where load-bearing means **the change is wrong if the assumption is false**. Mark each with exactly one of two labels, so the reader knows what still needs their own eyes:
  - **verified** — this review settled it from the code in the resolved window; it holds.
  - **left to the reader** — the review could not settle it from the code available, *and the entry says why* (it turns on runtime data, an external system's behavior, or product intent the code cannot express).
  The discriminator is mechanical, in three branches on one question — *could the review settle it from the code in the resolved diff window and its blast radius?* **No** → **left to the reader**, carrying the reason. **Yes, and it holds** → **verified**. **Yes, and it does not hold** → it is not a brief entry at all but a **correctness finding**; name it here only as a pointer to that finding, so the brief and the findings can never disagree. Explicit none: **"no load-bearing assumptions identified."** `(basis: derived — the report is produced after the hunt, so an unqualified "assumptions to test" list would read as a to-do for work already done and would leave the reader unable to tell a checked assumption from an unchecked one; the two labels are what make the review's actual coverage legible, which is the purpose the field was asked for.)`
- **Read these first** — the files in the order someone evaluating the change should open them, each with one clause on why it is on the list. The ordering is **judgment**: lead with the file carrying the change's core, then what it calls or depends on, then the tests that pin it — but weigh the change's actual shape rather than following that as a template. Cap the list at the files that carry the change's *meaning*; enumerating every touched file rebuilds the wall of text the brief exists to replace. **Paths must resolve in the tree the reader has**: emit them relative to the root of the checkout the review actually read its files in — the one the window was resolved in ([scope-the-review](01-scope-the-review.md)). For the local default that is the current working tree, which is the **linked worktree's own root** when the run is inside one, never the primary checkout's; a path built from the primary root will not open for a reader working in the worktree. For `--pr` it is the isolated checkout materialized at the PR head ([pull-request](../modules/pull-request.md)), so the paths are repo-relative to that head. `(basis: derived — the field exists to spend the reader's attention well, so it is capped by meaning rather than by coverage; the worktree clause resolves a reported failure where emitted links resolved against the wrong root, by naming the one root that is always correct — the window's own.)`
- **A scope line** — what was reviewed: the resolved diff window (the base and endpoint that [scope-the-review](01-scope-the-review.md) settled on) and anything deliberately excluded. This makes the review's coverage legible — the author sees exactly what window the findings, and the silence, cover.

How tightly each field is written follows `output.verbosity`, whose values and default are defined in [report-style-settings](../../init/rules/report-style-settings.md) — including the constraint that no value may drop a field from this shape. What is specific here: a field with nothing in it is **accounted for, never omitted** — a missing field and an empty one read identically to the reader, and only one of them is honest. But accounting for it costs a line, not a sentence each: when **two or more** fields are empty, fold them into a single *nothing owed* line that names each one, and keep a per-field sentence only where a single field stands empty. A clean change is the common case and the one where a seven-field preamble buys the reader least, so the fold is what keeps the brief worth reading on exactly the reports that should be shortest. `(basis: ratified by the maintainer, 2026-09-02, from a measured cost — the brief as first written ran 29% longer than the report it replaced on a no-findings review, and the mandatory per-field none-case sentences were where that length sat. The fold keeps every field accounted for, so nothing the honesty floor protects is dropped; what it removes is the repetition, which the floor never protected.)` With `--comment`, the brief heads the posted review body as well — it is the same orientation a pull-request reader needs ([publish-to-vcs](../modules/publish-to-vcs.md)); under `--inline` it stays in the summary comment and is never anchored to a line.

### The findings sections

- **Correctness findings**, then **craft findings**, in two separate sections — the reader must be able to tell a must-fix defect from an optional cleanup at a glance ([separate-correctness-from-taste](../rules/separate-correctness-from-taste.md)).
- **Each finding, in rank order within its section**, as a fixed record led by its severity marker: `<🔴/🟠/🟡/🔵/⚪> severity · confidence · file:line — what is wrong — the failing scenario or concrete cost — the smallest suggested fix` (the marker is the pinned one for that severity, paired with the word — [severity-scale](../rules/severity-scale.md)). The location and scenario are mandatory ([anchor-every-finding-to-evidence](../rules/anchor-every-finding-to-evidence.md)); the suggestion is the least-invasive one that resolves it ([prefer-the-smaller-suggestion](../rules/prefer-the-smaller-suggestion.md)).
- **Scope findings**, if any, in their own short section — the bundled-but-unrelated changes, kept out of the verdict. A scope finding **carries no severity and no confidence grade**: it is a boundary note, not a graded defect — one line naming *what* is out of scope and *why* (bundled and unrelated to the change's intent, so not reviewed here), optionally with "consider splitting it." Do not put it on the severity scale or fold it into the verdict tally. (basis: severity grades a defect *in the change under review* by its consequence; a scope finding states something is *outside* that review, so it has no consequence-in-the-change to grade — a run that reaches for the general scale invents a rung the scale never defined. If a bundled change is itself *wrong*, that wrongness is a normal correctness finding on that change, not a "severe" scope note.)

**A reference to a finding carries the finding.** Wherever a finding is named outside its own record — in the brief, in a summary line, in what `--fix` reports as applied, in a comment posted back onto the change — identify it by its `file:line` and a few words of the defect, never by a bare ordinal. "Issue #3" is legible only to someone currently looking at the list, which excludes the author returning to it tomorrow and the reader holding two other changes in their head; the brief's assumptions field, which names a disproved assumption as a pointer to its finding, is governed by this same pin. `(basis: ratified by the maintainer, 2026-09-01 — the reported cost is concrete: working several sessions at once, a bare ordinal forces a "what issue is this?" reload of a list the reader had already put down. Carrying a location and a few words costs the writer once; omitting them costs every reader, every time.)`

That record shape is the pinned output; do not vary the fields run to run. (basis: the field set is the minimum an author needs to act — grade, certainty, location, why, and the fix — mirroring the finding shape a review output conventionally carries, as the harness's own review channel does; pinning it is what makes two cold reviewers format identically.)

Where the review's outcome is state a later session would re-derive — that this change was reviewed, at what verdict, and what it left outstanding — record it under the entry shape and the verify-before-acting discipline in [carry-status-across-sessions](../../develop/rules/continuity/carry-status-across-sessions.md).

## Before it goes out, read it as its reader

Put the finished report through [deliver-at-the-readers-register](../../communicate/rules/deliver-at-the-readers-register.md) before delivering it: take from that rule the obligations this phase has not already settled for itself, and apply its honesty floor to the result. A run with no register to write to falls back on the only vocabulary it has loaded — this procedure's own — which is how a report comes out accurate and unreadable. Read the floor from the rule item by item rather than from memory — the passages it protects are exactly the ones that read as padding to anyone not checking whether the claim is true — and let its carve-out for named levels and verdict values hold the graded rungs and status names this skill defines and reports on.

**And a visual where prose would carry it worse.** Where what this report describes alters a *structure* — a shape, a flow, a set of relationships — show it rather than describing it, per `output.diagrams` (`when-structural` by default — [report-style-settings](../../init/rules/report-style-settings.md)) and the judgment in [when-a-visual-is-owed](../../communicate/rules/when-a-visual-is-owed.md), which decides whether one is genuinely owed here. A visual is earned by what the subject *is*, never by how long the prose ran: it stands in for the paragraph that would have described the shape, and it is decoration the moment it sits beside that paragraph instead.

## The alternate and additional sinks

The sinks are independent and composable; the report above is always the record, and a flag adds or redirects delivery on top of it:

- **`--comment`** publishes the findings back onto the change through the vcs capability instead of returning them only locally — see [publish-to-vcs](../modules/publish-to-vcs.md). `--inline` modifies that module to anchor each finding to its exact line rather than posting one summary; it does nothing without `--comment`. If the vcs capability reports the backend unavailable, degrade — fall back to the local report and say the findings were not posted (the `vcs` skill owns guiding the user through `init:vcs`).
- **`--fix`** applies the accepted findings to the working tree as edits and re-checks each at its site — see [apply-fixes](../modules/apply-fixes.md).
- **`--typed`** also emits the findings to the harness's typed finding channel as structured records, beside the report rather than instead of it — see [typed-findings](../modules/typed-findings.md).
- **`--gate`** computes a pass/fail status from the findings at or above the floor and exits accordingly — see [gate-mode](../modules/gate-mode.md).

## How the sinks compose

The interactions are defined, not left to chance:

- **`--gate` with `--comment`** — both fire: post the findings *and* set the pass/fail status. The gate reads the same floored list the report shows; commenting does not change the verdict. Here the posted review's **stance** follows the gate verdict — a pass posts as an approval, a fail as a request-for-changes ([publish-to-vcs](../modules/publish-to-vcs.md)); `--comment` *without* `--gate` posts comment-only, never casting an approval on the caller's behalf.
- **`--fix` with `--comment`** — apply what can be auto-fixed, then comment on what remains (the findings not auto-fixable, e.g. a design-level correctness issue). Do not comment "fixed" as a finding; report the applied fixes in the summary.
- **`--fix` with `--gate`** — apply fixes first, then compute the gate status against what *remains* after fixing, so a fully-fixed change can pass.

(These combinations are the resolution of the sinks' interaction question — independent sinks over one shared floored list, each reading the same triaged findings; no combination redefines severity or the floor.)

Whatever sinks fire, return the record of what was delivered — the findings, and for `--fix`/`--comment`/`--gate`, what was applied, posted, or gated — so the run's outcome is auditable.
