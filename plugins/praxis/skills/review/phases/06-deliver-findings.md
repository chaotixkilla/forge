## The default sink: a structured report

Render the findings as a report with a fixed shape, so two runs are comparable and an author knows where to look. The report has two parts, in this order: **the reader's brief**, then **the findings sections**.

### The reader's brief

The brief is the report's head: the orientation a reader needs to judge the change *before* reading a single finding, and to pick the thread back up in a later session without re-deriving it. Emit it when `output.brief` is true — its default, and the value that applies whenever the setting cannot be read ([report-style-settings](../../../craft/writing/report-style-settings.md) defines the four keys, their domains, and what to do with a value it does not define). When it is false, skip the brief and put the fitness, verdict, and scope lines back directly above the findings sections: those three are the report's record and are never dropped, only relocated. `(basis: derived from the maintainer's cost of parsing a whole report to learn what a change means)`

The fields are pinned in this order; do not vary them run to run:

- **Fitness** — whether the change *does what it set out to*, as one result per acceptance on the results scale in [results-and-certainty](../../../craft/evidence/results-and-certainty.md): the **central goal** first, then each other stated acceptance of the requirement the change is held to — the stated intent from [build-the-mental-model](02-build-the-mental-model.md), or the linked ticket/spec when one is in hand. Every result's scope is the window in the scope line, read and not run. Weigh every graded finding here, including one the floors withhold from the findings sections; name a withheld one by its `file:line` and defect. Place each acceptance by asking in order, and stop at the first that answers: `(basis: derived from review reading the code, not running it, and from the standard's placement questions)`
  - **fails** — a finding at traced certainty or above breaks it (its failing scenario falls inside what the acceptance requires), or the code doesn't attempt it at all. Name the gap: what the change leaves unmet.
  - **not checked** — nothing the review read bears on it, such as an external system's behavior or product intent the code doesn't express. Give that reason and what would settle it.
  - **unsettled** — code the review read bears on it but doesn't settle it: an inferred finding would break it if real, it turns on a runtime property a read can't settle, or a part it rests on went unread. Name what would settle it: that finding checked, a verify or test run, or the part read.
  - **holds** — the code meets it and every part bearing on it was read. An unverified finding doesn't move a result, and a nit that touches no acceptance is a low/info finding, never a fitness result.

  For example: *central goal, export invoices as CSV: holds · totals match the ledger: unsettled, the inferred finding at `export.py:88` would break it · runs under 2s for 10k rows: fails, the traced finding at `export.py:40` rescans every row for each row; were that finding only inferred, it would be unsettled, a timed run at 10k rows settling it · the bank's importer accepts the file: not checked, nothing the review read shows the importer's format; a test against it would settle it.* Fitness is distinct from the defect list: a change can be defect-free yet fail its central goal (it built the wrong thing), or carry nits yet hold on every acceptance. Judge against the *stated* requirement; never re-litigate whether the requirement itself is right (that is `spec`'s job). When no requirement is stated at all — no ticket, no described goal — say so and judge against the change's own apparent intent, rather than inventing a requirement to grade against: that intent working is the central goal and each behavior it introduces an acceptance, and there only a finding at high or above moves a result, placed by the tests above. In a pass that reads the author's rationale ([prior-pass](../modules/prior-pass.md)), a goal the description states joins the requirement, and each result is placed again against it. (basis: derived from the review role's "does it achieve its goal" question)
- **A verdict line** — the outcome at a glance: a single combined count by severity across both sections, each count led by its pinned severity marker ([severity-scale](../rules/severity-scale.md)) so the worst is visible without reading — e.g. **🟠 1 high · 🟡 2 medium · 🔵 3 low** — highest severity first, or plainly **"no findings"** when the list is empty. The tally is combined; the correctness/craft split lives in the sections below, not in the verdict line. Silence is a real verdict, not an empty section ([weight-by-impact-not-count](../rules/weight-by-impact-not-count.md)).
- **What a user will notice** — the change's effect at the product's outer boundary: something a person *using* the running software can observe without reading code — a screen or rendered output, a message, a flow that behaves differently, a response they consume, a delay they would feel. The discriminator is **who bears it**: this field is for someone who uses the product and never reads this repo; anything only a person writing code against this repo would notice belongs to the next field. A codebase with no runtime surface of its own — a library, an internal package — legitimately has **none** here, its whole effect landing in the developer-facing field. State the none-case as **"no user-observable change"**; it is a real outcome, not an omitted section. `(basis: derived from a split by artifact type collapsing on a library, whose users are developers)`
- **What another developer must know** — which of a colleague's correct assumptions this change invalidates: a signature, return shape, error mode, or default that moved; a config key or environment expectation; an invariant the code used to guarantee; a build, test, or release step that now runs differently; a business-logic assumption someone working elsewhere would reasonably still hold. The discriminator: **could another developer's correct code or correct mental model become wrong because of this change, without their file being touched?** If yes, it belongs here. Read this from the contracts [build-the-mental-model](02-build-the-mental-model.md) already mapped rather than re-deriving them. Explicit none: **"nothing outside the diff changes for other developers."** `(basis: derived from the contracts [build-the-mental-model](02-build-the-mental-model.md) maps)`
- **Assumptions the change rests on** — the load-bearing ones only, where load-bearing means **the change is wrong if the assumption is false**. Give each one result on the results scale ([results-and-certainty](../../../craft/evidence/results-and-certainty.md)), so the reader knows what still needs their own eyes. The placement turns on one question — *could the review settle it from the code in the resolved diff window and its blast radius, or from evidence its caller supplied?*
  - **No, and nothing the review can read bears on it** → **not checked**, *and the entry says why*: it turns on runtime data, an external system's behavior, or product intent the code cannot express.
  - **No, though code the review read bears on it** → **unsettled**, naming what would settle it.
  - **Yes, and it holds** → **holds**, citing the code or the caller's evidence (a cited document, a test run) that settled it.
  - **Yes, and it does not hold** → it fails, and is not a brief entry at all but a **correctness finding**; name it here only as a pointer to that finding, so the brief and the findings can never disagree.

  Explicit none: **"no load-bearing assumptions identified."** `(basis: derived from the field's purpose: making the review's coverage legible; the unsettled branch from the standard's line between unsettled and not checked)`
- **Decisions the change makes** — the choices an approval ratifies. List a choice when a reasonable author could have made it otherwise **and** its effect reaches beyond the lines it touches: into other code, users, data or operations. Mark the one-way doors among them, by the test in [design-for-reversibility](../../../craft/engineering/design-for-reversibility.md). Each entry is `the choice — instead of the alternative — accepting the risk`, e.g. *stores export rows as JSON in the invoices table — instead of a separate export table — accepting that a later schema change needs a data migration · one-way door*. Where the rationale names the alternative the author weighed, use theirs; otherwise name the likeliest one and say it's the review's reading. The discriminator against its neighbours: an **assumption** is a fact the change believes (true or false), a **decision** is a choice it made (better or worse), and a **finding** is a defect. A plainly wrong decision is a finding, named here only as a pointer to it, as the assumptions field does. Explicit none: **"no decisions beyond what the requirement dictates."** `(basis: maintainer, 2026-09-30)` `(routed to maintainer: the two-part inclusion bar, since the list is meant to stay small and a choice confined to the change is the author's own)`
- **Read these first** — the files in the order someone evaluating the change should open them, each with one clause on why it is on the list. The ordering is **judgment**: lead with the file carrying the change's core, then what it calls or depends on, then the tests that pin it — but weigh the change's actual shape rather than following that as a template. Cap the list at the files that carry the change's *meaning*; enumerating every touched file rebuilds the wall of text the brief exists to replace. **Paths must resolve in the tree the reader has**: emit them relative to the root of the checkout the review actually read its files in — the one the window was resolved in ([scope-the-review](01-scope-the-review.md)). For the local default that is the current working tree, which is the **linked worktree's own root** when the run is inside one, never the primary checkout's; a path built from the primary root will not open for a reader working in the worktree. For `--change` it is the isolated checkout materialized at the review request head ([hosted-change](../modules/hosted-change.md)), so the paths are repo-relative to that head. `(basis: derived from the field's purpose and a reported failure: links resolved against the wrong root)`
- **A scope line** — what was reviewed: the resolved diff window (the base and endpoint that [scope-the-review](01-scope-the-review.md) settled on, the endpoint as a commit, so a later pass can tell whether the change has moved since) and anything deliberately excluded.

How tightly each field is written follows `output.verbosity`, whose values and default are defined in [report-style-settings](../../../craft/writing/report-style-settings.md) — including the constraint that no value may drop a field from this shape. What is specific here: a field with nothing in it is **accounted for, never omitted** — a missing field and an empty one read identically to the reader, and only one of them is honest. But accounting for it costs a line, not a sentence each: when **two or more** fields are empty, fold them into a single *nothing owed* line that names each one, and keep a per-field sentence only where a single field stands empty. A clean change is the common case and the one where an eight-field preamble buys the reader least, so the fold is what keeps the brief worth reading on exactly the reports that should be shortest. `(basis: maintainer, 2026-09-02, after the first brief ran 29% longer than its no-findings report)` When the review is posted on the change, the brief heads the posted review body as well — it is the same orientation a review-request reader needs — and it stays in the summary, never anchored to a line.

### The findings sections

- **Correctness findings**, then **craft findings**, in two separate sections — the reader must be able to tell a must-fix defect from an optional cleanup at a glance ([separate-correctness-from-taste](../rules/separate-correctness-from-taste.md)).
- **Each finding, in rank order within its section**, as a fixed record led by its severity marker: `<🔴/🟠/🟡/🔵/⚪> severity · certainty · file:line — what is wrong — the failing scenario or concrete cost — the smallest suggested fix` (the marker is the pinned one for that severity, paired with the word — [severity-scale](../rules/severity-scale.md)). The location and scenario are mandatory ([anchor-every-claim](../../../craft/evidence/anchor-every-claim.md)); the suggestion is the least-invasive one that resolves it ([prefer-the-smaller-suggestion](../rules/prefer-the-smaller-suggestion.md)).
- **Scope findings**, if any, in their own short section — the bundled-but-unrelated changes, kept out of the verdict. A scope finding **carries no severity and no certainty**: it is a boundary note, not a graded defect — one line naming *what* is out of scope and *why* (bundled and unrelated to the change's intent, so not reviewed here), optionally with "consider splitting it." Do not put it on the severity scale or fold it into the verdict tally. (basis: derived from severity grading only defects in the change under review)
- **Questions for the author**, if any, in their own section after the scope findings, each as `file:line — the question — what raised it`, in the form [questions-for-the-author](../rules/questions-for-the-author.md) pins. (basis: maintainer, 2026-09-30)

**A reference to a finding carries the finding.** Wherever a finding is named outside its own record — in the brief, in a summary line, in a comment posted onto the change — identify it by its `file:line` and a few words of the defect, never by a bare ordinal. "Issue #3" is legible only to someone currently looking at the list, which excludes the author returning to it tomorrow and the reader holding two other changes in their head; the brief's assumptions field, which names a disproved assumption as a pointer to its finding, is governed by this same pin. `(basis: maintainer, 2026-09-01)`

That record shape is the pinned output; do not vary the fields run to run. (basis: derived from the conventional review-finding shape, as the harness's own review channel carries it)

## Before it goes out, read it as its reader

Put the finished report through [deliver-at-the-readers-register](../../../craft/writing/deliver-at-the-readers-register.md) before delivering it, applying its honesty floor item by item from the rule, not from memory.

**And a visual where prose would carry it worse:** where the report describes a *structure* — a shape, a flow, a set of relationships — show it rather than describe it, per `output.diagrams` ([report-style-settings](../../../craft/writing/report-style-settings.md)) and [when-a-visual-is-owed](../../../craft/writing/when-a-visual-is-owed.md), which decides whether one is owed.

## The additional sinks

The report above is always the record. Two flags shape it further, and they compose:

- **`--typed`** also emits the findings to the harness's typed finding channel as structured records, beside the report rather than instead of it — see [typed-findings](../modules/typed-findings.md).
- **`--gate`** computes a gate result — holds, fails or not checked — from the findings at or above the floor and returns it — see [gate-mode](../modules/gate-mode.md).

Both read the same triaged, floored list; neither redefines severity or the floor. Return the record of what the run produced — the findings and, under `--gate`, the gate result — so its outcome is auditable. Posting the review on the change, and acting on its findings, belong to whoever delivers it.
