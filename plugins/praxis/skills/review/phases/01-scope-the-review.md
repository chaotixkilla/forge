Before any work, ask whatever the run needs answered, all in one message ([ask-while-the-user-is-here](../../gather/rules/ask-while-the-user-is-here.md)); with `--rigor=max`, that includes the cost question ([ask-before-a-heavyweight-run](../../gather/rules/ask-before-a-heavyweight-run.md)).

Fix *what* is under review and load *enough* to judge it: every later phase assumes both. A review that starts before its subject is pinned judges lines that aren't the change, misses lines that are, and holds the diff to a context it never loaded.

## Resolve the diff window

`--hold-rationale` changes what this phase may fetch and read, so read [hold-rationale](../modules/hold-rationale.md) before resolving anything. `--prior=<review>` makes a prior pass over the same change this one's starting point: read [prior-pass](../modules/prior-pass.md) first too.

The change under review is a set of version-controlled differences, and the window is chosen by input:

- **Default — the working-tree diff against the base.** With no source flag, review the change on the current branch: the uncommitted edits plus the commits made on this branch since it diverged from the integration line. `--changed` names this same default explicitly. **Derive the base, never assume a name** — take the merge-base between the current branch and the repository's integration line: its default branch, resolved from the repository (the remote's default head, or the local default branch when there's no remote) rather than assumed to be `main`. The window is that merge-base to the working tree. The task's documentation, where it sits inside the working tree, is never part of the window: it's the task's record, not the work ([document](../../document/SKILL.md) keeps it out). When the base can't be derived (a detached or root state, no resolvable default), fall back to the uncommitted working-tree changes against the current commit. Either way, **state which window you settled on** — surfaced to the author as the scope line in [deliver-findings](06-deliver-findings.md) — so they know exactly what was and wasn't reviewed. (basis: derived from methods-over-facts)
- **`--change=<ref>` — a remote review request.** Fetch the review request's diff *and* its description and context through [vcs](../../vcs/SKILL.md); the description feeds the intent in [build-the-mental-model](02-build-the-mental-model.md). The window is the review request's **declared base..head** carried in the fetched metadata, *not* a merge-base re-derived against this repo's default branch. This is the scoping path that reaches the vcs backend (a filed `--prior` is read through artifacts): [hosted-change](../modules/hosted-change.md) holds how it fetches, materializes the review request head for the reads below, and degrades.

`--lenses` and `--rigor` are read here and carried into the passes; they do not change *what* is scoped, only how hard it is later reviewed.

## Load enough surrounding code to judge the change

The diff alone is not judgeable — a changed line is correct or wrong only relative to what calls it, what it calls, and what it must preserve. Measure the change first: count its files and its changed lines, the lines added plus the lines deleted in each file, from the diff, never by eye. At low or medium rigor, a change of at most 5 files and 300 changed lines is small, and is read inline without recruiting, here and in [build-the-mental-model](02-build-the-mental-model.md). A file the diff gives no line count, such as a binary one, or a count that can't be computed, is never small, and high and max keep their full breadth. (basis: after measured small-change sizing in automated review practice) Otherwise, load the change's context: recruit the **code explorer** to locate the definitions and call sites of every symbol the diff touches, and the **repository explorer** to surface recent history near the changed lines (a prior attempt, a revert, a linked discussion that explains why the code is as it is). Without fan-out, do these reads inline before proceeding — locate the touched symbols and their callers yourself; the reads are not optional, only the delegation is. Recruit only as [fan-out-only-when-it-pays](../../gather/rules/fan-out-only-when-it-pays.md) allows.

How much context is enough is deliberately not a fixed number — **load the definition and call sites of each touched symbol, and the invariants those symbols participate in, until you can predict the change's runtime behavior on each; stop when reading one more file would not change a verdict.** (This is the [read-the-diff-in-its-blast-radius](../rules/read-the-diff-in-its-blast-radius.md) method; here you are loading the radius, in [hunt-for-defects](03-hunt-for-defects.md) you judge across it.) *Deliberately open:* pinning a hop count would be false precision — a pure leaf function needs its three callers, a changed shared signature needs all thirty, and only the change in front of you says which.

## State the scope boundary — and actively set aside the noise

Close the phase by stating what is in scope and what is not — the files under review, the window, and anything the diff touches that you are deliberately *not* judging. This is not a passive list: **name each set-aside category, apply its membership test, and exclude its lines from the passes** so the hunt and craft passes never spend attention on churn. State the boundary either way — the author must see what the findings, *and the silence*, cover.

The set-aside categories and their membership tests:

- **Generated / vendored files** — a file *produced by a tool*, not hand-authored: a lockfile, a compiled or minified bundle, an OpenAPI/GraphQL schema emitted by a generator, code copied wholesale from a dependency. The membership test is **provenance**: is this file the output of a build/codegen/vendoring step rather than something a human edits directly? If yes, set it aside — you do not review a generator's output for craft, and its correctness is the generator's, not this change's.
- **Formatting / whitespace / EOL churn** — a hunk that changes only layout: reindentation, a line-ending flip (CRLF↔LF), import reordering, a formatter sweep. The membership test is **does the hunk change any token the compiler/runtime sees?** If it changes only whitespace or line endings, set it aside and **review the semantic diff** (the diff computed with whitespace ignored) rather than the raw hunks — a 900-line reformat must not drown the three real changed lines inside it, and must not each read as a finding.

**The re-entry test — when a set-aside file comes back into scope.** Setting a file aside is provisional, not blind. A generated or churned file **re-enters scope when its diff encodes a real contract or behavior change**, not mere regeneration/formatting noise — a generated schema that *drops a field* or changes an endpoint, a lockfile that moves to a version with a known break, a "formatting-only" hunk that also flips a boolean. The test: *does the change to this file alter what a consumer of it observes?* If yes, review that specific change. Where it lands: if the contract change is **unintended** (a regeneration silently dropped a schema with no corresponding source change), it is a **scope finding** — a bundled change the author likely did not mean; if it is **wrong** (a generated contract the change intends but got wrong), it is a **correctness finding**. When you cannot tell whether a generated-artifact change was intended, surface it as a scope finding and say so — the author resolves the intent ([respect-author-intent](../rules/respect-author-intent.md)). (basis: derived from two cold runs that split on whether to review generated and reformatted lines)

This is where [respect-author-intent](../rules/respect-author-intent.md) starts: if the diff bundles a change unrelated to its apparent intent, note it here as an out-of-scope item to be reported as a scope finding later, not folded into the review of the intended change.
