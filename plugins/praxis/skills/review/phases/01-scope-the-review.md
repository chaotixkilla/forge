A review that starts before its subject is pinned wanders: it judges lines that aren't the change, misses lines that are, and holds the diff to a context it never loaded. This phase fixes *what* is under review and loads *enough* to judge it — the two facts every later phase assumes. Get the scope wrong here and every finding downstream is scoped wrong; get the context short and the hunt guesses where it should read.

## Resolve the diff window

The change under review is a set of version-controlled differences, and the window is chosen by input:

- **Default — the working-tree diff against the base.** With no source flag, review the change on the current branch: the uncommitted edits plus the commits made on this branch since it diverged from the integration line. `--changed` names this same default explicitly. **Derive the base, never assume a name** — take the merge-base between the current branch and the repository's integration line: its default branch, resolved from the repository (the remote's default head, or the local default branch when there's no remote) rather than assumed to be `main`. The window is that merge-base to the working tree. When the base can't be derived (a detached or root state, no resolvable default), fall back to the uncommitted working-tree changes against the current commit. Either way, **state which window you settled on** — surfaced to the author as the scope line in [deliver-findings](06-deliver-findings.md) — so they know exactly what was and wasn't reviewed. (basis: methods-over-facts — the base is *derived* each run, never a hard-coded ref that goes stale across repos and branches; reading the local diff is ambient — no capability is required to see it.)
- **`--pr=<number>` — a remote pull request.** Fetch the PR's diff *and* its description and context through the vcs capability; the description feeds the intent in [build-the-mental-model](02-build-the-mental-model.md). The window is the PR's **declared base..head** carried in the fetched metadata — *not* a merge-base re-derived against this repo's default branch (that derivation is the local-diff rule above; re-applying it to a PR opened on a non-default base reviews the wrong window). The module also **materializes the change to an isolated checkout at the PR head** so the surrounding-code reads below hit the reviewed revision, and cross-checks the checkout's file/hunk counts against the PR metadata to catch a stale or force-pushed head. This is the one scoping path that reaches a backend — see [pull-request](../modules/pull-request.md). The fetch goes through the vcs capability (the `vcs` skill owns the `tools.vcs` prerequisite); if it reports the backend unavailable, degrade — a remote PR cannot be fetched without it, so report that clearly rather than reviewing the wrong (local) diff.

`--lenses` and `--effort` are read here and carried into the passes; they do not change *what* is scoped, only how hard it is later reviewed.

## Load enough surrounding code to judge the change

The diff alone is not judgeable — a changed line is correct or wrong only relative to what calls it, what it calls, and what it must preserve. Load the change's context: recruit the **code explorer** to locate the definitions and call sites of every symbol the diff touches, and the **repository explorer** to surface recent history near the changed lines (a prior attempt, a revert, a linked discussion that explains why the code is as it is). Without fan-out, do these reads inline before proceeding — locate the touched symbols and their callers yourself; the reads are not optional, only the delegation is.

How much context is enough is deliberately not a fixed number — **load the definition and call sites of each touched symbol, and the invariants those symbols participate in, until you can predict the change's runtime behavior on each; stop when reading one more file would not change a verdict.** (This is the [read-the-diff-in-its-blast-radius](../rules/read-the-diff-in-its-blast-radius.md) method; here you are loading the radius, in [hunt-for-defects](03-hunt-for-defects.md) you judge across it.) *Deliberately open:* pinning a hop count would be false precision — a pure leaf function needs its three callers, a changed shared signature needs all thirty, and only the change in front of you says which. The stopping test bounds the openness so two reviewers converge on "enough."

## State the scope boundary — and actively set aside the noise

Close the phase by stating what is in scope and what is not — the files under review, the window, and anything the diff touches that you are deliberately *not* judging. This is not a passive list: **name each set-aside category, apply its membership test, and exclude its lines from the passes** so the hunt and craft passes never spend attention on churn. State the boundary either way — the author must see what the findings, *and the silence*, cover.

The set-aside categories and their membership tests:

- **Generated / vendored files** — a file *produced by a tool*, not hand-authored: a lockfile, a compiled or minified bundle, an OpenAPI/GraphQL schema emitted by a generator, code copied wholesale from a dependency. The membership test is **provenance**: is this file the output of a build/codegen/vendoring step rather than something a human edits directly? If yes, set it aside — you do not review a generator's output for craft, and its correctness is the generator's, not this change's.
- **Formatting / whitespace / EOL churn** — a hunk that changes only layout: reindentation, a line-ending flip (CRLF↔LF), import reordering, a formatter sweep. The membership test is **does the hunk change any token the compiler/runtime sees?** If it changes only whitespace or line endings, set it aside and **review the semantic diff** (the diff computed with whitespace ignored) rather than the raw hunks — a 900-line reformat must not drown the three real changed lines inside it, and must not each read as a finding.

**The re-entry test — when a set-aside file comes back into scope.** Setting a file aside is provisional, not blind. A generated or churned file **re-enters scope when its diff encodes a real contract or behavior change**, not mere regeneration/formatting noise — a generated schema that *drops a field* or changes an endpoint, a lockfile that moves to a version with a known break, a "formatting-only" hunk that also flips a boolean. The test: *does the change to this file alter what a consumer of it observes?* If yes, review that specific change. Where it lands: if the contract change is **unintended** (a regeneration silently dropped a schema with no corresponding source change), it is a **scope finding** — a bundled change the author likely did not mean; if it is **wrong** (a generated contract the change intends but got wrong), it is a **correctness finding**. When you cannot tell whether a generated-artifact change was intended, surface it as a scope finding and say so — the author resolves the intent ([respect-author-intent](../rules/respect-author-intent.md)).

This is where [respect-author-intent](../rules/respect-author-intent.md) starts: if the diff bundles a change unrelated to its apparent intent, note it here as an out-of-scope item to be reported as a scope finding later, not folded into the review of the intended change. A stated boundary is what stops a later phase from reviewing past the mandate. (basis: the set-aside categories were descriptive-only — listed as examples with no exclusion instruction, no membership test, and no re-entry path — so two cold runs diverged wildly: one reviewed 23k generated lines and a 900-line reformat, another set them aside; the membership tests and the re-entry test are what make the boundary reproducible, mirroring the sibling "how much surrounding code" bar above, which already carries its own test.)
