Judging a change you have not understood produces confident nonsense: findings that flag intended behavior as a bug, or miss the real defect because you assumed the wrong goal. Before hunting, build the model the hunt will judge against — what the change is *trying* to do, the contracts it touches, and how it is *reached* at runtime. This phase is the difference between reviewing the change and reviewing your guess about it.

## Establish the intent

State, in a sentence or two, what this change sets out to accomplish — read from the diff, the commit messages, and (for `--pr`) the pull-request description fetched in [scope-the-review](01-scope-the-review.md). The intent is the standard the change is held to ([respect-author-intent](../rules/respect-author-intent.md)): a change is good if it achieves *its* goal correctly, not if it matches how you would have solved the problem.

When the diff's actual behavior and the stated goal (its description or commit message) **disagree**, do not silently pick one as authoritative — the divergence is itself a finding. Report it as "the change is described as X but does Y": a **correctness** finding when the stated goal is a real requirement the code fails to meet, or a **stale-description / scope note** when the code is right and the description merely lags. (basis: behavior-over-labels — [confirm-before-claiming](../rules/confirm-before-claiming.md) says trust what the code *does* over what it's described as — but review *surfaces* an intent/behavior gap for the author to resolve, it does not decide the author's intent for them.) Judge the rest of the review against the stated goal; where the goal is genuinely unstated or ambiguous, record that at the checkpoint below rather than inventing one.

An **in-repo spec or design doc bundled in the diff** (a `docs/specs/*.md`, a design note the change edits or adds) is intent *evidence*, not ground truth. Read it as another statement of the goal — but the code, not the doc, is authoritative about what the change *does* ([confirm-before-claiming](../rules/confirm-before-claiming.md)). So a spec that disagrees with the code is handled exactly like the description/behavior divergence above: **staleness-check the spec against the code and surface the gap** ("the spec says one-per-frequency, the code allows named alerts") — do not silently treat the spec as the requirement and flag the code, nor treat the code as truth and silently ignore a spec the change was supposed to satisfy. Surface which lags for the author to resolve; do not decide it for them.

A **linked work-item** — a tracked ticket or issue the change references (in the PR description, a commit trailer, or the branch name) — is intent evidence of the same class as an in-repo spec, living in the tracker rather than the diff. When the change carries one or more such references *and* a tracker is configured, fetch each through the [project-mgmt](../../project-mgmt/SKILL.md) port (its *fetch a work-item* operation returns the title, description, acceptance criteria, and status) and handle them exactly as the in-repo spec above, reading several together as a single statement of intent. review holds no tracker prerequisite of its own — the port owns `tools.project_mgmt`, and review sheds it the way it sheds `vcs`: with no reference present, no tracker configured, or the port reporting the backend unavailable, proceed on the diff, commits, and description alone and note that the linked item was not consulted. `(basis: the fetch is delegated to the project-mgmt port per doer-owns-prerequisites — mirroring maintain's linked-work-item read — and degrades to unblock like every praxis backend touch.)`

## Map the contracts and the runtime reach

Two reads turn intent into something judgeable:

- **The contracts it touches** — the signatures, invariants, and implicit assumptions the change leans on or alters. Trust what the code does over what its names and comments claim ([confirm-before-claiming](../rules/confirm-before-claiming.md)); a function named `validate` that rejects nothing is exactly where intent and behavior diverge. Recruit the **code explorer** to trace how the changed code is actually reached and what it actually calls; without fan-out, trace the paths yourself before proceeding.
- **Why the code is the way it is** — recruit the **repository explorer** for the history behind the changed lines (a prior fix, a revert, the reason a seemingly-odd guard exists), and, when `--effort` is high or max, the **community-practices explorer** for the established idiom when the change uses an unfamiliar pattern. Without fan-out, apply these lenses inline as the effort level warrants.

**When the change is a dependency upgrade**, the symbols it leans on live in the dependency, not the repo — and the blast-radius method's assumption that touched symbols are readable in-tree ([read-the-diff-in-its-blast-radius](../rules/read-the-diff-in-its-blast-radius.md)) fails when the *target* version isn't installed (the tree still holds the old version). Before judging such a change, **obtain the dependency's API at the locked (new) version** — fetch its published package source (wheel/sdist, package tarball, or the tagged source at that version) and read the actual classes, signatures, and behavior the change now depends on. Verifying against whatever version happens to be installed produces confident false findings (a "symbol undefined" or wrong-signature verdict checked against the old API, or a false-clean checked against the wrong class hierarchy). This is a *reachability* step — getting the radius in front of you — distinct from how *much* of it to read, which stays governed by the stopping test.

## Learn the local conventions

Read enough of the surrounding code to know its norms — naming, error handling, the abstractions it reaches for, the indirection it tolerates. This is what the craft pass will judge conformance against ([judge-against-the-surrounding-code](../rules/judge-against-the-surrounding-code.md)); you cannot flag a deviation from a convention you have not read, and reading it now (with the code already open) is cheaper than in [assess-craft](04-assess-craft.md).

## Checkpoint: confirm the model before hunting

Before leaving this phase, confirm you can state the change's intent, the contracts it moves, and how it is reached — because a wrong model here propagates into every finding the hunt and craft passes produce, and a false finding rooted in a misread intent is expensive to walk back after it is reported. If any of the three is still a guess, resolve it — another read, or a note that the intent is genuinely ambiguous — before proceeding. This is the one gate in the procedure; the passes after it assume the model is sound.
