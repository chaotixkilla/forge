With correctness swept, switch modes. This pass asks a different question — not "how does this break?" but "how does this read, and how will it evolve?" It is a separate phase precisely so the craft observations do not dilute the correctness hunt; now that the defects are found, give the change's *form* its own attention. Everything found here is optional-to-fix by definition ([separate-correctness-from-taste](../rules/separate-correctness-from-taste.md)): if you can name an input where the code is wrong, it is a defect and belongs to [hunt-for-defects](03-hunt-for-defects.md), not here.

## Sweep the craft lenses in scope

If you partitioned a large change for the correctness hunt ([cover-a-large-change](../rules/cover-a-large-change.md)), assess craft over the *same* units — the craft pass covers the same surface the hunt did, so no subsystem's form goes unjudged. For the change's form, at the breadth `--effort` sets and `--lenses` narrows:

- **Reuse** (`reuse`) — the change reimplements something the codebase already provides: an existing helper, a pattern, an abstraction in the same module. The cost is the future edit that now has to happen in two places.
- **Simplification** (`simplification`) — accidental complexity that isn't pulling its weight: dead code, a premature abstraction with one caller, speculative generality, nesting that a guard clause would flatten, a layer that only forwards.
- **Efficiency** (`efficiency`) — needless work: a redundant pass, an allocation in a loop, an N+1 access pattern, repeated computation of an invariant. Weight it by where it sits — a quadratic loop on a hot path is a real finding; the same off a cold path is often `info`.
- **Altitude and consistency** (`altitude`) — naming that misleads about role or intent, an abstraction pitched too high or too low for its one job, and divergence from the conventions the surrounding code establishes.
- **Comment hygiene** (`comments`) — comments carrying nothing the code does not already say: a line restating the statement beneath it, a description the code has since moved past, a narrated history of how the change came to be. Judge by the recover-it-from-the-code-alone discriminator that [comment-the-why-not-the-what](../../develop/rules/comments/comment-the-why-not-the-what.md) defines, and never by how heavily the file already comments, which is not a convention to match ([match-surrounding-conventions](../../develop/rules/change-hygiene/match-surrounding-conventions.md)). The cost is a reader misled by a comment that no longer matches, plus every later reader paying to read what the code already told them. The **inverse is a finding only where the why is genuinely unrecoverable** from the code itself: do not manufacture a request for narration, which would invert the lens into the thing it exists to remove.

## Judge against the neighborhood, and suggest the smallest fix

Every craft finding is measured against *this* codebase, not an external ideal ([judge-against-the-surrounding-code](../rules/judge-against-the-surrounding-code.md)): a change that matches a strong local convention is fine even if you would have chosen otherwise, and a change that breaks one is a finding even when what it does is defensible in the abstract. When you propose a fix, propose the least-invasive one that resolves the finding — point at the existing helper, don't design a new abstraction layer ([prefer-the-smaller-suggestion](../rules/prefer-the-smaller-suggestion.md)). Anchor each finding to its `file:line` and its concrete cost — the specific future edit, the specific reader misled — not a vague "this is messy" ([anchor-every-finding-to-evidence](../rules/anchor-every-finding-to-evidence.md)). Tag each with a **confidence** on the craft ladder — how sure you are its premise holds: that the existing helper you cite really exists and applies, that the blocks you call duplicates really match, that the simpler form really preserves behavior ([calibrate-confidence-to-effort](../rules/calibrate-confidence-to-effort.md)). A craft finding whose premise you asserted but did not verify (an "existing helper" you never located) is *speculative*, and survives only where the effort floor admits it — just like a speculative defect.

## Recruit a simplicity-hawk at high effort

At `--effort=high` or `max`, recruit the **simplicity-hawk critic** — its lens is "what here is not pulling its weight?" — handing it [calibrate-confidence-to-effort](../rules/calibrate-confidence-to-effort.md), and [severity-scale](../rules/severity-scale.md) for a *provisional* craft-cost read that [triage-and-rank](05-triage-and-rank.md) re-grades so it grades on those rules' own rungs and anchors rather than a ladder of its own, and fold its surviving findings in. Without fan-out, apply that lens yourself: for each new abstraction, indirection, or duplicated block, ask what would be lost by deleting or inlining it, and record the ones that answer "nothing." Watch the boundary case: a craft problem one plausible refactor away from becoming a wrong result is a medium-severity *correctness* footgun, moved back to the correctness pile with the evolution named — not left here as mere style ([separate-correctness-from-taste](../rules/separate-correctness-from-taste.md)).

The output is a set of *candidate* craft findings, each anchored and carrying its cost and confidence — unranked, unvalidated, awaiting [triage-and-rank](05-triage-and-rank.md) alongside the correctness candidates.
