Decide how the change ships: how existing state moves to the new shape, what keeps working during the transition, how it's verified and watched, and what makes it safe enough to proceed. For a purely internal or greenfield change there may be little to move; say so and keep the phase short.

## Choose the rollout / migration pattern — teach the selection, don't crown one

Each rollout pattern fits a different scope and pays a different cost, so select correctly; don't default to a favorite. Route with three ordered discriminators `(basis: Fowler, Sato, Humble, Hodgson and Letuchy's dark launch for the patterns; Newman, Monolith to Microservices, ch. 3, as the practitioner basis for choosing among them, since no authority defines that selection)`:

1. **Scope of the thing changing.** A single backward-incompatible interface / signature / message / schema → **parallel change (expand → migrate → contract)**. A module/library/supplier deep in the code → **branch by abstraction**. A whole running legacy system/subsystem → **strangler fig**.
2. **Where you can intercept.** At the perimeter (proxy/router) → strangler fig; only inside the code, protecting concurrent devs → branch by abstraction.
3. **What you must prove before flipping traffic.** Correctness/NFR equivalence under real inputs → **parallel run** (call both, compare, old is source of truth) and/or **dark launch** (shadow real traffic, discard output).

**Feature flags/toggles are the orthogonal switch**, not a rival — they flip which path is live and compose with all of the above; tag each toggle by intent (release / experiment / ops / permissioning) and give it a **removal owner and date**, because an unretired flag is the named failure mode; whether a change earns a toggle at all is [feature-flagging-risky-changes](../../../craft/engineering/feature-flagging-risky-changes.md)'s test. The patterns compose (strangler at the boundary, branch-by-abstraction inside, a parallel run to verify cutover). Reversibility drives the choice ([design-for-reversibility](../../../craft/engineering/design-for-reversibility.md)); a migration is not *done* until its terminal step (contract / flag-removal / legacy-elimination) is scheduled with an owner. **Two sub-forks route to the maintainer:** for a consistency-critical data move, *dual-write vs CDC/shadow-write* `(routed to maintainer: default to CDC/shadow-write with the old store as source of truth; hand-rolled dual-write risks partial abort and unrecoverable divergence)`; for a small, fully-coordinatable system, *big-bang vs incremental* `(routed to maintainer: big-bang only when the world can be stopped atomically; otherwise incremental)`.

## Keep it compatible during the transition

State what must keep working mid-rollout: the dual-version window a parallel change opens, the contract the old callers still rely on until they migrate, the backfill that runs while both shapes coexist. Name the point at which the old path is safe to remove.

## Define testing and observability

Say how the rollout is verified before and during ship (the parallel-run comparison, the canary metrics) and what is watched after — the signals that tell you it is healthy and the ones that trigger a rollback.

## The ship bar — safe enough to proceed

`(basis: maintainer, 2026-07-05; after AIAG-VDA Action Priority, Google SRE error budgets and DORA)`

Rate each rollout flow on [the risk scale](../rules/risk-scale.md), then the rollout may proceed only when (1) holds and (2) holds or is explicitly waived. Never gate a single rollout on a team's change-failure rate: that's an aggregate team-health metric, not a per-rollout bar.

1. **[MUST — never waivable]** No *Critical*-severity rollout flow has an open *High* likelihood-to-bite without either a documented mitigation or an explicit maintainer sign-off. (routed to maintainer: the invoking user signs off, unless the repository names code owners for the affected area, who then do; who may waive a Critical risk is a house call.)
2. **[SHOULD — waivable only with a documented reason and a maintainer risk-acceptance sign-off]** The rollout is safe to reverse and to expose — all three sub-checks hold: **(2a) reversible** — a rollback/recovery path *exists* (no one-way or destructive step without one; whether it is fast *enough* is (2c)'s concern, not this one); **(2b) progressive** — rolled out incrementally (canary/staged) rather than as an atomic cutover, so a failure is caught before it reaches the whole population; it applies where the change deploys to a running population, and a release its users adopt on their own schedule — a library, a command-line tool — has no cutover to stage, so (2b) is recorded as not applicable there rather than failed; **(2c) recoverable in time** — that recovery path fits the error budget (the team's stated recovery-time / SLO expectation; `basis: Google SRE error budget`). A rollout *fails* (2) by violating any sub-check, and each sub-check names the risk its failure carries: **(2a)** → the irreversibility / data-loss risk (a one-way or destructive migration with no recovery path, regardless of cadence); **(2b)** → the atomic-cutover / coordination risk (a **big-bang** fails here on its atomic cadence even when the affected population is small — the small-system big-bang admitted above is exactly this); **(2c)** → the slow-recovery / error-budget-overrun risk (a recovery path that exists but blows the budget — fails here, not (2a)). To proceed on a (2)-failure, the sign-off must **consciously accept the specific risk each failed sub-check names** — one risk per failed sub-check, all of them where several fail. *(Where no formal error budget/SLO is defined, (2c) is open-by-design: judge the recovery against the team's recovery-time expectation and route the threshold to the team's SLO — pinning a universal number would be false precision.)*

When a sign-off is needed and no one can be asked in the run — plan invoked by another skill — record each failed check and the risk it names as an open sign-off in the plan's result, never as accepted; the caller puts it to the maintainer.

That (2) risk-acceptance is a **distinct** decision from the pattern-selection routing above (which judges only whether a pattern is *admissible* — a feasibility call): the same maintainer may make both, but the risk-acceptance is recorded here at the ship bar, never inferred from the pattern approval. And where one flow trips **both** (1) and (2), a single recorded sign-off may cover both, but it must consciously name and accept **each** risk — the (1) Critical/High risk *and* each failed-(2) risk — whether they coincide (a one-way migration, where the Critical severity *is* the irreversibility) or are distinct (a recoverable-but-Critical breach shipped big-bang); record it once, listing every risk accepted, don't seek two.

Recruit the **future-self** critic here to hunt the irreversible move with no way back — the migration or flag flip whose reverse nobody specified; without fan-out, apply that lens yourself, as its own pass. Under `--critics`, scale that scrutiny ([adversarial-critics](../modules/adversarial-critics.md)).

The output is a rollout with a chosen (and composed) pattern, a backward-compatibility plan through the transition, a test-and-observability strategy, and a stated ship bar — the last thing [slice-and-validate](06-slice-and-validate.md) confirms is closed.
