# Design for reversibility

The cost of a design decision is dominated not by whether it is right but by how hard it is to undo when it is wrong. A decision you can reverse in one deploy can be made fast and corrected later; a decision that bakes into a persisted format or a public contract must be right the first time, because getting back to where you were may be impossible. The trap is treating both with the same weight — deliberating endlessly over a reversible call, or casually shipping an irreversible one. This rule classifies each load-bearing decision by reversibility and matches the care to the class.

## The two classes

`(basis: Jeff Bezos, Amazon 2015 & 2016 shareholder letters, coin "one-way door / two-way door" (Type 1 / Type 2) decisions and tie the class to process weight — Type 1 deliberate, Type 2 fast. Grady Booch, "On Design" (2006) and Martin Fowler, "Who Needs an Architect?" (IEEE Software, 2003) map this to software: architectural significance = cost of change ≈ cost of reversal. The two-part sorting test and the software anchors are the maintainer's ratified reading, 2026-07-05.)`

- **One-Way Door (Type 1).** The decision is **both** (a) *consequential* — it shapes the system, with lasting blast radius — **and** (b) *irreversible, or reversible only at high cost/coordination given the team's actual tooling*: you cannot cheaply reopen the door and walk back. Handle it deliberately; decide it near the last responsible moment, with consultation. *Anchor (clearly one-way):* a published API / on-the-wire or persisted **data format** that external, uncontrolled consumers depend on — you cannot migrate the callers, so reversal breaks third parties; or a destructive one-way data migration over production data.
- **Two-Way Door (Type 2).** Reversible at low cost within your own control — revert with a deploy, no external party to coordinate. Decide it fast, at ~70% of the information you wish you had; do not gate it behind heavyweight review. *Anchor (clearly two-way):* an implementation choice hidden behind an interface you fully own — swap the library or algorithm behind the port and revert in one deploy.

## The assignment test reads tooling as it is now

Reversibility is **not** purely intrinsic to an artifact — it is partly a function of the tooling and practice you actually have. A database schema is a one-way door with no migration tooling and a two-way door with it. So classify by the cost to reverse *given the team's real tooling as of now*, not by the artifact's reputation. `(basis: Fowler, "Who Needs an Architect?" — his colleague made schema changes routinely reversible with migration tooling; good architecture works to convert one-way doors into two-way ones.)` The competing reading — treat reversibility as near-intrinsic and classify conservatively — is safer against a missing-tooling surprise but pushes more decisions into the slow Type 1 process; where the codebase's convention already settles this (does it treat schema/contracts as fixed or as migratable?), follow it. `(routed to maintainer: any numeric threshold for "how consequential + how costly-to-reverse" tips a decision into Type 1 — no authority sets it.)`

**Standing directive:** where a Type 1 decision can be *converted* into a Type 2 one cheaply — a version negotiation, an abstraction you own, a reversible migration path — prefer designing that in over deliberating the irreversible choice. Turning a one-way door into a two-way door is usually a better spend than getting the one-way choice perfect.
