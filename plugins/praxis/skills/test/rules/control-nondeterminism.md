# Control nondeterminism

Pin every source of nondeterminism a case touches — the clock, random seeds, iteration and collection ordering, concurrency and scheduling, and any external timing — so the case's result depends only on the behavior under test. A case that can pass or fail on the *unchanged* code is not a weaker test; it is a broken instrument, and a suite full of them trains everyone to retry past red until it turns green, which is how a real regression ships unnoticed.

The stance this rule takes: **a flaky test is a defect in the test, not background noise.** It is fixed at setup ([set-up-the-harness](../phases/04-set-up-the-harness.md)) by removing the nondeterminism, not managed at run time by re-running. This is the same line [failure-classification](failure-classification.md) draws when it sorts a red into *flake* — the flake is a defect to root-cause, and its critical guard applies: a green rerun does not clear the code, because the nondeterminism may sit in the production code, not only the test. `(basis: Martin Fowler, "Eradicating Non-Determinism in Tests" — a non-deterministic test is "useless" because it destroys the suite's signal; the dominant flake root causes — async/timing, concurrency, order dependency — are Luo et al. FSE 2014's top three.)`
