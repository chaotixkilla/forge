# Prove the test can fail

A test that has only ever been green proves nothing — it may assert nothing, assert against the wrong thing, or never reach the code it claims to exercise. Confirm a new or changed test actually catches the behavior by watching it go **red** for the right reason before its green is trusted. Reach for the methods in this order, preferring the ones that touch no production code:

1. **Run the test against the pre-change code** — for a test guarding a behavior the change *alters*, the pre-change revision computes the old behavior, so a correct test reddens there on the *value*. This is the fail-before / pass-after check, and it mutates nothing. Caveat for a behavior the change *introduces* (a new function or parameter): the pre-change code reddens merely because the signature/behavior is *absent* (e.g. a `TypeError` on the new argument) — that proves the test *runs*, not that its assertion *discriminates the value* (an assertion of the wrong expected value would redden pre-change too). For an introduced behavior, method 1 is inconclusive for value-discrimination — fall through to method 2. (This is the same "absent pre-change is not a value-reproduction" distinction the scope test draws in [report-the-verdict](../phases/06-report-the-verdict.md).)
2. **Feed a deliberately-wrong expectation or input** — assert against a known-bad value, or drive the case with an input the behavior must reject, and confirm the case reddens. This exercises the test, not production code.
3. **A transient, self-reverting break** — only when neither method above can produce red (typically a regression-guard test for behavior that *predates* the change, so the pre-change code is already green): briefly break the behavior under test, observe the red, and immediately restore. This is a **verification probe, not a modification** — it leaves a net-zero diff and never appears in the deliverable, so it is inside the skill's no-production-change boundary (which forbids *delivering* a production change, not transiently observing a red). When even this is infeasible, record the test as **not proven-red** — a residual risk surfaced in [report-the-verdict](../phases/06-report-the-verdict.md), never a silent green.

A test never seen red is an unproven assertion wearing a green check.

This is the operational core of "discriminating" in [design-the-cases](../phases/03-design-the-cases.md): a case discriminates only if some plausible wrong implementation makes it fail — a case no wrong implementation can redden covers nothing, however green it looks. It is applied in [run-and-observe](../phases/05-run-and-observe.md) before a new test's green is trusted as evidence, and it is why a suite of never-red tests grades *inadequate* in [coverage-adequacy](coverage-adequacy.md) no matter its line percentage. `(basis: Kent Beck's TDD Rule 1 — write new code only after a failing test — and the "behavioral" test desideratum (a test's result must change when behavior changes); the mutation-testing adequacy notion that a test killing no mutant is inadequate — Just et al. 2014. Note: Beck's 2023 "Canon TDD" folds the see-it-fail step into the flow rather than listing it separately, so requiring it as a hard check is a defensible house tightening, not a verbatim canon step.)`
