# The coverage-adequacy scale

test's job is to design *meaningful* coverage, and "meaningful / enough" is the load-bearing judgment of the whole skill. If the bar is undefined, each executor invents its own: one calls a happy-path-only suite "enough," another demands every line covered, and the same change ships cleared by one reviewer and held by another. This rule pins the bar as a property of *behavior covered*, not a line-count: a coverage percentage measures whether code was executed, never whether a test would catch the change being wrong.

The scale answers one question: **does every behavior this change introduces or alters that could plausibly break have at least one *discriminating* case that would fail if it broke?** It is assigned in [design-the-cases](../phases/03-design-the-cases.md) and consumed by [report-the-verdict](../phases/06-report-the-verdict.md) (the coverage-gaps and residual-risk it surfaces). It rests on [risk-priority](risk-priority.md) (which behaviors *matter*) and [prove-the-test-can-fail](../../../craft/engineering/prove-the-test-can-fail.md) (whether a case actually discriminates).

This is a grade of the suite's reach, not a result. A result in [results-and-certainty](../../../craft/evidence/results-and-certainty.md) says what checking found about one claim; this grade says how much of what could break the checks reached, and it is reported beside the claim's result, never in its place. `(basis: maintainer, 2026-10-02)`

## The three grades

`(basis: Fowler, "TestCoverage"; Marick, "How to Misuse Code Coverage"; the ICSE 2014 coverage study; Software Engineering at Google, ch. 11)`

The universe assessed is **every behavior the change introduces or alters** (including the reverse-dependents it pulls in — see [map-the-surface](../phases/02-map-the-surface.md)); under `--from-spec` the spec's criteria are *added* as must-cover behaviors, never a narrowing of the change's own behaviors. The adequate/partial/inadequate line is pinned to the [risk-priority](risk-priority.md) tier of the uncovered behavior, so the two scales agree. **"Discriminate" is judged per behavior:** a behavior "covered" only by a non-discriminating case (a weak assertion that would not redden on a plausible bug — [prove-the-test-can-fail](../../../craft/engineering/prove-the-test-can-fail.md)) counts as **a gap at its own risk tier**, exactly as if it had no case — so "covered" below always means "covered by a *discriminating* case," and a weakly-covered Medium-risk behavior grades the same as an uncovered one (partial), a weakly-covered High the same as an uncovered High (inadequate). (An **unresolved-flaky** case is also non-discriminating — it does not reliably redden on a bug, [control-nondeterminism](../../../craft/engineering/control-nondeterminism.md) — so a behavior covered only by a flaky case is a gap until the flake is root-caused.) **The grade is the highest-risk gap:** a High gap → inadequate; else a Medium gap → partial; else adequate — with one override that dominates: if there is **at least one High- or Medium-risk behavior** and **none** is discriminatingly covered, the run is **inadequate** regardless of tier (nothing that needed a discriminating case has one). A change touching **only Low-risk behaviors** needs no cases — with no High/Medium behavior present the override does not fire, and the run is **adequate** (the uncovered Low behaviors are noted as residual risk).

- **adequate** — every **High- and Medium-risk** behavior the change touches is covered by at least one *discriminating* case (one a faithful implementation passes and a plausible wrong one fails — [prove-the-test-can-fail](../../../craft/engineering/prove-the-test-can-fail.md)): the risk-ranked boundaries and failure paths ([cover-the-edges-that-bite](../../../craft/engineering/cover-the-edges-that-bite.md)) and the counter-examples that must NOT pass are among them. A **Low-risk** behavior (unlikely to break *and* bounded/recoverable — [risk-priority](risk-priority.md)) need not be covered: an uncovered Low-risk behavior does **not** lower the grade, though it is noted as residual risk. A faithful refactor leaves the suite green; a behavior regression turns it red.
  - *Anchor (top of scale):* a changed discount calculator has cases for the zero / negative / over-100% boundaries, the rounding edge, and the "discount must not exceed price" counter-example — each seen to fail against the un-fixed code first. Injecting any plausible bug reddens a case; a cosmetic Low-risk copy-string tweak nearby is left uncovered and merely noted.
- **partial** — every High-risk behavior is covered and at least one behavior is discriminatingly covered, but at least one **Medium-risk** behavior that could still break is left a gap (a run with a High/Medium behavior but *no* discriminating case at all is inadequate per the override, not partial). Acceptable to land *only* if each gap is named as residual risk in the verdict, never if a gap is left silent.
  - *Anchor:* the calculator's happy path and its (High-risk) negative-discount guard are covered, but the (Medium-risk) rounding edge is not — a real but bounded gap, reported as residual risk.
- **inadequate** — a **High-risk** behavior is a gap (uncovered, or covered only by a non-discriminating case), **or** — the override — there is a High/Medium-risk behavior and *no* behavior is discriminatingly covered at all (assertions too weak to catch a wrong result, tests never seen red so they assert nothing — [prove-the-test-can-fail](../../../craft/engineering/prove-the-test-can-fail.md) — or only the happy path), so no behavior that matters is discriminated. Green here proves the code *ran*, not that it is *right*.
  - *Anchor (bottom of scale):* a single test that calls the calculator and asserts only that it "returns a number" — 100% line coverage of the function, zero behavior discriminated.

## The adjacent-grade discriminators

- **adequate vs partial** — is every **High- and Medium-risk** behavior covered by a discriminating case? adequate (an uncovered *Low-risk* behavior is a residual-risk note, not a gap that lowers the grade). Is a **Medium-risk** behavior left a gap? partial. (the risk-tier line — [risk-priority](risk-priority.md))
- **partial vs inadequate** — is every **High-risk** behavior discriminatingly covered and at least one behavior discriminatingly covered? partial. Is a **High-risk** behavior a gap, or does *no* behavior discriminate at all while a High/Medium behavior exists (the override)? inadequate. (the High-risk floor + the discrimination line — [prove-the-test-can-fail](../../../craft/engineering/prove-the-test-can-fail.md))

When adequate and partial both seem to fit, **partial wins** unless every Medium-or-higher-risk behavior has a discriminating case and every uncovered behavior is Low-risk and noted; an unnamed gap is partial (or inadequate if the uncovered behavior is High-risk), never adequate. A line-coverage percentage never promotes a grade: a 95%-covered change with weak assertions is *inadequate*; a 60%-covered change whose every High/Medium-risk behavior has a discriminating case is *adequate*.

## The authority fork — how "enough" is measured

Authorities genuinely conflict on what *measures* adequacy. This rule takes the behavior/risk-based position above and treats the alternatives as tools, not the bar:

- **coverage-% targets (line/branch)** — a floor/diagnostic to *locate* untested code, never the pass bar. Codifying a number as a shippability target invites gaming (Goodhart) — Fowler and Marick reject it and the ICSE-2014 study agrees. Use a % only diagnostically, and prefer it diff-scoped to changed lines, optionally with a do-not-decrease ratchet on them.
- **risk/behavior-based** — the default here: cover the behaviors that can break, ranked by [risk-priority](risk-priority.md).
- **mutation testing** — the stronger adequacy measure (does the suite *catch injected faults*, not merely execute code); available, not mandatory — reach for it when a claim stronger than "executed" is needed on a High-risk module.

Routing rule (non-gating): the project's existing coverage convention (an established threshold or coverage tool already in the repo → honor it, as a diagnostic/floor) → the house rule → the maintainer.

`(basis: maintainer, 2026-07-10, for the scale and the no-numeric-gate position; after Fowler, Marick and the ICSE 2014 coverage study)`
