# Match the suite's conventions

Follow the test framework, naming, fixture style, assertion idiom, and directory layout already in use in this codebase rather than importing a different one. New cases that read as natives of the suite are maintainable by whoever owns it; cases in a foreign idiom are an island the next maintainer has to learn separately, and they fracture the consistency that lets a reader trust the suite at a glance. Infer the convention from what [map-the-surface](../phases/02-map-the-surface.md) found — how similar surfaces are already exercised, where their tests live, how fixtures and doubles are built — and conform to it.

This rule also governs how test *names the runner*: it discovers and uses the project's own configured test command — the capability the suite already runs through — and never assumes or hardcodes a specific framework. Name what the runner *does* ("run the project's suite"), not which tool it is; the concrete tool is the project's, discovered from the codebase, not this skill's to pick. Where genuinely no convention exists (a greenfield surface), fall back to the language's mainstream idiom and say so — but the moment prior art exists in the repo, prior art wins.
