A verification that starts before its claim is pinned verifies the wrong thing: it confirms the suite is green without ever saying what green had to mean for this change, and a green suite that never exercised the risky path reads as a pass. This phase fixes *what* must hold, *at what level*, and *what "passing" concretely means* for this change — from the spec or the change, never guessed. Every later phase builds on the claim framed here.

## Pin the claim under test

State what observable behavior the change must exhibit — the contract a caller sees, not the internal mechanism ([test-behavior-not-implementation](../rules/test-behavior-not-implementation.md)). Not "the function works" but "given input X the change must produce Y, and must **not** produce Z." The claim **always covers the behaviors the change introduces or alters** (and the reverse-dependents it affects — mapped in [map-the-surface](02-map-the-surface.md)). A source flag *adds to* that claim; it never narrows the change's own behaviors out of scope — this is a change-verification skill, so the change is always under test.

- **Under `--from-spec=<path>`** — the spec's acceptance criteria are **added** as explicit must-verify claims: the spec is the source of the intended *contract*, while the change is still the surface under test, so a behavior the change alters stays in scope even when the spec omits it (and [coverage-adequacy](../rules/coverage-adequacy.md) is assessed over the change's behaviors, not only the criteria). Map each criterion to a check — but a criterion often names *what* must hold without its observable *form* ("a discount over 100% is rejected" — thrown? an error value? clamped to 100%?), and that form is not known until the surface is mapped in [map-the-surface](02-map-the-surface.md). So state each criterion as a **mechanism-agnostic** claim now ("an over-100% discount must be rejected"), then pin the concrete assertion form once mapping reveals how rejection actually surfaces; if the change's intended mechanism is itself ambiguous, surface it to the caller rather than guessing one. And when mapping reveals **no** mechanism at all — the change simply didn't implement the criterion (often the defect the run will catch) — do not guess one (`assertRaises` vs a clamped value vs a sentinel): assert the **weakest observable property every candidate rejection form shares** — for an over-100% discount, "the total is never negative"; for a negative discount, "the total never exceeds the subtotal" — each chosen so it reddens on *its own* criterion's defect, so the case discriminates that failure regardless of how rejection is eventually built. When the spec and the current suite disagree about expected behavior, the spec is the source of *intent* but the suite may encode a real prior decision the spec missed — surface the disagreement rather than silently overriding either. `(basis: testable-or-its-not-a-requirement — spec's own bar; a spec/suite divergence is a finding the caller must adjudicate, not something test resolves silently.)`
- **Under `--changed`** — narrow the framed *surface* to the changed files plus their reverse-dependents (the callers that inherit the change's behavior); this scopes *which code's* behaviors enter the claim, it does not drop the change's behaviors. When there is no diff to derive (not a version-controlled tree, or nothing changed), frame the whole relevant surface and say so.

## Decide the test level(s) — the pyramid / trophy fork

For each behavior, decide the level at which it is verified — unit, integration, or end-to-end. Authorities conflict on the mix (the test pyramid puts most tests at unit; the testing trophy puts most at integration), the conflict is partly definitional (the trophy's "integration" is often the pyramid's sociable-unit test) and partly stack-dependent, so this is encoded as a fork with a routing rule, not a fixed ratio:

- **Routing (non-gating):** match the project's existing level-mix convention — infer it from the test-directory layout, the framework, and the current ratio, and place new tests at the same levels using the project's own definition of each ([match-the-suites-conventions](../rules/match-the-suites-conventions.md)). Where no convention exists, apply only the converged invariants: bias each behavior to the **lowest** level that can actually catch it breaking, and keep end-to-end the **thinnest** layer — the top-heavy "ice-cream cone" (mostly e2e/manual) is the universally-named anti-pattern.

`(basis: the convergent core across the Cohn/Fowler pyramid, the Dodds testing trophy, and Software Engineering at Google Ch.11 — write at multiple levels, e2e is the smallest and most brittle layer (~5–10%), and local consistency outweighs the exact shape; the ice-cream-cone anti-pattern is corroborated across ~6 independent origins. Sources: Fowler, "TestPyramid"; Dodds, "The Testing Trophy"; Software Engineering at Google Ch.11.)` `(basis: ratified by the maintainer, 2026-07-10. When no project convention exists, the target mix is pyramid-shaped (majority unit, thin e2e) for backend/domain-heavy code and integration-heavy (trophy) for JS/front-end where higher-level tests are cheap and stable. No external authority pins a universal number, so this per-project-type default is the maintainer's ratified house call.)`

## State what "passing" means for this change — deliberately open

The concrete pass condition is per-change and cannot be pinned in advance: for one change it is "these three criteria hold and no counter-example passes," for another "the p99 stays under the budget." **Deliberately open-by-design** — pinning a universal pass condition would be false precision, because the deciding specifics live in the change, not here. What *is* required every run: write the pass condition down *explicitly before designing cases* — the specific, checkable observation(s) that must hold for the claim to be met — so [report-the-verdict](06-report-the-verdict.md) can state pass/fail against it rather than against "the suite is green." An unstated pass condition is the open-by-omission defect; a per-run stated one is the closure.

## Output

The framed claim: the behaviors under test, their level(s) (fork routed), the explicit pass condition, and — under `--from-spec` — the criterion → check map. This is what [map-the-surface](02-map-the-surface.md) and [design-the-cases](03-design-the-cases.md) build on.
