# publish-artifact — usage

Take a finished artifact — authored content organized into sections — shape it into a page tree, and publish it to the configured artifacts backend via the matching adapter, returning where it landed.

## When to use
- You have a finished artifact — authored content in sections — and need it to live in the team's `tools.artifacts` destination, not just in the session.
- Another skill produced durable output (a spec, a plan, a research report, a review write-up) and the natural next move is "put this where the team reads things."
- You want the placement, page model, and links handled for you: map the tree to whatever the backend calls a page, dispatch to its adapter, hand back the location.
- You need publishing to be repeatable — re-run in place, cut a new version, or preview before writing — without hand-managing the backend's page ids or file layout.

## Not for / use instead
- Sending a message, status update, or notification to people (a channel, a thread, a heads-up) → **communicate**. publish-artifact writes a document to a store; communicate delivers a message to humans. Publish the artifact, then communicate the link.
- Wiring the artifacts backend itself — provider, transport, destination, credentials → **init** (specifically `init:artifacts`). publish-artifact consumes `tools.artifacts`; it does not configure it.
- Pushing code, opening a PR, or landing a change in the codebase → **integrate**. That's source control and delivery, a different capability than authoring a document artifact.
- Producing the *content* of the artifact — the spec, plan, or report body → **spec** / **plan** / **deep-research** / **review**. publish-artifact is the last-mile writer; it moves an already-authored tree, it does not draft one.

## Examples
`--to=<target>` — override the destination for this one publish (a backend name, a path, or a page id) instead of the configured default. Use when this artifact belongs somewhere other than the usual home — e.g. `--to=handbook/onboarding` or `--to=<page-id>`.

`--dest-dir=<path>` — for a file-backed destination, set the base directory the tree is written under, overriding the configured one. E.g. `--dest-dir=docs/specs/2026-q3`.

`--draft` — publish in a non-final draft state so reviewers can see it before it goes live. Reach for this when the artifact needs sign-off; promote it on a later run.

`--version` — write a new versioned copy and preserve the prior outputs. Use when history matters and each publish should be a distinct, retrievable snapshot rather than a mutation.

`--idempotent` — re-publish in place: update the existing pages rather than minting a duplicate. The right default for a living document you republish repeatedly; without it, a second run can create a parallel copy.

`--dry-run` — show exactly what would be published (target, page mapping, paths/links) without writing anything. Cheap safety check before a real publish, especially with `--to`/`--dest-dir` overrides.

`--to=<page-id> --idempotent` — common combination: pin to a known page and update it in place, so the same artifact keeps one canonical, evolving home.

`--draft --version` — cut a fresh versioned copy in draft state — a reviewable snapshot that leaves the last published version untouched.

## Gotchas
- `config_requires: tools.artifacts` — if the backend isn't configured, the skill guides you through `init:artifacts` and otherwise blocks. It will not silently pick or invent a destination.
- The input is a *finished artifact*: authored content organized into sections. This skill shapes it into the page tree (deciding what becomes a subpage vs. stays inline) — you do not pre-carve the tree. What it cannot use is an unstructured blob with no sections; there's nothing to carve or map, so give it sectioned content.
- How the tree maps depends on the backend's page model (nested pages vs. an index plus section files); the concrete calls live in `adapters/<backend>`, not in the procedure. You address the *capability*, the adapter owns the backend specifics.
- `--idempotent` and `--version` pull opposite directions: idempotent updates one canonical location, version fans out a new copy each run. Pick per artifact — a living doc wants idempotent, an audit trail wants version. Neither together makes sense.
- `--draft` publishes; it does not gate. The artifact is written (in draft state) and its location returned — it is not held back pending approval, just marked not-yet-final.
- It publishes what you give it. It does not author, edit, or validate the artifact's content, and it does not notify anyone that the artifact exists — pair it with **communicate** for that.
- It publishes a *clean export of the substance* and adds no process metadata of its own — no "generated by / authored via praxis" footer, no run log, no phase/agent/tool trace, no branding. Stripping every internal-process reference is the *producing* skill's job, done before it hands the tree over; this skill neither adds such machinery nor scrubs it.
- `--dry-run` is the free pre-flight. Use it whenever you override the target, so a typo'd `--to` or `--dest-dir` is caught before it writes into the wrong place.
