  flags:
    --to=<target>: override the destination (a backend name, path, or page id)
    --dest-dir=<path>: base directory for written files, overriding the configured destination
    --draft: publish in a non-final draft state for review before going live
    --version: write a new versioned copy, preserving prior outputs
    --idempotent: re-publish in place rather than minting a duplicate
    --dry-run: show what would be published, without writing
  config_requires:
    - key: tools.artifacts
      if_missing: guide via init:artifacts, else block

Usage & examples — when to reach for this skill, and concrete flag invocations: see [usage.md](usage.md).

A thin port over the artifacts backend: it names the capability, and the configured backend's adapter holds the concrete calls. A caller hands it a finished artifact — authored content organized into sections; this skill shapes that content into a page tree, resolves the destination, maps and dispatches the tree, and returns where it landed. It shapes *structure* only — it authors, edits, and scrubs no *content*. The depth lives in the rules cited below, not in a deep procedure.

**Contract — clean export, published faithfully.** An artifact is a clean export of the session's *substance* for a human audience: it renders the content and the decisions, never the machinery — no internal tool calls, no agent/phase/skill mechanics, no praxis process, no account of how it was produced. The split is owned on both sides and neither half is optional: the *producing* skill strips every internal-process reference before it hands the tree over; **this** skill publishes what it is given faithfully — it does not re-author, edit, scrub, or validate the content, and it adds **no** process metadata of its own (no "generated by / authored via praxis" footer, no run log, no phase/agent/tool trace, no branding). `(basis: ratified house decision — "artifacts are team-facing documents": team-facing output carries the content and the decisions, never the machinery.)`

1. Resolve the target: read tools.artifacts for the backend, then resolve the destination. A `--to`/`--dest-dir` **override**, if given, resolves the destination directly by the precedence in [stable-identity-and-precedence](rules/stable-identity-and-precedence.md). Otherwise resolve from the artifact's **type** — which *is* one of the `destinations` keys (`plans`, `specs`, `reviews`, `postmortems`, `research`, `decisions`), named by the caller with the artifact and looked up directly. There is no synonym table: the type the caller hands is the key, so the lookup has one reading. A type that names none of those keys (a spike write-up, an onboarding note, a general team doc), or whose entry is empty, resolves to the `destinations.default` entry (`default` is the reserved catch-all, never a type a caller names). If `default` is also empty **and** no override was given, do **not** invent or silently pick a destination — **ask the user where to publish** this artifact (name it and its type) and use their answer as a one-shot destination for this publish (classified by the same `--to` precedence). Reject a contradictory invocation (e.g. `--idempotent` with `--version`) up front.
2. Shape the finished artifact's content into a portable page tree — one main page + ordered subpages, content as backend-neutral sections — by the boundary method in [portable-tree-shape](rules/portable-tree-shape.md).
3. Map the tree to the backend's page model (nested pages, or an index plus section files); where a block cannot be represented, degrade it by [degrade-unsupported-content](rules/degrade-unsupported-content.md) rather than dropping or erroring silently.
4. Dispatch to the matching adapter, handing it the destination resolved in step 1 (the type's key entry, `destinations.default`, or a user-supplied target — the adapter does not re-derive it from the type): the concrete backend calls live in adapters/&lt;backend&gt;. Create parents before children, in tree order.
5. Return the published location to the caller — links/paths to the main page and every subpage, in tree order, plus any advisories that accompany a successful publish (e.g. an ignored `--dest-dir`, a degraded block) — or a capability-level failure the caller can react to, from [failure-taxonomy](rules/failure-taxonomy.md), never a raw provider error.

## Flag behaviors

- **`--to` / `--dest-dir`** override where the artifact lands (a backend/path/page id; a file-backed base directory). They resolve against the config default by the precedence in [stable-identity-and-precedence](rules/stable-identity-and-precedence.md).
- **`--draft`** publishes in the backend's non-final/unlisted state. If the backend has no draft concept, report `unsupported-content` (per [failure-taxonomy](rules/failure-taxonomy.md)) rather than silently publishing live — each adapter declares its draft support.
- **`--version`** writes a new labeled copy alongside prior outputs, preserving history, resolving the prior by the same stable identity ([stable-identity-and-precedence](rules/stable-identity-and-precedence.md)). Mutually exclusive with `--idempotent`.
- **`--idempotent`** matches the already-published artifact by stable identity and updates it in place. If identity cannot be resolved reliably, fail `conflict` rather than mint a duplicate — see [stable-identity-and-precedence](rules/stable-identity-and-precedence.md).
- **`--dry-run`** runs resolve → shape → map but performs no writes; returns the resolved target and the tree that would be published, so an override can be checked before it writes.
