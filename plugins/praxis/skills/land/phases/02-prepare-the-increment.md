This phase is local git work against the integration target resolved in [assess-the-change](01-assess-the-change.md), all of it done before the change leaves the machine: staging, committing, reconciling and resolving are ambient (no hosted backend); pushing and merging are [merge](04-merge.md)'s job.

## Stage coherent commits

- **Carve by concern.** Shape the working tree into commits each scoped to a single reviewable concern ([one-coherent-change-per-unit](../rules/one-coherent-change-per-unit.md)) — split unrelated changes apart, keep a pure refactor separate from a behavior change. Where the tree bundles concerns mechanically separable (unrelated files/hunks), split them; where they are entangled in the same lines, surface it rather than fabricate a split — re-authoring the change is develop's job, not land's.
- **Message the why.** Write each commit's message to the settled core and the resolved format — the house Conventional Commits baseline (verbs, breaking-change signaling, semver mapping) **by default**, displaced only by a preference the caller states this run or one persisted for this project from a past run. Absent a set preference, if recent commits *consistently* do not parse as Conventional Commits, **surface the conflict and ask the user** which to use rather than silently adopting the history's shape — then apply the answer to these commits and persist it for next time (non-interactive: fall back to the baseline and record the unresolved conflict; under `--dry-run`, preview it and write nothing) — and attach the repo's required trailers, never an AI-attribution one ([commits-tell-the-why](../../../craft/engineering/commits-tell-the-why.md)).
- **`--message=` is a phase input.** When the caller supplied `--message=`, use that text **verbatim** as the commit message instead of synthesizing one — the caller owns what it says — and still flag it in the report when it doesn't conform to the applicable format, attach the trailers the repo requires (a mandated sign-off), strip any AI-attribution trailer, since that bar isn't the caller's to waive, and note a message that merely restates the diff. When absent, synthesize per the rule. (The default-selector test: the phase always produces *some* message — the flag only selects its source — so it is a phase input, not a module.)
- **Honor the repo's commit policy.** Record the commits so the repo's enforced commit-object policy holds: let pre-commit hooks run and never bypass them (a hook failure — a formatter, a secret-scan hit, a message linter — is a stop), and sign the commits when the repo requires signed commits ([honor-commit-policy](../../../craft/engineering/honor-commit-policy.md)).

## Reconcile with the current target

Reconcile even when develop hands the branch off clean. `(basis: derived from [integrate-against-current-target](../rules/integrate-against-current-target.md))`

- **Bring the branch to the target's live head.** The *reconcile* method — merge the target *into* the branch, or rebase the branch *onto* the target — is a different axis than the *land-time* strategy ([match-the-team-flow](../rules/match-the-team-flow.md)'s merge-commit/squash/rebase governs how the change finally lands, not how the branch is updated now). Choose the reconcile method by the team's branch-update convention where it has one, honoring the rebase golden rule (never rewrite pushed/shared history). **Absent a detected convention, default to merge-in** — the lower-risk update for any branch and any land strategy — and reserve rebase-onto for where the convention calls for it *and* the golden rule permits it (a purely local, unshared branch). The default holds regardless of the land strategy; it merely *matters least* under **squash**, where the branch's local history is discarded at land so either reconcile method produces identical landed content. The point of reconciling at all is that the gate runs on the *merged result*, the real post-merge tree, not the base the branch forked from.
- **Bound it.** Reconcile enough to gate the true merge — a branch a few commits behind reconciles inline. A branch that has drifted so far that reconciling means re-authoring the change is a signal the work needs re-basing before it lands: surface it and route back, rather than absorbing an open-ended rebase into a routine landing.

## Resolve conflicts by intent

When the reconcile conflicts, resolve by reconstructing what each side intended, never by mechanically accepting one side or stacking both ([resolve-conflicts-by-intent](../rules/resolve-conflicts-by-intent.md)). A resolved tree is a third artifact neither side tested, so a resolution is not done until its result is re-gated in [run-the-gate](03-run-the-gate.md).

## Close the phase

The increment is ready when the change is a set of coherent, messaged commits sitting on the current target with no unresolved conflict. Under `--commit` ([commit-only](../modules/commit-only.md)), the run **terminates here** with the *committed-only* outcome — nothing is pushed or landed. Under `--dry-run`, report the commits and the reconcile that *would* be made without writing them. Otherwise, hand the reconciled increment to [run-the-gate](03-run-the-gate.md).
