# Capability first, then provider

init is the one skill whose *deliverable* is a concrete provider name — it exists to write `vcs.provider = "…"`. That makes it the skill most likely to leak: if its own prose starts enumerating the candidate products for a slot, the capability-not-tool line that keeps the whole plugin portable is breached at exactly the point it matters most.

## Where provider names may live, and where they may not

`(basis: maintainer, 2026-07-05)`

- **Skill prose — capabilities only.** SKILL.md, the phases, and the rules name the *capability* (vcs, ci, knowledge, artifacts, project-management, communication, telemetry) and the *field* (provider, transport, the per-category fields), never a concrete product. The test is the swap test from the kit-wide discipline: if a sentence would have to be reworded when the backend behind a capability is swapped, it has named a tool — reword it up to the capability. "The remote's host maps to the vcs provider" passes; "detect whether the backend is that one named product" fails.
- **`config.template.json` — the provider menu, as data.** The shipped template carries the option-strings (a `provider-a | provider-b | …` menu on each slot) as the value-shape the user picks from. This is *data the run reads*, exempt exactly as an adapter's provider list is exempt — it is not skill prose, it is the fill-in menu. init reads the candidate providers *from the template's menu at run time*, rather than hard-coding them in a phase.
- **Adapters (and the explorer) — the reach, resolved lazily, not a gate.** A configured provider is *reached* through some mechanism: every capability is port-backed and dispatches through its port's adapter — vcs, ci, knowledge, artifacts, project-management, communication and telemetry alike. init does **not** gate what it may configure on whether that mechanism already exists — whether a chosen backend is actually reachable is verified *lazily* by the consuming skill when it first dispatches, not eagerly here. So in any posture with a user (default, `--guide`), init records the chosen provider regardless of whether its adapter exists yet and lets reachability resolve downstream — it never disables a capability *merely* for lacking an adapter. (Under `--degrade` there is no user to choose a provider or transport, so a slot whose values aren't *derivable* — including a not-yet-built port whose transport nothing fixes — is disabled per that mode's keep/disable rule; that is disabling for a missing headless-determinable value, not an adapter gate.) `(basis: derived from the lazy-gate stance)` This is also why the menu is read from the template (the ratified shape), not from an adapter inventory.

## The method: walk by capability, resolve to provider

When [resolve-tools](../phases/02-resolve-tools.md) walks a slot, it leads with the capability — *what the slot is for* — and only then resolves *which provider fills it*, reading the candidate menu from the template rather than reciting names. Framing the walkthrough this way keeps the written config anchored to the capability key (`tools.vcs`), so a later provider swap changes only the value, never the shape, and the skill layer never has to be edited when a new provider adapter is added.
