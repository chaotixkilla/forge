The roster is the half of the config no environment fully encodes. A remote names a provider; nothing on disk names who owns the auth service, who must review a payments change, or who to @-mention in which tool. This phase fills the `me`, `teams`, and `team[]` keys — the identity and ownership map downstream skills read to route reviews, assign work, and address people. It is where the scale bottoms out: most of what it needs is *absent* signal, and asked, not inferred.

## `me` — who is running this

`me` holds the current user's member id, matching one entry's `id` in `team[]`, so a skill can answer "who am I" — which reviews are mine, which handle to post as. Derive a *suggestive* proposal from the version-control identity (the configured commit author name/email is a candidate), and confirm it against the roster; it is suggestive, not derivable, because the committer identity need not match the intended roster id. If the roster has no matching entry yet, add the current user as one.

## `team[]` — the individuals

**Acquiring the member set** comes first, and no environment signal reveals it — the roster's membership is *absent* signal. Get it by posture: under the default posture, **solicit the roster** — seed it with the current user (from the derived identity), then ask for additional members one at a time until the user says the roster is complete; the loop is bounded by the user's "done," not a fixed count. Under `--degrade`, with no user to ask, the roster is left empty — the member set is *absent* signal and the version-control identity is only *suggestive*, both of which `--degrade` skips — to be filled by a later `--phase=team` run ([degrade-gracefully](../modules/degrade-gracefully.md)). An empty or single-member roster is valid either way — the roster fills over time.

Each member is one entry carrying the full field set the shipped shape defines; fill every **top-level** field of an entry, never a subset of them (an entry with `name` set but `owns` left blank is the half-filled member [write-and-validate](04-write-and-validate.md) rejects). The one field whose *sub-keys* are individually optional is `handles` — see its bullet below: a member legitimately has no identity in a capability they don't use, and an empty handle there is resolved, not a half-filled entry.

- **`id`** — a stable short handle for the person, referenced by `me` and by ownership.
- **`name`** — display name.
- **`role`** — their function (the value is the project's own vocabulary, not a fixed enum).
- **`owns`** — the areas this member owns; the map review and work-routing read to find the responsible person. *Absent* signal — asked. Record the answer in **the project's own vocabulary for an ownership area** — filesystem paths, module or package names, or named domains/roles-as-areas ("payments," "the auth service") — as given; it is a free-form ownership label, not required to parse as filesystem paths. If the answer names roles or domains rather than paths, that *is* a valid `owns` value; do not force it into a path shape or invent an escape hatch. (basis: `owns` is read to route to a responsible person, and a project names its ownership boundaries its own way; pinning it to paths would reject the roles/domains answer a real team gives.)
- **`reviewer`** — whether they are a designated reviewer (boolean). *Absent* signal — asked; never inferred from activity.
- **`timezone`** — for scheduling/handoff; *absent* unless a handle resolves it — asked.
- **`handles`** — the per-capability address book: the member's identity in `vcs`, `communication`, and `project_management`, so a skill addressing them through a capability knows the right handle. Its sub-keys are filled **per configured capability, and only where the person has an identity there** — a non-engineer with no version-control account has an empty `handles.vcs`, and that is a *resolved* absence (an *optional* sub-key, like an optional-when-configured tools field), **not** a half-filled member. Do not block the roster write because someone lacks one capability's handle; do not invent a handle to fill the gap.
  - **Sourcing order** — for each configured capability, resolve handles from *that capability's* backend before asking: the communication workspace lists its members, the version-control host lists org/repo members, the tracker lists its users. A handle so found is *suggestive* — proposed, confirmed against the person, never committed blind. Only ask openly for a handle the backends can't resolve.
  - **Disambiguation** — when a lookup returns more than one candidate for a name (two accounts for one person, one first name matching two people, a person not found by full name), **do not guess**. Narrow it: cross-reference across the other capabilities' backends (the same person's handles tend to correspond), or ask the user to pick; record only the confirmed match. Misresolving a handle misdirects real people downstream — a review routed to the wrong account, an @-mention to a stranger — so an ambiguous handle is left empty-and-asked, never silently committed to the likeliest guess. (basis: the phase named one sourcing method and no disambiguation rule, so a real init hit ambiguous/duplicate matches on most lookups and improvised an ad-hoc cross-reference; pinning the per-capability sourcing order and the never-guess disambiguation is what makes two runs resolve the same handle the same way.)

`owns` and `reviewer` are the bottom anchor of the signal scale ([infer-before-asking](../rules/infer-before-asking.md)): a team decision no repository state encodes, so under the default posture they are asked outright, and under `--degrade` they are skipped rather than guessed ([confirm-dont-assume-defaults](../rules/confirm-dont-assume-defaults.md)). Guessing an owner or a reviewer is precisely the silent-wrong-default this skill refuses.

## `teams` — optional grouping

`teams` is an optional map for a project that spans more than one named team; for the common single-team project it stays `{}`, which is complete and valid — not an unfilled placeholder. Populate it only when the roster genuinely divides into named teams the project needs to address as groups. `(open by design: the shipped template fixes teams as an object and leaves its internal shape open, and team[] members carry no team-reference field; with no multi-team project to pin it against, init treats {} as the valid default and defers the multi-team grouping shape to the maintainer who first needs it, rather than inventing a membership mechanism the template doesn't ratify.)` Do not manufacture entries to look thorough; an empty `teams` on a single-team repo is the right answer, and [write-and-validate](04-write-and-validate.md) treats it as resolved, not as a placeholder.
