Fill the `tools` map from the graded proposals [detect-environment](01-detect-environment.md) staged — on a re-run, only the slots its review hands on, the rest carried as they stand — one slot at a time, resolving every slot to a real decision — configured, or deliberately disabled — and asking the user only where the environment was silent. Get a slot wrong here and a downstream skill talks to the wrong backend or none at all.

## Walk each slot by capability, then resolve the provider

Cover all eight slots — vcs, ci, knowledge, artifacts, project-management, communication, telemetry, workspace — and for each, lead with *what the capability is for* before *which product fills it* ([capability-first-then-provider](../rules/capability-first-then-provider.md)); do not recite product names in this procedure. Read the candidate provider menu from the template's option-strings (the ratified shape) at run time. init configures the provider the user picks and does **not** eagerly require a backing adapter to exist first: whether a chosen backend is actually reachable is verified *lazily* by the consuming skill when it first dispatches — the same static-not-eager stance detection takes — so init never disables a capability merely for lacking an adapter today. `(basis: derived from the lazy-gate stance)`

For each slot, resolve four things:

- **provider** — which backend fills the capability (or `null` if the project deliberately doesn't use it — see the disabled case below).
- **transport** — how praxis reaches the provider. Transport is not an independent environment signal; its tier *follows the chosen provider's reach*, in three cases:
  - a **port-backed provider with a built adapter** — read the adapter: one transport → **derivable**, several → **suggestive** (propose among them, **preferring the no-secret transports — an already-authorized `mcp` connector, then an authenticated `cli` — and ranking `api` last as the fallback that alone makes praxis store a token; see [route-secrets-to-userconfig](../rules/route-secrets-to-userconfig.md). When `api` is the proposal, say plainly it means entering a token into userConfig, so the user can pick a no-secret path instead if they have one**);
  - a **provider reached without a port adapter** (a local filesystem root) — the backend's own nature fixes it: a filesystem root → **derivable**;
  - a **port-backed capability whose adapter is not built yet** — nothing fixes the transport (no adapter to read, no backend nature), so it is **suggestive**, never silently defaulted: asked under the default posture, and disabled under `--degrade` (no user to pick it) per the keep/disable rule — which is disabling for a value that can't be determined headless, not for the adapter's absence per se. With a user to ask, the provider is kept: the port learns it on first use ([learn-adapter](../../learn-adapter/SKILL.md)), over the transport chosen here, a connector the session already has proposed first, then a command-line tool on the path. Say so when the slot is written. `(basis: maintainer, 2026-10-13)`
  `(basis: derived from the transports each reach mechanism supports)`
- **adapter** (optional, on a slot, a knowledge source or an audience space, any port but workspace) — `learned` forces the learned route even where praxis has an adapter for the provider; absent, a built adapter governs. `(basis: maintainer, 2026-10-13)`
- **the per-category fields** — each capability carries typed fields beyond provider/transport, and each is either *required-when-configured* (the consumer cannot use the capability **at all** without it — empty on a configured slot is a defect) or *optional-when-configured* (needed only for a subset of the consumer's operations, so empty is a resolved slot that fills lazily). The classification, per field:
  - **knowledge** — `sources` (**at least one** on a configured slot): one entry per place the project's knowledge lives, and several are normal — a platform used before the current one and never migrated, a company-wide space beside engineering's. Propose a source for each connection detection surfaced whose provider is on the template's knowledge menu, then ask whether knowledge also lives anywhere else. Per source: `name` (**required**, unique among the sources — results and fetches are tagged with it; the provider's name, suffixed `-2`, `-3`… when sources share a provider), its provider and transport (resolved as above), `root` (**required**: the entry point of that source's space — nothing can be read from it without one), `note` (**optional**, asked, never guessed, since detection can't see what a source holds: what it holds, whether only engineering or the whole company can read it, and whether it is current or legacy and frozen — the knowledge-base lane reads it to choose which sources to search), and `secret_ref` (below). `(basis: maintainer, 2026-10-01)`
  - **artifacts** — the slot's own provider, transport and `secret_ref` are the **home**, where everything praxis publishes lands by default. Its provider defaults to `local`, with the task documentation kept in the main checkout under `.claude/praxis/docs/` (`destination`), untracked like the rest of praxis's state, since task documentation is never versioned in the repository `(basis: maintainer, 2026-10-14)`; the default is still proposed for confirmation like any other. A live connection that could hold artifacts is only a *suggestive* alternative — proposed beside the default, never displacing it — so the default is **derivable**, and `--degrade` keeps it. `(basis: derived from a connection's presence being suggestive, never derivable)` `(basis: maintainer, 2026-09-30)` `destination` (**optional**): where in the home praxis publishes; left empty, artifacts asks at the first publish. `task_log` (**optional**, default `true`): whether the task log — one page listing every task — is kept in the home. Leave the default unless the user asks for no log. `audiences` (**optional**, default none): ask once whether the project wants a place for documents meant for non-engineering readers — product, leadership — kept apart from engineering's, written to only under communicate's audience rule. Per audience space: `name` (**required**, unique among the spaces — a publish selects the space by it), its provider and transport (resolved as above), `destination` (**required** unless the space's provider places artifacts without one, since a publish there runs past the point where anyone can be asked where), `for` (**required**: who the space serves, such as "product managers and leadership" — delivery matches a request's reader against it), and `secret_ref` (below). No space is written `audiences: []`. `(basis: maintainer, 2026-10-01)`
  - **project-management** — `project_key` (**required**): the tracker's identifier for this project's work items — the capability cannot address work items without it.
  - **communication** — `channels` (**optional, per entry**): the channels posts go to by purpose — `default` for broad reports, `incident` for incident updates. With the roster's handles, these are the only targets a post may reach unasked ([who-may-be-reached](../../communication/rules/who-may-be-reached.md)), so an empty entry holds a post meant for it for hand delivery; a configured communication slot is resolved even with both empty.
  - **workspace** — `files` and `commands` (**required**); with `commands: container`, `provider` and `setup` (**required**: its `kind` and `definition`); `env_files`, `services` and `recipes` (**optional**), but a service needs its `kind`, an `app` or `worker` its `root` and `mount` keys (empty is a value: the whole repository, code baked into the image), a data service whose namespace kind is `database` or `bucket` its `create` and `drop`, and a recipe its `service` and `command`. A slot configured is one with `files` and `commands` set: with `commands: host`, an empty `provider` and `setup` are resolved, not defects. Learned as the next section says.
  - vcs, ci, telemetry carry only provider/transport/`secret_ref` in the shipped shape — no extra typed field.
  A per-category field with no environment signal is *absent* and asked under the default posture; the required/optional line above is exactly what [write-and-validate](04-write-and-validate.md) checks — a required field empty on a configured slot is a defect, an optional one is not. Never leave a field as a placeholder string.
- **secret_ref** — set per [route-secrets-to-userconfig](../rules/route-secrets-to-userconfig.md): a credential reference (the `<cap>_token` userConfig key name) when the transport needs one, empty when it doesn't. Never a token value. Resolve it *after* the transport, since whether a credential is needed is decided by the transport.

## The workspace slot — learn the project's runtime once

Each field means what [workspace](../../workspace/SKILL.md)'s slot section says; this section says where init reads each one from.

**The two choices.** Ask them with their recommendations: a worktree for each task, or work in place (recommended: worktree); the project's containers for running its code, or the host (recommended: containers when detection found a setup and the runtime's tool, else the host, since nothing else can be filled). `(basis: maintainer, 2026-10-13)` Neither is derivable, so `--degrade` disables the slot, which the workspace port reads as host mode.

**With `commands: host`**, write `provider` and `transport` empty and `setup` in the template's shape with every field empty, and learn only the env files (4 below), since the port runs nothing but bare commands on the host.

**With `commands: container`**, read the setup through the workspace adapter's description of the main checkout's definition — never the task worktree's, which may hold a task's change, and never by parsing a definition here — and present what it learned once, grouped by service, for the user to confirm or correct as a block. `(basis: derived — a field-by-field walk of a learned setup is dozens of prompts)`

1. **The setup.** The one detection found. Among several kinds, the multi-service definition, else the development-environment definition, else the container build file `(basis: maintainer, 2026-10-13)`; within a kind, the files the project's own default start reads together, else asked. Its `lockfiles` are the dependency lockfiles its builds copy in. The dev stack's project and network are the definition's explicit names, else the ones the runtime derives from the main checkout's folder, read statically; with several networks, the one the app services share with the data services they reach, else asked.
2. **The services**, as the adapter describes them; a setup that defines none gets the slot section's single `app`, at the working directory the adapter reports, else asked. A container build file's `context` and `target` are the folder and stage CI builds it from, else its own folder and its last stage. A service's kind: `app` when it is built from or binds the repository's code and serves; `worker` when it is built from or binds that code and runs background jobs; `database`, `search`, `cache` or `storage` for a data service by what it stores; `other` for anything else. A volume mounted inside the service's `mount`, or at a path its build installs dependencies into, is one of its `caches`; any other is data. A data service's namespace kind, its `create` and `drop`, and its `setup` recipe follow the slot section's meanings, a search-like or cache server taking `prefix` only when an app's variable names its index or prefix, else `none`; the commands derived from the server's own client tool in its image and its documentation. `reach` comes from the variables the app services read to reach it, with `{host}` and `{name}` put in, and every credential kept as a `${VAR}` reference to the env-file variable that holds it. A credential that only exists inside a connection URL has no variable to reference: write `reach` with a reference to a new variable for it, `<SERVICE>_PASSWORD`, ask the user to add that variable to their env file, and mark the service `missing variable <SERVICE>_PASSWORD`; until they do, its runs fail naming the variable.
3. **The recipes.** For each app service, its tests, linters and migrations, and the generators the [documentation-kit](../../../craft/writing/documentation-kit.md) runs that the project already has — the commands that produce a schema dump, a contract export or diff, a module graph, a coverage report, benchmark results, visual snapshots or their diffs — named as the slot section says. Read them, like the setup, from the main checkout. Where the project's CI configuration and its documentation or task scripts disagree, CI's command wins, since it is what the project runs, with any wrapper that starts containers itself unwrapped to the command it runs inside; the others fill purposes CI lacks. A recipe `uses` a data service when its CI job or documentation runs it beside one.
4. **The env files** git ignores that the project's apps or setup load and the main checkout has, at the repository's root and its services' roots — learned for either `commands` choice, since a worktree needs them either way.

Nothing is run. Each learned recipe is written `unproven`, and so is each service a recipe runs in or uses; a recipe or service a run has already proven (it carries no mark) is kept as it stands, on any re-run. A task's first run proves them ([workspace](../../workspace/SKILL.md)). `(basis: maintainer, 2026-10-14 — init stays static; the first real run is the proof)`

## init points at backend state — it never creates or restructures it

Resolving a slot means **recording a pointer to backend state that already exists** — a repository, a workspace, a tracker project, an artifact destination. It does **not** mean provisioning or reorganizing that backend. When a field's answer implies the target isn't there yet or isn't shaped the way the answer assumes (a destination that doesn't exist, a knowledge root that would need pages moved, a tracker project not yet created), init does not rename or restructure destinations, move content, design schemas, or otherwise mutate the backend to make the pointer valid. It **records the intended target and tells the user to provision it**, then resolves the slot against that target (or leaves it asked/deferred if the user must act first). Reachability is verified lazily by the consuming skill at first use anyway — the same static-not-eager stance the rest of this phase takes — so init never needs to touch backend state to prove a pointer good.

Two temptations to refuse explicitly, because a backend answer invites them: **do not reorganize the backend** to fit a slot (that is the user's change to make, on their own terms, not a side effect of configuring praxis), and **do not go hunting for cross-skill collisions** in the backend (whether another tool or workspace already writes to the candidate target). A shared backend is normal and not init's to police; if the user points two slots at genuinely conflicting targets, that surfaces when they confirm the values, not through init auditing the backend. init's job ends at a recorded pointer and, where needed, a "you'll need to create/adjust X" instruction. (basis: derived from a real run that reorganized a backend unasked, 2026-07-13)

## Apply the posture to each field

Each field is filled according to its signal tier and the run's mode, per the matrix in [confirm-dont-assume-defaults](../rules/confirm-dont-assume-defaults.md). In the default posture: a *derivable* field (the provider a recognized remote host fixes) is proposed pre-filled for one-shot confirmation; a *suggestive* field (which slot a live connection fills) is proposed as a question over its narrowed candidates; an *absent* field (a `project_key`, a `destination`, a `channels` entry, a source's `root`) is asked openly. `--guide` explains each slot's options and re-confirms even the derivable fills ([guided-walkthrough](../modules/guided-walkthrough.md)); `--degrade` takes the derivable fills silently and disables the rest ([degrade-gracefully](../modules/degrade-gracefully.md)).

## The disabled case — a slot the project doesn't use

A capability the project genuinely doesn't use is not a gap to leave blank — it is a decision to record. Write it disabled: `provider: null`, the rest of the slot left empty — for knowledge, `provider: null` beside `sources: []` — distinct from an un-replaced option-string placeholder, which means "not yet decided," and from an omitted key. The downstream `config_requires` gate reads `provider: null` as deliberately unconfigured and applies the consumer's own `if_missing` posture. `(basis: maintainer, 2026-07-05)` This is the representation `--degrade` writes for every slot it skips, and it is what makes a narrowed config *valid* rather than *incomplete* — the distinction [write-and-validate](04-write-and-validate.md) enforces. Confirm a disable the same way any inference is confirmed under the run's posture; don't disable a slot the user never spoke to unless `--degrade` authorized skipping the ask.

## Scoped to one capability

When invoked as `init:<cap>` (equivalently `--phase=<cap>`), this phase runs for exactly one slot and merges the result over the existing config without touching the others — the mechanics are in [single-phase](../modules/single-phase.md). This is the entry point every sibling skill's `guide via init:<cap>` resolves to, so each of the eight capability names is a valid target here.
