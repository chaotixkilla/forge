This phase fills the `tools` map — the seven capability slots every other praxis skill reads to know which backend to talk to. It takes the graded proposals [detect-environment](01-detect-environment.md) staged and, one slot at a time, turns each into a resolved decision: a provider, a transport, the fields that capability needs to be usable, and a credential reference where one is required. Get a slot wrong here and a downstream skill talks to the wrong backend or none at all; leave one an untouched placeholder and the config is defective. The discipline is to resolve every slot to a real decision — configured, or deliberately disabled — asking the user only where the environment was silent.

## Walk each slot by capability, then resolve the provider

Cover all seven slots — vcs, ci, knowledge, artifacts, project-management, communication, telemetry — and for each, lead with *what the capability is for* before *which product fills it* ([capability-first-then-provider](../rules/capability-first-then-provider.md)); do not recite product names in this procedure. Read the candidate provider menu from the template's option-strings (the ratified shape) at run time. init configures the provider the user picks and does **not** eagerly require a backing adapter to exist first: whether a chosen backend is actually reachable is verified *lazily* by the consuming skill when it first dispatches — the same static-not-eager stance detection takes — so init never disables a capability merely for lacking an adapter today. `(basis: derived — the lazy-gate stance applied to init (config accretes; reachability is checked at first use, not at setup), and it honors the settled model in which knowledge is reached through the gather explorer with no praxis adapter; see [capability-first-then-provider](../rules/capability-first-then-provider.md). This reconciles the template menu (candidate shape) with the adapters/explorer (lazy reach) as one non-conflicting model, not two competing provider sets.)` Keeping the walkthrough anchored to the capability key means a later provider swap changes only the value.

For each slot, resolve four things:

- **provider** — which backend fills the capability (or `null` if the project deliberately doesn't use it — see the disabled case below).
- **transport** — how praxis reaches the provider. Transport is not an independent environment signal; its tier *follows the chosen provider's reach*, in three cases:
  - a **port-backed provider with a built adapter** — read the adapter: one transport → **derivable**, several → **suggestive** (propose among them, **preferring the no-secret transports — an already-authorized `mcp` connector, then an authenticated `cli` — and ranking `api` last as the fallback that alone makes praxis store a token; see [route-secrets-to-userconfig](../rules/route-secrets-to-userconfig.md). When `api` is the proposal, say plainly it means entering a token into userConfig, so the user can pick a no-secret path instead if they have one**);
  - a **provider reached without a port adapter** (knowledge through the explorer, or a local root) — the backend's own nature fixes it: a live connection's protocol or a filesystem root → **derivable**;
  - a **port-backed capability whose adapter is not built yet** — nothing fixes the transport (no adapter to read, no backend nature), so it is **suggestive**: asked under the default posture, and disabled under `--degrade` (no user to pick it) per the keep/disable rule — which is disabling for a value that can't be determined headless, not for the adapter's absence per se.
  `(basis: derived — the reach mechanism advertises or implies the transport(s) it supports, so the provider fixes or narrows the transport; where no reach yet fixes it, the field is suggestive, never silently defaulted. There is no environment signal for transport independent of the provider, which is why detection stages a provider/capability and leaves transport to be resolved here.)`
- **the per-category fields** — each capability carries typed fields beyond provider/transport, and each is either *required-when-configured* (the consumer cannot use the capability **at all** without it — empty on a configured slot is a defect) or *optional-when-configured* (needed only for a subset of the consumer's operations, so empty is a resolved slot that fills lazily). The classification, per field:
  - **knowledge** — `root` (**required**): the entry point of the knowledge space the gather skill reads from — gather has nowhere to read without it.
  - **artifacts** — `destinations` (**optional, per entry**): where each artifact *type* publishes — `plans`, `specs`, `reviews`, `postmortems`, `research`, `decisions`, and a `default` catch-all for any type without its own entry (a spike write-up, an onboarding note, a general team doc). publish-artifact needs only the destination for the type it is currently publishing, so each entry is filled independently; an empty type entry falls back to `default`, and an empty `default` merely defers that type's wiring. A configured artifacts slot is resolved even with some or all destinations still empty.
  - **project-management** — `project_key` (**required**): the tracker's identifier for this project's work items — the capability cannot address work items without it.
  - vcs, ci, communication, telemetry carry only provider/transport/`secret_ref` in the shipped shape — no extra typed field.
  A per-category field with no environment signal is *absent* and asked under the default posture; the required/optional line above is exactly what [write-and-validate](04-write-and-validate.md) checks — a required field empty on a configured slot is a defect, an optional one is not. Never leave a field as a placeholder string.
- **secret_ref** — set per [route-secrets-to-userconfig](../rules/route-secrets-to-userconfig.md): a credential reference (the `<cap>_token` userConfig key name) when the transport needs one, empty when it doesn't. Never a token value. Resolve it *after* the transport, since whether a credential is needed is decided by the transport.

## init points at backend state — it never creates or restructures it

Resolving a slot means **recording a pointer to backend state that already exists** — a repository, a workspace, a tracker project, an artifact destination. It does **not** mean provisioning or reorganizing that backend. When a field's answer implies the target isn't there yet or isn't shaped the way the answer assumes (a destination database that doesn't exist, a knowledge root that would need pages moved, a tracker project not yet created), init does not rename databases, move content, design schemas, or otherwise mutate the backend to make the pointer valid. It **records the intended target and tells the user to provision it**, then resolves the slot against that target (or leaves it asked/deferred if the user must act first). Reachability is verified lazily by the consuming skill at first use anyway — the same static-not-eager stance the rest of this phase takes — so init never needs to touch backend state to prove a pointer good.

Two temptations to refuse explicitly, because a backend answer invites them: **do not reorganize the backend** to fit a slot (that is the user's change to make, on their own terms, not a side effect of configuring praxis), and **do not go hunting for cross-skill collisions** in the backend (whether another tool or workspace already writes to the candidate target). A shared backend is normal and not init's to police; if the user points two slots at genuinely conflicting targets, that surfaces when they confirm the values, not through init auditing the backend. init's job ends at a recorded pointer and, where needed, a "you'll need to create/adjust X" instruction. (basis: a real run let an artifacts-slot answer trigger an un-guided backend reorg — renaming databases, moving pages, designing schemas — plus a self-initiated collision check, none of which init asked for or should; the boundary is the same one that keeps init from typing a token — it configures by *reference*, and provisioning the referent is the user's, not init's.)

## Apply the posture to each field

Each field is filled according to its signal tier and the run's mode, per the matrix in [confirm-dont-assume-defaults](../rules/confirm-dont-assume-defaults.md). In the default posture: a *derivable* field (the provider a recognized remote host fixes) is proposed pre-filled for one-shot confirmation; a *suggestive* field (which slot a live connection fills) is proposed as a question over its narrowed candidates; an *absent* field (a `project_key`, a `destinations` entry) is asked openly. `--guide` explains each slot's options and re-confirms even the derivable fills ([guided-walkthrough](../modules/guided-walkthrough.md)); `--degrade` takes the derivable fills silently and disables the rest ([degrade-gracefully](../modules/degrade-gracefully.md)).

## The disabled case — a slot the project doesn't use

A capability the project genuinely doesn't use is not a gap to leave blank — it is a decision to record. Write it disabled: `provider: null`, the rest of the slot left empty. `(basis: ratified by the maintainer, 2026-07-05 — a deliberately-unconfigured slot is marked provider:null, distinct from an un-replaced option-string placeholder, which means "not yet decided," and from an omitted key. The downstream config_requires gate reads provider:null as "deliberately unconfigured" and applies the consumer's own if_missing posture.)` This is the representation `--degrade` writes for every slot it skips, and it is what makes a narrowed config *valid* rather than *incomplete* — the distinction [write-and-validate](04-write-and-validate.md) enforces. Confirm a disable the same way any inference is confirmed under the run's posture; don't disable a slot the user never spoke to unless `--degrade` authorized skipping the ask.

## Scoped to one capability

When invoked as `init:<cap>` (equivalently `--phase=<cap>`), this phase runs for exactly one slot and merges the result over the existing config without touching the others — the mechanics are in [single-phase](../modules/single-phase.md). This is the entry point every sibling skill's `guide via init:<cap>` resolves to, so each of the seven capability names is a valid target here.
