# degrade-gracefully (`--degrade`)

Activated by `--degrade`, referenced from [resolve-tools](../phases/02-resolve-tools.md) and [write-and-validate](../phases/04-write-and-validate.md).

The base run reaches the user for every gap and every inference. This module runs *without a user* — for a non-interactive or automated context where prompting is impossible. It fills what the environment settles and disables the rest, producing a valid config with no prompts. Deletion test: remove it and init runs interactively, asking its gaps; the no-user, fill-what-you-can behavior is the added mode.

## The delta — decide at the granularity of the whole slot

`--degrade` acts per *slot*, not per field, because a half-filled slot (a provider with an empty required field) would be a **defect** and this mode must never write one. The rule:

- **Keep a slot configured only if it fully resolves without the user.** A tools slot is kept when its **provider, its transport, and every required-when-configured per-category field** ([write-and-validate](../phases/04-write-and-validate.md)) are *all* **derivable** — fillable from the environment with no human. (Provider and transport are the always-required base fields; the required per-category fields are `knowledge.root` and `project_mgmt.project_key`. This is the same field set the disable test below keys on — the two are one rule stated twice.) Those derivable values are committed without confirmation: this is the one mode where an inference lands unseen, justified because there is no user to see it and each signal admits only one value. An *optional* field with no signal is left empty, as at any posture.
- **Disable the whole slot the moment a required field needs the user.** If the provider is *suggestive*/*absent*, or its transport is not derivable (its reach admits several transports with none forced), or any required per-category field is absent (a `project_key`/`root` no signal supplies), write the slot **disabled** — `provider: null`, dropping any derivable fills it did have. Don't leave a provider standing next to an empty required field; disabling the whole slot is what keeps the headless config valid rather than defective. `(basis: derived — the disable granularity is the whole slot because validity is defined per slot: a slot is resolved as configured or as provider:null, with no valid in-between, so a slot that can't be fully configured without the user must be disabled entire.)`
- **The roster is left empty, not disabled.** `provider: null` is a tools-slot marker with no meaning for `me` (a string) or `team[]` (an array). The member set is *absent* signal and the version-control identity is only *suggestive* ([resolve-team](../phases/03-resolve-team.md)) — and `--degrade` skips suggestive-and-absent fields (the posture matrix in [confirm-dont-assume-defaults](../rules/confirm-dont-assume-defaults.md)), committing only what a signal *uniquely* determines. So a headless run writes an empty roster — `me: ""`, `teams: {}`, `team: []` — a valid thin roster ([write-and-validate](../phases/04-write-and-validate.md)), and defers it to a later interactive `--phase=team`. It does **not** commit the suggestive identity unseen; that would break the derivable-only rule the keep test rests on.
- **Record what was skipped.** Report the slots left disabled and why (no signal / needed disambiguation / a required field the environment couldn't supply), and that the roster was left empty for `--phase=team`, so a later interactive run can finish them.

## Why a degraded config is still valid

The distinction that makes this safe: a disabled slot (`provider: null`) is *resolved*, not *defective* — the gate reads it as "deliberately unconfigured" and applies the consuming skill's own `if_missing` posture, exactly as if the user had disabled it. A `--degrade` run therefore never writes a defect; it writes a narrower but valid file. `(basis: ratified by the maintainer, 2026-07-05 — the disabled marker is provider:null, and --degrade writing it for every unresolvable slot is what lets a headless run produce a valid config rather than one full of placeholders.)`

`--degrade` and `--guide` are contradictory (avoid vs. maximize user involvement); passing both should be rejected rather than silently resolved to one.
