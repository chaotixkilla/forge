# scope-source (`--from-scope=<ref>`)

Activated by `--from-scope=<ref>`, referenced from [interrogating-prompts](../phases/01-interrogating-prompts.md).

The base spec draws its scope from the request. This module bounds it by a source someone outside the work already approved: an approved plan, a board of agreed tests, a brief a decider signed. Deletion test: remove this module and spec still runs on the request alone; holding a spec to an outside source is behavior a flag turns on. It is separate from [ingest-from-discussion](ingest-from-discussion.md): that module distills intent from chatter, while this one holds every requirement to an approved boundary. `--from-scope` may be given beside either ingest flag, the source then bounding what they seed. (basis: field findings, 2026-11-25 — sets specified without their approved source carried about three times its scope)

## The delta

- **Read the source** named by `<ref>`: a file in the repository, read as written; else a document through the [knowledge](../../knowledge/SKILL.md) port's read; else the text the caller hands. With it, record its **decider**: the person who approved it, as the source or the caller names them. They are the work's outside decider when the intent names no other ([documentation-plan](../../../craft/writing/documentation-plan.md)'s Documents for an outside decider). A source with no decider named is still a source, its decider missing, and the spec asks who it is once, with its other questions. An approval read from a backend settles nothing until the developer confirms it, so the spec asks that once too, for the whole source ([items-and-agreements](../../document/rules/items-and-agreements.md)).
- **One item per element.** Each element of the source becomes a source item, kind `SRC`: the smallest unit the source itself labels or enumerates, such as a test on a board, a bullet of an approved plan or a numbered clause of a brief, or, in unlabelled prose, one sentence that obliges something. Context and rationale oblige nothing and aren't elements, and a choice the source makes is a decision (below), not an element. Its shape is the spec type's `SRC` ([spec](../../document/rules/types/spec.md)). When the intent or the epic's decomposition assigns elements to this task, only those become its items, and the rest are listed once, by the sibling task that owns them. When the intent names sibling tasks working from the same source and nothing assigns its elements, the assignment is asked once, with the spec's other questions, its default the elements whose subject this task's intent names.
- **Every requirement serves an element.** Each requirement `serves` the `SRC` item it answers to, directly or by `rests-on` the requirement it derives from ([trace-each-requirement-to-a-need](../rules/trace-each-requirement-to-a-need.md)). A requirement a law or a compliance rule imposes, or without which a computed check on the spec page fails, is kept, serving what imposes it as a need outside the documentation, on a second list headed *Kept beyond the source*, shown to the decider with the other list. (basis: maintainer, 2026-11-25) Any other requirement that serves no element is **left out of scope**: it is not filed as a requirement, and goes, with one line on why it was drafted, to the spec's one list headed *Left out of scope*, shown to the source's decider once, as a whole, as section 5 of the spec page, and again only when a later round changes it. Nothing on that list is asked as a question of its own. The decider brings one back by answering; it then serves a new `SRC` item holding their answer.
- **The source's own decisions enter agreed.** A choice the source already makes, stated as made, enters as a decision whose `decider` is the source's decider and whose `applies-to` is every task the source covers, its tier axes set by the register's own tests. Once the decider is named and the developer has confirmed the source, it is `agreed` under an agreement whose decider is theirs and whose link is the source; until then it is `proposed` ([items-and-agreements](../../document/rules/items-and-agreements.md)). No critic the spec or a later step recruits may reopen it: a critic's objection to one becomes a question for that decider, never a change to the decision. An option the source names without choosing stays an open question, as any is.

## Prerequisite and degrade

A source on the knowledge backend is a reason spec reaches the knowledge capability; the base path touches no backend. Following doer-owns-prerequisites, spec **declares no knowledge prerequisite**: the capability is owned by its port skill.

When the source can't be read (the port reports any failure, or the file is gone), stop and report that the scope source couldn't be read and what would read it. Never spec as though no `<ref>` was given: a spec drafted without its approved boundary is the failure this module exists to stop.
