A result arrives in the shape its step produced; this phase decides its document type and shapes it to that type, adding nothing the result doesn't carry. A kit piece close-out hands over isn't typed: it goes where the [documentation-kit](../../../craft/writing/documentation-kit.md) places it. It shapes results only: pieces an earlier filing already shaped, handed over again, skip it.

## Which type

Match the result to a type by its membership test: the [task record](../rules/types/task-record.md) for where the task stands now, in its family's sections; the [task history](../rules/types/task-history.md) for what the task was asked and what each round did (a skipped step's outcome and reason included); or one of these:

- **work records** — the [spec](../rules/types/spec.md), the [plan](../rules/types/plan.md), the [traceability](../rules/types/traceability.md) table, the [scratchpad](../rules/types/scratchpad.md), the [review record](../rules/types/review-record.md), the [round record](../rules/types/round-record.md), [ship notes](../rules/types/ship-notes.md), an [incident record](../rules/types/incident-record.md), a [research report](../rules/types/research-report.md), [spike findings](../rules/types/spike-findings.md), an [audit report](../rules/types/audit-report.md);
- **decision records** — a [decision record](../rules/types/decision-record.md);
- **the documents the task's documentation plan owes**, each in the [type-files](../rules/type-files.md) catalogue;
- **system documentation** of the part the task touched — an [explanation](../rules/types/explanation.md), a [reference](../rules/types/reference.md), a [how-to](../rules/types/how-to.md), a [concept](../rules/types/concept.md). It covers only what the task touched, one part and one content type a page, is dated by the task and is never edited after the task ends; a later task writes its own pages and links back, and an item there that `amends` one here targets it by link, not id. (basis: maintainer, 2026-09-30, after Diátaxis)

When the act file names the type a result files as, that decides. One result can yield several documents: a review record, and a decision record for each of its decisions that passes that type's test. A result that matches no type isn't filed: tell the caller, naming the result. (basis: maintainer, 2026-09-30, the three kinds of documentation)

A document the current round already filed — the same type about the same subject: one unit's review, one decision — is updated, not filed again. `(basis: derived from one type per page)` One an earlier round filed stays as it stands, and the current round files its own, but for the task history, one page per task, which takes each round's section ([pages-belong-to-their-task](../rules/pages-belong-to-their-task.md)), but for a decision record a ship round sets to accepted, updated in place.

Restate the task record's current state ([task-record](../rules/types/task-record.md)) on every filing; choosing among the claims results already carry adds none. (basis: maintainer, 2026-10-07)

## Shape it

Shape each document to its type, under [one-type-per-page](../rules/one-type-per-page.md), which sets the footer line every page closes with. What a type file holds is [type-files](../rules/type-files.md). When a type's file declares item kinds, its content is held as items, with agreement over them held as agreements, under [items-and-agreements](../rules/items-and-agreements.md).

Every page has one reader: a teammate on the system who wasn't part of the task and doesn't use praxis, reading later to act on what the task found. On [audience-tiers](../../../craft/writing/audience-tiers.md) that reader is a peer, so the system's own terms are used bare; system documentation — an explanation, a reference, a how-to, a concept — is pitched to a newcomer to the part it covers, since its reader arrives at that part without the task's context. (basis: derived from the documentation's readers, people who don't use praxis) Three things hold for every type:

- **What to act on comes first.** A page opens with what its type's file says it leads with, or, where the type names no lead, the result's conclusion, and then what to act on, unless the type's file already places it — an incident's follow-ups, an audit's findings with their fixes ([lead-with-the-takeaway](../../../craft/writing/lead-with-the-takeaway.md)). (basis: maintainer, 2026-10-02) What to act on is only an action the result itself names — a remediation, a follow-up, a next step — and a page whose result names none has no such line; one is never inferred from the conclusion. (basis: derived from laying out adding no claim) Headings, lists and tables let a reader find their part without reading in order ([structure-for-scanning](../../../craft/writing/structure-for-scanning.md)): findings, and a scratchpad's claims, are list entries or table rows a reader can run down, never paragraphs. A relation the result carries — a flow, a set of states, what depends on what — is drawn as a diagram where [when-a-visual-is-owed](../../../craft/writing/when-a-visual-is-owed.md) says one is owed, to [diagram-legibility](../../../craft/writing/diagram-legibility.md), even when the step didn't draw it, from what the result carries: each node and edge traced to a claim in it, so laying it out adds no claim. (basis: maintainer, 2026-10-07) Figures the result carries for a quantity over a continuum, with their claim, axes, units and number of observations, are handed over as a chart block where that rule says a chart is owed, rather than as the table the step reported them in. (basis: maintainer, 2026-10-07) Which details sit in the body and which lower down follows [right-size-the-detail](../../../craft/writing/right-size-the-detail.md)'s need-to-know test for this reader and the action the page's conclusion asks of them, and each sentence is cut to what it carries ([respect-the-readers-time](../../../craft/writing/respect-the-readers-time.md)). Laying a result out moves, orders and tightens what it carries; it adds no claim.
- **Every claim keeps its source.** Carry each claim's source through from the result: code at a commit and `file:line`, a document, a test run, a conversation. A claim the result gives no source for is marked `(unsourced)` where it stands, never given one. (basis: maintainer, 2026-09-30) A source is written as a link a reader can follow: code to its line by [vcs](../../vcs/SKILL.md)'s link a file at a commit, at the commit the result read it at, else the head the page's pin line names; a review request, a ticket, a thread or a document to its address; an item id as an in-tree reference to the section that shows it. So is every source a page names in passing, such as a playbook, whether or not the page's readers can open it. A source named by an id also says what it is, since a reader who can't open it is otherwise left with a bare name, in words right after the id unless the backend's adapter shows them with it: its title as the result carries it, re-read at the source when the result carries none and this run can reach it, else said not to be recorded. An id that isn't unique on its own, such as a section's, a playbook's or a bare number, also names the source it sits in, such as the epic's playbook 3; an id naming two sources on one page set is told apart by that larger source. An address is one the result carries, or one that follows from it: an address the result carries that holds the id, with the id replaced, for an id of the same family, such as another ticket on the same tracker or another review request on the same repository; never a guessed host, repository or page. A source whose address the result doesn't carry, a vcs link that fails, or a commit of the task's own it hasn't pushed stands as text marked `(no link)` right after its id or name, before any words saying what it is. (basis: field prototype, the maintainer had to ask for linked evidence; maintainer, 2026-11-13, tickets and playbooks named without links)
- **Plain terms, no machinery.** A page says what was done and found in its reader's terms ([match-reader-vocabulary](../../../craft/writing/match-reader-vocabulary.md)), never how praxis ran it: no skill, step, phase, lane or explorer names, no tool calls ([clean-export](../../../craft/writing/clean-export.md)), and none of the work's own words for what happened to a finding or a claim, which give way to what happened: not "first pass" but "before the author's explanation was read". A review's marks for what the author's explanation did to an item are already in the reader's terms ([prior-pass](../../review/modules/prior-pass.md)), and so are the words a result grades a claim with — whether it holds, how sure it is ([results-and-certainty](../../../craft/evidence/results-and-certainty.md)): both pass through as the result gives them. Work that was skipped is still recorded, as what wasn't checked and why — "the retry library's behavior wasn't checked against its documentation: the reviewer judged it unnecessary" — never as a skipped step. (basis: maintainer, 2026-10-02)

## Items, pages and checks

The round's brief, handed with the filing, carries the documentation plan ([documentation-plan](../../../craft/writing/documentation-plan.md)). A task outside the plan's scope ([documentation-plan](../../../craft/writing/documentation-plan.md)) runs steps 1, 3 and 4 below for its types that declare item kinds, and skips Owed this filing and step 2: its pages are placed as [publish-and-link](03-publish-and-link.md) lays them out.

**Owed this filing.** A document the plan owes and nobody dropped gets its page from the filing its due point arrives:
- **before the build:** the first filing;
- **during the build:** the first filing of a build step;
- **before the gate that needs it opens:** as the [documentation-plan](../../../craft/writing/documentation-plan.md) defines it;
- **from its trigger:** the filing whose result first meets it;
- **after:** close-out.

A document the plan owes whose items a filing carries before its due point gets its page from that filing, its items shown and the rest in minimum form, its detail finished at its due point: a plan's gates and metrics stand on the cutover plan from the plan skill's filing. Before its due point such a page is held to the shared findings only, its type's computed checks applying from the due point on. (basis: benchmark, 2026-11-12, gate and metric items filed with no page to show them) A page with nothing filled yet stands in its type's minimum form. A document whose due point passed without its page, or with a section of its page still in minimum form where the plan owes more by then, is listed as late in the task record's open-items section.

1. **Items.** A result, or a waiting piece, whose type declares item kinds is laid out as items of the merged store:
   - each piece matched to an existing item, or made new, as [items-and-agreements](../rules/items-and-agreements.md) says;
   - its fields filled only from what the result carries;
   - a confirmed feedback proposal from [find-the-task-documentation](01-find-the-task-documentation.md) entering as the agreement or change it proposed.
   - what changes about an item — its state, owner, decider, decide-by, latest verification, rank and dates — reaches a page only through a view or the item's own block, never restated in a page's prose, which names the item by in-tree reference. What an item says, its substance and its reasons, may stand in prose. (basis: benchmark, 2026-11-12, pages contradicting each other on what had passed)
2. **Pages.** Each owed type takes the page its type file's Page line names ([type-files](../rules/type-files.md)).
3. **Restricted items.**
   - **The copy.** They go on a restricted copy, which holds only the pages that have restricted items, under a main page titled `<key> · restricted`. That page has one line saying what the copy holds, and links the team documentation. Each restricted page keeps its team page's title and its place in the team tree's order, shows only its restricted items, and reaches team items by link. The copy has no groups.
   - **The team pages.** Each team page that leaves some out says so in one line at the end of the section that leaves them out: `<n> restricted items: ask <their owners>`, the owners in store order and comma-joined, an item with no owner adding "owner not recorded" to the list.
   - **The team store** keeps an agreement that settled both kinds, naming the restricted ids without their content. One that settled only restricted items stays out of it.
   - **The destination** is the one the entry's `restricted` field names, which the caller settles with the developer.
   - **With no destination named**, the restricted items are returned to the caller unfiled, as pieces carrying their ids, so their numbers stay reserved. Their placeholder lines stand.
4. **Checks.** Before anything is handed to publish, run every owed type's computed checks, but for a page filed before its due point, as Owed this filing says, and the findings that block publishing in [items-and-agreements](../rules/items-and-agreements.md), over the merged store. Write the merged store, with every decide-by filled in, to the session's scratchpad, and run [check_store.py](../scripts/check_store.py) on it. It prints the shared findings, flags and links to verify, and exits non-zero when there is a finding. Resolve each link it lists to verify; an unresolved one is a finding too. Then write the pages' view blocks into the store's `views` in [item-store-and-views](../../artifacts/rules/item-store-and-views.md)'s shape, keyed by page and position with each block's subject, and run [resolve_views.py](../../artifacts/scripts/resolve_views.py) on it: each view it rejects is a finding. A view that resolves to `none` isn't one; its caption and "none" are that section's one line saying what isn't known yet. The type-specific checks are run as each type file states them.
   - **A finding on a team item** stops only the team publish, and **one on a restricted item** stops only the restricted one. Each copy publishes on its own.
   - **Each finding** is returned to the caller naming the item and what is wrong, for the developer to supply. What the stopped publish would have added comes back unfiled, as pieces carrying their items, and the next filing runs them through this section again.
   - **Judgment checks** go to the [document-critic](../../../agents/critics/document-critic.md) once the computed checks pass, before anything is handed to publish. It is recruited with each page about to publish, its type, its type file's path, and the items of that page's own copy. On a team page, its line names a restricted item by id only. Its result for each page is returned with the filing as prompts for review, and never stops it. Without fan-out, apply its written lens to each page yourself in a separate pass.
   - **On the pages.** A page that publishes passed its computed checks, and says so in a line: `Computed checks: holds`. Under it stands `Review:` with the critic's line for the page: *holds*, or each finding with its anchor as a link. The checks it couldn't reach go back to the caller only. (basis: maintainer, 2026-11-11, a holds mark computed, never typed)

The output is the shaped documents, their pages and the merged store, the restricted copy when there is one, the judgment prompts, and any unfiled pieces, for [publish-and-link](03-publish-and-link.md).
