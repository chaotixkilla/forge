## Publish the tree

Bring the task record up to date with this filing ([task-record](../rules/types/task-record.md)), the pieces handed over already shaped included: a page joins the documents filed so far, and a section joins its page in the act's row order — a waiting piece's row, step key and what it ran for are those its opening line names, else those its `<row>-<skill>.md` file name carries, this filing's in the step key it's handed — with a piece that has no step key after every step's, in the order filed, and the delivery's after those (basis: derived — a piece with no row follows the rows, as `closing.md`'s pages do). Within one round's pages, among pieces of one step key, what it ran for, type and section heading, whether filed, waiting or this filing's own, the latest stands and replaces the rest, as a step's result filed again does: this filing's own beats any waiting piece, a later piece in a file beats an earlier one, and between waiting files the later write wins. (basis: maintainer, 2026-10-07, a correction replacing the claim it corrects; the section heading, derived — two sections of a page aren't one claim) A piece of a step the act runs more than once that names nothing it ran for, as an earlier version wrote it, matches whatever a piece of its step key ran for. (basis: derived — such a piece can't say what it ran for) Then publish the task's whole documentation through [artifacts](../../artifacts/SKILL.md) at the destination the first phase resolved — new on the task's first filing, in place on every later one and on every filing to a file backend (its `--idempotent` publish, with the identity the first phase resolved). Shape it as a portable page tree ([portable-tree-shape](../rules/portable-tree-shape.md)): the task record first, as the main page's landing summary, then one subpage per document, the current round's first and each earlier round's after it, latest first. (basis: derived — the artifacts port has no operation that adds one page beneath another; latest first, maintainer, 2026-10-02) Within a round, pages take the act's row order of the result each came from, a page first filed from `closing.md`, or from a piece with no step key, after every step's, in the order filed, and several from one result keep the order it holds them in; a folded task's own task record leads its round's pages, and a round's round record leads its round's pages. (basis: derived from the sections' row order above) Each subpage is titled `Round <n> · <type>` from the first round on, `Round 1 · Scratchpad`, so a title never changes as rounds join. When a round files more than one page of a type, each title adds what tells them apart: a decision record's number and slug, `Round 1 · Decision record 001 · cursor pagination`, a stacked change's request, `Round 2 · Review record · request 231`, or a system document's subject. When a second page of a type joins a round, the first is retitled with its own distinguishing part, as a rename. (basis: maintainer, 2026-10-07; the distinguishing part, derived from a reference finding its page by title) A page handed over under a title this rule no longer gives, an earlier version's or a folded task's, is renamed to the title it gives. Every in-tree reference naming its old title, in the pages of the same tree as the renamed page (this task's, or a folded task's), frozen ones included, is rewritten to the new one in the same filing, and a reference whose words were the old title takes the new title as its words ([pages-belong-to-their-task](../rules/pages-belong-to-their-task.md)). (basis: derived — a reference that kept an old title would point at nothing) Each page filed so far in this task's documentation is handed over with the location the last publish or fetch returned for it, so the port updates it in place under its new title rather than replacing it; a folded task's pages go without one, being new to this tree.

Return to the caller each page's location and the task record's location, with the reach the artifacts port returned for it and, when that reach is `private-until-shared`, the port's share line, and every advisory the port returned, an in-tree reference that didn't resolve among them. The task record's location is the link the task's memory entry keeps.

## Degraded and preview

When the artifacts port reports the backend unavailable or fails the publish, hand back to the caller, marked unfiled with the reason, what this filing's own result added, as shaped, each piece labelled with the step key it came with, or `no step`, and what it ran for: each page shaped from it, and each section it adds to another page — its scratchpad section, its entry in the task record's "What was done", the delivery's update to the review record. Never hand back that other page whole, since every filing rebuilds it from what it's handed, nor a piece handed over already shaped, which the caller still holds ([keep-the-act-marker](../../work/rules/keep-the-act-marker.md)). A failure that left the task record's page published, as a `partial` publish can, also returns that location with its reach, as a success would, so the next filing goes there. (basis: derived from how the work orchestrator keeps unfiled results, and from a page backend's location being known only from a publish's return) A `partial` whose every page left as it was is held by a reader's comment counts as filed for the pages that landed: each held page and its commented words come back as an advisory, for the user to resolve. What this filing added to a held page comes back unfiled, each piece with its step key, as a failed filing's does, so the next filing tries it again; when the held page is the task record, the task log isn't mirrored. (basis: maintainer, 2026-10-07, so one comment doesn't send every step's pages back to the unfiled directory) Under `--dry-run`, run the artifacts port's own `--dry-run` and return what it would publish, and where.

The output is the locations above, or the unfiled pieces, for [mirror-the-task-log](04-mirror-the-task-log.md).
