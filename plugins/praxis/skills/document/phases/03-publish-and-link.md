## Publish the tree

Bring the task record up to date with this filing ([task-record](../rules/types/task-record.md)), the pieces handed over already shaped included: a page joins the documents filed so far, and a section joins its page in the act's row order — a waiting piece's row, step key and what it ran for are those its opening line names, else those its `<row>-<skill>.md` file name carries, this filing's in the step key it's handed — with a piece that has no step key after every step's, in the order filed, and the delivery's after those (basis: derived — a piece with no row follows the rows, as `closing.md`'s pages do). Within one round's pages, among pieces of one step key, what it ran for, type and section heading, whether filed, waiting or this filing's own, the latest stands and replaces the rest, as a step's result filed again does: this filing's own beats any waiting piece, a later piece in a file beats an earlier one, and between waiting files the later write wins. (basis: maintainer, 2026-10-07, a correction replacing the claim it corrects; the section heading, derived — two sections of a page aren't one claim) A piece of a step the act runs more than once that names nothing it ran for, as an earlier version wrote it, matches whatever a piece of its step key ran for. (basis: derived — such a piece can't say what it ran for) Then publish the task's whole documentation through [artifacts](../../artifacts/SKILL.md) at the destination the first phase resolved — new on the task's first filing, in place on every later one and on every filing to a file backend (its `--idempotent` publish, with the identity the first phase resolved). Shape it as a portable page tree ([portable-tree-shape](../rules/portable-tree-shape.md)), titled with the task's key and title: the task record as the main page, titled with its family's name, `The change`, `The incident`, `The answer` or `The verdict` ([task-record](../rules/types/task-record.md)); then one page per reader tab after it, in the order [reader-tabs](../rules/reader-tabs.md) gives, the main page being the Status tab with its family's name as its kicker; each tab page is titled with its tab's label and joins the current round's page of each type it hosts as sections in the rule's order, a type with several pages, such as decision records, one section each, told apart by id and slug; then a group titled `Rounds and working records`, holding one page per work record and decision record not shown above, an earlier round's page of a plan type included, and no plumbing type, the current round's first and each earlier round's after it, latest first; then, when the task filed system documentation, a group titled `System documentation`, holding those pages in the order filed; then, last, a group titled `Work history`, holding the [task history](../rules/types/task-history.md) first and then each round's round record and scratchpad, latest round first. (basis: maintainer, 2026-11-12, pages as reader tabs that host types, and bookkeeping out of the reader's path; round titles stay on the history groups, which hold the record of how the task went rather than answers to a reader's question) An open task's pages from before this layout move as the rename rule below moves any page: plumbing to Work history, the rest to Rounds and working records under their round titles. The kit's pieces stand in the task record's sections ([documentation-kit](../../../craft/writing/documentation-kit.md)). A group's own page carries one line saying what it holds, for Rounds and working records that it is the history behind the task record, kept as written, and not a description of the task as it stands now, and then a table of its pages: the page as an in-tree reference, its round, and one line on what it holds. The task history is titled `Task history`, outside the round titles below, and its row in the table gives "all rounds" as its round. A group's page has no type and closes with no footer. The task record carries no table of contents of its own, since the groups and their tables are the way in, and [portable-tree-shape](../rules/portable-tree-shape.md)'s landing summary, table of contents and carve don't apply to a task's documentation. A group page handed over, as a fetch returns it, is no document: it is rebuilt here, keeping the location it came with. A folded task's group pages are dropped, its pages placed as its round's pages, and its task history's round sections carried into this task's task history as the folded round's. A piece waiting from before front pages labelled as a section of the task record lands in the task history: its round section when it is a round's, its The task when it is that section; anything else is restated into the task record. (basis: maintainer, 2026-10-08; latest first, maintainer, 2026-10-02) Within a round, pages take the act's row order of the result each came from, a page first filed from `closing.md`, or from a piece with no step key, after every step's, in the order filed, and several from one result keep the order it holds them in; a folded task's own task record leads its round's pages, and a round's round record leads its round's pages. (basis: derived from the sections' row order above) Each page in Rounds and working records and in Work history is titled `Round <n> · <type>` from the first round on, `Round 1 · Scratchpad`, so a title never changes as rounds join. When a round files more than one page of a type, each title adds what tells them apart: a decision record's number and slug, `Round 1 · Decision record 001 · cursor pagination`, a stacked change's request, `Round 2 · Review record · request 231`, or a system document's subject. When a second page of a type joins a round, the first is retitled with its own distinguishing part, as a rename. (basis: maintainer, 2026-10-07; the distinguishing part, derived from a reference finding its page by title) A page handed over under a title this rule no longer gives, an earlier version's or a folded task's, is renamed to the title it gives. Every in-tree reference naming its old title, in the pages of the same tree as the renamed page (this task's, or a folded task's), frozen ones included, is rewritten to the new one in the same filing, and a reference whose words were the old title takes the new title as its words ([pages-belong-to-their-task](../rules/pages-belong-to-their-task.md)). (basis: derived — a reference that kept an old title would point at nothing) Each page filed so far in this task's documentation is handed over with the location the last publish or fetch returned for it, so the port updates it in place under its new title rather than replacing it; a folded task's pages go without one, being new to this tree.

When the store has items, build the live-state file ([item-store-and-views](../../artifacts/rules/item-store-and-views.md)) before publishing:
- **What is observed.** For each live field a kind declares, observe its value through the capability the field names: [vcs](../../vcs/SKILL.md), [ci](../../ci/SKILL.md), [project-mgmt](../../project-mgmt/SKILL.md) or [telemetry](../../telemetry/SKILL.md), for each item of that kind. A field naming the change reads the change the round's line in the entry names.
- **Time.** The file carries the time the build started.
- **Unavailable capabilities.** A capability that is unconfigured or unavailable observes nothing, and its fields stay empty. Nothing is written into an item.

Hand the store and the live-state file to the publish with the tree. Then publish the restricted copy, when there is one, with `--restricted`, to the space the entry's `restricted` field names, where it lives as [find-the-task-documentation](01-find-the-task-documentation.md)'s Where it lives places task documentation, with the space's own destination. The live-state file is built the same way for that copy, and its own store holds only its items and the agreements over them. Its location is returned to the caller, which records it in the entry's `restricted` field. A restricted publish that fails comes back unfiled with its pieces, as a failed publish does, and the team tree still stands. (basis: maintainer, 2026-11-11)

**The reader sweep.** Once per round, after the round's first publish of the team copy, when the [documentation plan](../../../craft/writing/documentation-plan.md) finds the work is an epic or the developer's request asks for a sweep, run this loop with the [reader-sweep](../../../agents/critics/reader-sweep.md). Hand it the published pages and their screenshots as the artifacts port returns them, or the pages as its fetch returns them and a line saying no screenshots came back, and the team copy's store; the restricted copy isn't swept. Then fix, and sweep again: at most three sweeps, a fix after each of the first two.
- Each filing finding's pieces are refiled through [shape-the-document](02-shape-the-document.md)'s Items and Checks and published as any filing is; a finding that blocks that publish comes back as that phase says, and ends the sweeps.
- Each gap is looked for in the task's sources, read as [mine-the-sources](../../../craft/evidence/mine-the-sources.md) says; what a source holds is filed with its citation.
- After the first sweep only, each claim a reader acts on, as the reader-sweep's hunt point 2 defines it, is read against the source it cites, and one citing no source is looked for as a gap is. One its source doesn't state is refiled as the source states it, or graded `unverified` with what would check it when no source states it ([results-and-certainty](../../../craft/evidence/results-and-certainty.md)). An `agreed` item isn't refiled: a question is filed `opened-by` it, as mine-the-sources says.
- After each of the first two sweeps, two claims hunt point 2 finds contradicting each other are settled the same way, each by its source; when each matches its source, the sources disagree, and a question is filed with both positions, as mine-the-sources' item 2 says.

Another sweep follows only a fix that filed or refiled something. What the last sweep still finds, its filing and renderer findings and the gaps no source fills, goes back to the caller with the advisories, so the developer's report shows them. (basis: maintainer, 2026-11-13, a sweep after the first draft that reads the rendering too, and brings the documentation up to standard against its sources)

Return to the caller each page's location and the task record's location, with the reach the artifacts port returned for it and, when that reach is `private-until-shared`, the port's share line, and every advisory the port returned, an in-tree reference that didn't resolve among them. The task record's location is the link the task's memory entry keeps.

## Degraded and preview

When the artifacts port reports the backend unavailable or fails the publish, hand back to the caller, marked unfiled with the reason, what this filing's own result added, as shaped, each piece labelled with the step key it came with, or `no step`, and what it ran for: each page shaped from it, and each section it adds to another page — its scratchpad section, its entry in the task history's round section, the delivery's update to the review record. Never hand back that other page whole, since every filing rebuilds it from what it's handed, nor a piece handed over already shaped, which the caller still holds ([keep-the-act-marker](../../work/rules/keep-the-act-marker.md)). A failure that left the task record's page published, as a `partial` publish can, also returns that location with its reach, as a success would, so the next filing goes there. (basis: derived from how the work orchestrator keeps unfiled results, and from a page backend's location being known only from a publish's return) A `partial` whose every page left as it was is held by a reader's comment counts as filed for the pages that landed: each held page and its commented words come back as an advisory, for the user to resolve. What this filing added to a held page comes back unfiled, each piece with its step key, as a failed filing's does, so the next filing tries it again; when the held page is the task record, the task log isn't mirrored. (basis: maintainer, 2026-10-07, so one comment doesn't send every step's pages back to the unfiled directory) Under `--dry-run`, run the artifacts port's own `--dry-run` and return what it would publish, and where.

The output is the locations above, or the unfiled pieces, for [mirror-the-task-log](04-mirror-the-task-log.md).
