With the failure framed and reproducible, gather the observable facts around it *before* forming any theory — because a hypothesis formed before the evidence is in tends to go looking for its own confirmation, and the fastest way to waste a debugging session is to fixate on the first plausible cause. The goal here is breadth: assemble what is actually true around the failure — the code on the failing path, what changed near it, what the running system recorded, and whether anyone has seen this signature before — so the localize→hypothesize loop reasons from facts, not from the mental model that already failed to predict the bug.

This is a **bounded, failure-scoped sweep, not a full investigation.** It recruits explorers directly for the specific failure and touches no knowledge backend, so debug stays config-less here — it does *not* delegate to the `gather` skill (that is the weighted cross-lane engine for open questions; this is a targeted pull of the evidence a single known failure sits in). Keep the sweep anchored to the failure: every fact gathered should bear on *this* symptom, its path, or its onset.

## Sweep the evidence lanes in parallel

Recruit the explorers for the lanes that bear on the failure, in parallel, each returning findings anchored to a source (or, without fan-out, walk each lane yourself in sequence before moving on):

- **The failing code path** — the [code explorer](../../../agents/explorers/code.md): trace the actual route from entry point to the symptom site, and the state it carries. This is where the fault physically lives; you need the path before you can bisect it.
- **What changed near the symptom** — the [repository explorer](../../../agents/explorers/repository.md): recent commits, blame, and history around the suspect files. A failure that appeared at a known time is often a change at that time — the history is the first place a regression's cause hides, and it is what makes [bisect-aggressively](../rules/bisect-aggressively.md) over commits possible.
- **Prior occurrences of this signature** — the [community-practices explorer](../../../agents/explorers/community-practices.md): has this error signature, stack shape, or symptom been hit before — in this project's issues, or as a known bug in a dependency? A signature someone has already root-caused collapses the search.
- **The documented contract** — the [official-documentation explorer](../../../agents/explorers/official-documentation.md): what a library, API, or platform on the failing path *promises* to do, when the bug may be a violated or misread contract rather than local logic.

Which lanes to run is a **keep test per lane**, not a reflex to run all four — the **code** lane always runs (the failing path always exists and you need it before you can bisect); each other lane runs only when its trigger is present, and is skipped, not run-anyway, when it is absent:

- **repository / history** — run when the failure has an onset or regression window: it *worked before*, appeared at a known time or deploy, or its age is knowable. Skip for a bug with no time signal (a defect of unknown age with no "used to work").
- **community-practices** — run when the failure carries anything *externally searchable*: an error string or message, a named exception or stack signature, or a value that flows through **an operation with a documented external contract** on the failing path — any library or standard-library call (a `module.function`), *and* the bare builtins whose own behavior is a documented, discussed gotcha (`round`'s rounding, `sorted`'s stability/key, `open`'s default encoding, `int(x, base)`, floating-point summation). Skip only a **pure behavioral wrong-result** produced entirely by **transparent operations that need no lookup** — arithmetic, slicing, indexing, `len`, comparison, control flow, and your own first-party functions. The discriminator is *searchable contract vs. transparent logic*, not surface syntax (module-qualified or not): a generic `TypeError`-style string still runs, because "has anyone hit this string before" is exactly what the lane answers; and the CSV example below skips because its wrong count comes from transparent integer/index arithmetic — nothing with a documented contract on the path. The margin — is *this* operation's contract "surprising enough" to be worth a search? — is deliberately left to the executor's judgment: the set of gotcha-bearing builtins can't be enumerated here, and the tie-break below defaults any genuine doubt to *run*, so the openness only ever adds a cheap lane, never misses a cause. ("The failing path" is the traced route the code lane surfaces — an operation two frames upstream of the wrong value is *on* it; recruit the lane late if the trace surfaces the operation after entry.)
- **official-documentation** — run when the failing path crosses a library, API, or platform boundary whose contract could be violated or misread. Skip a bug wholly inside first-party logic.

Skipping a lane whose trigger is absent is the correct call, not a coverage gap — over-running lanes buries the failure-relevant evidence in noise. Evaluate each trigger from what the framing already shows — the symptom, the stack or error message in hand, any onset, and any `--from-*` seed — which is usually enough to tell whether a lane bears on the failure at entry. And because the code lane runs alongside the others, if its trace later surfaces a trigger that wasn't visible at entry (a dependency on the failing path you hadn't expected), recruit that lane then — the sweep is not frozen at entry. The one tie-break for a genuinely borderline call — e.g. a dependency the trace shows *near* the failing path but not clearly on it, so the docs/community trigger is neither clearly present nor clearly absent: run the lane and record that you did (breadth is cheap against a missed cause). Any trigger not *clearly absent* runs, so the borderline always defaults to running and two runs draw the same line; the load-bearing boundary is the per-lane *skip* test above, each of which is binary. (Worked example — the CSV "drops the last row" defect: a wrong row count produced by first-party integer/index arithmetic, no stated onset, and no library call or error text on the path: code runs; history, community, and docs triggers are all clearly absent, so the lane set is code alone.)

## Pull the recorded signals — telemetry and logs

The running system's own record is first-class evidence, and it is often the only witness to a failure you cannot yet reproduce locally:

- When a `--from-telemetry` or `--from-logs` seed is in play, its intake module ([from-telemetry](../modules/from-telemetry.md), [from-logs](../modules/from-logs.md)) has already pulled the signal; fold it in here — the error's onset, frequency, affected scope, correlated signals, and sample traces.
- Otherwise, pull what bears on the failure now: a hosted signal or log stream through the telemetry capability (the [telemetry](../../telemetry/SKILL.md) port), or a local log file by a direct read. Anchor on the **onset** (when the signal first appears — the seam a regression crossed) and the **first-cause line**, not the loudest downstream error ([follow-the-first-divergence](../rules/follow-the-first-divergence.md)).

If telemetry isn't configured, the port reports it unavailable and this lane degrades — proceed on the code, history, and reproduction evidence you do have, and note the missing lane rather than stalling.

## Record facts, not conclusions

Capture each finding as an anchored observation — a file:line, a commit, a log entry, a trace — that a later step can re-check, and keep it separate from any interpretation. Believe what the evidence shows over what the code's names, comments, or types claim it should do ([trust-observations-over-assumptions](../rules/trust-observations-over-assumptions.md)); where a suspected boundary is invisible, note it as a place to instrument in the loop that follows ([make-the-invisible-observable](../rules/make-the-invisible-observable.md)) rather than assuming its behavior now.

The output of this phase is the anchored evidence set the localize→hypothesize→confirm loop reasons over. Evidence-gathering is not one-and-done: as the loop narrows the fault to a span, expect to return here for targeted evidence about that span — a value at a boundary, the history of one function — rather than re-sweeping the whole system.
