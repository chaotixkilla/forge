# Ingest the source

A decomposition is only as good as the inventory it starts from, and the two ways to start badly are opposite. One is to decompose something that is not ready — to invent an approach or a contract under the guise of "just breaking down the work," which smuggles design into a step that has no business making it. The other is to re-derive a design the upstream plan already closed — re-litigating decisions, re-drawing seams, doing plan's work over. This phase does neither: it decides whether the source is *ready* to decompose or must route back, and — when it is ready — extracts the raw inventory of work the source implies, before any sizing or ordering.

## Consume the driving source — branch on what you were handed

What you were handed decides how much is already settled for you. Get this branch right first:

- **A plan (`--from-plan=PATH`, the preferred entry).** A plan has already closed the solution space: it carries buildable units, their ordering, concrete interfaces, a rollout, and flagged risks. **Consume it as the authoritative inventory** — parse its units, decisions, and risks straight into the candidate list rather than re-deriving them. The seams the plan drew are the seams you keep: plan owns the design carve, and decompose re-sizes those units to the team's cadence (phase 3) *along the boundaries the plan set*, never re-opening them ([cut-along-natural-seams](../rules/cut-along-natural-seams.md)). Trace every candidate back to a plan decision. If a plan unit proves un-decomposable as written — it hides a decision the plan left open, or cannot be scoped to a single outcome — surface that as a finding and route it back (below); do not quietly redesign it.
- **A spec (`--from-plan` absent, a spec supplied).** A spec fixes *what* must be true (requirements, acceptance criteria, priority) but not *how*. It gives you value slices, not buildable units. Decompose a spec directly only when the units are self-evident from it; the moment identifying a unit needs a design decision (an approach, a shared interface, a seam), that is plan's work — apply the readiness gate.
- **Neither (a free-form request).** Frame the work first: state it in a sentence, its acceptance condition, and the touch-points it names. Then apply the readiness gate.

## The readiness gate — decompose, or route back

This gate resolves the run's terminal outcome, so it must partition cleanly. The discriminator is the **decompose/plan line**, reused from develop's ratified develop/plan line: *can you identify the units without making an unmade design decision?*

- A **design decision** is a plan-level commitment other work must then conform to: choosing the *overall approach*, introducing or changing a *shared interface/contract*, or adding a *requirement the spec did not state*. If naming the units forces any of these, the input is not ready to decompose.
- **Route on the gap.** *Unclear what* — requirements fuzzy, acceptance undefined → route to **spec**. *Undesigned how* — requirements clear but approach/interfaces/seams unmade → route to **plan**. Name the next skill, state what it must produce, and **end the run reporting the terminal outcome `routed-back`**. decompose breaks down an approved design; it neither sets requirements nor chooses the approach, so a run that cannot start without that work stops rather than fabricating it.
- A **self-evident** request — units are obvious and no design decision is required (e.g. "add a `--verbose` flag to these three commands") — is decomposed directly.

**The terminal-outcome partition.** Every run lands in exactly one of two outcomes: **`decomposed`** (units identified and carried forward to emit) or **`routed-back`** (stopped here, next skill named). The run that appears to fall between the two — *part* ready, *part* needing design — is decided by the **spine test**: trace whether you can identify and order the *spine* of the work — the backbone of units on one end-to-end path ([prefer-vertical-slices](../rules/prefer-vertical-slices.md)'s walking skeleton) — *without* the missing design decision.

- If the missing decision **blocks the spine** — you cannot identify or order the backbone units without it — the whole run is **`routed-back`**: naming the units *is* the design work here, and that is `plan`'s to do (or `spec`'s, when the gap is in the requirements).
- If the spine is fully identifiable and orderable **without** the missing decision — **no unit the gap blocks lies on the backbone** — the run is **`decomposed`**: carve and order the spine and the ready branches, and represent **each** not-ready off-backbone branch as its own unit **flagged blocked-on-a-plan-pass** — a dependency handed to `plan`, sequenced before the units that would need its result. The *number* of such off-backbone branches is irrelevant to the outcome (a spine is one thin path, so most units legitimately sit off it); what decides `decomposed` vs `routed-back` is solely whether the gap touches the backbone. Each blocked branch renders as its own unit, not one lumped placeholder. This branch is **not a spike**: a spike ([size-the-unknowns-as-spikes](../rules/size-the-unknowns-as-spikes.md)) is a timeboxed investigation decompose's executor runs to retire a technical *unknown*, whereas an unmade plan-level *design decision* is `plan`'s work — so the branch is a route-back-to-plan pointer, not an investigation carried out here.

`(basis: the two-outcome partition mirrors develop's landed/checkpointed/blocked terminal-outcome discipline, and the design-decision discriminator is develop's ratified develop/plan line reused as the decompose/plan line — ratified by the maintainer, 2026-07-10. The spine-vs-branch test that makes "core" checkable is derived from the walking-skeleton / tracer-bullet spine that plan's slice-and-validate already uses (Cockburn, Crystal Clear, 2004): the spine is the backbone that must be orderable for a decomposition to exist at all, so a gap that blocks it blocks the run, and a gap off it does not.)`

## Extract the raw inventory

Once the source is ready, sweep it for every distinct piece of work it implies — a candidate unit is anything that must be built, changed, tested, migrated, or wired. Recruit the **code explorer** to ground each candidate in the real codebase — where it lands, what already exists there, which surfaces it touches — so the inventory answers to reality and not to the document's abstraction level; without fan-out, do that locating yourself: find the touch-points by symbol and usage before trusting the source's own list. If **no codebase is reachable at all** — a greenfield plan, or a target system that is not in this working tree — do not stall: proceed on the plan's own inventory and flag the surfaces and capabilities the plan names (an "existing" queue, middleware, table, or auth flow) as **ungrounded assumptions to confirm at build time**, so the decomposition is honest about what it could not verify rather than asserting touch-points it never checked.

Keep this list **raw**: deliberately un-sized and un-ordered — sizing is phase 3, sequencing is phase 3, and pre-empting them here just produces worse versions of both. Give each candidate a provisional single outcome ([one-unit-one-outcome](../rules/one-unit-one-outcome.md)); a candidate you cannot state an outcome for is a heading, not a unit, and it is flagged to split in carve. The output of this phase is the candidate inventory plus the readiness verdict, handed to [carve-into-units](02-carve-into-units.md).
