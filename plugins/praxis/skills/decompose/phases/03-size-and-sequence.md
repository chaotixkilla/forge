# Size and sequence

Give every carved unit a **size verdict** and put the set in a buildable **sequence**: size wrong and the tracker fills with either monoliths no one can review or dust no one should track; order wrong and a unit is scheduled before the thing it needs exists.

## Right-size each unit against the review/integration cadence

Walk each unit through the size scale and assign its verdict: **too-big → split**, **right-sized**, or **trivial → merge**. The scale, its per-verdict assignment tests, the adjacent-state discriminators, and the anchors live in [unit-size-scale](../rules/unit-size-scale.md) — apply it, do not re-invent it here.

- **Split a too-big unit along the value seam**, into thin vertical sub-units that each still deliver one observable outcome — never into horizontal layers that only integrate at the end ([prefer-vertical-slices](../rules/prefer-vertical-slices.md)). When `--from-plan` drove the run, a split runs *along the plan's existing seams*, refining for cadence — it does not re-open the design's boundaries.
- **Merge a trivial unit into the unit whose outcome it completes** — a pure sub-task with no independently-observable outcome folds into its parent rather than living as its own tracked item. When `--from-plan` drove the run, a merge — like a split — runs only *along* the plan's seams: apply the [unit-size-scale](../rules/unit-size-scale.md) to each plan unit by its **own** too-small test (no independently-observable outcome, **or** not verifiable until another unit is built) and re-size along the seam, never across it. Across the whole spectrum between a full table and a lone column, one test decides it — **reach**: how many distinct flows — user-observable journeys, not units — have a reason to read or write the entity this unit introduces, two units of one flow counting once (the reason-to-change test of [cut-along-natural-seams](../rules/cut-along-natural-seams.md)). `(basis: derived from the reason-to-change test)` A schema unit **clears the bar and is kept as drawn when its entity serves more than the one consuming flow** — a shared foundation (the `invitations` table that create, accept, revoke, resend, expiry, and audit all touch) is an independently-observable, independently-reviewable outcome, kept even though any single flow could absorb its columns. It **folds into its one flow when it exists only for that flow** — a fragment with a single reason to change (a lone `last_login` column, or a small table only the login unit ever touches — unit-size-scale's canonical too-small anchor) merges into that flow. Reach, not row-count, is the discriminator. Likewise a sanctioned architectural enabler is kept by the exception in [prefer-vertical-slices](../rules/prefer-vertical-slices.md), and a cross-cutting unit with no single parent has no clean merge target, so it stays. **Merge only** a genuine pure sub-task (a lone column, a single helper with no observable outcome of its own) into its one clear parent. unit-size-scale's lone-column merge anchor and prefer-vertical-slices' bare-table reject-anchor describe the case where decompose is **carving the seams itself** (no upstream plan) — they do not license dissolving a foundational unit the plan deliberately drew and that clears the bar on its own.
- **A unit you cannot size because it is genuinely uncertain** is not force-sized by guessing — carve it into a timeboxed investigation unit (a spike) and size the spike by its time box, not its unknown outcome ([size-the-unknowns-as-spikes](../rules/size-the-unknowns-as-spikes.md)).

## Sequence: hard dependencies first, then risk

Order the sized units so each rests only on what comes before it. Two passes, in this order ([order-by-dependency-then-risk](../rules/order-by-dependency-then-risk.md)):

- **Dependencies first.** Topologically order on the *hard* prerequisites — a unit that cannot be built until another exists comes after it. This pass is not a preference; a cycle in it is a carving error to send back. Units with **no** dependency between them carry no imposed order from this pass — their relative position is decided by the next one.
- **Then risk (the tie-break among the now-unordered).** Among units the dependency graph leaves free to reorder, pull the higher-exposure units earlier, graded on the three exposure levels (high / medium / low, uncertainty × blast radius) and their tie-break defined in [order-by-dependency-then-risk](../rules/order-by-dependency-then-risk.md), which also carries the risk-first-vs-value-first fork and its routing.

## Make the dependencies explicit as you go

Sequencing reveals the cross-unit prerequisites; capture each as a **named link** on the unit, not as an implicit "it's earlier in the list" ([make-dependencies-explicit](../rules/make-dependencies-explicit.md)).

The output is the set of right-sized units, each carrying its size verdict and its explicit dependency links, in a dependency-then-risk order — handed to [make-units-actionable](04-make-units-actionable.md).
