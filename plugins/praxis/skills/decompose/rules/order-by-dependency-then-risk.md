# Order by dependency, then risk

A set of well-sized units still has to be *sequenced*, and the sequence is a graded judgment: get it wrong and a unit is scheduled before the thing it needs exists, or the risky unknown that could invalidate the whole plan is left for last. This rule pins the ordering in two passes — a hard-constraint pass that admits no preference, then a tie-break pass that is a genuine, contested fork. It is cited by [size-and-sequence](../phases/03-size-and-sequence.md).

## Pass one: hard dependencies (not a preference)

Topologically order on the *hard* prerequisites: a unit that cannot be built until another exists comes after it. This pass is a constraint, not a judgment — there is no latitude in "B needs A, so A first." Two properties follow, and both are deliberately not graded:

- **A cycle is a carving error, not a sequencing choice.** If the dependency graph has a cycle, two units were cut *across* a coupling rather than *along* a seam; send them back to re-carve ([cut-along-natural-seams](cut-along-natural-seams.md)) rather than picking an arbitrary entry point.
- **Units with no dependency between them carry no imposed order from this pass.** Their relative position is decided by pass two, not here. `(deliberately open: the dependency pass has no graded bar to pin — a hard prerequisite is self-evident (the unit literally cannot build without its predecessor) and there is no authority that turns topological ordering into a ranked judgment; the interesting, contestable ordering decision is entirely in pass two.)`

## Pass two: risk, the tie-break among the now-unordered

Among the units the dependency graph leaves free to reorder, the sequencing decision *is* contestable, and it is a real fork — encode it, do not absolutize one side:

- **Risk-first ("fail fast").** Pull the riskiest and most-uncertain units earlier, so a wrong assumption surfaces while it is still cheap to change. Cost: you may build high-uncertainty scaffolding that delivers no shippable user value early, optimizing for learning over early return.
- **Value-first ("deliver value early").** Pull the highest-value, most-demonstrable units earlier, so value lands sooner and can be reacted to. Cost: the riskiest work is deferred, and a deferred unknown that proves expensive is discovered late, when it is costliest to absorb.

**Ranking risk — the exposure scale.** "Risk" is not left to each executor's private sense of it. Rank by a unit's **risk exposure** = how uncertain its outcome is × how much a wrong result would cost, on two named axes:

- **Uncertainty** — how likely the unit's approach or a load-bearing fact is to prove wrong: an unproven approach, a dependency whose behavior on *this* use is not yet established (an unfamiliar or third-party integration — or a familiar one applied in a way its prior use never exercised), a key fact not yet known (the spike-candidate uncertainty of [size-the-unknowns-as-spikes](size-the-unknowns-as-spikes.md)). **Prior experience retires uncertainty only to the extent it exercised *this* unit's failure surface**: a dependency used once on a simpler or different flow leaves the new flow's edges (its errors, limits, retries, webhooks) unproven, so the factor stands high — being *acquainted* with a dependency is not the same as having *proven* the use this unit needs.
- **Blast radius** — how much of the rest of the plan a wrong result forces to be reworked: how many downstream units rest on this unit's assumption, and whether a core seam depends on it.

Exposure is the **product** of the two, in three ordinal levels — a *relative order* for sequencing, never an absolute measurement:

- **high** — *both* uncertain *and* high blast radius. *Anchor (top):* integrate a third-party API the team has never used, on which the token module 5 of 8 later units depend — unproven **and** widely depended-on. Sequence first.
- **medium** — *one* factor high but not both: an uncertain unit nothing else rests on, **or** a near-certain unit a lot rests on. *Anchor:* a new caching layer used by one isolated feature — plausibly tricky, but its blast radius is a single bounded flow.
- **low** — *neither*: a well-understood change little else depends on. *Anchor (bottom):* a config-flag rename the type system enforces, used in three call sites. Sequence last.

Adjacent-level discriminators: **high vs medium** — are *both* factors high? high; only one? medium (the both-factors test). **medium vs low** — is *either* factor genuinely high? medium; neither? low. When a factor is genuinely borderline (a partially-mitigated uncertainty, an arguable blast radius), **round the exposure up**: an unproven mitigant is not a retired risk, and under-grading a live risk is the costlier error — it surfaces late, when it is most expensive to absorb (this rounding is fork-neutral: it grades the risk, it does not by itself sequence it). Order high → low; within a level, break toward the more uncertain, which surfaces its unknown sooner. This is what makes the cross-axis case (high-uncertainty/low-blast vs low-uncertainty/high-blast — both land *medium*) resolve the same way in two runs rather than one keying on uncertainty and the other on blast. `(basis: risk = uncertainty(≈likelihood) × blast-radius is the shared frame of risk-based prioritization — Boehm's Spiral (1988) and ISO/IEC/IEEE 29119's High/Medium/Low scheme, both treating the levels as ordinal, never an absolute score. This scale mirrors the *shape* and the both-factors discriminator of praxis's ratified risk-priority scale (in the `test` skill), re-anchored from test cases to decomposition units (unit-uncertainty × downstream-blast). The three-level cut-points are ordinal and the anchors are the maintainer's ratified house calls, consistent with that sibling — ratified 2026-07-10; 29119 and Bach both decline a fixed external boundary, so the cuts are a house standard.)`

**The fork only bites when the riskiest unit is not also the highest-value one.** When value and risk point at the same unit (high-value *and* high-risk), both positions agree — do it first. The fork is live only where the highest-value unit is low-risk, or the riskiest is low-value.

**Routing rule (non-gating): surrounding convention → house rule → maintainer.** Read how the team already sequences work — if its plans front-load risk, match that; if they front-load demoable value, match that. Absent any convention or house rule, the **terminal default is risk-first**: pull the riskiest units earlier. `(basis: risk-first vs value-first is a genuine authority conflict. Risk-first rests on Boehm's Spiral Model (IEEE, 1988 — order iterations by highest risk), RUP's "attack major risks early or they will attack you" (Kroll & Kruchten, 2003), and Cockburn's Walking Skeleton (Crystal Clear, 2004 — wire the architecture end-to-end early to retire architectural risk). Value-first rests on Agile Manifesto Principle 1 ("early and continuous delivery of valuable software," 2001) and Reinertsen's Cost-of-Delay / WSJF economics (2009 — highest economic-value-per-duration first). Cohn's value×risk matrix (Agile Estimating and Planning, 2005) is the reconciliation that defines the boundary above: high-value/high-risk first, low-value/high-risk avoided/deferred. The terminal default of risk-first — used only when convention and house rule are both silent — is ratified by the maintainer, 2026-07-10, matching the "fail fast" intent of decompose's spike handling.)`

The output of the two passes is a total-enough order: hard dependencies always respected, and the free positions resolved by the routed risk/value call.
