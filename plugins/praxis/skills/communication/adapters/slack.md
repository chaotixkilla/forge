# slack — communication adapter

Implements the **communication** capability for Slack, over the transport configured in `tools.communication.transport` (mcp or api). The [communication](../SKILL.md) skill names the operation and dispatches here; each operation below is one of the communication capability's requests, translated to Slack's concrete surface. In Slack a discussion thread is a **root message plus its replies** in a channel, addressed by the channel and the root message's timestamp (`ts`); a post target is a **channel** (by id, or by name resolved to an id via a channel lookup) or a **person** (by user id, or by handle/email resolved to a user id via a user lookup, to whom the adapter opens a DM). The message target is a per-call input from the caller — there is no configured default channel. Resolve exact tool/method/argument names against the live tool at call time (below) — the names here are not frozen.

## Operations

1. **Read a thread** — given a reference (normally a channel + thread `ts`, or a message permalink that encodes both), retrieve the thread's messages in order, each message's author, and the ordering, so the caller can distill decisions, constraints, rejected options, and open points. Resolve each author id to a display name, and preserve `ts` ordering so the conversation reads in sequence; if an author id cannot be resolved (a deactivated or cross-workspace user), return the raw id as the author rather than dropping the message or failing the read — a findable thread always reads in full, and author resolution never gates completeness. **Page to exhaustion:** Slack returns thread replies (and channel history) in cursor-paginated batches, so follow the pagination cursor until it is empty — a thread longer than one page must be walked in full and **never returned truncated as if complete**, because a dropped tail drops the very decisions the caller reconstructs from. If pagination cannot complete (e.g. throttled mid-read), report a *retryable* failure rather than returning a partial thread as whole.
   - *mcp:* the Slack connector's thread-read / conversation-replies call to read the root and replies by channel + `ts` (or resolve them from a permalink first), plus a users lookup to turn author ids into names, following the connector's cursor to the end.
   - *api:* `conversations.replies` (channel + `ts`) for a thread — or `conversations.history` when the reference is a channel rather than a single thread — paginating on `response_metadata.next_cursor`; `users.info` / `users.list` to resolve author ids to display names.
2. **Post a message** — post the caller's message (text and/or blocks) to the target channel or person, and return its reference. The delivered reference is the channel + message `ts`, plus a permalink fetched by a separate call and added when that call succeeds; **always return the reference once the message is delivered** (see the invariant in the Failure surface). A **person** target is addressed by opening (or reusing) a direct-message channel to that user before posting. Fetching the permalink runs as a separate call *after* delivery and is reported against the message's reference rather than folded into one pass/fail, so a failed permalink fetch never masquerades as a failed post.
   - *mcp:* if the caller gave a channel name or a person handle rather than an id, first resolve it to an id via the connector's list/lookup calls; then the connector's post-message call to the channel (or, for a person, an opened DM) with the caller's text/blocks; then a permalink call for the reference.
   - *api:* resolve a channel name via `conversations.list` (and a person handle/email via `users.lookupByEmail`) when the caller supplies a name rather than an id; `chat.postMessage` with `channel` set to a channel id (or a DM channel opened via `conversations.open` for a person) and `text`/`blocks`; `chat.getPermalink` for the reference.

## Failure surface

Report failures upward in capability terms — the caller hears an outcome, never a raw Slack error string:

- **Not authenticated / token missing or lacking a workspace-wide scope** (`invalid_auth`, `not_authed`, `account_inactive`, a scope the whole integration lacks) → report as "communication backend unavailable," which the caller's degrade path handles (and which the [communication](../SKILL.md) skill maps to guiding the user through `init:communication`).
- **Channel, thread, or user not found / wrong workspace** (`channel_not_found`, `thread_not_found`, `user_not_found`, a deleted message) → report "the requested thread/target was not found on the configured provider" rather than a raw error; do **not** fall back to a different channel, thread, or user.
- **Rate-limited or transient network failure** (`ratelimited` / HTTP 429 with `Retry-After`, transient 5xx) → report as a *retryable* communication failure, distinct from a permanent one, so the caller can back off or degrade. Slack rate-limits `chat.postMessage` per channel, so a burst of posts is the common retryable case.
- **Post partial failure — the invariant: once the message is delivered, always return its reference.** A post is non-atomic: the message lands first (yielding the channel + `ts`), then the permalink fetch runs as a separate call. If the message posted but the permalink fetch did not, return the message's reference **with the permalink flagged** — *retryable* when its cause was transient (a throttle) or *permanent* when structural — and **never re-post the message** to recover it (a re-post double-sends the notification); the channel + `ts` alone is already a complete, usable reference, so a caller never has to re-post to "fix" a missing permalink. A message that was **never delivered at all** is reported by cause: a *retryable* failure (throttle/network) to re-attempt, or the permanent rejection below for the caller to fix rather than blindly retry.
- **Permanent post rejection** (`not_in_channel` — the integration isn't a member of the target channel; `is_archived`; `msg_too_long`; `no_text`; `restricted_action`) → report as a *permanent* communication failure the caller must reconcile (join/invite the integration, split or rephrase the message), **not** a retry — a re-attempt hits the same wall. Distinguish it from the retryable class above so the caller's back-off logic never spins on a wall it can't clear.

## Call-time discovery

Slack's surface shifts (MCP connector tool names, Web API method names and argument shapes, and how a channel/person target is addressed), so name the operation and its purpose here and resolve the exact parameters when you call: confirm the current thread-read call and its pagination cursor field, the target-resolution calls (channel-name→id, handle/email→user-id), the post-message method and how a DM target is opened, and the permalink call, against the live connector or Web API at call time. An adapter that pins today's exact method names ages into a confident wrong call; one that names the operation and re-derives the arguments ages gracefully.
