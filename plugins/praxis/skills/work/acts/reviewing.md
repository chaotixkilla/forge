# Reviewing

**Entry condition.** The request is to judge a change someone else made — a review request, or a branch or diff whose author isn't the requester — before it lands. Reviewing the requester's own change, or asking for the review step alone, goes to the [review](../../review/SKILL.md) skill directly. (basis: maintainer, 2026-09-30) Each round reviews one change ([open-the-task](../phases/02-open-the-task.md)'s Rounds): a request naming several changes of one stack reviews the base-most one no round has reviewed at its current head, then, after that round's close-out, opens the next one's round in the same run, without asking whether to go on, until each change the request named has had its round. A round that ends without its Done when holding — stopped, blocked, declined, a step broken down, or its delivery held — ends the run there, and the report names the changes still without a round. A request naming several changes in no one stack runs the same way, one task per change, in the order it names them. A recorded preference to stop after each review ends the run after each close-out instead, as a delivery preference governs delivery ([run-the-act](../phases/03-run-the-act.md)). Whenever the run ends before every named change has had its round, the report names those still without one. (basis: derived from the steps' window being one change; field findings, 2026-10-28 — runs stopped after the first round of a request that named them all)

**Done when** the round's review has its Fitness, one result per acceptance; every finding and open question for the author has been delivered on the change — or, for a local branch no host carries, handed to the author by the requester, who confirms it — and the reviewer's task documentation records the review with where each part went. A review whose delivery waits on an unavailable host isn't done. (basis: maintainer, 2026-09-30)

## Rationale last

The author's rationale reaches only step 5 ([form-your-own-view-first](../../../craft/evidence/form-your-own-view-first.md)). Until then, every step, and every explorer a step recruits, reads the change's history only at or before its base, and reads no review-request or issue threads and no author notes. (basis: maintainer, 2026-09-30) Nor does it read this task's own earlier records: its task record, its rounds' review records and scratchpads. An acceptance about the integration line past the base, such as whether the change still merges or later work supersedes it, is recorded `not checked` by steps 1 to 4 and settled by step 5, which may read that line. Steps 1 to 4 run isolated whenever this context already holds what they mustn't read: from round 2 on, after a fold, and in any round when the change's description or another of the author's notes reached this context before the act opened, as when the user asked about the change first. Its title alone doesn't count, since it names the change rather than argues for it. (basis: field findings, 2026-11-19 — four rounds read the description before the act and had only round 2's rule to go by) Each runs in its own recruited agent, one at a time, or all four in order in one agent when a recorded preference caps a review below four recruited agents or forbids starting one on another's return. The agent is handed only the inputs this act names, the brief, the worktree's path, this section's read limits, which bind every explorer it recruits, and, when it runs all four, this act's Steps section, whose skip conditions and rules between steps it applies itself, and the rule that a step isn't over until every agent it recruited has returned ([run-the-act](../phases/03-run-the-act.md)). Its result comes back here to be recorded as any step's is. A step that can't recruit from there takes its skill's path without fan-out, and the report says so. Without fan-out at all, they run inline, and the report says what was in context. (basis: maintainer, 2026-10-20)

## Before the proposal

The brief's kinds and risk tier are read from the files the change touches, never from its description, title or its author's notes. It adds the evidence the kit owes for those kinds, for the review to look for. The curator is handed the files the change touches, as Before the steps fetched them, and reads no history past the change's base. It is handed no keys whose records it reads, its area search leaves out every task record that links this change and this task's own, and the brief takes no line from an earlier round's record, so no claim made about this change reaches steps 1 to 4 through it. The brief carries no open choices: the design choices the intent leaves open are things the review looks for. (basis: maintainer, 2026-10-19)

## Before the steps

The change is hosted or local, and each is brought in its own way:

- **A hosted change** — a review request. Fetch it through [vcs](../../vcs/SKILL.md) with its description held back — its diff, base and head commits, head branch, author and size — and fetch its head through vcs. If vcs can't hold the description back, the act stops here, with that as the task's next step. (basis: maintainer, 2026-09-30)
- **A local branch** — no host carries it. Read its head, author and size with local version control, its base being the merge base with the integration line. The steps' window is then the head against that base, exactly the change, never the author's branch itself. Read no commit message, note or branch description of the range: they're its rationale. A command that prints the head commit's subject as it runs — a checkout often does — runs with its output discarded. (routed to maintainer: a local-branch path, since the entry condition admits a branch and a hosted-only fetch can't review one.)

Give the task a detached worktree at the head through [workspace](../../workspace/SKILL.md) (its key and that commit), enter it, and record its path and the commit in the act marker's `worktree` and `made_at` ([keep-the-act-marker](../rules/keep-the-act-marker.md)). A worktree the marker already records, as after a takeover, is entered when it stands at that head, else made again at it. Steps 1 to 5 work in that worktree, and close-out removes it.

## Steps

(basis: maintainer, 2026-09-30; understand's diagram, maintainer, 2026-10-07)

| # | step | inputs | skipped by the act when |
|---|---|---|---|
| 1 | [understand](../../understand/SKILL.md) `--diagram --from-code=<the files the change touches>` | the change's diff, and the files it touches as they stood at its base, with their history up to it | never |
| 2 | [gather](../../gather/SKILL.md) `--explorers=official-documentation`, adding `authoritative-literature` when step 1's map lists a published standard the change implements (a format, a protocol, a code list) | the question: what is the published contract of each external contract step 1's map lists for the changed lines or the diff's additions, at the version the project pins, or, where it pins none, the version the environment runs (say which)? | step 1's map lists no external contract for the changed lines or the diff's additions |
| 3 | [test](../../test/SKILL.md) | the claims step 1's map carries as *inferred* or *unverified*, that step 2's evidence doesn't settle, about the behavior a changed line's correctness depends on — each with the behavior expected of it: the intent's, else the code's documented contract, else its behavior at the base — as claims added to the change's own behaviors; and that the change is under review, not being built, so test commits nothing | steps 1 and 2 leave no such claim |
| 4 | [review](../../review/SKILL.md) `--hold-rationale`, with `--change=<the change>` for a hosted change, or its default window in the worktree for a local branch | the intent, and the results of steps 1 to 3 | never |
| 5 | [review](../../review/SKILL.md) `--prior=<step 4's result>`, with `--change=<the change>` for a hosted change | the rationale — the description `--change` brings, or, for a local branch, the range's commit messages, notes and branch description — and step 4's result; from round 2 on, the reviewer's unresolved threads from earlier rounds, each judged fixed or not at this head, and the reviews recorded `outside:` when the round opened | never |

Step 3's cases are removed from the worktree before step 4, so the windows of steps 4 and 5 hold the author's change and nothing of the reviewer's. When a step breaks down — produces no result ([skip-only-with-a-reason](../rules/skip-only-with-a-reason.md)) — the steps after it take the breakdown as input, except when step 4 breaks down: that stops the act, since nothing after it has a review to build on. A negative result, a test that `fails` or an acceptance that `fails`, is a result. (routed to maintainer: the skip conditions for steps 2 and 3, and this breakdown rule, since a broken-down step's absence is evidence the later steps can weigh, while a review that broke down leaves nothing to build on.)

## Filed

The results of steps 1 to 4 file as sections of the round's scratchpad; step 4's files with no decision records. Step 5's result files as the round's review record, with a decision record for each of its decisions that earns one ([decision-record](../../document/rules/types/decision-record.md)), and close-out's delivery updates the review record with where each part went. (basis: derived from the document types' membership tests)

## Delivered

For a hosted change, close-out posts step 5's review on the change through vcs, with a stance, on the commit the round reviewed, the entry's `at`: the review's own brief and findings as the review summary, linking the task's documentation by [deliver-through-the-ports](../rules/deliver-through-the-ports.md), and each open question inline at its `file:line` when that line lies inside the diff's hunks, else in the summary with its `file:line`, since a host anchors inline comments only on changed lines and can refuse a whole review over one bad anchor. (basis: field findings, 2026-11-19) An anchor the host still rejects folds into the summary too. A thread from an earlier round that step 5 judged fixed is named in the summary as fixed, and resolving it is left to the reviewer. Close-out's question names each review on the change the reviewer posted outside praxis, read there, that this stance would replace. Closed questions and the marks of what the rationale changed stay in the review record. Before its question, close-out reads the change's head, and the reviews on it, through vcs. When it has moved past `at`, the round still posts at `at`, and the question names the move and offers the next round at the new head, which a yes opens in the same run once this round has closed. A host that refuses a post on a commit that is no longer the head gets it on the head instead, when the files the round reviewed are unchanged between the two, with the reviewed commit named in the summary; otherwise it goes on the change as a comment with no stance that names the reviewed commit, so the round is delivered and the next round reviews the new head. (basis: field findings, 2026-11-19 — a mid-round push left two readings and four steps re-ran)

Close-out proposes the stance from step 5's result, its Fitness one result per acceptance ([results-and-certainty](../../../craft/evidence/results-and-certainty.md)), and the reviewer confirms or changes it in close-out's question; with no answer, it's comment-only. (basis: maintainer, 2026-10-02)

A stance preference the brief carries governs as [run-the-act](../phases/03-run-the-act.md)'s Aim the work says, replacing these rules where it departs from them. Without one:

- **Request changes** — a finding about the change stands that would fail review's gate at its default floor ([gate-mode](../../review/modules/gate-mode.md)) — high or above, graded `traced` or higher — or any acceptance `fails`. A finding that holds at the base too, with the same behavior there, is pre-existing, whatever lines it sits in: the summary lists it as a follow-up, and it sets no stance.
- **Approve** — no finding but a pre-existing one stands above low, no question for the author is open, and every acceptance `holds`, but for rollout checks. An acceptance is a rollout check when both hold:
  - **what it asks** is something only a deployed or released version can show: a deploy, a release, a publication or a submission, or a behavior in production or for its users;
  - **its result** is `not checked` for that reason alone. One `unsettled` or `fails` is no rollout check.

  The summary lists rollout checks under any stance. Any other acceptance not checked leaves the stance comment-only, for close-out's question to settle. (basis: field findings, 2026-11-19 — five stance questions overridden, each for a pre-existing finding, a post-merge acceptance or a recorded preference)
- **Comment-only** — any other result, an acceptance `unsettled`, or `not checked` other than a rollout check, among them.

An approval settles no decision the change makes ([decision-record](../../document/rules/types/decision-record.md)), so the summary never says it confirms one.

For a local branch, no host carries the change: close-out returns the review in its report for the requester to hand to the author, and records it as sent by hand once the requester confirms it was. (routed to maintainer: the local-branch path, since with no host the requester is the only route to the author.)
