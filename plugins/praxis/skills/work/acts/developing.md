# Developing

**Entry condition.** The request is to build new behavior or change existing behavior in the requester's own code: a feature, a change to how something works, what an approved spec or ticket asks for. Fixing a defect goes to the fixing-a-bug act, and keeping code healthy without changing its behavior to maintaining. One step on its own that changes no code — only specifying, only planning — goes to that step's skill directly; a change to code always runs inside an act. (basis: maintainer, 2026-09-30)

**Done when** every unit of the change is built, tested — step 6's result `holds` ([results-and-certainty](../../../craft/evidence/results-and-certainty.md)) — verified — step 7's headline `holds`, or step 7 skipped because no flow reaches the unit, or its run-level `not checked` for *no reachable surface*, which says the same and is recorded as that, never as `holds` — and has passed review by [open-the-review-request](../rules/open-the-review-request.md)'s test; each of the change's review requests, its description written from the task's documentation, has been approved by its reviewers on the head the task's memory entry records for it, read through [vcs](../../vcs/SKILL.md) or, where no host carries the request, confirmed by the user, a request already merged into its target counting as approved; and, when step 4 ran, the units are filed where the team tracks work. A request still waiting on its reviewers, or one that came back with changes requested, isn't done: the wait or the changes are the task's next step, and the task stays open. (basis: derived from the steps' outcomes) (routed to maintainer: the task stays open through review, since feedback that re-enters the same task keeps its record whole.)

## Intent first

When the task takes over someone else's branch, their claims about it ("this part is done") are rationale, checked after your own look ([form-your-own-view-first](../../../craft/evidence/form-your-own-view-first.md)). A changed requirement reopens the spec and its traceability row before another unit is built. (basis: maintainer, 2026-09-30)

## The small-change path

A change with no behavior change and no new interface — a typo, a comment, a rename inside one unit — runs develop on the request itself, as its one unit with the request as its done-condition, then verify where a flow reaches the change. Every other step is skipped by this condition, and the review request opens once develop has landed the change and verify, where it ran, heads `holds` or reports `not checked` for *no reachable surface*, its description saying no review step ran. The path is done when that request is approved. (basis: maintainer, 2026-09-30) (routed to maintainer: the two conditions, as a typo fix meets them, since a change that alters no behavior and no interface has nothing a spec would add.)

## After approval

Before step 1, [give the task a branch](../rules/give-the-task-a-branch.md).

## Steps

(basis: maintainer, 2026-09-30; understand's diagram, maintainer, 2026-10-07)

| # | step | inputs | skipped by the act when |
|---|---|---|---|
| 1 | [understand](../../understand/SKILL.md) `--diagram`, with the intent as its question, and `--from-code=<the code>` when the intent names code | the intent, and any code it names | the small-change path, or the round is a rework after peer review |
| 2 | [spec](../../spec/SKILL.md), with `--from-issue` when the intent is a tracker item, or `--from-discussion` when it's a conversation | the intent's sources, a ticket file in the repository read as written | the small-change path; a rework after peer review, unless a comment it addresses changes a requirement, as [open-the-task](../phases/02-open-the-task.md)'s intent check counts; or, outside a rework, the intent already includes an approved spec: a spec the intent links whose approval is recorded on it, or the spec this task filed and its owner approved. A ticket's acceptance criteria are spec's input, never an approved spec |
| 3 | [plan](../../plan/SKILL.md) `--from-spec=<the spec>` | the spec, and step 1's map | the small-change path, or the round is a rework after peer review that step 2 didn't run in |
| 4 | [decompose](../../decompose/SKILL.md) | the plan | the small-change path, the round is a rework after peer review, or the plan names a single unit within decompose's size bar ([unit-size-scale](../../decompose/rules/unit-size-scale.md)) |
| 5 | [develop](../../develop/SKILL.md) `--from-plan=<the plan>` | the unit, with its done-condition, and step 1's map | never |
| 6 | [test](../../test/SKILL.md) `--changed --from-spec=<the spec>` | the unit's acceptance criteria | the small-change path |
| 7 | [verify](../../verify/SKILL.md) `--from-spec=<the spec>` | the spec's requirements the unit implements | the unit reaches no flow a user or an external caller runs |
| 8 | [review](../../review/SKILL.md) `--changed` | the unit's change, and its rationale | the small-change path |
| 9 | [plan](../../plan/SKILL.md) `--phase=5` | the latest plan, as its earlier phases' output, and the branch at its head, the topmost request's in a stack | the small-change path, the round isn't a rework after peer review, or step 3 ran in it |

Steps 5 to 8 run once per unit, in decompose's order. (basis: maintainer, 2026-09-30) After each unit passes step 8, [open-the-review-request](../rules/open-the-review-request.md)'s How many requests decides whether its review request ends there. In a rework after peer review ([open-the-task](../phases/02-open-the-task.md)), steps 5 to 8 run only for the units the addressed comments' anchors fall in, step 5's input for each being the comments its proposal settled as addressed, and step 1's map is the latest round's that ran step 1. In a rework whose comments change a requirement, steps 2 and 3 take those comments as input beside the latest spec and plan, and the units it rebuilds take the plan they return, the units that plan assigns a changed requirement to among them, and a unit it adds built as the build builds one. A rework that rebuilds a unit below others in a stack merges forward, as [open-the-review-request](../rules/open-the-review-request.md)'s A stack says, once every unit it rebuilds below has passed step 8 and before any unit above runs step 5, then runs step 6 for each unit above it doesn't rebuild, all before step 9. A follow-ups round runs the act from step 1 on its request, each skip condition judged against that request. (basis: maintainer, 2026-10-07)

When step 5 ends blocked — develop couldn't land the unit — the act stops at that unit, with the blocker as the task's next step. When step 6's result or step 7's headline is `fails`, or the unit doesn't pass step 8 — a finding stands that would fail review's gate at its default floor, or an acceptance `fails`, by [open-the-review-request](../rules/open-the-review-request.md)'s test — the unit goes back to step 5 with that step's whole result as its input — its failing tests, its failing units, or the review's failing acceptances and findings at high and above — and steps 6 to 8 run again; after the second failed pass, the act stops at that unit with its last result as the task's next step. A result that settles nothing — `unsettled` from step 6 or 7, test's `not checked`, verify's `not checked` for any reason but *no reachable surface*, such as *reach untraced*, or an acceptance step 8 leaves `unsettled` or `not checked` — sends nothing back: its gap becomes the unit's next step, and the unit isn't tested, verified or reviewed on that point until it's settled. The steps after it still run, and the review request opens with the gap stated in its description; the task isn't done until the gap is settled. (routed to maintainer: two passes before stopping, since a second failure on the same change says it needs more than another try.)

When step 3's or step 9's plan returns an open sign-off ([planning-rollout](../../plan/phases/05-planning-rollout.md)), steps 4 to 8 build on the plan, and close-out puts the sign-off to the maintainer: the task isn't done until it's recorded.

## Filed

Step 1's map and each unit's step 5 to 8 results file as sections of the round's scratchpad. Step 2 files as the spec, step 3 as the plan (with a decision record for each of its one-way doors), step 4's units in the plan, and step 9's rollout, when it differs from the latest plan's, as the round's plan, the latest plan restated whole with its rollout replaced. (basis: maintainer, 2026-10-07) The round's [round record](../../document/rules/types/round-record.md), when its membership admits one, is filed as the round closes, its Self-review linking step 8's section. (basis: maintainer, 2026-10-07) document keeps the traceability table as these arrive. When the change adds or changes something a person who uses that part without reading its code needs — an operator, an integrator, a caller — the task also files that part's system documentation, from the steps' results, at close-out: a reference page for a format, endpoint, setting or command it adds or changes, an explanation page for a flow, a state or an interaction between parts it changes, and a how-to for an operation someone performs that it adds. A change only to internals no such reader meets files none. (basis: maintainer, 2026-09-30)

## Delivered

- **The units.** File them as work-items per [file-the-units-as-work-items](../rules/file-the-units-as-work-items.md), when step 4 ran.
- **The review requests.** Open each per [open-the-review-request](../rules/open-the-review-request.md) once its units pass step 8 by that rule's test — on the small-change path, as that path says. In a rework after peer review, deliver as that rule's After a rework round says.
- **The work-item the task traces to.** Update it through [project-mgmt](../../project-mgmt/SKILL.md) to show the change is in review.
