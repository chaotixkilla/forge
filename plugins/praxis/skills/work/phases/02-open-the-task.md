## Find the task

Resuming a task — the one `--task=<key>` names, or one found below — reads its memory entry ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)) and the documentation it points to, fetched through the [artifacts](../../artifacts/SKILL.md) port by the location the entry records. Unless the fetch returns the whole tree, stop there and say what it returned: every filing republishes the documentation from what it's handed, so one handed less would drop the rest from the record. (basis: derived from the artifacts port's in-place republish removing the pages a tree no longer has) (routed to maintainer: no recovery route; the run stops each time) An entry that records no location has nothing published: go on with no documents filed so far. Then take the entry's next step by the first of these that fits, so a review waiting to be posted on a change reads as a delivery, never as a wait on that change: (basis: derived — a delivery's target can be a review request, so the delivery test must run first) A marker whose `revision` is set continues its revision: by route 1 once its delivery has begun (a channel in the marker's `delivery`), else by taking the act from the marker's next step through close-out, a marker listing `units` taking the first unit not done ([keep-the-act-marker](../rules/keep-the-act-marker.md)). Before it continues, the test for a review back runs again on the requests it changes (A revision, below).

1. **A delivery, or filing where one went**, rather than one of the act's steps or a round's peer review, which route 2 files — settle any marker from another session and record the running act (both below), then go straight to [close-out](04-close-out.md). The round finishes as its steps left it: a head that moved after they finished is for the task's next round to review, never a rerun of this one. (basis: derived from a later review of a change being its task's next round)
2. **A wait on a review request** — reconcile the round first where Reconcile what happened outside praxis (below) applies, then read the request's state through [vcs](../../vcs/SKILL.md): an approval completes that request, and a request still waiting is reported and leaves the task open. A comment-only review is still waiting, unless the user asks to act on its comments or for any other code-changing work on that request, which then counts as changes requested on it (basis: maintainer, 2026-10-19). `(routed to maintainer: a comment-only review waits, sparing a rework for notes meant only as notes.)` For an act that authors a change, the round waits on the requests its status names, and a review counts only when it was posted on the head the entry's links record for its request and no earlier round filed it. An approval an earlier round filed that still stands after a later fix ([open-the-review-request](../rules/open-the-review-request.md)) counts too; once each has such a review back, they are filed as its round's peer review: record the running act, the round's own (below), then go to [close-out](04-close-out.md); until then, report the requests still waiting and file nothing. In a ship round, a request land left awaiting review is no peer review: once it's approved, on whatever head land left it at, take the act from that request's step 1 by route 3, and while it waits, report it. Changes requested on it stop the ship round, as [close-out](04-close-out.md)'s Close the task says: record the running act, the round's own (below), then go to close-out; a later request to ship opens a new ship round for what's left. (basis: maintainer, 2026-10-07) A task whose latest round is a rework whose steps' reasons open `proposal declined:` reports the comments still open and opens nothing until the user asks to act on them; once each request its status names is approved on the head the entry's links record, record the running act, that round's own (below), and go to close-out, which files the approvals in the task record and closes the task when its done-condition holds. (basis: maintainer, 2026-10-07) Changes requested, or comments the user asks to act on, open the next round, a rework after peer review, below. (basis: maintainer, 2026-10-07) Other code-changing work the user asks for while the round waits goes as A revision, below, says.
3. **One of the act's steps** — take the act from there; a marker listing `units` resumes at the first unit not done ([keep-the-act-marker](../rules/keep-the-act-marker.md)).

A request to file a finding made outside the task's steps, while this session runs no act for it, takes none of these routes. Hand [document](../../document/SKILL.md) the task key, the entry, every document filed for the task so far, every file waiting in its unfiled directory but those another session's marker for the task names, and the finding, placed as [run-the-act](03-run-the-act.md)'s rules for findings place it. When another session's marker for the task was written within the marker idle time, first tell the user that its session may still be running and that its next filing would drop this one, and any finding this one carries from the unfiled directory, and file only on their go-ahead. Write no act marker and open no act. Whenever document returns the task record's location, a failed filing included, write it into the entry's docs link. When the filing fails, append what document hands back, each piece labelled with its step key and what it ran for, to `finding.md` in the task's unfiled directory ([keep-the-act-marker](../rules/keep-the-act-marker.md)). Report where it went, and leave the entry's next step as it stood. A closed task of an act that authors a change opens its follow-ups round for the finding (below), files the finding as that round's first result, and closes the round in the same filing, the entry back to closed, unless the user asks for work on it, which runs the act in that round; a finding with no work asked for always takes this route. When that filing fails, the round stays open, filing the finding its next step, until a filing carrying it lands. Any other closed task takes no more filings ([pages-belong-to-their-task](../../document/rules/pages-belong-to-their-task.md)): say so. Side work attached to a closed task, and a task moved into one, take neither route: they file into its latest round, labelled, the task staying closed ([side-work-asks-once](../rules/side-work-asks-once.md)). (basis: maintainer, 2026-10-07; the idle-time warning, derived from Take over's)

A next step of closing an act left behind, as a Close that failed leaves it, is settled by the offer below; after a Take over, take the next step the marker records by these routes, or, with no marker left for the task, the one its task history's latest round leaves (in a record written before front pages, its Rounds section's latest round). (basis: derived — the offer is the only place an act left behind is closed)

A key with no entry is an error — say so and stop. A closed task is reported as closed, and nothing opens unless a round opens on it (below).

Without the flag, find the task the request belongs to. For a review, it's the task whose entry's links name the change, open or closed — search the memory's `task-` entries, since a closed task's index line is gone; when several do, it's the one whose key the others carry with a `-<n>` added, a task closed `declined` passed over for the lowest-numbered one that isn't; the entries carrying the found task's key with a `-<n>` added are its earlier separate tasks (below), a task closed `declined` never among them nor offered for folding, since it holds no work — or else the one a stack proposes (below). For other work, the task whose round this session delivered in this conversation, open or closed, is the one found, when the request is code-changing work on its change. It is on its change when it names one of the task's review requests, or what it points at lies in them: a check, a conflict, or code in the files those requests change. It is also on its change when it says what the round delivered is wrong, or asks to change what it does. With several such tasks, the one delivered last is found. ([route-the-work](01-route-the-work.md); basis: maintainer, 2026-10-19, narrowing the no-named-task rule to this one conversation) Otherwise search the memory's `task-` entries, closed ones included, for a task that links the same change, ticket or branch as the request names — never the branch the session merely stands on in another open task's worktree. An open task found is resumed as above, and a closed review task opens its next round, unless it closed `declined`, whose work a new task with the next free number takes (below). Otherwise this is a new task — as is side work the user chose to keep separate ([side-work-asks-once](../rules/side-work-asks-once.md)), which matches no existing task and takes the date-and-slug key, so it is never resumed into, folded into or numbered after the task it came from. Its key names what it's about: for a review, the change (`review-230` for a review request, `review-<branch>` for a local branch); for other work, the ticket's identifier, else the branch name unless it's the integration line or another open task's, else the user's local date and a two-to-four-word slug of the request. (routed to maintainer: proposed in that order, each more stable than the next.) A new task whose key an entry already holds takes the next free number, `<key>-2`. (basis: derived — one entry per key) For other work, an open task is resumed. A task of an act that authors a change opens its next round for shipping it, a ship round, once the task has closed, an open round being taken first by the routes above; and, once closed, for other work on what it changed — never side work, which [side-work-asks-once](../rules/side-work-asks-once.md) settles — or a finding about it, a follow-ups round, which runs the act the router matched for the request. All of this applies with or without the flag. (basis: maintainer, 2026-10-07) A task of an act that authors a change closed `declined` opens its next round, a build, for a later request for its work, an open round being taken first by the routes above; any other act's takes the next free number, as below. (basis: maintainer, 2026-10-07) A closed task of any other act stays closed: the new task takes the key with the next free number, `PROJ-88-2`. (basis: maintainer, 2026-09-30)

A resumed task, found either way, may have an act marker from another session: one in the main checkout's `.claude/praxis/acts/` whose `task` is its key ([keep-the-act-marker](../rules/keep-the-act-marker.md)). Before going on to the task's next step, tell the user when that marker was last written, by its `updated`, and offer two choices. When it was written within the marker idle time ([keep-the-act-marker](../rules/keep-the-act-marker.md)), add that its session may still be running, and that taking it over locks that session's code changes. (basis: maintainer, 2026-10-02)

- **Take over** — move the marker to this session's path and resume from it, its steps and delivery as it records them, with its `answered` and `failure` fields as [keep-the-act-marker](../rules/keep-the-act-marker.md) sets them for a marker taken over. Enter the worktree the marker records through [workspace](../../workspace/SKILL.md); with none recorded and the task's branch checked out in another worktree, enter that one, never checking the branch out a second time. (basis: derived — git refuses a branch checked out twice, and working elsewhere edits the wrong tree)
- **Close** — for a marker whose `revision` is set, the offer says a revision is continued, never closed, and Close takes it over and continues it (A revision, below). Otherwise Close ends that act as abandoned. Ask the user's reason and record it as `skipped-by-user` on every step not yet run ([skip-only-with-a-reason](../rules/skip-only-with-a-reason.md)). When the act delivers on a change, read the change's review feedback through [vcs](../../vcs/SKILL.md) and match it as [close-out](04-close-out.md) does before posting, recording each channel it finds landed in the marker's `delivery` as `sent`. Hand [document](../../document/SKILL.md), in one filing, the memory entry brought up to date with its status `closed · abandoned` — written to the memory only once the filing lands, as [close-out](04-close-out.md) hands its closing status — those outcomes, the delivery the marker records in place of a waiting `delivery.md` ([keep-the-act-marker](../rules/keep-the-act-marker.md)), and every other file waiting in the task's unfiled directory. When that filing fails, nothing closes, and nothing it hands back is written to the unfiled directory: the marker returns to how it stood before Close was chosen, only the files waiting before Close stay, the task stays open with closing that act as its next step, the user is told why, and the run ends there, opening no act. (basis: derived — a Close that didn't happen leaves no trace a later Take over would inherit) When it lands, tear the act's environment down and remove its worktree through workspace as close-out does, discard what else the act file says to discard, by the paths the marker records; then the entry handed is written to the memory, its index line is removed ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)) and the marker is removed. Nothing more is delivered. (basis: derived from closing meaning the act stops where it stands, and from a closed task taking no more filings)

When this session's own marker holds a different task's act, that act stopped without its close-out: offer the same two choices for it before the new act opens. (basis: derived from one marker per session)

A run that can't ask ([ask-while-the-user-is-here](../../gather/rules/ask-while-the-user-is-here.md)) leaves either marker untouched, opens or resumes no act, and reports the marker with both choices for the user's next run. (basis: derived — closing ends someone's act and taking over can lock a live session's edits, so neither happens without the user)

## Reconcile what happened outside praxis

Route 2 reconciles a round of an act that authors a change that has delivered and waits on its peer review, a declined rework among them, with what happened to its review requests outside praxis. It does so before it reads the round's requests and before a revision opens on it. A ship round, a round still running and a reviewing task aren't reconciled: for the last two, a moved head runs the round again (Create or update the entry, below). (basis: maintainer, 2026-10-19)

For each request the round delivered onto, or, for a declined rework, each request its status names, read it through [vcs](../../vcs/SKILL.md), and bring in its current head through vcs's *fetch a change's head*. Through git, read the commits from the head the entry's links record for it to the current head, each with its author. When the recorded head is no longer in the current head's history, read them from the two heads' merge base. Left out of the commits read:
- a commit reachable from the integration line, or from the current head of the request it builds on;
- a merge commit whose other parent is reachable from the integration line and that brings in nothing else;
- a rebase's copy of a commit up to the recorded head, matched as [match-the-team-flow](../../land/rules/match-the-team-flow.md) matches one;
- a commit by the port's account touching only the task's documentation. When any read or fetch fails, the round's reconciliation is skipped, the report says so, and route 2 and a revision go on as without it. (basis: derived — no reading leaves route 2 as it reads)

What the reads find is recorded as a result labelled `outside:` for each case that applies:

- **No new commit, the head unmoved, the request open:** nothing.
- **The head moved, with no commit left after the exclusions:** one line naming the update from the integration line or the rebase made outside praxis, with the old and new heads. It takes no number. The links take the current head, and reviews on earlier heads are filed as for new commits, below.
- **New commits on any request:** one **outside revision** of the round, or, for a declined rework, of the task's latest round, numbered as A revision's Numbering says. It names each request with new commits. It holds those commits and their authors, and the threads posted on the recorded head or a later one, resolved and open. When a recorded head is no longer in the history, it also holds the old and new heads, with compare links from the old head noted as unavailable. The entry's links take each current head, and the round line takes the revision's number ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)). An outside revision's head counts, for every rule, as a head the round delivered. A review on the recorded head or a later one, but not on the current head, that no earlier round filed, is filed beside the round's peer review as a review of an earlier head, as A revision's Delivery says. Its reviewer isn't asked again, by the reconciliation or by route 2, which instead names each such review in its report as no longer counting, for the user to ask again if they want. A review of the current head is route 2's. (basis: maintainer, 2026-10-19 — a decimal, whoever reviewed it)
- **The request merged:** who merged it and the merge commit, as land's outcome records a merge. Route 2 takes the request as approved, and the peer review records the merge as its verdict when no review counts: `merged by <who>, no review`.
- **The request closed without a merge:** who closed it. Route 2 reads that request no further and leaves it out of the waits. The status gains `· review request <n> closed outside praxis`. When no other request of the task remains open, route 2's report asks whether to close the task, the default leaving it open, and a later request to close it needs `--task`. A yes closes the task as Close (above) does with no marker, the task's worktree being the one workspace names for it, and the closing outside praxis being the user's reason.

A merge or closing the task history already records isn't recorded again, and a vcs read that leaves who merged or closed a request not exposed is recorded as that.

Each outside commit is recorded as not checked by praxis, and nothing runs again for it. (basis: maintainer, 2026-10-19 — record only, since a bot's push would otherwise rerun a round each time) Each request's local branch moves to its current head when it holds no commit the current head lacks and, where it is checked out, its worktree has no uncommitted change; otherwise it stays, and the report says so. The links move either way. The entry's `at` stays the head praxis last checked. The entry's changes, its status and next step included, are written at once. The results are then filed by [run-the-act](03-run-the-act.md)'s rules for findings, with the updated entry, before route 2 reads the round's reviews.

## Rounds

A round's opening, below, compares the head the act's "Before the steps" brings in, and a stack's answer can remove the worktree it made, so when a run reaches either, carry that section out first, as Prepare the act says. It runs once per change: Prepare the act runs it again only for a different change, as when a stack's yes resumes another task's round. (basis: derived — a second run on the same change would make a second worktree, at a head neither decision read)

A task runs in rounds, starting at round 1, and has at most one round open. For a reviewing task, a round is one review of a change, and runs through its close-out. For an act that authors a change, a round runs from what opened it to the peer reviews of the review requests it delivers, closing once each has one: each review is read as it returns and filed when the last comes back, and changes requested on any request open the rework, which takes up the units the addressed comments' anchors fall in; its kind names what opened it: **build** for round 1 and for a round opened on a task closed `declined`, **rework after peer review** when that review requested changes or a `pending:` item waits in the round, **follow-ups** for work on, or a finding about, what a closed task changed, and **ship** when the shipping act runs on the change. Any other act's task has one round. A follow-ups round that changes code closes at its peer review; one opened only to file a finding closes in that filing; a ship round closes at its close-out, when shipping's done-condition holds or close-out stops it on a request it hadn't merged. A round's act is the task's own, `act` in its entry, but for a ship round, which runs shipping, a follow-ups round that runs another act, and a rework after peer review, which runs the act of the round that last delivered onto the requests it answers, never a ship round; its line names any act that isn't the task's own. (basis: maintainer, 2026-10-07) A later review of a change whose task is closed — the change itself, or one stacked on it that the user joins to it (below) — is that task's next round, reviewing the change at its current head, when that head, as "Before the steps" brings it in, differs from the latest round's commit, the entry's `at`. With the head unmoved, the closed round stands: remove the worktree "Before the steps" made, through workspace with the commit it was made at, report that the change hasn't moved since that round, and open nothing. (basis: derived — a round is a review of a commit, and that commit's review stands) A round that opens puts its line first in the entry's `rounds` ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)), the entry turns open and its index line is restored. A rework round takes as its input, from each request whose review requested changes or whose comments the user asks to act on, every review summary's requests and every inline comment whose thread isn't resolved, posted on the reviewed commit. A round that delivers several requests names each in the entry's links. (basis: derived — a resolved thread is settled on the host) The earlier rounds' documentation is fetched as resuming fetches it, above, and goes to every filing as documents filed so far, so the republish keeps them. (basis: maintainer, 2026-10-02)

**A revision.** Code-changing work the user asks for on the change of a round that waits on its peer review is a revision of that round, when no review of any kind is back on the requests it changes. A statement that what the round delivered is wrong counts as such work. A revision is not a round. The round stays open, and its pages, peer review and record stay the round's. (basis: maintainer, 2026-10-19)

The requests it changes are those its units fall in, those its merge forward would move, and those a stack's rebase replays. A review is back in three cases:
- route 2 would count it;
- it was posted on the request after this round first delivered onto it, on a head this round delivered before its latest;
- an earlier round filed one, on a request this round hasn't delivered onto.

The work can be:
- a failed check;
- a conflict with the integration line;
- a defect they point at;
- undoing what an earlier revision did;
- a change to a requirement, in the ticket or in the user's own words, that adds, removes or changes an acceptance criterion in the baseline the task history copied. Its words stand beside the intent, and it is a pending item instead when a review is back on a request whose units carry that requirement by the plan;
- in an act with a plan step, a change of design: one that replaces a decision the latest plan or a decision record states, such as an approach, an interface or a data shape. Before step 3 it is tested against the requests the user's request names. After step 3 it is tested against those the plan's changed, added or removed units fall in. (basis: derived from the plan holding the design's decisions)

The test runs again whenever a unit joins, on the request that unit falls in. When it finds a review back, the revision stops before that unit's next step:
- its request becomes a pending item (below);
- its commits stay on their branches, unpushed but for those a merge forward or an update already pushed, for the rework the pending item opens; the delivered head stands in the record only. Its `pending:` filing says that the latest results of the steps it ran, for the units it ran them for, describe revision `<n.m>`'s commits, stopped and not delivered, which the rework the pending item opens delivers. The entry's status goes back to the wait on review. That rework files its results again as its own and takes its units from step 6, step 5 done. The round's own record check counts only to its last delivered head;
- its marker is removed.

These are not revisions (basis: maintainer, 2026-10-19):
- **Work that would change a request whose review is back is a pending item.** Hand [document](../../document/SKILL.md) the request, in the user's words, labelled `pending:`, by the route for a finding (Find the task, above). Hand it before any peer-review filing of its round. Then go on by route 2, and [close-out](04-close-out.md) opens the rework with it.
- **On a fixing-a-bug round:**
  - A request saying the diagnosis or its guard is wrong is a pending item, never side work or a finding, so the next round diagnoses again.
  - A fix that needs design, by that act's When the fix needs design, needs a developing task of its own. Say so, and leave the round waiting.

How a revision runs:
- **Start.** It runs the round's act from the start step the act names, restarting the marker (Record the running act, below). While it runs, the entry's status is `open · revision <n.m> running on review request <n>`, each request it changes named, and its delivery sets it back to the wait on review. The request, in the user's words, is never given a disposition.
- **Evidence and units.** The request and its evidence are added to the round's brief, which the start step takes. The evidence is what the request points at: a failed check's output, read through [ci](../../ci/SKILL.md), or, with ci not configured, what the request quotes of it, the brief saying the output wasn't read; or the files the conflict names or the code the defect is in, read through [vcs](../../vcs/SKILL.md). In a rework round, these stand in place of the addressed comments and their anchored units.
  - The units are those whose files the evidence names or tests. For a change of design or of a requirement, they are the units the plan changes, adds or removes.
  - A unit the plan removes is reverted in its request, running step 5 alone, with its removal as the done-condition. A removed unit that was a whole request is named in the `revision:` result, for the owner to close.
  - Evidence in no unit's files is a unit of its own, on the request whose check failed, else the base-most request. The request is its done-condition and its acceptance.
  - A unit the start step also changes joins them for the steps after it.

  (basis: derived from close-out anchoring land's outcome at the files its failed checks or its conflict name)
- **Conflict.** When the revision is a conflict with the integration line, once its proposal settles, each branch it changes takes its target before the start step, base-most first, by the method [match-the-team-flow](../../land/rules/match-the-team-flow.md)'s Updating a branch gives work's update, and is pushed back before the start step as that rule says. The entry's `at` then moves to the updated head. (basis: derived — one home for how a request's branch takes the integration line)
- **Delivery.** It delivers onto the requests it changes, as [open-the-review-request](../rules/open-the-review-request.md)'s After a revision says. It also opens any request How many requests gives a unit its plan added.
  - Its delivery filing hands document a result labelled `revision:`, with its number, the request, and what it changed.
  - Its delivery writes its number into the round's line ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)).
  - A review posted on an earlier head this round delivered is filed beside the round's peer review, as a review of that head. It counts for neither route 2 nor the act's done-condition. Its reviewer is asked again once: by the revision's delivery when it came back while the revision ran, else when route 2 reads it.
  - The task's work item is updated, as the act's Delivered says.
  - A revision for a failed check awaits that check on the delivered head through ci at its close-out, for up to ten minutes, and files the verdict as a finding; with ci not configured, it is skipped and the finding says the check wasn't read. A check still failing, or still running, becomes the task's next step, which route 2 reads through ci on the next resume before it reads the reviews. (basis: derived — ten minutes covers a typical check run without holding the session)
- **Another's commits.** A revision opens after its round is reconciled (Reconcile what happened outside praxis, above), so it starts from the current head. When its delivery's push is refused because the request's head moved meanwhile, the reconciliation runs again: it records the outside revision and moves the links and the round line, but not the branch. The revision merges those commits in, its merge commit counted as an update and `at` staying at its last step's head. Its marker's `revision` changes to the number after the outside revision. Close-out then checks the record again, files the `outside:` result with its delivery filing, and delivers. A review found back then stops it as a review back stops a revision. (basis: maintainer, 2026-10-19)
- **Numbering.** The first revision of round `n` is `n.1`. Each later one takes the next number after the highest among the round's `revision:` results, outside revisions and revisions a `pending:` filing names.
- **Stopped.** A revision stopped before it delivers, by the user or by its session ending, keeps what its steps produced. A stop the act itself makes, at a blocked step or a second failed pass, ends it as an early stop ends any act: what passed is delivered as the revision, and the rest becomes the task's next step. (basis: derived — a blocked step can't be continued, and the act allows no third pass) It is continued when the task next resumes (Find the task, above). A marker this session holds for a stopped revision, of this task or another, is continued first. A new request on the same task then runs as the next revision.

**A stack.** A review request with no task linking it may build on other open ones. Read what it builds on through [vcs](../../vcs/SKILL.md): the requests it returns, nearest first, are its stack below it. A read that comes back partial gives the stack as far as it reached, one that fails otherwise gives none, and the report says so either way. When the stack holds any, run-the-act's question proposes it as one task, base-most request first. It joins the task of the nearest request below that has one, as that task's next round. When that task is open, a yes writes the stack's requests into that task's entry's links at once, removes the worktree "Before the steps" made (with the commit it was made at), and resumes that task's open round as a found task is resumed (above), since its round in progress comes first; the report says so, and the stack's later changes are reviewed in that task's later rounds. With no such task, it becomes a new task keyed by the base-most request, `review-230`, whose first round reviews this one. On yes, the entry's links name every request of the stack, base-most first. On no, or with no answer, the change is reviewed alone under its own key. (basis: maintainer, 2026-10-02) (basis: derived — the nearest keeps a split the user chose earlier, and alone is the default since joining reshapes another task's record) A local branch has no host to read, and is reviewed alone.

**Earlier separate tasks.** Entries keyed `<key>-<n>`, `review-230-2`, are separate earlier tasks on the same change. When a round opens on a task that has any, it's numbered after the highest of this task's own rounds and those `<n>`, whether or not they're folded, so a later fold never collides. Run-the-act's question offers to fold the closed ones in as earlier rounds, in key order: `<key>` is round 1, `<key>-2` round 2, and so on. An open one is left alone: it's resumed under its own key when asked for, and offered once it's closed. On yes, fetch each folded task's documentation through artifacts, and hand [document](../../document/SKILL.md), in one filing before the first step, those trees as the pages of their rounds, carried as they stand. When it lands, add each folded round's line to this task's `rounds`, retire each folded task's documentation through the [artifacts](../../artifacts/SKILL.md) port's Retire, superseded by this task's record, and remove the folded task's memory entry, since this task's entry and record now hold its round. Report each document Retire didn't remove, with what the port returned, for the user to remove by hand. A fold is all or nothing: when any fetch or the fold's filing fails, nothing of it is filed — what that filing hands back is dropped, and no later filing is handed the folded pages — nothing is retired or removed, and the report says so. On no, with no answer, or after a failed fold, the earlier tasks stay their own, and the offer comes again at each later round. (basis: maintainer, 2026-10-02)

## Prepare the act

If the act file has a "Before the steps" section, carry it out now, unless it already ran under Rounds above on the change this round works on: it brings in what the rest of this phase reads, such as the change's branch name and head commit. A path it records in the act marker goes into a marker taken over above at once, and otherwise into the marker this phase writes below. When it needs a port that isn't configured, carry out what it can without the port, and the rest once the proposal's answer has set the port up ([run-the-act](03-run-the-act.md)).

## Gather the intent, locate the rationale

Classify each input by [form-your-own-view-first](../../../craft/evidence/form-your-own-view-first.md) as you meet it. Read the intent now — the ticket, a spec, an RFC, the requirement the work must meet, the conversation the request points at — fetching a tracker item through [project-mgmt](../../project-mgmt/SKILL.md) and a document through [knowledge](../../knowledge/SKILL.md); a file in the repository is read directly. Find its reference in the request, the change's branch name or the task's own record, never inside the rationale; when none of them names one and the request's own words don't state what's required, record that, and the proposal in [run-the-act](03-run-the-act.md) asks for it. Of the rationale, record only where it is, and don't open it here: every inline step inherits what this context has read, so a description read now would reach every step.

A ticket that also proposes a solution is read whole, and the task history notes that its proposal was seen. (routed to maintainer: an isolated reader passing on only the requirements would keep the proposal out, at the cost of a subagent per ticket.)

On resume, compare the intent as it stands now with the requirements and acceptance criteria the task history copied when the task opened (in a record written before front pages, its own The task section). A change in what it requires — a requirement or acceptance criterion added, removed, or changed in meaning — runs the act again from its first step; a rewording that leaves every requirement the same is noted in the task history and changes nothing. (routed to maintainer: rerun on a requirement change, note a rewording, since only a change in what's required can make finished steps wrong.) Read other people's edits to the task's documents under [edits-change-intent-not-actions](../rules/edits-change-intent-not-actions.md).

## Create or update the entry

A new task's title comes from its ticket, else its branch name when that isn't the integration line, else a short phrase from the request — never from the change's description or title, which are rationale. `(basis: derived from rationale being read last)` Creating the task, or opening a round, writes its memory entry and its index line at once, in the format [keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md) pins — the hooks key on it — so a run that stops mid-act can be resumed. A task opened as linked side work writes `related` as [side-work-asks-once](../rules/side-work-asks-once.md) says. A ticket read through project-mgmt writes its `parent`, when the fetch returns one. (basis: maintainer, 2026-10-19 — so a brief can read earlier tasks under the same parent item) When a stack or a fold waits on run-the-act's question, this write and the marker's below wait for its answer, and are made right after it, under the key and round number it settles; a yes that joins an open task writes only that task's links, and the resume it takes writes the rest.

On a resume that doesn't go straight to close-out, isn't a revision continuing (its marker's `revision` set), and runs a round that hasn't delivered yet, other than a declined rework, or any round of a reviewing task, when the change's head has moved past the commit the entry records since a step of this round ran — which, since the entry records the act's own head after every step, means someone else's commits — the round runs again from its first step, from a fresh "Before the steps". A delivered round's moved head is reconciled instead (Reconcile what happened outside praxis, above).

## Record the running act

A marker taken over above is kept as it records, unless the act runs again from its first step (below): when its session ended between a delivery and that delivery's filing, it is newer than the task record, and seeding it again would deliver twice. (basis: derived from never delivering twice in [deliver-through-the-ports](../rules/deliver-through-the-ports.md)) Otherwise write this session's act marker in the shape [keep-the-act-marker](../rules/keep-the-act-marker.md) pins, since the hooks key on it, with `worktree` and `made_at` set to what "Before the steps" recorded, else, on resume, the task's worktree under `.claude/worktrees/` as workspace names it, when it exists, which the session enters before the next step, or empty, `docs` empty until a filing returns it, and `answered` empty until the proposal is answered, or, on resume, as [keep-the-act-marker](../rules/keep-the-act-marker.md) seeds it. For a new task or round, every step is `pending`. On resume, seed it step by step, a skip the record or a waiting file gives as a declined proposal taking a reason that opens `proposal declined:`:

- a step whose result waits as the step's file in the task's unfiled directory ([keep-the-act-marker](../rules/keep-the-act-marker.md)) is `ran`, or the skip and reason the file's task-history section records (a task-record section, in a file written before front pages), with `filed` `false`, or `true` when every piece in it is marked held, that path in `unfiled`, and `failure` as [keep-the-act-marker](../rules/keep-the-act-marker.md) seeds it — never `pending`, which would run it again;
- any other step takes the outcome the task history's current round gives it (in a record written before front pages, its Rounds section's current round), with `filed` `true`, or stays `pending` when it gives none;
- `delivery.channels` takes where the task history's current round, or a `delivery.md` waiting in the unfiled directory, says each part went, so nothing is delivered twice; a waiting `delivery.md` goes in `delivery.unfiled`, with its `delivery.failure`, the way a step's file does.

When the round has delivered, a rerun the intent check makes is a revision starting at step 1 (A revision). When the round runs again from its first step, as the intent check or a moved head above runs it, each step's file waiting in the task's unfiled directory, and each piece in `finding.md` keyed to one of its steps, belongs to the run it supersedes: discard them and tell the user which, since the rerun's results replace them in the record. Only then does every step become `pending`, and `answered` empty so the rerun is proposed again, in place of that seeding and in a taken-over marker too. A marker taken over or seeded that lacks a row its act now has gains it: when a later row, or the round's delivery, has already ended, its skip condition is judged then, and it is recorded `skipped-by-act` when that holds; otherwise it is `pending`. A rerun only ever follows a step still to run, so no delivery or close-out filing has happened to supersede. (basis: derived from route 1 taking every resume with a delivery or filing pending)

A revision, when it opens, restarts the marker this phase writes or seeds for its round from its start step ([A revision](#rounds), above):
- that step and every step after it are `pending`;
- `delivery.channels` is empty, since the round's earlier delivery stays in its task history;
- `answered` is empty;
- `revision` holds its number, and `revision_from` its start step.

(basis: maintainer, 2026-10-19)

When the head is past the commit the task record's Status reflects, say so before taking it (basis: maintainer, 2026-10-07). Then continue at the entry's next step. Under `--dry-run`, write nothing ([dry-run](../modules/dry-run.md)).

The output is the open task — its key, its memory entry, the intent read, and where the rationale is — and the marker, for [run-the-act](03-run-the-act.md).
