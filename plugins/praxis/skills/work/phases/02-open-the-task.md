## Find the task

Resuming a task — the one `--task=<key>` names, or one found below — reads its memory entry ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)) and the documentation it points to, fetched through the [artifacts](../../artifacts/SKILL.md) port by the location the entry records. Unless the fetch returns the whole tree, stop there and say what it returned: every filing republishes the documentation from what it's handed, so one handed less would drop the rest from the record. (basis: derived from the artifacts port's in-place republish removing the pages a tree no longer has) (routed to maintainer: no recovery route; the run stops each time) An entry that records no location has nothing published: go on with no documents filed so far. Then take the entry's next step by the first of these that fits, so a review waiting to be posted on a change reads as a delivery, never as a wait on that change: (basis: derived — a delivery's target can be a review request, so the delivery test must run first)

1. **A delivery, or filing where one went**, rather than one of the act's steps or a round's peer review, which route 2 files — settle any marker from another session and record the running act (both below), then go straight to [close-out](04-close-out.md). The round finishes as its steps left it: a head that moved after they finished is for the task's next round to review, never a rerun of this one. (basis: derived from a later review of a change being its task's next round)
2. **A wait on a review request** — read the request's state through [vcs](../../vcs/SKILL.md): an approval completes that request, and a request still waiting is reported and leaves the task open. A comment-only review is still waiting, unless the user asks to act on its comments, which then counts as changes requested. `(routed to maintainer: a comment-only review waits, sparing a rework for notes meant only as notes.)` For an act that authors a change, the round waits on the requests its status names, and a review counts only when it was posted on the head the entry's links record for its request and no earlier round filed it; once each has such a review back, they are filed as its round's peer review: record the running act, the round's own (below), then go to [close-out](04-close-out.md); until then, report the requests still waiting and file nothing. In a ship round, a request land left awaiting review is no peer review: once it's approved, on whatever head land left it at, take the act from that request's step 1 by route 3, and while it waits, report it. Changes requested on it stop the ship round, as [close-out](04-close-out.md)'s Close the task says: record the running act, the round's own (below), then go to close-out; a later request to ship opens a new ship round for what's left. (basis: maintainer, 2026-10-07) A task whose latest round is a rework whose steps' reasons open `proposal declined:` reports the comments still open and opens nothing until the user asks to act on them; once each request its status names is approved on the head the entry's links record, record the running act, that round's own (below), and go to close-out, which files the approvals in the task record and closes the task when its done-condition holds. (basis: maintainer, 2026-10-07) Changes requested, or comments the user asks to act on, open the next round, a rework after peer review, below. (basis: maintainer, 2026-10-07)
3. **One of the act's steps** — take the act from there.

A request to file a finding made outside the task's steps, while this session runs no act for it, takes none of these routes. Hand [document](../../document/SKILL.md) the task key, the entry, every document filed for the task so far, every file waiting in its unfiled directory but those another session's marker for the task names, and the finding, placed as [run-the-act](03-run-the-act.md)'s rules for findings place it. When another session's marker for the task was written within the marker idle time, first tell the user that its session may still be running and that its next filing would drop this one, and any finding this one carries from the unfiled directory, and file only on their go-ahead. Write no act marker and open no act. Whenever document returns the task record's location, a failed filing included, write it into the entry's docs link. When the filing fails, append what document hands back, each piece labelled with its step key and what it ran for, to `finding.md` in the task's unfiled directory ([keep-the-act-marker](../rules/keep-the-act-marker.md)). Report where it went, and leave the entry's next step as it stood. A closed task of an act that authors a change opens its follow-ups round for the finding (below), files the finding as that round's first result, and closes the round in the same filing, the entry back to closed, unless the user asks for work on it, which runs the act in that round; a finding with no work asked for always takes this route. When that filing fails, the round stays open, filing the finding its next step, until a filing carrying it lands. Any other closed task takes no more filings ([pages-belong-to-their-task](../../document/rules/pages-belong-to-their-task.md)): say so. (basis: maintainer, 2026-10-07; the idle-time warning, derived from Take over's)

A next step of closing an act left behind, as a Close that failed leaves it, is settled by the offer below; after a Take over, take the next step the marker records by these routes, or, with no marker left for the task, the one its task history's latest round leaves (in a record written before front pages, its Rounds section's latest round). (basis: derived — the offer is the only place an act left behind is closed)

A key with no entry is an error — say so and stop. A closed task is reported as closed, and nothing opens unless a round opens on it (below).

Without the flag, find the task the request belongs to. For a review, it's the task whose entry's links name the change, open or closed — search the memory's `task-` entries, since a closed task's index line is gone; when several do, it's the one whose key the others carry with a `-<n>` added, a task closed `declined` passed over for the lowest-numbered one that isn't; the entries carrying the found task's key with a `-<n>` added are its earlier separate tasks (below), a task closed `declined` never among them nor offered for folding, since it holds no work — or else the one a stack proposes (below). For other work, search the memory's `task-` entries, closed ones included, for a task that links the same change, ticket or branch as the request. An open task found is resumed as above, and a closed review task opens its next round, unless it closed `declined`, whose work a new task with the next free number takes (below). Otherwise this is a new task. Its key names what it's about: for a review, the change (`review-230` for a review request, `review-<branch>` for a local branch); for other work, the ticket's identifier, else the branch name unless it's the integration line, else the date and a two-to-four-word slug of the request. (routed to maintainer: proposed in that order, each more stable than the next.) A new task whose key an entry already holds takes the next free number, `<key>-2`. (basis: derived — one entry per key) For other work, an open task is resumed. A task of an act that authors a change opens its next round for shipping it, a ship round, once the task has closed, an open round being taken first by the routes above; and, once closed, for other work on what it changed or a finding about it, a follow-ups round, which runs the act the router matched for the request. All of this applies with or without the flag. (basis: maintainer, 2026-10-07) A task of an act that authors a change closed `declined` opens its next round, a build, for a later request for its work, an open round being taken first by the routes above; any other act's takes the next free number, as below. (basis: maintainer, 2026-10-07) A closed task of any other act stays closed: the new task takes the key with the next free number, `PROJ-88-2`. (basis: maintainer, 2026-09-30)

A resumed task, found either way, may have an act marker from another session: one in `.claude/praxis/acts/` whose `task` is its key ([keep-the-act-marker](../rules/keep-the-act-marker.md)). Before going on to the task's next step, tell the user when that marker was last written, by its `updated`, and offer two choices. When it was written within the marker idle time ([keep-the-act-marker](../rules/keep-the-act-marker.md)), add that its session may still be running, and that taking it over locks that session's code changes. (basis: maintainer, 2026-10-02)

- **Take over** — move the marker to this session's path and resume from it, its steps and delivery as it records them, with its `answered` and `failure` fields as [keep-the-act-marker](../rules/keep-the-act-marker.md) sets them for a marker taken over.
- **Close** — end that act as abandoned. Ask the user's reason and record it as `skipped-by-user` on every step not yet run ([skip-only-with-a-reason](../rules/skip-only-with-a-reason.md)). When the act delivers on a change, read the change's review feedback through [vcs](../../vcs/SKILL.md) and match it as [close-out](04-close-out.md) does before posting, recording each channel it finds landed in the marker's `delivery` as `sent`. Hand [document](../../document/SKILL.md), in one filing, the memory entry brought up to date with its status `closed · abandoned` — written to the memory only once the filing lands, as [close-out](04-close-out.md) hands its closing status — those outcomes, the delivery the marker records in place of a waiting `delivery.md` ([keep-the-act-marker](../rules/keep-the-act-marker.md)), and every other file waiting in the task's unfiled directory. When that filing fails, nothing closes, and nothing it hands back is written to the unfiled directory: the marker returns to how it stood before Close was chosen, only the files waiting before Close stay, the task stays open with closing that act as its next step, the user is told why, and the run ends there, opening no act. (basis: derived — a Close that didn't happen leaves no trace a later Take over would inherit) When it lands, discard what the act file says to discard, by the paths the marker records; then the entry handed is written to the memory, its index line is removed ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)) and the marker is removed. Nothing more is delivered. (basis: derived from closing meaning the act stops where it stands, and from a closed task taking no more filings)

When this session's own marker holds a different task's act, that act stopped without its close-out: offer the same two choices for it before the new act opens. (basis: derived from one marker per session)

A run that can't ask ([ask-while-the-user-is-here](../../gather/rules/ask-while-the-user-is-here.md)) leaves either marker untouched, opens or resumes no act, and reports the marker with both choices for the user's next run. (basis: derived — closing ends someone's act and taking over can lock a live session's edits, so neither happens without the user)

## Rounds

A round's opening, below, compares the head the act's "Before the steps" brings in, and a stack's answer can discard the copy it made, so when a run reaches either, carry that section out first, as Prepare the act says. It runs once per change: Prepare the act runs it again only for a different change, as when a stack's yes resumes another task's round. (basis: derived — a second run on the same change would make a second copy, at a head neither decision read)

A task runs in rounds, starting at round 1, and has at most one round open. For a reviewing task, a round is one review of a change, and runs through its close-out. For an act that authors a change, a round runs from what opened it to the peer reviews of the review requests it delivers, closing once each has one: each review is read as it returns and filed when the last comes back, and changes requested on any request open the rework, which takes up the units the addressed comments' anchors fall in; its kind names what opened it: **build** for round 1 and for a round opened on a task closed `declined`, **rework after peer review** when that review requested changes, **follow-ups** for work on, or a finding about, what a closed task changed, and **ship** when the shipping act runs on the change. Any other act's task has one round. A follow-ups round that changes code closes at its peer review; one opened only to file a finding closes in that filing; a ship round closes at its close-out, when shipping's done-condition holds or close-out stops it on a request it hadn't merged. A round's act is the task's own, `act` in its entry, but for a ship round, which runs shipping, a follow-ups round that runs another act, and a rework after peer review, which runs the act of the round that last delivered onto the requests it answers, never a ship round; its line names any act that isn't the task's own. (basis: maintainer, 2026-10-07) A later review of a change whose task is closed — the change itself, or one stacked on it that the user joins to it (below) — is that task's next round, reviewing the change at its current head, when that head, as "Before the steps" brings it in, differs from the latest round's commit, the entry's `at`. With the head unmoved, the closed round stands: discard the copy "Before the steps" made, report that the change hasn't moved since that round, and open nothing. (basis: derived — a round is a review of a commit, and that commit's review stands) A round that opens puts its line first in the entry's `rounds` ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)), the entry turns open and its index line is restored. A rework round takes as its input, from each request whose review requested changes or whose comments the user asks to act on, every review summary's requests and every inline comment whose thread isn't resolved, posted on the reviewed commit. A round that delivers several requests names each in the entry's links. (basis: derived — a resolved thread is settled on the host) The earlier rounds' documentation is fetched as resuming fetches it, above, and goes to every filing as documents filed so far, so the republish keeps them. (basis: maintainer, 2026-10-02)

**A stack.** A review request with no task linking it may build on other open ones. Read what it builds on through [vcs](../../vcs/SKILL.md): the requests it returns, nearest first, are its stack below it. A read that comes back partial gives the stack as far as it reached, one that fails otherwise gives none, and the report says so either way. When the stack holds any, run-the-act's question proposes it as one task, base-most request first. It joins the task of the nearest request below that has one, as that task's next round. When that task is open, a yes writes the stack's requests into that task's entry's links at once, discards the copy "Before the steps" made, and resumes that task's open round as a found task is resumed (above), since its round in progress comes first; the report says so, and the stack's later changes are reviewed in that task's later rounds. With no such task, it becomes a new task keyed by the base-most request, `review-230`, whose first round reviews this one. On yes, the entry's links name every request of the stack, base-most first. On no, or with no answer, the change is reviewed alone under its own key. (basis: maintainer, 2026-10-02) (basis: derived — the nearest keeps a split the user chose earlier, and alone is the default since joining reshapes another task's record) A local branch has no host to read, and is reviewed alone.

**Earlier separate tasks.** Entries keyed `<key>-<n>`, `review-230-2`, are separate earlier tasks on the same change. When a round opens on a task that has any, it's numbered after the highest of this task's own rounds and those `<n>`, whether or not they're folded, so a later fold never collides. Run-the-act's question offers to fold the closed ones in as earlier rounds, in key order: `<key>` is round 1, `<key>-2` round 2, and so on. An open one is left alone: it's resumed under its own key when asked for, and offered once it's closed. On yes, fetch each folded task's documentation through artifacts, and hand [document](../../document/SKILL.md), in one filing before the first step, those trees as the pages of their rounds, carried as they stand. When it lands, add each folded round's line to this task's `rounds`, retire each folded task's documentation through the [artifacts](../../artifacts/SKILL.md) port's Retire, superseded by this task's record, and remove the folded task's memory entry, since this task's entry and record now hold its round. Report each document Retire didn't remove, with what the port returned, for the user to remove by hand. A fold is all or nothing: when any fetch or the fold's filing fails, nothing of it is filed — what that filing hands back is dropped, and no later filing is handed the folded pages — nothing is retired or removed, and the report says so. On no, with no answer, or after a failed fold, the earlier tasks stay their own, and the offer comes again at each later round. (basis: maintainer, 2026-10-02)

## Prepare the act

If the act file has a "Before the steps" section, carry it out now, unless it already ran under Rounds above on the change this round works on: it brings in what the rest of this phase reads, such as the change's branch name and head commit. A path it records in the act marker goes into a marker taken over above at once, and otherwise into the marker this phase writes below. When it needs a port that isn't configured, carry out what it can without the port, and the rest once the proposal's answer has set the port up ([run-the-act](03-run-the-act.md)).

## Gather the intent, locate the rationale

Classify each input by [form-your-own-view-first](../../../craft/evidence/form-your-own-view-first.md) as you meet it. Read the intent now — the ticket, a spec, an RFC, the requirement the work must meet, the conversation the request points at — fetching a tracker item through [project-mgmt](../../project-mgmt/SKILL.md) and a document through [knowledge](../../knowledge/SKILL.md); a file in the repository is read directly. Find its reference in the request, the change's branch name or the task's own record, never inside the rationale; when none of them names one and the request's own words don't state what's required, record that, and the proposal in [run-the-act](03-run-the-act.md) asks for it. Of the rationale, record only where it is, and don't open it here: every inline step inherits what this context has read, so a description read now would reach every step.

A ticket that also proposes a solution is read whole, and the task history notes that its proposal was seen. (routed to maintainer: an isolated reader passing on only the requirements would keep the proposal out, at the cost of a subagent per ticket.)

On resume, compare the intent as it stands now with the requirements and acceptance criteria the task history copied when the task opened (in a record written before front pages, its own The task section). A change in what it requires — a requirement or acceptance criterion added, removed, or changed in meaning — runs the act again from its first step; a rewording that leaves every requirement the same is noted in the task history and changes nothing. (routed to maintainer: rerun on a requirement change, note a rewording, since only a change in what's required can make finished steps wrong.) Read other people's edits to the task's documents under [edits-change-intent-not-actions](../rules/edits-change-intent-not-actions.md).

## Create or update the entry

A new task's title comes from its ticket, else its branch name when that isn't the integration line, else a short phrase from the request — never from the change's description or title, which are rationale. `(basis: derived from rationale being read last)` Creating the task, or opening a round, writes its memory entry and its index line at once, in the format [keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md) pins — the hooks key on it — so a run that stops mid-act can be resumed. When a stack or a fold waits on run-the-act's question, this write and the marker's below wait for its answer, and are made right after it, under the key and round number it settles; a yes that joins an open task writes only that task's links, and the resume it takes writes the rest.

On a resume that doesn't go straight to close-out, when the change's head has moved past the commit the entry records — which, since the entry records the act's own head after every step, means someone else's commits — the round runs again from its first step, from a fresh "Before the steps".

## Record the running act

A marker taken over above is kept as it records, unless the act runs again from its first step (below): when its session ended between a delivery and that delivery's filing, it is newer than the task record, and seeding it again would deliver twice. (basis: derived from never delivering twice in [deliver-through-the-ports](../rules/deliver-through-the-ports.md)) Otherwise write this session's act marker in the shape [keep-the-act-marker](../rules/keep-the-act-marker.md) pins, since the hooks key on it, with `copy` set to the path "Before the steps" recorded, or empty, `docs` empty until a filing returns it, and `answered` empty until the proposal is answered, or, on resume, as [keep-the-act-marker](../rules/keep-the-act-marker.md) seeds it. For a new task or round, every step is `pending`. On resume, seed it step by step, a skip the record or a waiting file gives as a declined proposal taking a reason that opens `proposal declined:`:

- a step whose result waits as the step's file in the task's unfiled directory ([keep-the-act-marker](../rules/keep-the-act-marker.md)) is `ran`, or the skip and reason the file's task-history section records (a task-record section, in a file written before front pages), with `filed` `false`, or `true` when every piece in it is marked held, that path in `unfiled`, and `failure` as [keep-the-act-marker](../rules/keep-the-act-marker.md) seeds it — never `pending`, which would run it again;
- any other step takes the outcome the task history's current round gives it (in a record written before front pages, its Rounds section's current round), with `filed` `true`, or stays `pending` when it gives none;
- `delivery.channels` takes where the task history's current round, or a `delivery.md` waiting in the unfiled directory, says each part went, so nothing is delivered twice; a waiting `delivery.md` goes in `delivery.unfiled`, with its `delivery.failure`, the way a step's file does.

When the round runs again from its first step, as above, each step's file waiting in the task's unfiled directory, and each piece in `finding.md` keyed to one of its steps, belongs to the run it supersedes: discard them and tell the user which, since the rerun's results replace them in the record. Only then does every step become `pending`, and `answered` empty so the rerun is proposed again, in place of that seeding and in a taken-over marker too. A marker taken over or seeded that lacks a row its act now has gains it: when a later row, or the round's delivery, has already ended, its skip condition is judged then, and it is recorded `skipped-by-act` when that holds; otherwise it is `pending`. A rerun only ever follows a step still to run, so no delivery or close-out filing has happened to supersede. (basis: derived from route 1 taking every resume with a delivery or filing pending)

When the head is past the commit the task record's Status reflects, say so before taking it (basis: maintainer, 2026-10-07). Then continue at the entry's next step. Under `--dry-run`, write nothing ([dry-run](../modules/dry-run.md)).

The output is the open task — its key, its memory entry, the intent read, and where the rationale is — and the marker, for [run-the-act](03-run-the-act.md).
