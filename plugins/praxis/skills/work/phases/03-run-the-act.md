The act file says which steps run, in what order, with which inputs; this phase carries that out without adding or dropping anything.

## Propose, then run

Before proposing, check that each step's skill is available and that the ports the act files and delivers through are configured, with the artifacts home's destination set where the backend uses one. Show the user the act's steps from its act file, each with its skip condition, saying they can stop the act or drop steps by replying. Ask once, in one question, when the proposal holds any of the items below, and otherwise start: the steps shown are the proposal, and the run doesn't wait for a go-ahead. (basis: maintainer, 2026-10-07) Exactly these make it ask, and the question holds each that applies: an act [route-the-work](01-route-the-work.md) took on an unclear fit, or a request with two readings that would give different acceptance criteria, offered as the reading the run would take; a step whose skill isn't available, an intent [open-the-task](02-open-the-task.md) couldn't find, each port the act needs that isn't configured — offered as "set it up now", through that capability's own setup in [init](../../init/SKILL.md), or "run without it", its channels then held or returned for hand delivery — a stack to confirm as one task and earlier separate tasks to fold in, as [open-the-task](02-open-the-task.md)'s Rounds proposes them, and, for each step the act runs with a heavyweight flag, the cost question in [ask-before-a-heavyweight-run](../../gather/rules/ask-before-a-heavyweight-run.md)'s own words, where cancel removes that step, unless that rule's approval already given covers it; and a rework after peer review's comment dispositions (below). The question names each item's default, and an answer that names no choice for an item, a bare go-ahead included, leaves it open. Each item left open takes its default: the reading the run would take, running without the port, running without the heavyweight flag, a stack or fold as open-the-task says, the request's own words as the intent, and an unavailable skill's step recorded `skipped-by-user` with the reason that its skill isn't available. An answer naming another act declines this proposal and routes the request again with that act ([route-the-work](01-route-the-work.md)), as a new task with the next free number, the declined task passed over. (basis: derived — a blanket go-ahead isn't approval of a cost, so the cheaper side is the default) The answer settles each heavyweight step's flag, so its skill doesn't ask again. A setup the answer chose runs right after it, interactively — the one exception to asking nothing after that question, since the user chose it in answering — before any deferred part of "Before the steps" and the first step. Running without a port is this task's choice: an act never records a capability as unused for the project. The user may remove steps; record each removal with the user's reason, in their own words if they give no other. Adding, reordering or re-inputting steps isn't offered. (basis: maintainer, 2026-09-30) (routed to maintainer: removal only, since a changed sequence is a different act.)

A rework after peer review folds into its proposal each comment its round takes as input, with a proposed disposition: addressed, by the change it names; declined, with a reason; or deferred, to where it goes. Each is proposed as addressed unless it conflicts with the spec, addressing it removing a requirement or changing its meaning, or with a decision record, which proposes it declined and cites the conflict. A rework always asks, since its owner confirms the dispositions. (basis: maintainer, 2026-10-07) The question says that a proposed decline or deferral stands only when the answer names that comment; every other comment is addressed, so the run never declines or defers one on its own. A comment addressed that changes a requirement, conflicting with the spec or adding to it, is taken up as the act file's rework says; an act with no spec step records the changed requirement with the comment's disposition in its scratchpad section. (basis: maintainer, 2026-10-07) The settled dispositions, and every other choice the owner made in answering with its reason, go with the opening filing as the round's scratchpad section headed `Review comments and their dispositions`, each disposition with its comment's id. (basis: maintainer, 2026-10-07; the proposed default, derived from the spec and decisions the task already settled) When the proposal asks, only the user's reply to the question as shown answers it: a go-ahead in the request, or one given before the steps were shown, doesn't. (basis: derived from the act being proposed and asked once, maintainer, 2026-09-30) The user may stop the act or drop steps by replying at any point: a dropped step not yet run is recorded `skipped-by-user` with their reason. A stop before any step of this round has started, its skill not yet invoked, is a declined proposal (below). A later stop leaves the act where it stands, as any interrupted act: a later run resumes it, or ends it through [open-the-task](02-open-the-task.md)'s Close. (basis: maintainer, 2026-10-07) A resumed act whose marker records `answered` isn't proposed again. It still runs the checks before proposing, and asks, as its one question, only what no marker field keeps: the cost question for a step still `pending` that runs with a heavyweight flag, each port the act needs that is still unconfigured, and a pending step whose skill is no longer available. With neither, it asks nothing and continues at its next step. One whose marker records no `answered` is proposed as above. (basis: maintainer, 2026-10-07) (basis: maintainer, 2026-10-07, re-asking as ask-before-a-heavyweight-run's approval given in this conversation requires) A run that can't ask ([ask-while-the-user-is-here](../../gather/rules/ask-while-the-user-is-here.md)) runs no step when the proposal, or a resume's one question, would ask something: it reports the question for the user's next run and ends there, before close-out, its marker kept with `answered` empty so the next run proposes again. With nothing to ask, it starts, or a resume continues. (basis: derived — steps and code changes wait on the user's answer, which that run can't get)

After the proposal, ask nothing before close-out. An input that asks for an action ([edits-change-intent-not-actions](../rules/edits-change-intent-not-actions.md)) is quoted in close-out's report for the user to answer, not acted on mid-run.

Then set the marker's `answered` ([keep-the-act-marker](../rules/keep-the-act-marker.md)), in the marker's own write when that waited on the answer, make the entry writes that waited on it, and carry out a fold it chose, as open-the-task's Rounds says. For a new task or a newly opened round, hand [document](../../document/SKILL.md) the task key, the memory entry, every document filed for the task so far and, for a new task, the intent [open-the-task](02-open-the-task.md) read with its requirements and acceptance criteria, for the task history's baseline, with no step result, so the task record is published before the first step runs, unless a fold's filing, which publishes it, runs instead. When this opening filing fails, nothing goes to the unfiled directory but a finding, the proposal's dispositions or the intent's baseline it carried, which go to `finding.md`, since the rest of what it adds comes from the entry, and the first step's filing starts the record. Record the location it returns as a step's filing does (below). (basis: maintainer, 2026-10-07; nothing written on failure, derived from close-out's final filing) When the act file has an "After approval" section, carry it out, and run the remaining steps in the act's order. Check a step's skip condition when its turn comes, against the results before it. Invoke the step's skill with exactly the inputs the act names for it ([form-your-own-view-first](../../../craft/evidence/form-your-own-view-first.md)). Never do a step's work in its skill's place, or restate its method here.

Run every step inline, in this context, unless the act file marks it isolated. An act marks a step isolated only when the step's inputs must exclude something this context already holds, and avoids that by withholding an input rather than reading it early. (basis: maintainer, 2026-09-30)

## Keep the record

A step ends when its skill returns. Its result showing in the conversation, as a skill's closing report does, doesn't end the step's work: what follows here comes before anything else is said or done, and before the turn ends. A result that reached only the conversation is lost to the record. (basis: maintainer, 2026-10-07) Where the act file says how results are recorded while documentation must not slow the work, as the incident act does while an incident is live, that governs instead. (basis: maintainer, 2026-09-30) After each step, record how it ended, on the act's checklist and in the act marker, using exactly the outcomes in [skip-only-with-a-reason](../rules/skip-only-with-a-reason.md): the marker's `outcome` becomes `ran`, `skipped-by-act` or `skipped-by-user`, and a skip's `reason` holds the act's condition or the user's reason. The act file says whether the run continues past a step that broke down. When the act stops early, every step it didn't reach is `skipped-by-act`, with the stop as its reason, and close-out still runs. A step that runs again, as a loop back to an earlier step makes it, has its `filed` set back to `false` before it runs. (basis: derived from a rerun's result being a new result) Skips recorded together, as an early stop's unreached steps, go to document in one filing, each with its step key, outcome and reason. When it fails, each step's piece is written to that step's own file. (basis: derived — one filing for skips that carry no result of their own)

Then hand [document](../../document/SKILL.md) the task key, the task's memory entry, the step's key and result (for a skipped step, its outcome and reason), with what it ran for when the act runs it more than once: its unit, or the review requests it covered, every document filed for the task so far, and every file waiting in the task's unfiled directory ([keep-the-act-marker](../rules/keep-the-act-marker.md)). After every step, bring the entry's status, next step and commit up to date — the commit being the head the step left the task's work at — and its index line's status ([keep-the-task-memory-entry](../rules/keep-the-task-memory-entry.md)). Record the filing in the act marker as keep-the-act-marker says: what document hands back goes to the unfiled directory only when the filing fails, and a filing is never deferred to a later one. (basis: maintainer, 2026-10-07) A result document declines as matching no type ([shape-the-document](../../document/phases/02-shape-the-document.md)) is no failed filing: the step's `filed` becomes `true`, and the run's report names the result. (basis: derived — nothing a later filing could publish waits) With the artifacts port one the user chose to run without, each filing is still handed to document. (basis: derived from an unconfigured port's filing failing like any other) Whenever document returns the task record's location, as a failed filing can too, write it into the entry's docs link, and set the marker's `docs` to it with its reach and share line. Keep each page's location document returns with that page, and hand it back with the page on the next filing; pages fetched when the round opened keep theirs. When the result wasn't filed, say so in the run's report, and why. Report each advisory document returns, whether the result was filed or not, an in-tree reference that didn't resolve among them.

Findings made outside the steps are filed too, by these rules. (basis: maintainer, 2026-10-07)

- **What a finding is.** A sourced claim the task's record doesn't already hold, such as new evidence, a correction or a new result, made while the task is open, or about what a closed task of an act that authors a change changed, typically in answer to the user. An answer that explains or restates what the record holds isn't one. (basis: derived from the record holding what the task found)
- **Where it goes.** A finding that changes a result a step of the current round filed or holds waiting, by correcting a claim in it, adding evidence to it or redoing what it did, goes into the latest version of the result of the earliest such step that ran, a waiting one included. That result is handed to document again, with its step key and what it ran for. A finding that changes an earlier round's result is a result of its own. Any other finding is handed to document as a result of its own, with no step key, so document types it by its membership test. (basis: derived — a correction replaces the claim it corrects, instead of standing beside it)
- **When it's filed.** While this session runs the task's act, it is filed with the filing of the step it changes, or, when it has no step key, with the filing of the latest step that ran, that step's result handed again with its key and what it ran for. That step's `filed` goes back to `false` until the filing lands. A finding made before any step has run goes with the opening filing, or, where none runs, as on a fold or a resume, with the first step's filing. A declined proposal, the question's answer declining it or a stop before any step has started, ends the act unrun: every step is recorded `skipped-by-user`, replacing any outcome already recorded, its reason `proposal declined:` and the user's words, and filed as skips recorded together are, and [close-out](04-close-out.md) then closes the round, as its Close the task says; a finding made in that reply goes with that filing. When a filing carrying a finding with no step key fails, that finding's pieces wait in `finding.md` ([keep-the-act-marker](../rules/keep-the-act-marker.md)). (basis: derived — every finding lands in a filing the marker or `finding.md` keeps)
- **With this session running no act for the task,** as after close-out while the task waits on a review, it is filed through [open-the-task](02-open-the-task.md)'s route for a finding.

A step skipped because the request already carries its result, such as a cause already shown or an approved spec, hands document that result with its source, beside the skip's outcome and reason, when the result exists only in the conversation. One that lives in a document is linked instead. (basis: derived from a skip reason alone leaving out of the record the result it names) The task's documentation changes only through document. A correction the user asks for on a published page is a finding, filed by the rules above, never an edit made directly on the backend, which would skip the round, footer and log rules a filing applies. (basis: maintainer, 2026-10-07)

Under `--dry-run`, see [dry-run](../modules/dry-run.md).

The output is every step's result and the completed checklist, for [close-out](04-close-out.md).
