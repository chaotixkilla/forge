# Keep the act marker

While an act runs, a marker file records where it stands: the end-of-turn checks hold the run to it, and the edit guard lets code change only while this session has one whose proposal is answered. Each session keeps its own, so an act left behind by a session that ended never unlocks another session's edits, and two acts running at once never overwrite each other. (basis: maintainer, 2026-10-02)

## Where it lives

`.claude/praxis/acts/<session-id>.json` in the repository's main checkout: the path and session id praxis's session-start context states, or, when that context states none, the ones praxis's note states once work is invoked in a session with no marker. A session running in a worktree writes there too, never in its own worktree, so every worktree of the repository shares one set of markers. When neither states the path, the main checkout is the one [write-and-validate](../../init/phases/04-write-and-validate.md) names. (basis: maintainer, 2026-10-14) (routed to maintainer: a directory in the project's `.claude/`, as session bookkeeping, since the task's state lives in its documentation.)

## What it holds

    {"updated": "2026-10-02T14:41:00Z", "task": "review-230", "act": "reviewing",
     "answered": "2026-10-02T14:12:00Z", "revision": "", "revision_from": "", "filing": "per-round", "parked": "",
     "docs": {"location": "<the task record's location>", "reach": "private-until-shared", "share": "<the port's share line>"},
     "worktree": "<the task's worktree path>", "made_at": "<the commit it was made at, or empty>",
     "steps": [{"step": "1:understand", "outcome": "pending", "reason": "", "filed": false, "waiting": "", "queued": "", "unfiled": "", "failure": ""}, …],
     "units": [{"unit": "<the unit>", "request": "405", "steps": ["5:develop", "6:test", "7:verify", "8:review"], "done": false}, …],
     "delivery": {"channels": [], "filed": false, "waiting": "", "unfiled": "", "failure": ""},
     "coordinating": [{"worker": "worker-1", "address": "<its address>", "task": "<key>-w1"}, …],
     "worker_of": "",
     "feedback": [], "prompts": []}

- `updated` is a UTC time in ISO 8601, set by every write.
- `feedback` holds the feedback proposals and notes the latest filing returned, each as document returned it with its id, and the user's answer on a proposal once one is given, and `prompts` the judgment prompts filings returned, each with its page. (basis: maintainer, 2026-11-11)
- `worker_of` is a worker session's coordinator address ([worker](../modules/worker.md)), and empty otherwise: its rows record each step's outcome, and the coordinator files.
- `coordinating` lists a coordinated round's workers ([coordinate](../modules/coordinate.md)), and is empty otherwise; a resume finding it carries on as the coordinator.
- `answered` is the UTC time the act's proposal was settled ([run-the-act](../phases/03-run-the-act.md)): the user's answer when it asked a question, else the moment its steps were shown. It is read from the clock at the write that records it, never estimated, and stays empty until then. While it's empty no step runs and no code changes: the edit guard and the end-of-turn checks read it. (basis: maintainer, 2026-10-07) A marker seeded on resume, or taken over, that has no `answered` gets the time of that write when it holds an outcome for any step of this act, a revision's marker counting only its steps from its `revision_from` on, from the task history's current round (or a record's Rounds section, written before front pages), a file waiting in the queued or unfiled directory or the taken-over marker itself. Otherwise it stays empty. A taken-over marker that records `answered` gets the take-over write's time in its place, so none of this session's earlier work counts against it. (basis: derived — no step runs before the answer; the clock, derived from the end-of-turn check's transcript timestamps)
- `filing` is the round's filing cadence, `per-round` or `per-step` (Queued results, below). Every marker written fresh, a new round's, a revision's or one seeded on resume, gets `per-round`; a taken-over one keeps its own, and an older one with none reads as `per-step`, as it ran.
- `parked` is empty, or, for a parked act, one string, its UTC time and why: `2026-11-25T10:00:00Z · work on PROJ-90 opened` (Parking an act, below).
- `docs` holds the task record's location, its reach and, for `private-until-shared`, the port's share line, as document last returned them. They stay empty until a filing returns them.
- `worktree` holds the path of the task's worktree as [workspace](../../workspace/SKILL.md) returned it, empty when the task works in place; `made_at` the commit a detached worktree was made at, as a review's or an audit's is, else empty. An older marker's `copy` is read as `worktree`.
- `revision` holds the number of the revision the act runs, `1.2`, and `revision_from` the step it started at, `5:develop`; both are empty otherwise ([open-the-task](../phases/02-open-the-task.md)). (basis: maintainer, 2026-10-19)
- `steps` lists the act's steps in order, each keyed by its row number and skill so two steps of one skill stay apart. `outcome` stays `pending` until the step ends in one of the outcomes in [skip-only-with-a-reason](skip-only-with-a-reason.md), and `reason` holds a skip's reason. A word for how the step went, such as passed, green or done, belongs in its result, never in `outcome`. (basis: field findings, 2026-11-25) A skip owes no filing of its own: its outcome and reason here are its record until the round's next filing carries it, so a skip with `filed` `false` is recorded. (basis: field findings, 2026-11-25 — skips recorded at the proposal blocked turns until each was marked waiting) A `skipped-by-user` row may stand ahead of steps still pending: the user can drop a later step at any time, and the proposal records its defaults that skip a step this way. Every other outcome is written when its step's turn comes, or, as `skipped-by-act`, by an early stop for the steps after the one it stopped at ([run-the-act](../phases/03-run-the-act.md)). `filed` becomes `true` once document has filed the step's result. `waiting` names what a step is still waiting on, so a turn may end without it reading as unrecorded: `agents` while the step hasn't ended because explorers, critics or background work it started are still out ([run-the-act](../phases/03-run-the-act.md)'s Keep the record); `filing` while its filing is handed to document, or waits behind another filing, and hasn't returned; `messages`, on the row of the step it waits in, while a coordinated round waits on another session's message ([coordinate](../modules/coordinate.md)). Set it in the write that starts the wait, never later, and empty it when the wait ends. For a filing, that is the write recording the step's outcome, or the delivery's channels, or, for a skip recorded before its filing started, or a checkpoint filing (below), the write handing that filing on, which sets it on every row the filing carries. (basis: field findings, 2026-11-19 — six runs set it only after the end-of-turn check had blocked) The delivery's `waiting` takes only `filing`. An entry seeded or taken over from another session has its `waiting` emptied, since that session's agents and filings ended with it. (basis: field findings, 2026-10-28) `queued` holds the path of the step's queued file while its filing waits for the round's next checkpoint (Queued results, below). `unfiled` and `failure` are set together, only when a filing fails (below): what waits for a filing that hasn't run yet is `queued`, never `unfiled`. (basis: field findings, 2026-11-25) An entry seeded or taken over with an `unfiled` file and no `failure` gets `failure` saying the file waits from an earlier session. (basis: derived — the waiting file doesn't keep the port's outcome)
- `units` lists, for an act whose steps run once per unit, each unit in the order it runs, with its request, the steps it runs, and `done`.
  - It is written in full once the units are known: from decompose's return, from the plan when decompose is skipped, or when a revision or rework opens. A unit that joins later is appended when it joins.
  - A unit's steps are all the per-unit steps, or fewer, as for a unit above a merge forward that runs only its test. They grow back to all of them when a failed step sends that unit back.
  - `done` becomes `true` when the unit passes its last step.
  - The `steps` rows are never reset between units. They hold each step's latest outcome, and a step running again has its `filed` set back to `false`. A per-unit step that no unit runs, as step 5 in a rework taking its units from step 6, is recorded `skipped-by-act` with that reason.
  - A resume takes the first unit not `done`, at its first step with no result for that unit filed or waiting from this run of the act, counted from the marker's `revision_from` in a revision, else from the round's opening, whatever the rows say, so a unit is never passed over.
  - Before an upper unit's first step, its branch takes the merge forward from the branch below, if it lacks it.
  - It is empty for an act whose steps run once. (basis: derived — rows per step can't say which unit a resumed act stands at)
- `delivery.channels` gets one entry per channel as close-out delivers it. A channel is one submission a port makes, named by the port, the target reference it was handed, and the part, as the port's operation names it: a review summary and its inline feedback are two channels, since vcs posts them as two submissions. A ship round's report names in its part the requests it covers and what each reached ([shipping](../acts/shipping.md)).

      {"port": "vcs", "target": "review request 230", "part": "review summary",
       "disposition": "sent", "where": "<the reference the port returned, or what's missing>"}

  `disposition` is spelled `sent`, `held`, `degraded-return` or `sent-by-hand`, the four of [deliver-through-the-ports](deliver-through-the-ports.md). `sent` and `sent-by-hand` both count as delivered. A channel the user chose to deliver anyway also carries `"anyway": "<their words>"`, and one a default settled carries `"default": "<the reason>"`. `delivery.filed`, `delivery.unfiled` and `delivery.failure` record the record update after delivery, the way a step's own fields record its filing.

## Queued results

A round files per round unless its marker's `filing` says `per-step`. It may say `per-step` only while the task's documentation is shared, its `docs` reach anything but `private-until-shared`, and the user has said someone follows it live. It goes back to `per-round` when the reach returns to private, or when the user says so. The one exception is close-out, whose first filing sets `per-step` whatever the reach, and it holds to the round's end (below). (basis: maintainer, 2026-11-25 — filing after every step cost far more than the work) A switch to `per-step` runs the checkpoint filing at once.

Under `per-round`, a filing that the rules elsewhere hand to document after a step, or with a step's filing, or with the next filing, is queued instead of run: everything it would hand document, the step's result, a skip's carried result, a finding, a labelled result, is written at once to the task's queue directory, `.claude/praxis/queued/<task>/` in the main checkout. A piece with a step key goes to that step's file, `<row>-<skill>.md` as for an unfiled result, and one with none, a labelled result among them, to `finding.md`. Each piece is opened by a line naming its step key or `no step`, a skip's outcome and reason when it is one, its label when it carries one, and what it ran for:

    <!-- queued · 5:develop · unit 2 -->
    …the step's result…
    <!-- queued · 2:spec · skipped-by-act · the request carries an approved spec -->
    …the result the request already carried…
    <!-- queued · no step · research: how other teams version the API -->
    …

A later result for the same step and the same thing it ran for is the step's whole result as corrected, and replaces the earlier one; a finding or a late agent's return keyed to the step, and any other piece, is appended. A piece with no step key is appended, unless it corrects the same labelled piece, which it replaces. A step may have both a queued and an unfiled file. Put the step's file path, relative to the main checkout, in the entry's `queued`, with `filed` `false`. A queued file is recorded. (basis: maintainer, 2026-11-25)

The checkpoint filing hands document, in this order, so the newer replaces the claim it corrects ([publish-and-link](../../document/phases/03-publish-and-link.md)), every file waiting in the unfiled directory; every queued piece, each as the result, finding or skip it is, with its step key or label and what it ran for; every step whose skip has `filed` `false`; and the brief, when it changed since the round's last filing. It runs only when one of these is owed, and only after every agent and filing in flight has returned. It runs at each checkpoint:
- close-out's first filing ([close-out](../phases/04-close-out.md)). Close-out sets `filing` to `per-step` in the marker write that begins it, whether or not that filing runs, so a correction close-out makes is filed at once and nothing queued outlives the round;
- before the task's documentation, or a link to it, is shared with or sent to anyone but the user while the round runs, through a delivery or a share; a coordinated round's messages to its workers aren't sharing. When it fails, the share waits as a channel waits on an unfiled step;
- before the act stops between steps: the user's stop, a blocked step, or an early stop. A question asked mid-run isn't a stop: the act goes on from its answer, and the queue stays on disk meanwhile;
- after the step whose result is a document's due point in the documentation plan, such as the first build step while the plan owes documents before a gate;
- before the act is parked (below).

When it lands, each queued file it carried is removed, and its entry's `filed` becomes `true` with `queued` cleared, as does each skip it carried. When it fails, what document hands back is written to the unfiled directory as below, and each queued file it carried is removed once its pieces are written there, its entry's `queued` cleared and its `unfiled` and `failure` set. A session that ends with files queued leaves them for the next session to carry, as it leaves unfiled ones. (basis: derived — the queue is the filing deferred, so its pieces land where the filing's would have)

## Unfiled results

When a filing fails, document hands back what that filing added, as it shaped it, with the outcome the artifacts port returned ([publish-and-link](../../document/phases/03-publish-and-link.md)). Only then, write it at once to the task's unfiled directory, `.claude/praxis/unfiled/<task>/` in the main checkout, as one file: `<row>-<skill>.md` for a step's result, its step key with the colon as a hyphen, `delivery.md` for the record update after delivery, `closing.md` for what close-out's own filing adds, the documentation no step produced, and `finding.md` for the pieces of a finding filed outside the steps that came with no step key, and for everything a finding filed while no act runs hands back ([open-the-task](../phases/02-open-the-task.md)), a later one appended to it. Four filings write nothing here when they fail, since the memory entry or the review host keeps what each adds: the filing of a round's peer review ([close-out](../phases/04-close-out.md)), the opening filing ([run-the-act](../phases/03-run-the-act.md)), the one that closes a left-behind act ([open-the-task](../phases/02-open-the-task.md)), and the one that ends close-out ([close-out](../phases/04-close-out.md)). A finding, a proposal's dispositions, the brief or the intent's baseline the opening filing carried are the exception: their pieces go to `finding.md`. So are the steps the proposal recorded `skipped-by-user` that it, or a fold's filing standing in for it, carried: each one's piece goes to its own step's file, since the marker, not the entry, keeps them. The file holds the pieces in the order document handed them back, each opened by a line naming its type's slug, with `· section` for a section of a page, the step key the piece came with, or `no step`, what the step ran for when it came with one, and `· held` for a piece a reader's comment held:

    <!-- document: review-record · 4:review -->
    …the review record as document shaped it…
    <!-- document: scratchpad · section · 5:develop · unit 2 -->
    …
    <!-- document: scratchpad · section · no step -->
    …

The key decides where a waiting piece lands when it is filed ([publish-and-link](../../document/phases/03-publish-and-link.md)), so a correction that waited still replaces the claim it corrects. (basis: maintainer, 2026-10-07)

Put that file's path, relative to the main checkout, in the entry's `unfiled` and the port's outcome in its `failure`, and keep `filed` `false`: a file waiting here never counts as filed. Pieces a filing hands back because a reader's comment held their page are written to the step's file the same way, the hold as their `failure`, while the step's `filed` stays `true` for the pages that landed; seeding on resume keeps it so. A file written without a failed filing is a filing skipped, and the end-of-turn check reads an `unfiled` with no `failure` as unrecorded. (basis: maintainer, 2026-10-07) `closing.md` and `finding.md` have no entry: the file waiting is their only record. The next filing for the task, in this session or a later one, hands document the content of every file waiting there, each under its file name, along with its own result, and document publishes them all in that one filing. When it lands, each file it carried is removed, and its entry's `filed` becomes `true` with `unfiled` and `failure` cleared. When it fails, every file stays waiting, and the new result's pieces are written to its file: appended to a step's waiting file, replacing the pieces it holds for what the new result ran for, and those naming nothing it ran for under the same type and section heading, or all of them for a step that runs once, as a loop back's rerun or a correction does. (basis: maintainer, 2026-10-02) A filing that carries the delivery hands document every channel `delivery` records, with where it went, so it stands in for a waiting `delivery.md` rather than carrying it: when it lands, that file is removed with the ones it carried, and when a failure writes a new `delivery.md`, it replaces the waiting one and loses nothing. (basis: derived from the marker holding every channel a waiting `delivery.md` holds)

## Parking an act

An act is parked when the user asks to park it, or when work on another task opens while this session's act runs ([open-the-task](../phases/02-open-the-task.md)). Parking happens between steps, never during close-out, which finishes first: a request for other work made mid-step waits until the step has ended. Every step whose `waiting` is `agents` or `filing` waits for it to end and is recorded. A coordinating act parks only once every worker has reported. Until then it isn't parked, the work that would have parked it doesn't open, and the user is told the coordinated round must finish, or be stopped, first. (basis: derived — a worker reporting to a parked coordinator would find no one) Then the checkpoint filing runs (Queued results, above); when it fails, the park goes on, since what it hands back waits unfiled and is recorded. Then write `parked`, and move the marker to `.claude/praxis/parked/<task>.json` in the main checkout. An automatic park's reason is `work on <key> opened`, the other task's key; one the user asked for is `parked on request`, with their reason when they gave one. A worker session ([worker](../modules/worker.md)) isn't parked while its coordinator waits on it: the user is told to finish or stop the worker's piece first. The worktree and the task's environment stay as they are, the running environment of a parked task being one session-start offers to stop through work's tidy. The entry's status names the next step and that the act is parked. (basis: maintainer, 2026-11-25 — one marker per session forced a full close-out before the next task could start)

A parked marker belongs to no session. The end-of-turn checks and the edit guard never read it, the idle report below leaves it out, and session-start lists it as parked. Only [open-the-task](../phases/02-open-the-task.md) takes it over or closes it. (basis: maintainer, 2026-11-25)

## A marker its session left behind

A session that ends mid-act leaves its marker. Only [open-the-task](../phases/02-open-the-task.md) takes it over or closes it, when the task is resumed. praxis's session-start hook reports each other session's marker that has gone more than the marker idle time, two hours, without a write, with its task key. (basis: maintainer, 2026-10-02 — two hours, longer than one step usually runs, so a live act seldom reads as left behind, while an ended one is reported the same day.)
