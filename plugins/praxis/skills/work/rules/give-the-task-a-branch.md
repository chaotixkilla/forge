# Give the task a branch

An act that changes the code builds on a branch of its own, so nothing reaches the integration line except through a review request. (basis: derived from [open-the-review-request](open-the-review-request.md)'s no-direct-merge)

Before step 1, give the task a branch: when the work starts on the integration line, cut one from its head, named for the task's key, and run every step on it; work already on a branch of its own stays there, and on resume, a task whose branch exists checks it out instead of cutting another. A rework works on the branch of each request whose comments it answers or whose units it rebuilds. A follow-ups round cuts a fresh branch, named for the task's key and the round, `PROJ-88-round-3`: from the head of the topmost of the task's review requests still open, or, with none open, from the integration line's head. (basis: derived — commits added to a reviewed request would put its review on a head no one reviewed, and a merged branch carries nothing left to review)

When [open-the-review-request](open-the-review-request.md)'s How many requests ends a request and another unit follows, cut the next request's branch from the head of the one that ended, named for the task's key and the request's place in the stack, `PROJ-88-part-2`, and build the units that follow on it. On resume, check out the branch the latest unit built on, and in a rework or a revision, the branch of the request that carries each unit it rebuilds.

**Its name.** The names above are the fallback. When the repository records a branch-naming convention — in its instruction files or contributing guide, or as a preference in memory, as the brief's obligations carry it — every branch the task cuts follows it, with the task's key in it and a round's or a request's suffix after it, as `fix/PROJ-88-export-dates-part-2`. A convention that has no place for the key puts it right after the type prefix, before the description, and a description the convention asks for is taken from the task's title. Renaming a branch after its review request opened can close the request on some hosts, so the name is settled when the branch is cut. (basis: field findings, 2026-10-28 — a bare-key branch broke a recorded convention and its review request had to be reopened)

**The task's worktree.** Under the workspace's `files: worktree`, the task works in one worktree of its own, `.claude/worktrees/<key>`, holding whichever of its branches the step at hand works on: give the task its branch through [workspace](../../workspace/SKILL.md) (its key, the branch and the base it is cut from), which makes the worktree or switches it, enter it, and record its path in the act marker's `worktree` ([keep-the-act-marker](keep-the-act-marker.md)). On resume, re-entering it comes before the step it resumes at. A ship round gives it back from the branch of the request it ships when close-out removed it, switching it to each request's branch, base-most first, before that request lands. (basis: maintainer, 2026-10-14)

- **The user's own branch.** A task whose branch is checked out in the main checkout works in place there, since moving it would pull it from under the user; the proposal says so.
- **The user's own worktree.** A session already working in a worktree of the repository outside `.claude/worktrees/`, on the task's branch, uses it, recorded in the marker, and praxis never removes it.
- **One task per worktree.** A worktree belongs to the open task whose memory entry links its branch, or whose marker records it. A new task never adopts one that belongs to another: opened from inside one, it starts as if on the integration line, with its own branch and worktree.
- **Any checkout.** A task working in place or in the user's own worktree hands workspace that checkout's path, so its commands run there.
