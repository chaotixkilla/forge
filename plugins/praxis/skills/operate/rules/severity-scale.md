# The incident-severity scale

Every incident operate handles carries a severity, and severity is the dial the rest of the response turns on: it sets how fast and how widely you communicate ([right-sized-status-updates](right-sized-status-updates.md)), how aggressively you mitigate, and how high the bar sits for declaring the incident resolved ([remediate-and-verify](../phases/04-remediate-and-verify.md)). If the scale is undefined, each responder invents their own ladder — one calls a single-region latency bump "critical," another "minor," and the same incident gets two incompatible responses and two different update cadences. A severity assigned against no defined scale is not a lighter-weight triage; it is a triage whose most load-bearing output is left to chance. This rule pins the scale so two cold responders land the same incident on the same rung.

Severity is assigned in [assess-and-triage](../phases/01-assess-and-triage.md), and only *after* [real-signal-vs-flapping](real-signal-vs-flapping.md) has confirmed there is a real incident to rate — a flapping alert is stood down, not assigned a severity. It answers one question: **how badly is the user's ability to use the product affected, and how widely?**

## The three levels

`(basis: ratified by the maintainer, 2026-07-11 — the 3-level SEV1/SEV2/SEV3 house default, impact-keyed. There is NO cross-vendor authority for an operational severity scale: Google SRE deliberately publishes none (it uses declaration thresholds), and PagerDuty (5 levels), Atlassian (3), incident.io (3), and ITIL (5, impact×urgency) conflict on both the rung count and the definition of the top rung. So the ladder itself is the maintainer's ratified house standard; the discriminators and anchors below are sourced from the authorities' points of agreement — functional impact, user impact, and blast radius. When a project's runbook already defines a severity vocabulary, that wins over this default — see [match-the-runbook-conventions](match-the-runbook-conventions.md).)`

- **SEV1 — critical** — a core customer-facing capability is completely unavailable for all or most users, **or** confirmed data loss/corruption, **or** a security/privacy breach. No workaround; the product cannot be used for its primary purpose.
  - *Anchor (top of scale):* the primary API returns errors for every request — all users are locked out; or customer records have been irreversibly deleted; or an auth bypass is exposing one tenant's data to another.
- **SEV2 — major** — key functionality is broken or badly degraded, but the damage is bounded: a subset of users, or a non-core flow for everyone, with a painful-but-real workaround or partial availability. The product is impaired, not down.
  - *Anchor:* checkout succeeds but retries for ~10% of users on one payment method; or search returns results 5× slower than baseline for everyone while the rest of the app is fine.
- **SEV3 — minor** — minor or cosmetic impact with a ready workaround; users are largely unaffected and the fix can wait for business hours.
  - *Anchor (bottom of scale):* a secondary dashboard shows a stale timestamp; a layout glitch on a rarely-visited settings page.

## The adjacent-level discriminators

Assign by walking down from SEV1 until a level fits; the boundary tests are what stop an incident sliding between two rungs:

- **SEV1 vs SEV2** — is the impact *total and unworked-around* on a core capability (full outage of a primary flow, data loss, or a breach)? SEV1. Is it *bounded* — a subset of users, a non-core flow, or a real workaround exists — so the product stays usable? SEV2. (functional impact + blast radius + recoverability)
  - **Partial degradation of a core flow** (some requests fail, most succeed) is the case the round-up clause most often gets misapplied to, so pin it: the rung turns on **effective usability**, not the raw error fraction. If most affected users can still complete the action — a retry succeeds, a workaround exists — it is **SEV2** even on a revenue-critical flow. It rounds up to **SEV1** only when the failure rate is high enough that the capability is *effectively unusable* for **all or most users** — not merely a bounded subset, since a total failure confined to a small subset stays SEV2 by the blast-radius test above — or data-loss/breach is in play. An elevated error rate alone does not make a SEV1 — *effective unavailability* of a core capability, at scale, does. `(basis: derived from the impact-keyed ladder + PagerDuty's "product unusable / unable to use the product" gate for its top rungs — the top rung is effective unavailability, which keeps the round-up clause from firing on error percentage alone. Worked example: checkout errors at ~12% with retries succeeding → SEV2 (most users still complete); checkout failing for most attempts → SEV1.)`
- **SEV2 vs SEV3** — does a *real user on a path they actually use* hit *broken or badly degraded* behavior? SEV2. Is the impact *cosmetic or trivially worked around*, with users largely unaffected? SEV3. (functional impact + user impact)

When two levels both seem to fit, **round up** — but only if you can name the affected capability, the scope, or the user impact that justifies the higher rung; absent that concrete impact, drop a level. `(basis: PagerDuty and incident.io independently prescribe rounding up under uncertainty — "always assume the worst when uncertain between levels.")` A severity you cannot anchor to a concrete user-facing consequence is a guess dressed as a grade.

## Duration is a secondary axis — re-assess as the incident ages

Severity is not fixed at declaration. A lower-severity incident that **persists** or is **actively worsening** escalates: a SEV2 degradation that is still spreading an hour in, or a SEV3 that has begun affecting a core flow, is re-rated up, and the re-rating tightens the communication cadence with it. `(basis: Atlassian makes duration an explicit rung boundary; ITIL isolates urgency/time-sensitivity as an axis distinct from impact. Encoded here as a re-assessment trigger rather than a fourth level, to keep the ladder impact-keyed.)` Treat the severity set in triage as the *current* rung, and re-open it whenever the blast radius or duration changes materially.

## When the runbook defines a different scale

This 3-level ladder is the house default, not a mandate. If the project's runbook already runs on a different vocabulary — PagerDuty P1–P5, a 5-level SEV0–SEV4 with a public-comms-gated top rung, ITIL priority — **adopt the runbook's scale and its boundaries**, do not re-map it to SEV1–3 ([match-the-runbook-conventions](match-the-runbook-conventions.md)). The one genuine fork the authorities leave open is the **top rung**: whether SEV1 is earned by impact alone (this default, and Atlassian/incident.io) or additionally requires a public-notification / executive-liaison trigger (PagerDuty's SEV-1). This default keys the top rung to impact; a runbook that gates it on public comms is honored when present. Either way, the discriminators above — functional impact, blast radius, user impact — are what place the incident; only the labels and the top-rung gate change.
