An audit that starts before its surface is pinned wanders: it threat-models code that isn't under review, misses the entry point that is, and holds the subject to boundaries it never mapped. This phase fixes *what* is under audit and maps the surface every later phase reasons over — the entry points where adversary-controlled data enters, the trust boundaries it crosses, the assets worth protecting, and the reachable paths between them. Get the surface wrong here and every threat modeled downstream is scoped wrong; map it short and the hunt guesses where it should trace.

## Resolve the subject under audit

The subject is chosen by input, and the default frame is the whole subject, not a diff — security-review models a *surface*, and `--changed` narrows it:

- **Default — the whole subject the caller points at.** With no scope flag, audit the subject named in the invocation (a component, a module, a service, or the repository) as a complete surface: all its entry points and boundaries. This is the fresh-system / whole-component audit, and it is the default because threat modeling and the `--exhaustive` sweep are surface activities — "enumerate every entry point" is a statement about a system, not a diff. `(basis: the skill's own phase architecture — scoping a surface, modeling threats, enumerating entry points are whole-system activities; the change-scoped audit is the narrowed case, reached by --changed. This is the design call that distinguishes security-review from review, whose only subject is a diff. Ratified by the maintainer 2026-07-10, together with the ambient --changed model below: reading the local diff is plain git, not a vcs-port delegation — the port has no local-diff-read operation.)`
- **`--changed` — narrow to the working-tree change and its blast radius.** Restrict the surface to the diff against the derived base *plus what the change newly reaches*: the touched code, and the entry points and sinks that now connect to it. **Derive the base, never assume a name** — take the merge-base between the current branch and the repository's integration line (its default/integration branch: the remote's default head, or the local default branch when there's no remote), not a hard-coded `main`. Reading the local working-tree diff and deriving its base is **ambient** — it needs no configured backend, exactly as it is to review. (A change *hosted* on a version-control host, fetched by reference rather than read from the local tree, would be a vcs-capability delegation to the [vcs](../../vcs/SKILL.md) skill, which owns `tools.vcs` — but this skill takes no hosted-change flag; its `--changed` is the local tree.) Computing the blast radius — what the change newly reaches — is code-reading: recruit the **code explorer**, or trace it inline. When a target is *also* named (`<target> --changed`), `--changed` restricts to the diff *within* that target — the change intersected with the named surface — not the whole diff and not the whole target. `--changed` is a **scope-window input** to this phase, not a separable behavior — the phase always resolves *some* surface; the flag only selects which.

State which surface the run settled on (surfaced as the scope line in [reporting-findings](05-reporting-findings.md)), so the reader knows exactly what was — and was not — audited.

## Degrade and empty cases

- **No derivable base under `--changed`.** Reading the local diff is ambient, but it presupposes the subject *is* a version-controlled working tree with a derivable base. When none exists — a detached or root state, no resolvable integration branch, or a subject not under version control at all — security-review **degrades**: it cannot scope a change, so it audits the whole subject instead and says plainly that `--changed` could not scope a diff. It does not silently review a guessed window.
- **`--changed` with an empty change window.** When `--changed` resolves to no diff — a clean working tree against the derived base — there is no change to audit, whether or not a target was also named. Stop and redirect: drop `--changed` and name a target for a whole-subject audit, or make the change first — rather than inventing a surface, auditing an empty window, or silently auditing the whole target (which answers a different question than `--changed` asked).

## Map the surface: entry points, boundaries, assets

With the subject resolved, map the surface the hunt will navigate — recruit the **code explorer** to locate the entry points (where external data enters), the sinks (interpreters, file paths, privileged actions, responses), and the reachable paths between them; recruit the **repository explorer** for history near the surface (a prior security fix, a known-weak area, a revert that explains an odd guard). Without fan-out, do these reads inline before proceeding — the reads are not optional, only the delegation is.

Record the surface as three things, because the later phases navigate by them, not by file list:

- **Entry points** — every place adversary-controlled input crosses into the subject.
- **Trust boundaries** — where data or control passes between differently-trusted parties, per [trust-boundaries-over-features](../rules/trust-boundaries-over-features.md); the hunt is prioritized by these.
- **Assets** — what is worth protecting behind those boundaries (the data, the privileged actions, the secrets), read against how the project already defends them ([match-the-projects-security-posture](../rules/match-the-projects-security-posture.md)).

## Set the breadth: the default subset versus `--exhaustive`

How much of the surface to enumerate is a breadth dial, and `--exhaustive` sets it (a phase input — the phase always maps *some* breadth):

- **Default — the high-likelihood subset.** Map the entry points and boundaries where adversary-controlled data most plausibly reaches a dangerous sink: the externally-reachable edges, the privilege and tenant crossings, the sinks the project's own posture treats as sensitive. The discriminator for "in the subset": **is there a plausible adversary-controlled path to a sink of consequence here?** — enumerate those first and deepest.
- **`--exhaustive` — every entry point, every threat class.** Trade speed for completeness: enumerate *all* entry points and carry *every* threat class against each in [hunting-vulnerabilities](03-hunting-vulnerabilities.md), including the low-likelihood combinations the subset skips. This is the high-assurance pass; it is slower by design.

## State the scope boundary

Close the phase by stating what is in scope and what is not — the surface under audit, the window (`--changed` or whole-subject), the breadth (default or `--exhaustive`), and anything deliberately excluded (generated code, vendored dependencies audited elsewhere, a bundled but unrelated change). **How much surface is enough is deliberately open** — *pinning a fixed count would be false precision: a leaf utility needs its handful of callers mapped, a public API needs every route, and only the subject in front of you says which.* The stopping test bounds the openness: **stop mapping when you can name every place adversary-controlled data enters and every sink of consequence it could reach, and mapping one more file would not change which threats you model.** A stated boundary is what stops a later phase from auditing past the mandate — and what makes the audit's silence legible.
