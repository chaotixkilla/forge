Usage & examples — when to reach for this skill, and concrete invocations: see [usage.md](usage.md).

A thin port over where a task's work happens: its files, in a worktree of the repository, and its runtime, in the project's containers or on the host. It names the capability; the configured container runtime's adapter holds the concrete calls. Callers name the operation they need; this skill resolves it.

1. Resolve the workspace: read `tools.workspace` (its shape below) — the provider and transport, `files`, `commands`, and what init learned of the project. **Host mode** is `commands: host`, or `commands: container` with no `setup`, or a disabled slot or no config at all, where work also runs in place. Every result says so, for the caller to note once in the task's proposal: host mode isolates nothing, and the project's code reaches whatever its own environment points at. `(basis: maintainer, 2026-10-13)`
2. Take the requested operation and its inputs from the caller. Every operation but the three lists takes the task key and, for a task working in place or in the user's own worktree, that checkout's path, which then stands for the task's worktree. Names below use `<repo>`, the main checkout's folder name, and `<key>`, the task key, each lowercased with every character outside `a-z0-9-` made a hyphen.
   - **Make a task's worktree** (task key; a branch and the base it is cut from, or a commit alone): at `.claude/worktrees/<key>` in the main checkout. `(basis: maintainer, 2026-10-14)` Fetch first; when the remote can't be reached, go on from local refs and say so. A new branch is cut from the base's remote-tracking head, or from its local head when the base is one of the task's own branches the remote doesn't have yet; a branch that exists locally or only on the remote is checked out as it is. A commit alone makes a detached worktree at it, whatever `files` says, since a tree read at an exact commit is never the user's checkout; the result names that commit as where the worktree was made. Git's own output is never shown, so no commit subject is printed. Copy in each of `env_files` present in the main checkout, noting any missing; a run copies one again when the main checkout's is newer. A `.claude/worktrees/<key>` that exists is the task's: it is switched to the requested branch or commit when git switches it without force, else **refused** with what holds it. A branch checked out in another worktree returns that worktree. **Refused**: a branch checked out in the main checkout, which is the user's. Under `files: in-place`, a branch gets no worktree and the current checkout is returned.
   - **Enter it** (task key): move the session into the worktree through the harness's worktree switch when it can enter an existing worktree, else return its path for the caller to work by. `(basis: maintainer, 2026-10-14)` Under `files: in-place`, nothing moves.
   - **List the task worktrees** (optionally, the integration line): those under `.claude/worktrees/`, each with its branch, whether git would remove it without force, whether it is pushed, and, given the integration line, whether it is merged.
   - **List every task's environment** (no task key): each task with resources in this repository, by its key: its containers and own instances with their states, and any volumes or network left without them, and when its environment record was last written.
   - **List or remove the unused shared pieces** (optionally, the pieces to remove): the images and dependency caches made for this repository that no task's container uses and that the main checkout's and every task worktree's current build files and lockfiles no longer key. Removing one in use by then is **refused**.
   - **Remove a task's worktree** (task key, the integration line, whether its review request merged, the commit it was made at when it was made at one): only when its branch is pushed, merged, or still at the commit it was made at — a detached worktree holds no branch, so it loses no commit — and git removes it without force — which refuses modified tracked files and untracked files git doesn't ignore. The branch is kept. **Pushed**: after a fetch, its tip is contained in its remote-tracking branch. **Merged**: its tip is contained in the integration line's remote head, or the caller says its review request merged, which covers squash merges. A remote that can't be reached leaves both unproven: **unavailable**. A session inside it leaves it first. `(basis: maintainer, 2026-10-14; the definitions derived from what loses no commit)`
   - **Run a command** (task key; a recipe name and any arguments it is given, or a command and the folder it runs from; whether it installs or changes dependencies): whatever the project's tooling runs runs in the task's containers — tests, builds and type checks, linters and formatters, code generation, scratch scripts, dependency installs, migrations. git, the hosting CLI, file reads and edits, logins, secret pulls and the browser stay on the host; git hooks run where git runs them. `(basis: maintainer, 2026-10-13)`
     - *Where:* a recipe names its service; a bare command runs in the service whose `root` holds its folder, the longest match winning, an `app` before other kinds on a tie, then the first listed; with none it is **permanent**. The worktree's `root` folder is mounted at the service's `mount`, in place of the definition's own mount of it, and the command runs at `mount` plus its folder's path below `root`; a recipe runs at `mount`, any path in its arguments read relative to the service's `root`. A service with no `mount` can't run the task's code: **permanent**.
     - *What it reaches:* its environment carries every service's `reach` entries filled for the task — `{host}` its own instance where it has one, started first if stopped, else the shared server, and for an `app` or `worker` service the task's own container by its alias `praxis-<repo>-<key>-<service>` (in an own full stack, the service's own name), never the shared one; `{published}` the host address `localhost:<port>` the task publishes for that service, for what a browser or other host-side client follows; `{name}` the task's namespace; each `${VAR}` the value of that variable in the task's env files. Every `reach` variable is set by the port, over any value the env files give it, so the app never reads its own default; a `${VAR}` the env files don't set fails the run as **permanent**, naming it. Each service a recipe `uses` is the task's own, made first: its namespace when its kind is `database`, `prefix` or `bucket`, else its own instance, so a recipe never writes to a shared server. A recipe that is itself a namespace's `setup` runs once when that namespace is first made. A bare command gets the task's namespace made first in every service with a namespace kind, as a recipe's `uses` does. `(basis: derived from the shared-infrastructure guarantee)`
     - *A first run proves it:* a recipe or service marked `unproven` that fails on its environment — the command or its dependencies not found, a connection or permission refused, before the project's own code loads — is re-derived once from the adapter's description of the setup and run again. Re-derivation checks, in order, that the mount puts the code where the service runs it, that no dependency path is hidden by it (a hidden one joins `caches`), that the entrypoint runs a given command (else it becomes the image's shell, as the adapter reports it, given the whole command as one string to run), and that the command is the one the main checkout's CI runs; it changes the first mismatch, never adding an install step to the command. Only a mark reading `not yet run` is re-derived. A run that loads the project's code, passing or failing on it, saves the change in `tools.workspace` (mount and caches on the service, entrypoint and command on the recipe) and clears the mark on the recipe, its service and the services it used (one marked for a missing variable clears only once that variable is set); a second failure keeps the original, sets the recipe's mark to `re-derivation failed:` and what was tried, which stops further re-derivation until init re-learns it, and comes back **permanent**, for the caller to report and the user to fix through init. The first start of an unproven app proves it the same way; the first namespace or instance made on an unproven data service proves it, a failing `create` re-derived once from the server's client tool and its documentation. A task with its own full stack re-derives against its worktree's definition and saves nothing to the slot. A failure inside the project's own code is a result. `(basis: maintainer, 2026-10-14; one re-derivation, since a second failure means the derivation, not a detail, is wrong)`
     - *Leaves nothing behind:* files a run writes into the worktree that git neither tracks nor ignores, such as caches the tooling writes through the mount, are named in its result, and removed unless the caller's step made them on purpose, so the worktree stays removable without force.
     - *Returns* the exit status, how long it ran, and the last 200 lines of output, the whole output saved in the task's runs folder, the main checkout's `.claude/praxis/runs/<key>/`, with its path returned; a nonzero exit is a result, not a failure. `(basis: derived — enough for a failure's trace without flooding the caller)`
     - *In host mode* it runs in the worktree, as the user would, reaching what the user's own environment points at, with no namespace made; a `migrate-` recipe or a namespace's `setup` recipe is **refused**, since its purpose is to change the schema or data and on the host it would land on the shared default. `(basis: maintainer, 2026-10-14)`
   - **Start, stop or list a task's services** (task key, service names): the task's app and worker containers, built and wired as a run is, the task's namespace made first in every service with a namespace kind, and any of its stopped instances started. Each published port is a free port the OS hands out, never one the shared stack's definition publishes nor one another task's containers hold, as the adapter reports them, allocated for every app and worker on the task's first container operation and kept for the task's life in its environment record, so `{published}` is filled before anything starts; a collision when it starts is retried once on a new port, recorded, and the containers reaching it recreated. `(basis: derived — the dev stack keeps its defaults, and tasks must not collide)` Returns each one's name, state and ports. Some failing to start comes back **partial**, with the ones started; none is rolled back.
   - **Give a task its own namespace or instance** (task key, service, or the whole stack; optionally fresh, dropping and remaking a namespace the task already has): which one follows from what the task does, the caller choosing by this table. `(basis: maintainer, 2026-10-14)`

     | What the task does | What it gets |
     |---|---|
     | Migrations, seed or test data in a database server | Its own database on the shared server |
     | Cache or queue keys | Its own key prefix |
     | Files in object storage | Its own bucket |
     | A server-wide schema deploy (such as a search engine's) | Its own instance of that service |
     | A server's version, config or extensions | Its own instance of that server |
     | The dev stack's definition or a service's container build | Its own full stack, from the definition in its worktree |
     | Background jobs a shared worker would run | Its own instance of the worker |

     A namespace is `praxis_<repo>_<key>` with hyphens made underscores, `praxis-<repo>-<key>` for a bucket, cut to 63 characters, the tightest common limit on database identifiers and bucket names; a namespace with the task's name is the task's. It is made by the service's `create` command (a `prefix` needs none) and set up by its `setup` recipe once, when first made; making one that exists returns it. An own instance, and each server in an own full stack, runs on the task's own data, never a shared volume, holds the task's namespace too, and is set up the same way; the task's running app and worker containers are recreated, removed and started again with their environment filled afresh, so they reach it. A setup that fails leaves what was made, returned **partial**.
   - **Stop a task's environment** (task key): stop its containers and own instances, keeping their data and its namespaces.

   **The environment record.** `environment.json` in the task's runs folder holds `ports` (each service's allocated port), `state` (`running` while any of its containers or instances runs, else `stopped`) and `updated` (a UTC time, ISO 8601), written by every operation that allocates, starts or stops, and `updated` rewritten by every other operation on the task, runs included, so a task at work never reads as idle; the session-start hook reads it to tell which tasks hold an environment.
   - **Tear a task's environment down** (task key): remove its containers, own instances and their data, drop the task's namespace in every service with a namespace kind on the shared server, before removing containers (an own instance's goes with its data); remove its network and its runs folder. Every piece is attempted; what is already gone counts as done; what stays comes back **partial**, each piece with where it is and why. The worktree is removed separately, by its own rule.

   A task's containers are its own, never the dev stack's, and a resource is the task's only when it carries both the task and the repository; a name taken by something else is **refused**. The setup's definition is read from the task's worktree, so a task's change to it is exercised. A task with its own full stack runs and starts within that stack. The task's network is made on its first container operation and removed at teardown. A shared server an operation needs that isn't running is **unavailable**, with which: the dev stack is the user's to start. A `container-build` setup has no shared servers and a `dev-environment` setup no services, so the operations needing them, own full stacks included, are **unsupported** there.
3. Dispatch: worktree operations are local git — praxis's declared local version-control substrate `(basis: maintainer, 2026-10-01)` — and the harness's worktree switch, needing no adapter; container operations go to the adapter for the configured runtime, the concrete calls in adapters/&lt;runtime&gt;. In host mode any container operation but a run is **unsupported**: nothing is started, and the caller carries on without isolation.
4. Return the result, saying where it ran (the worktree or in place; a container or the host, and why), with every namespace and instance it made and every port it published, for the caller to show; beyond the environment record, nothing needs recording, since a task's resources are found by its key. Or a capability-level failure, never a raw tool error, as a cascade where the first "no" wins: can this mode and setup do it at all? (no → **unsupported**) is the runtime, the shared server or the remote reachable? (no → **unavailable**; never a silent fall back to the host) does the named worktree, recipe, service or namespace exist? (no → **not-found**) did a transient fault stop it? (yes → **retryable**) is the request invalid as asked? (yes → **permanent**, the caller must change it) would it break a guarantee? (yes → **refused**, with which) did all of it complete? (no → **partial**, each part's outcome listed). `(basis: derived from the other ports' cascades, with unsupported first since no retry or change of request helps)`

**The guarantees.** A task never changes, starts, stops, restarts or reconfigures shared infrastructure, and touches only resources that are its own. A worktree git won't remove without force is never removed. No container definition is ever written into the project. A secret in an env file is copied into the worktree, never printed or recorded.

## The slot

`tools.workspace`, as init writes it, keyed by the definition's own service names:

    {"files": "worktree", "commands": "container", "provider": "<runtime>", "transport": "cli",
     "setup": {"kind": "dev-stack", "definition": ["<files>"], "context": "", "lockfiles": ["<files>"],
               "target": "", "project": "<the dev stack's project name>", "network": "<its network>"},
     "env_files": ["<file>"],
     "services": {"api": {"kind": "app", "root": "api/", "mount": "<path>", "caches": ["<path>"]},
                  "db": {"kind": "database", "namespace": "database",
                         "create": "<command, {name}>", "drop": "<command, {name}>", "setup": "migrate-api",
                         "reach": {"<VAR>": "<scheme>://<user>@{host}:<port>/{name}"}}},
     "recipes": {"test-api": {"service": "api", "command": "<test command>", "entrypoint": "", "uses": []},
                 "migrate-api": {"service": "api", "command": "<migrate command>", "entrypoint": "", "uses": ["db"],
                                 "unproven": "not yet run"}}}

- `files`: `worktree` or `in-place`. `commands`: `container` or `host`.
- `setup.kind`: `dev-stack` (a multi-service definition), `dev-environment` (a development-environment definition), or `container-build` (one container build file). Paths are relative to the repo root: `definition` lists the setup's files, `lockfiles` the dependency lockfiles its builds depend on; for a container build file, `context` the build context (empty: the repo root) and `target` a build stage. A setup that defines no services has one, `app`, holding the whole repository. `project` and `network` are the dev stack's own, as it runs.
- `env_files`: gitignored files the project's setup reads.
- `services`: `kind` is `app` (built from or binding the repository's code, serving), `worker` (the same, running background jobs), `database`, `search`, `cache` or `storage` (a data service, by what it stores), or `other`. `root` is the repo folder the service holds (empty: the whole repo) and `mount` where it holds it, empty when its code is baked into its image. `caches` lists the paths where the service holds installed dependencies, shared by every task with the same lockfiles; its other volumes are data, each task's own. `namespace` is the kind of namespace a task gets on it: `database` for a server that holds separate databases, `prefix` for one keyed by name prefixes with no server-wide schema (nothing to make), `bucket` for object storage, `none` for a server whose schema is deployed server-wide, so a task changing it gets its own instance. `create` and `drop` make and remove a `database` or `bucket` namespace, and `drop` may remove a `prefix` one's keys (without it, teardown reports the keys left); `setup` names the recipe that prepares a new one. `reach` maps each environment variable an app reads to reach the service, its value a template over `{host}`, `{name}`, `{published}` and `${VAR}`; a credential in it is a `${VAR}` reference to an env file, never a value.
- `recipes`: named `<purpose>-<service>` (purposes `test`, `lint`, `migrate`, and the generators a documentation kit runs — `schema`, `contract`, `graph`, `coverage`, `bench`, `visual`; a second suite of one purpose adds its name, `test-api-integration`), each with `service`, `command`, `entrypoint` when the service's own ignores commands, and `uses`, the services whose namespaces the command needs made.
- `unproven`, on a recipe or service: one of `not yet run`, `missing variable <VAR>`, or `re-derivation failed: <what was tried>`, removed once a run proves it.

**`--dry-run`** runs steps 1–2 and stops: it returns the operation that would be performed, the provider and transport it would reach and where it would run, and performs nothing.
