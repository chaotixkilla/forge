# docker — workspace adapter

Implements the **workspace** capability's container operations for the Docker runtime, over its command-line interface (`tools.workspace.transport: cli`): the `docker` CLI with its `compose` plugin, and the `devcontainer` CLI for a `dev-environment` setup. The [workspace](../SKILL.md) skill names the operation, resolves the task's names, ports and environment, and dispatches here. Resolve exact flags against the live CLI at call time (below) — the names here are not frozen.

## A task's resources

Everything made for a task carries the labels `praxis.task=<key>` and `praxis.repo=<main checkout path>` — except shared cache volumes and `praxis-<repo>` images, which carry `praxis.repo` only, since no one task owns them — and containers `praxis.ports=<published ports>`; a resource is the task's only when both labels match. Names start `praxis-<repo>-<key>`: the compose project, the network, `praxis-<repo>-<key>-<service>` for a started service or own instance and its alias on the task's network, `praxis-<repo>-<key>-<volume>` for a data volume.

**The task's overlay.** For a `dev-stack` setup, every task command uses the worktree's definition files plus an overlay this adapter writes outside the repository, at `${CLAUDE_PLUGIN_DATA}/stacks/<repo>-<key>.yml`, under the project name `praxis-<repo>-<key>`:

- each service's fixed `container_name` cleared (`!reset`), and the task's labels added; each built service's `build.labels` given `praxis.build=<hash>`, the hash below, an image without that label counting as changed;
- the task's network joined, and the dev stack's network (`setup.network`, declared external) joined too when it exists, so shared servers answer by their service names; when it doesn't, an operation that needs a shared server is *unavailable* and the rest go on without it;
- each service's whole `volumes` list rewritten (`!override`): the worktree's `root` at `mount` in place of the definition's bind of it, a volume `praxis-<repo>-<service>-<path>-<lock>` at each `caches` path, `<path>` made lowercase `a-z0-9-` and `<lock>` the first 12 hex characters of the SHA-256 over the task worktree's `lockfiles` bytes in listed order, separated by NUL bytes, so a task that changes them gets a cache of its own; a run the skill says installs or changes dependencies, and every run while the worktree's lockfiles differ from the main checkout's, mounts the task's own volume `praxis-<repo>-<key>-cache-<path>` instead, so it never writes into a shared cache; each other named volume as the task's, other binds kept;
- an own instance's service on the task's network only;
- for an own full stack: every service in the worktree's definition (as `compose config` lists it, the slot's entry used where it has one), on the task's network only, each fixed network `name` cleared too, and each published port replaced (`!override`) by one the skill allocated.

`!reset` and `!override` need Compose 2.24 or later; an older Compose makes every dev-stack operation **unsupported**, with that reason. External networks and volumes the definition names, other than the dev stack's own network, are **refused** in a full stack: they are shared.

## Operations

1. **Run a command** — `docker compose -p praxis-<repo>-<key> -f <definition files> -f <overlay> run --rm --no-deps` of the service, `-w` at the working directory the skill resolved, the recipe's `entrypoint` as `--entrypoint` when set, the skill's environment as `-e` entries, and `--build` when the service's build file or lockfiles in the worktree changed since its image was built, which the image's `praxis.build` label (the first 12 hex characters of their SHA-256) records. For `container-build`: build the definition's `target` stage once per state, from `context`, tagged `praxis-<repo>:<hash>` and labelled `praxis.repo`, `<hash>` the first 12 hex characters of the SHA-256 over the build file's bytes, each lockfile's bytes in listed order, and the `target`, separated by NUL bytes; then `docker run --rm` it with the worktree's `root` at `mount`, each `caches` volume at its path, `-w`, `--entrypoint` and `-e` as above, on the task's network. For `dev-environment`: `devcontainer up` with the worktree as the workspace folder, the task's labels as `--id-label`s and the environment as `--remote-env`s, then `devcontainer exec` the command in it.
2. **Start, stop or list services** — *start:* as a run but detached (`-d`), named, and without `--rm`, so stopping keeps it; each port the service's definition publishes (its container side) published with `-p` to the port the skill allocated, never the definition's own host ports; labelled with its ports. A stopped container of the task is started instead, unless its environment would now be filled differently: it is then removed and started afresh. *recreate:* the same, for running app and worker containers, when an own instance appears. *stop:* `docker stop` the task's containers. *list:* `docker ps -a` by the task's labels: each one's name, state and published ports. *every task:* `docker ps -a`, `docker volume ls` and `docker network ls` by the `praxis.repo` label alone, grouped by `praxis.task`. *taken ports:* every `praxis.ports` label of another task across `docker ps -a`, and the ports the dev stack publishes, from the main checkout's definition as the user runs it.
3. **Namespaces** — run the service's `create` or `drop` command, `{name}` filled, inside the server the task reaches: the dev stack's container for the service (found by `setup.project` and the service name), or the task's own instance, through `docker exec`, retrying while the server isn't yet accepting connections, for up to 60 seconds, then *retryable*. "Already exists" on create returns it; "doesn't exist" on drop counts as done.
4. **An own instance** — start the service like an app, detached, on the task's network only, with no published port, its data on the task's volumes, aliased `praxis-<repo>-<key>-<service>`, which the skill puts in `{host}`. A stopped one is started instead.
5. **An own full stack** — `docker compose -p praxis-<repo>-<key> -f <definition files> -f <overlay> up -d`, the overlay in its full-stack form; `{host}` is then each service's own name on the task's network.
6. **Stop the environment** — `docker stop` every container with the task's labels.
7. **Tear down** — first drop the task's namespace in each service with a namespace kind (operation 3), on the dev stack's server, an own instance's going with its volumes; then `docker compose -p praxis-<repo>-<key> down -v`, which removes a full stack and does nothing without one; `docker rm -f` every remaining container with the task's labels; remove the overlay file; `docker volume rm`, `docker network rm` and `docker image rm` everything with the task's labels or its project's name. Images tagged `praxis-<repo>` and shared cache volumes are kept for other tasks.
8. **Describe the setup** (for init, and to re-derive an unproven recipe) — `docker compose config --no-interpolate` over the main checkout's definition files, never printing an env file's values, only its variable names, the task stacks labelled as praxis's left out, giving each service's binds of repository folders and where, its named and anonymous volumes and their paths, its published ports, its env-file entries and environment, its build context and stage and the lockfiles its build copies, its entrypoint, whether that runs a given command, and the shell its image provides, and the stack's project name and networks as the definition names them, else as the runtime derives them from the main checkout's folder, read without querying the runtime; for a container build file, read from the file, the `target` stage's working directory, entrypoint and shell, the lockfiles it copies and the paths it installs dependencies into; for a development-environment definition, its workspace folder.

9. **Unused shared pieces** — among images tagged `praxis-<repo>` and volumes named `praxis-<repo>-<service>-<path>-<lock>`, the ones the skill's rule leaves, use read from `docker ps -a --filter ancestor=` and `--filter volume=`, and the hashes as above; on request `docker image rm` and `docker volume rm` without force, so one in use by then fails as **refused**.

## Failure surface

Report failures upward in capability terms — the caller hears an outcome, never a CLI's error text:

- **Compose older than 2.24** → *unsupported*, with the reason.
- **No `docker` CLI on the path, or its daemon not running (`Cannot connect to the Docker daemon`); the dev stack's container for a needed service not running** → *unavailable*, with which.
- **No such service in the definition, no such container, network or recipe for the task** → *not-found*.
- **An image pull or registry call that times out, a busy daemon, a port already bound when a container starts** → *retryable*.
- **A recipe or entrypoint the service doesn't have, a malformed command, a build that fails** → *permanent*, with the build's or command's last lines.
- **A name taken by a resource without both of the task's labels; an external network or volume in a full stack** → *refused*, with the reason.

## Call-time discovery

The CLI's surface shifts between releases: confirm the current flags of `compose run` (naming, labelling, publishing a port with `-p`, never `--service-ports`), how `compose config` prints a service's mounts, ports and networks, the overlay tags `!reset` and `!override` against the installed Compose, the label filter syntax of `ps`, `stop`, `rm`, `volume rm` and `network rm`, and the `devcontainer` CLI's `up`, `exec`, `--id-label` and `--remote-env` options when you call them.
