# github — vcs adapter

Implements the **vcs** capability for GitHub, over the transport configured in `tools.vcs.transport` (cli, api, or mcp). The [vcs](../SKILL.md) skill names the operation and dispatches here. Resolve exact field/flag names against the live tool at call time (below) — the names here are not frozen.

## Operations

1. **Fetch a change** — given a pull request reference (number), retrieve the unified diff plus the PR title, body, base/head refs, and the change-size metadata the caller cross-checks against (changed-file count, and additions/deletions where available).
   - *cli:* the GitHub CLI's PR view/diff commands (request the diff and the metadata fields the caller needs, including `changedFiles`). *api/mcp:* the pull-request read + files/diff endpoints for the repo and number.
   - *With the description held back*, return the diff, the base and head commits, the head branch, the author and the size metadata only, and never request the title or body. *cli:* name only those fields in the PR view request. *api:* select only those fields (a GraphQL pull-request query takes a field list; the REST diff media type returns the diff alone). *mcp:* only through a read the server offers that leaves the body out; without one, this is the failure below, never a full read with the body ignored.
2. **Materialize a change** — given a pull request reference, check its **current head** out into an **isolated working copy** (a worktree) so the caller can read definitions, call sites, and invariants at the reviewed revision without disturbing the user's working tree. Return the working-copy path; the caller discards it when done.
   - *cli:* fetch the PR head and add a detached worktree at it (the GitHub CLI's PR-checkout into, or combined with, a `git worktree` at the fetched head). *api/mcp:* resolve the head SHA from the remote's pull-request head ref (`refs/pull/<number>/head`) rather than from a pull-request read, which carries the body; fetch that ref and add a worktree at the SHA. Materializing never reads or returns the description. Materialize the head the fetched metadata reports — never a pre-existing local branch of the same name, which may lag a force-push.
3. **Post a review summary** — add the caller's summary text to the pull request as a review carrying the caller's **stance** (comment-only, approve, or request-changes — see the stance note below), submitted against the caller's commit when it names one, else the head.
4. **Post inline feedback** — attach each item as a review comment anchored to its file and line on the PR's diff at the caller's commit, else the head, submitted as a single review carrying the caller's **stance**, so they post as one batch, not N notifications.
5. **Set a status** — set a commit status / check-run on the head ref reflecting the caller's pass/fail verdict, so the platform's merge protection can read it. This is best-effort: a failed status post is reported upward but never fabricates or changes the caller's verdict.

6. **Push a branch** — publish the local branch to the remote, setting its upstream. Never force-push: a rejected push (the remote moved) is reported, so the caller reconciles, never overwritten.
   - *cli:* a plain `git push` with upstream tracking (pushing is git itself, whichever transport serves the rest). *api/mcp:* the same local push; the API has no push of local commits.
7. **Open a review request** — open a pull request from the head branch onto the base, with the caller's title and description, and request review from the caller's reviewers. Return the request's number and link. A request already open for the same head is returned as-is, never duplicated.
   - *cli:* the GitHub CLI's PR-create command, then its reviewer-request flag or edit. *api/mcp:* the create-pull-request endpoint, then the request-reviewers endpoint.
8. **Update a review request's description** — given a pull request number, replace its body with the caller's, leaving its title. Return the number and link.
   - *cli:* the GitHub CLI's PR-edit command with the body. *api/mcp:* the update-pull-request endpoint with the body field.
9. **Read a review request** — given its number, or a head branch (the open request whose head it is; none open is *not-found*), return its base branch, its state (open, merged, closed), whether it is approved and by whom, any changes requested, and the review feedback on it: each review's summary, in submission order, with its id, its link, its author, its state as the stance (`COMMENTED` → comment-only, `APPROVED` → approve, `CHANGES_REQUESTED` → request changes) and its commit; each inline comment with its id, its link, its author, file and line, the commit it was posted on, the id of the comment its thread began with (its `in_reply_to`, or its own id), and whether its thread is resolved; each conversation comment with its id, its link, its author and its body; each review and comment also with its body as text; and the authenticated account's login as the account the port posts as. A review's commit is the one it was submitted against; an inline comment's is its original commit, never the later one GitHub moves a still-applicable comment to.
   - *cli:* the GitHub CLI's PR-view with the review and comment fields, plus the review-comments API for inline threads. *api/mcp:* the pull-request read, the list-reviews endpoint, the list-review-comments endpoint, and the issue-comments list for the pull request's number; thread resolution through the review-threads read.
10. **Reply in a review thread** — given a pull request number and a review comment's id, post the caller's text as a reply in that comment's thread. Return the reply's link.
   - *cli/api/mcp:* the reply-to-review-comment endpoint for the repo, number and comment id (the CLI through its API passthrough).
11. **Post a comment** — given a pull request number, post the caller's text as a conversation comment, outside any review. Return its link.
   - *cli:* the GitHub CLI's PR-comment command. *api/mcp:* the issue-comments endpoint for the pull request's number.
12. **Request review again** — given a pull request number and reviewers, request their review again. A reviewer who already reviewed is asked anew. Return the reviewers asked.
   - *cli:* the GitHub CLI's PR-edit with its add-reviewer flag. *api/mcp:* the request-reviewers endpoint.
13. **Compare two commits** — given two commits of the repository, return the host's link to the diff from the first to the second. Nothing is read or written.
   - *cli/api/mcp:* the repository's compare link, `<repo>/compare/<from>...<to>`.
14. **Read what a review request builds on** — given a pull request number, return the numbers of the open pull requests it builds on, nearest first: its base branch is another open pull request's head, that one's base in turn, and on until a base is the head of no open pull request, which ends the chain. A base that is the head of several open pull requests, or of one already returned, ends it too. (basis: derived — which of several it builds on can't be told, and a loop would never end) A pull request that builds on none returns an empty list. Read only each pull request's number and its base and head branches — never a title, body, review or comment.
   - *cli:* the GitHub CLI's PR view and PR list (filtered by head branch and open state), naming only those fields. *api:* select only those fields (a GraphQL pull-request query takes a field list; filter open pull requests by head branch). *mcp:* only through a read the server offers that leaves the body out; without one, this is the description failure below, never a full read with the rest ignored.
15. **Read a landing constraint** — given a target branch, return whether it requires an approved review (and how many approvals), which status checks must pass, and whether it blocks direct pushes, from the branch's protection rules and rulesets. A branch with no protection returns "no constraint", never an error.
   - *cli/api/mcp:* the branch-protection and rulesets reads for the branch; a protection the token may not read is the *not authenticated* failure below, never "no constraint".
16. **Merge** — merge an approved review request, or a branch onto its target, by the caller's strategy: merge commit, squash or rebase, with the caller's message as the subject and body of the commit the merge or squash makes; a rebase makes none, so its message isn't used. Merge only what protection allows; never use an admin bypass or force past a required review or check. Return the merged commit.
   - *cli:* the GitHub CLI's PR-merge with the strategy flag and its subject and body flags (or a plain `git merge` with the message, and push, for a branch with no request). *api/mcp:* the merge-pull-request endpoint with its merge method and commit title and message.
17. **Change a review request's base** — given a pull request number and a branch, make that branch the pull request's base. Return the number and link.
   - *cli:* the GitHub CLI's PR-edit command with its base flag. *api/mcp:* the update-pull-request endpoint with the base field.

**The review stance (operations 3 and 4).** GitHub requires every review submission to declare an event — one of `COMMENT`, `APPROVE`, or `REQUEST_CHANGES`; there is no "just attach comments" call that omits it. The caller passes a capability-neutral **stance** and this adapter maps it: *comment-only* → `COMMENT`, *approve* → `APPROVE`, *request-changes* → `REQUEST_CHANGES`. The caller decides the stance; the adapter never invents one, and never posts through a raw API call that bypasses this operation.

## Failure surface

Report failures upward in capability terms — the caller hears an outcome, never a raw HTTP code:

- **Not authenticated / token missing or lacking scope** → report as "vcs backend unavailable," which the caller's degrade path handles (and which the [vcs](../SKILL.md) skill maps to guiding the user through `init:vcs`).
- **PR or repo not found / wrong repo context** → report "the requested change was not found on the configured provider" rather than a 404; do not fall back to a different change.
- **Rate-limited or transient network failure** → report as a *retryable* vcs failure, distinct from a permanent one, so the caller can back off or degrade.
- **Description can't be held back** (a transport whose only pull-request read returns the body) → report that the change can't be fetched, or what it builds on read, without its description, so the caller can stop rather than read it.
- **Builds-on read cut short** (a read after the first fails) → report it as partial, returning the pull requests read so far and what stopped the next.
- **Inline anchor rejected** (a comment on a line outside the diff hunks) → report which items could not be anchored, so the caller can fold them into the summary rather than dropping them.
- **Merge refused** (protection requires a review or a check the change lacks, or the request isn't mergeable — a conflict, a stale head) → report which requirement refused it, so the caller stops at the right outcome; never retry with a bypass.
- **Push rejected** (the remote moved since the branch was last fetched) → report it as needing a reconcile, never resolve it by forcing.

## Call-time discovery

GitHub's surface shifts (flag names, endpoint shapes, review-submission payloads), so name the operation and its purpose here and resolve the exact parameters when you call: confirm the current diff-fetch flags, the review-comment payload shape (path + line + side for inline), the reply and conversation-comment endpoints, the check-run vs commit-status choice, the PR-create, PR-edit and merge flags, and the protection and rulesets reads against the live CLI/API at call time.
