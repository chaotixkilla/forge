# The verdict scale

Every spike ends in one judgment: did the probe answer the question it was built to answer? That verdict is prototype's whole output — the code is thrown away, so the verdict *is* the deliverable. If the scale is undefined, each executor invents its own bar: one calls a promising-but-stubbed run a success, another calls the same run inconclusive, and the same spike unblocks a decision for one caller and blocks it for another. A verdict with no defined scale is not a lighter-weight spike; it is a spike whose single load-bearing judgment is left to chance.

The verdict answers one question: **did something actually run and observe the framed unknown, and which way did it point?** It rests entirely on observed behavior, never on reasoning about the code ([ground-claims-in-a-run](ground-claims-in-a-run.md)); how far the result generalizes beyond what ran is a separate axis ([keep-the-real-thing-in-view](keep-the-real-thing-in-view.md)). It is assigned in [evaluate-against-the-question](../phases/05-evaluate-against-the-question.md), consumed by [capture-and-discard](../phases/06-capture-and-discard.md) (it leads the findings blob) and by the [parallel-fan-out](../modules/parallel-fan-out.md) module (raced approaches are compared verdict-first).

**The verdicts are asymmetric, by their epistemics.** A run can *refute* conclusively — one genuine counter-instance is enough to kill an assumption — but it can never *prove*; the strongest an `answered` verdict can be is *corroborated and not yet refuted*. Word and read the verdicts accordingly: `refuted` is terminal, `answered` is provisional.

## The three verdicts

`(basis: ratified by the maintainer, 2026-07-09. The three-verdict structure is corroborated by the literature — the asymmetry of refutation vs corroboration (Popper, via SEP — https://plato.stanford.edu/entries/popper/; Fisher, *The Design of Experiments* 1935: "the null hypothesis is never proved... but is possibly disproved") and the closest published three-way scale, winner/loser/inconclusive (Optimizely). But no external authority pins the rung *boundaries* the way CVSS pins security severity — Fisher's own p<0.05 was an admitted convenience — so the boundaries below are the maintainer's ratified house standard. The answered-vs-still-open discriminator is the load-bearing one: it is where two cold executors most diverge.)`

- **answered** — the probe ran, exercised the framed unknown itself, and produced a stable observation pointing *toward* feasibility: the assumption is **corroborated** — it holds under the conditions tested, and the decision the question unblocks can be made on that evidence. This is not proof; it is "not refuted, and the evidence points this way." Say so in the verdict.
  - *Anchor (top of scale):* the question was "can library X sustain 10k writes/sec on our shape of data?" The spike ran X against production-shaped data and held ~12k/sec across three runs. **Answered** — the throughput assumption is corroborated, with margin.
- **refuted** — the probe ran, exercised the framed unknown, and produced a stable observation demonstrating it *fails*: the assumption is falsified, the approach is off the table for this question. Refuted is the one terminal, hard verdict — it retires the risk decisively.
  - *Anchor:* the same question — X sustained only ~1.2k/sec and GC-stalled under the real payload, repeatably. **Refuted** — the throughput assumption fails; X is off the table.
- **still-open** — the probe ran but the observation does not conclusively resolve the question, in *either* direction: the run did not exercise the *real* risk (it stubbed the thing under test, or ran on unrepresentative data/scale), the signal is partial or ambiguous, the result did not reproduce, or the spike simply *did not show the assumption failing* without positively demonstrating it works. A still-open verdict is an honest, expected result — the common outcome, not a failure of the spike — and it is what a timebox expiry reports when the answer wasn't reached.
  - *Anchor (bottom of scale):* the throughput spike hit 15k/sec — but it stubbed the serialization step, the very thing the question turned on. Nothing about the real risk was observed. **Still-open** — the promising number says nothing about the framed unknown.

## Judge against the pre-committed success test

Assign the verdict against the observation named *before building* in [frame-the-question](../phases/01-frame-the-question.md) — not a bar chosen after seeing the result. Moving the goalpost to fit what the spike happened to produce (lowering the throughput target, slicing to the subset that passed, re-running until a green appears) manufactures a false `answered`; the pre-committed signal is what keeps the verdict honest. `(basis: hypothesis-driven development pins the signal before the run "to reduce biased interpretation" — Thoughtworks/O'Reilly, *How to Implement Hypothesis-Driven Development*; post-hoc adjudication and peeking are the documented ways inconclusive results get mis-read as wins — Optimizely.)`

## The adjacent-verdict discriminators

- **answered vs refuted** — *direction of the conclusive observation.* Both require the identical evidentiary bar (the real unknown exercised, stably observed); they differ only in sign. But their strength differs: `refuted` is terminal, `answered` is provisional-until-refuted — never round a corroboration up to a proof.
- **refuted vs still-open** — *demonstrated failure vs absence of success.* `refuted` needs the run to positively *show the assumption failing* (it ran the real thing and it didn't work). A spike that merely *didn't manage to show it working* — ran out of time, couldn't get the real component wired, produced an ambiguous result — is **still-open**, not refuted. Absence of evidence is not evidence of absence; collapsing "I didn't see it work" into "it doesn't work" is the most common way a still-open is mis-reported, and it wrongly kills viable approaches. `(basis: an inconclusive result "lacks sufficient evidence," distinct from a demonstrated null — AB Tasty; the absence-of-evidence fallacy, Lakens.)`
- **answered vs still-open** — *this is the load-bearing boundary, where "how much evidence is enough" is decided.* A verdict is **answered** only when **both** hold: **(1)** the run exercised the framed unknown *itself* — the actual risky component, under conditions faithful to what the question named (real-enough data, scale, integration), not a stub, mock, or toy substitute *of the very thing in doubt* ([isolate-what-you-test](isolate-what-you-test.md), [keep-the-real-thing-in-view](keep-the-real-thing-in-view.md)); **and (2)** the observation is *stable* — it reproduced, not a single lucky or unlucky run. If **either** fails, the verdict is **still-open**, no matter how promising the number looked. "Enough" is not a count of runs; it is: *the framed unknown was observed under conditions faithful to the question, and the observation held.* A promising signal from a run that dodged the real risk is still-open, not answered.

When `answered` and `still-open` both seem to fit, `still-open` wins unless you can name the observation that exercised the real risk and state that it reproduced. Overstating a still-open run as answered is the failure mode this scale exists to prevent — it ships a decision resting on evidence that was never gathered. Cross-check any `answered` against [ground-claims-in-a-run](ground-claims-in-a-run.md): if the claim rests on what the code *should* do rather than what a run *showed*, it is not answered.
