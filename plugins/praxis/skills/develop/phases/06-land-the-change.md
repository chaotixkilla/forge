# Land the change

Bring the change to rest in a state someone else can pick up. Landing is not "I stopped typing" — it is a defined, checkable condition: the working tree clean and committable, the full local check green, and the change measured against the definition of done. develop lands to a clean **local** state and stops there; opening a PR, pushing, merging, and shipping are `integrate`'s job, deliberately outside this skill.

## Run the full local check

The per-slice loop proved each slice; landing proves the *whole* change together. Run the repo's **full local check** — the set the repo itself gates on (its CI / pre-commit / documented "run everything" target); where the repo defines no single gate, that is the build + the test suite it runs + any lint/type gate it *enforces* (not optional style checks a reader can ignore) — over the complete change, not just the last slice's scope. A change whose slices were each green but whose whole fails is not landed; the full check is what catches the cross-slice interaction the per-slice loop couldn't see. If `--lens` was set, its check is part of this full green too. A whole-change failure here whose cause **is** in the change's own diff is more work to do before landing; one whose cause **isn't** localizable to the change in hand (a cross-slice or pre-existing interaction you can't pin to your lines) is a **blocked** outcome — a `debug` hand-off, not a signal to keep reworking inside develop ([verified-slice](../rules/verified-slice.md)'s fault-localization discriminator applies to the whole-change check too).

## Confirm the definition of done

Landing is gated on the [definition of done](../rules/definition-of-done.md) — the five criteria (complete, integrated/reachable, verified-green, coherent, landed-clean), each with its own test, are checked here. This is develop's marquee bar: do not declare done by feel. Walk the criteria; a change that fails any one is not done. Any leftover debris found now is a *coherent* failure to close before landing ([leave-no-debris](../rules/change-hygiene/leave-no-debris.md)).

## Commit locally to a clean state

Bringing the tree to a **clean, committable state** — no half-staged work, no stray files, the change coherent — and then **recording the commit** are both **local, ambient git**: they need no configured backend, exactly as develop reads the working tree, and they always happen. develop names no concrete tool and declares no `config_requires`; because it commits *locally only* and pushes nothing to a host, there is no version-control *host* to be unconfigured and nothing here degrades. Commit the change (and, with `--checkpoint-commit`, the per-slice commits already recorded — see [checkpoint-commit](../modules/checkpoint-commit.md), which carries the commit-granularity fork: per-slice checkpoints vs a squashed single commit). Pushing, opening a PR, and merging are `integrate`'s hosted job, deliberately outside develop. `(basis: ratified by the maintainer 2026-07-11 — a local commit needs no configured backend, so it is ambient plain git like develop's local reads, not a vcs-port delegation; the vcs port is host-only. Supersedes the earlier degrade-when-vcs-unconfigured framing, which mis-modeled a local commit as a host operation.)`

## Report the terminal outcome

Every develop run ends in exactly one of three outcomes — state which:

- **landed** — the definition of done is met and the change is committed to a clean local state. The normal terminal state.
- **checkpointed** — the run stopped short of done *by request* (a `--until` condition — a slice, a phase, first-green — deliberately reached) to report state. Not a failure; a requested pause. (see [until-checkpoint](../modules/until-checkpoint.md))
- **blocked** — the run **cannot proceed to done within develop**, for any of: a red state whose cause is not localizable to the change in hand and needs `debug` (a per-slice red — [verified-slice](../rules/verified-slice.md) — *or* a whole-change full-check failure at landing that isn't in the diff); an upstream plan/spec decision that proved unbuildable as written; or work that isn't develop's to start yet (the [orient](01-orient-in-the-code.md) direct-request bailout that recommends a `spec`/`plan` pass first). The run stops and hands off with the blocker and its next-owner named. `--until=red` is the requested-stop form of reaching a red state.

`(basis: routed to maintainer, ratified 2026-07-10, hardened after the gate's partition finding. The partition is exhaustive and mutually exclusive by construction: a run either reaches the done bar (**landed**), stops early *by request* before it (**checkpointed**), or *cannot* reach it within develop (**blocked**) — the three carve on "done / stopped-by-choice / cannot-proceed", so every reachable run lands in exactly one. Non-overlap is settled by enumeration plus one routing tie-break, not by a clean by-request/by-inability split: checkpointed's by-request triggers are the *enumerated* `--until` stops (slice / phase / first-green) and deliberately exclude red, while `--until=red` — a request to halt at an *inability* — is routed to blocked because inability dominates the label. (That tie-break is why "by-request vs by-inability" alone wouldn't partition: `--until=red` is both, and is assigned by the rule that red → blocked.) Blocked is defined by its rationale — *cannot proceed* — not by an enumerated list of triggers, precisely so a novel can't-proceed state (the gate found the whole-change-red-at-landing and the pre-build bailout) lands in it rather than falling outside the set; a binary landed/not-landed would force a requested pause and an unresolvable block onto the same "not done," hiding whether a human should resume, re-plan, or route to debug.)`

A landed change is ready for `review` (the independent read) and `integrate` (getting it into the trunk and out the door) — develop's job ends at the clean local state.
