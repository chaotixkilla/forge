# Decide or route

A builder meets decisions all through a change, and each one is either the builder's to make, the plan's to make, or the user's to weigh in on. Absorbing a plan-level decision silently builds a design nobody chose; escalating every small choice stalls the work. This rule sorts them.

**The develop/plan line (the discriminator for what you decide vs. route):** decide a choice in-flight when it is **contained in this change's own diff and reversible by editing this change** — a local variable's shape, which existing helper to call, how to structure a function. Route it to `plan` (or surface it, `--from-spec`) when it is a **plan-level commitment other code must conform to**: introducing or changing a *shared interface or contract*, choosing the *overall approach*, or adding a *requirement* the spec didn't state. The test: does the decision create something outside this diff that other code must now match? If yes, it is not develop's to make alone.

**The third branch — put it to the user.** The line above sorts a decision by *altitude*; this one sorts by *whether the user would want a say before you build on it*, and it fires during the build, not only at framing. Stop and put the decision to them when **both** hold: the choice delivers something **materially different from what was asked** — a hand-rolled substitute for behavior a dependency was supposed to provide, a footprint grown past the task's stated bounds, a stated constraint that can now only be met by breaking another — **and** it is **expensive to unwind**, meaning undoing it later discards work beyond the slice in hand. With only one, proceed and surface it in the run's report; with neither, it is an ordinary in-flight call needing no mention. Both conditions are required: either alone over-fires, and escalating everything is its own failure — the user is trying *not* to be interrupted — while a real one missed leaves the user to discover after the fact a call that was never put to them. When no one can be asked — develop invoked by another skill, as an act runs it, or an unattended run ([ask-while-the-user-is-here](../../gather/rules/ask-while-the-user-is-here.md)) — don't build on the decision: stop with the outcome `blocked`, the decision and the option you would take as the blocker, so the caller puts it to the user.

When you do escalate, make it a **call to action, not a narration**: carry the ask's own bar ([make-the-ask-explicit](../../../craft/writing/make-the-ask-explicit.md)) and add what this moment needs on top of it — the option you would take and why, so the user confirms a recommendation instead of being handed an open question mid-build. `(basis: maintainer, 2026-09-01)`
