# Reach the real entry point

A verify run is worth exactly what its drive is worth, and a drive is real when it **enters the running application where the application's user enters, and takes its reading where that user reads the result** — with nothing in between stood in for. Concretely: the instance is the one the project's own start command produces; the first action is taken from *outside* that instance, through an access path the application itself exposes when it runs as it ships; and the confirmation is taken at the surface the user gets back — a rendered view, a returned payload, a written record read back the way a user would read it, an outbound message actually delivered. That definition is the whole boundary between this skill and test, which owns the automated suite and never drives the application. Driving the unit proves the unit, and no proof about a unit can tell you that nothing links to it, that the address a user's action names resolves somewhere else, that the view never renders, that authorization refuses the user the change was for, or that the configuration the shipped path reads is absent in the instance you are actually running. Those are the defects verify exists to catch, and every one of them lives *between* units.

## The skipped-layer test

The discriminator is mechanical, and it is worth applying twice — once when you choose an entry point, once after you have driven the flow, because a drive often turns out to have entered lower than you intended.

1. **Derive the layers this flow's shipped path crosses**, from this project rather than from a checklist, between the user's first action and the effect they would see. The usual members, as prompts rather than a fixed set: the process and transport boundary the action crosses (with the encode/decode on each side of it); address resolution and dispatch to the code that handles it; configuration, feature state, and credential resolution *as the running instance resolves them*; identity, session, and authorization; data access and whatever migration or schema state that access assumes; the presentation or response layer that renders the result in the form the user receives; and any effect that leaves the process to reach another system.
2. **For each layer the drive did not cross, ask one question: could a defect live in this layer, and would this drive have shown it?** A single "no" makes the drive a substitute rather than a verification, and it cannot support a verdict about that flow — only about the smaller thing it actually exercised.

The test's teeth come from an asymmetry: the layers a substitute drive skips are precisely the layers where a written suite is least likely to hold a case, because a case at that altitude is expensive to write and easy to defer. So the skipped layers are not a random sample of the risk — they are where the residual risk concentrated after everything cheaper was already checked.

Apply the test to the **exit** half too. Confirming the effect by reaching inside the running instance — reading an internal value, querying state through a path no user traverses — ends the drive inside the application, which skips the layers between that internal state and the effect a user can see in exactly the way a back-door entry skips the layers before the handler. This rule's half of that is which layers went unexercised; what may be written down as having happened is [observation-over-inference](observation-over-inference.md)'s, and a self-report taken as the effect is its case. An internal reading may be worth taking for diagnosis; it is not the observation the flow's claim needs.

`(basis: the front-door principle and the named cost of going under the surface — Meszaros, *xUnit Test Patterns*, "use the front door first": exercise the system through the interface real callers use, because back-door manipulation bypasses the logic the real path would run and can pass while that path is broken; and Fowler's *subcutaneous test*, which names a drive that stops just below the user-facing surface and is explicit that it says nothing about the layer it skipped. The layer question above is those two positions read as a test rather than a preference — if the shipped path crosses a layer this drive did not, the drive is silent about that layer — together with the standing definition of system-level testing as exercise of the integrated system through its external interfaces.)`

## The substitutes, and what each one skips

Each of these is a legitimate engineering act and none of them is a verify drive. Naming them is how you catch yourself mid-run:

- **Calling the function or the handler directly** — skips everything before the handler: reachability, resolution, encode/decode, identity, and the fact that nothing may point at the handler at all.
- **Exercising the application in-process, through its own internals** — keeps the code but loses the boundary: real encoding, real configuration resolution, and the transport the user's action crosses go unexercised.
- **Driving through the automated suite's harness** — inherits the harness's fixtures, doubles, and configuration, so the run proves the code under the harness's world, not the application under its own. This is the substitute that feels most like verifying and is the least like it.
- **Seeding or reading state through a back door** — skips the path that produces or exposes that state, which is usually the path under check.
- **Taking a build result, a type check, or a self-reported health signal as the observation** — no user path traverses any of them ([observation-over-inference](observation-over-inference.md) owns why a self-report is not the effect).
- **Concluding from reading the change** — a different skill's method entirely, and not evidence of running behavior at all.

A near-miss worth its own line, and it splits in two — the discriminator is **which layers of the shipped path the drive did not cross**, never whether a surface is labelled *development*:

- **A development-only surface that stands in for application layers** — a debug-only access path, a fixture-driven mode, a bypass switch — is a different entry point than the shipped one. It can be the right call, and it is a narrowing: record which entry point you drove, since the environment the verdict is scoped to is part of the verdict.
- **A development-only endpoint that merely *receives* what the application actually emitted** through its own shipped path — the local stand-in on the far side of a boundary the flow crosses outward, holding the message, request, or artifact the instance really sent — skips no application layer. It is the point at which the crossing is observed, and the substitution is the *recipient beyond* the boundary, recorded in the environment like any other. Whether the unit is still capped then follows the framed claim's terminus, the discriminator [observation-over-inference](observation-over-inference.md) already pins: where the claim ends at the application emitting the thing and the user acting on it, the effect is observed and the unit is not capped; where the claim is that the real recipient receives it, the substitution sits under a claimed effect and [verdict-scale](verdict-scale.md)'s substitution-or-unknown cell caps the unit at `indeterminate`.

`(basis: ratified by the maintainer 2026-07-27, on the build's recommendation — the shipped-path-layer test as the sole discriminator for a development-only surface, splitting a *substitute for* the app's own layers from a *receiver of* what the app emitted. Because the scale's own `works` anchor drives an out-of-band delivery path while this rule called every development-only surface a narrowing: one run graded that anchor `works` and another `indeterminate`, on the same drive, each citing a different file.)`

## The one legitimate exception: narrowed scope, recorded

Some seams genuinely cannot be driven from outside with the access a given run holds — a step gated on a credential, counterparty, device, or external system the run cannot reach; a step whose real firing is destructive and not permitted even against throwaway state; a surface that only exists after a provisioning step this run cannot perform. When that happens, the exception is **a narrower claim, not a different drive**: keep the drive real up to the seam, stop there, and record the narrowing where the verdict is assigned — name the step you could not drive, the layers it left unexercised, and which of the framed claims therefore rest on nothing observed. If part of the flow past the seam is reachable through its own real access path, drive that part and record it as a separate observed segment with a gap between; if the only way past is a back door, nothing you do past it belongs to this flow's observation. A substitute exercise you run anyway is recorded as what it is — an observation of the code behind the seam — never as the flow's drive.

`(basis: ratified by the maintainer 2026-07-27, on the build's recommendation — the disposition above — an undriveable seam narrows the claim and is recorded in the verdict, rather than being worked around or silently dropped. Derived here, not taken from a source. Why this over the alternatives: stopping the whole flow discards the substantial part that *was* observed, and substituting a harness drive manufactures a pass at the one layer most likely to hold the defect, which is the failure this rule exists to prevent. Recording the gap keeps both the information and the honesty, and leaves the question of how far the gap caps the flow's verdict to the step that assigns verdicts.)`

Which seams count as genuinely undriveable is **deliberately open** — it varies with the project, the environment stood up, and the access the run holds. What is pinned is the test that decides each case — *can the shipped path be driven from outside with the access this run has?* — and the obligation to record every "no".

Two degenerate cases fall out of the same rule. If **no** real entry point can be reached at all — the instance will not serve, or no access path exists — that is the run's reported outcome, not an invitation to fall back to the harness: a verdict earned through the harness answers a question about the code, and the question asked was about the application. And if a *framed flow* turns out to have no reachable entry point, that is not an obstacle but the finding — a completed feature with nothing pointing at it is the exact defect no in-process drive can see, and it is reported as a defect in the flow rather than as a gap in the observation.
