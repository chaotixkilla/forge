# Real defect vs environment fault

A flow misbehaved, and before that observation can become a verdict it has to be *attributed*. Both misattributions are expensive in opposite directions: a genuine defect written off as "something about my setup" ships the bug with a clean report attached to it, and an environment fault reported as a defect sends someone hunting a bug that is not in the code — and the second mistake, made twice, is what teaches a team to stop believing this skill's output. Naming the two classes settles nothing; the tests that sort them are the closure. The sharpest of them is the last, because the environment being **involved** is not the environment being **at fault**.

**Three terms, pinned once, because every test below turns on them.** A **re-drive** is the same flow driven again through the same entry point, on the same instance and the same revision, with nothing altered — it asks whether the behaviour is *stable*. A **baseline drive** is the same flow driven in the same instance against the *pre-change* state — the far side of the window [frame-the-observation](../phases/01-frame-the-observation.md) pinned as the change under observation, so "pre-change" is that window's base and not any other revision — a different question, whether the change *caused* the failure; never substitute one for the other. The **environment** is everything the stand-up step recorded standing around the change: the instance and its configuration, the dependencies it reaches, the data it starts from, the build actually being served, and the local resources it holds.

## The tests, in order

Apply them in order, and note where the order binds: tests 2 and 3 produce a **hypothesis**, never a classification. No failure is classified as an environment fault until test 4 has run on it. `(basis: derived from the tests' own dependency structure — every later test compares drives against each other, so stability is a precondition for the rest; and a setup signature is a surface the change itself can produce, so on its own it can only raise a hypothesis.)`

### 1. Re-drive before you classify

A single drive is an anecdote. The drive itself may have varied — an input entered differently, a step that never landed, a different pace — and a hand-driven flow is a far less repeatable instrument than an automated case. So re-drive the failing flow, and re-drive it **from the reproduction steps as you have written them down**, not from memory: that second drive is the first execution of the artifact this skill hands off, and a reproduction that only works when its author drives it is not a reproduction.

**Two matching observations settle it.** The original drive plus one re-drive reaching the same failure, at the same step, with the same observable surface: the failure is **reproducible**, and classification proceeds. Any divergence — a clean pass, a different failure, or the same failure at a different step — means it is not reproducible yet. Note the asymmetry that answers "how many clean re-drives": **one** is enough to call the behaviour unstable, because a divergence proves the trigger is not controlled, while no number of clean drives could prove it is. Drive it up to **three times in total**, record the ratio and what varied between drives, and carry it forward as *not established* — never as a confirmed defect, and never as a pass. A clean re-drive absolves nothing; it only says the uncontrolled condition has not been found yet. `(basis: the invariant — a failure must be made to happen again before it is acted on, and an intermittent failure means an uncontrolled condition you have not yet identified rather than an excuse — is Agans' Rule 2, "Make It Fail", *Debugging: The 9 Indispensable Rules* (2002), which also warns against over-trusting a small number of trials.)` `(basis: ratified by the maintainer, 2026-07-27 — the counts: two matching observations to call a failure reproducible, three drives as the cap on characterising an intermittent one. Derived here, not from an accountable source: the literature that does discuss rerun counts is about cheap automated reruns, and offers no number for an interactive drive of a whole flow, which costs minutes of real application time and manual attention. Reasoning for two: the second drive is executed from the written reproduction, so it validates the deliverable rather than merely re-confirming the failure — the most value one extra drive can buy. Reasoning for the cap: once a failure is known to be intermittent the honest output *is* the ratio and the variation, and further drives buy a marginally better ratio estimate with the run's remaining budget. Raise both where flows are cheap to drive and the project has known timing sensitivity. What must not move if the numbers do: one drive never confirms, and a clean drive never absolves.)`

### 2. Read the failure surface for a setup signature

Read what the failure actually said and ask whether it names a fact about the **setup** or a fact about the **behaviour under check**. Setup signatures point at the instance rather than the flow: a dependency that could not be reached, configuration or credentials absent, a data store with no schema or none of the seed data the flow needs, a version mismatch between what the instance provides and what the change expects, a port or resource already held, local resources exhausted, or a stale build being served instead of the change you meant to drive. Treat that list as examples of the test, not as the test — the durable question is whether the failure names the setup. The stale-build case is worth naming separately: it means you are verifying a revision you did not think you were driving, so confirm the instance is serving the change — by the code-identity test in [stand-the-app-up](../phases/02-stand-the-app-up.md), which sets what counts as confirmed and what does not — before classifying anything at all. And a signature raises a hypothesis and nothing more, because a change can produce every one of these surfaces *itself* — by depending on something it never declared, by shipping without the migration it needs, or by reading configuration it never documented.

### 3. Locate the failing layer relative to the change's reach

Find the layer where behaviour first diverged and ask whether it sits within the change's reach — the code the change touched, and what runs downstream of it. Where a pre-change state can be stood up in this same instance, take a **baseline drive**: the same failure on the baseline means the change did not cause it (a **pre-existing defect**, or an environment fault — the hypothesis survives and test 4 still decides); a clean baseline with the environment held constant implicates the change, and any environment hypothesis now has to explain why the same setup served the old revision. That question is frequently the whole answer.

Degraded form, for when no baseline is standable — the flow did not exist before the change, the earlier revision cannot run in this instance, or standing it up costs more than the run has: fall back to **reach**. Is any layer on the failure path inside the change's edit surface or its declared dependencies? If none is, the fault is presumptively outside the change; if one is, presumptively inside. Record that this was located by reach rather than by comparison and say so in the report — it is the weaker conclusion, and the reader is entitled to know which one they were handed. Nothing is absolved by this test either way, because test 4 still runs.

### 4. The residual test: would a correctly built change have behaved acceptably here?

This test is **mandatory** on every failure where the environment is implicated — a hypothesis surviving test 2, a failure that appears only in this instance, anything you are tempted to write off as noise. And it is not "was the environment involved". It is: *would a correctly built change have behaved acceptably in this environment?* Three moves make it operable.

**Name the one environment fact the failure depends on** — this dependency unreachable, this configuration value absent, this data not seeded, this version present, this resource under pressure. If you cannot name a specific fact, you do not have an environment hypothesis; you have an unexplained failure, and an unexplained failure is a defect until something explains it otherwise.

**Ask who owns that fact.** The **change** owns it when the fact is a precondition the change introduced or relies on *and* the project's own setup contract — its setup instructions, its configuration schema, its dependency declarations, its migration set — does not state it, or the change does not check it. That is the defect wearing an environment costume: absent configuration is the environment's state, but the missing guard is the change's. The **environment** owns it when the fact contradicts a precondition the project *does* state and this instance simply fails to satisfy it. `(basis: preconditions must be explicit for responsibility to be attributable at all — an unmet *stated* precondition is the caller's fault, while an unstated assumption that breaks is a defect in the component (Bertrand Meyer, design by contract, *Object-Oriented Software Construction*); explicit declaration of dependencies and of configuration as the software's own obligation is The Twelve-Factor App, factors II and III, and its factor X, dev/prod parity, is the same argument about environments that differ.)`

**Then measure the behaviour against the acceptable bar, not against success.** Acceptable behaviour under a broken precondition is not completing the flow — it is failing immediately, visibly, and with an actionable statement of what is missing. A flow that stops early with a clear and accurate message naming the missing precondition *has* behaved acceptably: the environment is at fault, and the observation is void until repaired. A flow that hangs, fails opaquely, reports a success it did not achieve, presents a wrong result as right, loses or half-writes data, or leaves state it cannot recover from has **not** behaved acceptably, whatever triggered it. `(basis: Jim Shore, "Fail Fast", IEEE Software (2004) — on an unexpected condition, correct software stops immediately and reports rather than continuing in an unknown state, precisely so that the failure stays attributable.)`

The compressed form, worth carrying out of this rule: **the environment can excuse a flow not completing; it never excuses a flow completing wrongly.** A failure only *reachable* because of the environment is still the change's defect when what happened on reaching it was silent, wrong, or destructive — the environment supplied the trigger, not the misbehaviour.

- *Anchor (defect in an environment costume):* the flow fails with an unactionable error because a configuration value this change newly reads is absent; the setup instructions never mention it and the change never checks it. Environment fact, change's defect — undeclared precondition, no guard.
- *Counter-anchor (environment fault):* the flow fails because a dependency the project's own setup contract lists as required is not running here, and the flow stops at once saying exactly that. Environment fault — repair it, record the repair, re-drive; the pre-repair observation is void.
- *Anchor (the residual case):* under a dependency slow enough to time out, the flow reports the operation succeeded and persists half of it. Reachable only in this environment, and still a defect: completing wrongly is not excused by the conditions that triggered it.

## Repairing the environment, and the line you may not cross

Repairing the environment to get a flow driven is allowed and expected — an unrunnable instance yields no observations at all. Two obligations come with it. **Record the repair** as part of the environment the verdict is scoped to: what was wrong, what you changed, and at what point in the run. **Re-drive whatever the repair may have invalidated** — any already-driven flow whose path touched the repaired fact, since its observation was collected in an environment that no longer exists; where you cannot tell whether the fact sat on that flow's path, re-drive it, because the cost is one drive and the alternative is a verdict resting on a superseded environment. Repair one fact at a time and re-drive between repairs: three simultaneous repairs followed by a clean drive tells you nothing about which mattered, and one of them may have been masking the defect. `(basis: verify's own scoping rule — a verdict covers the flows driven in the environment the stand-up step recorded — which is what makes an observation collected in a since-changed environment unable to support the verdict it was collected for.)`

The line: **editing the change under test ends the verification.** Adjusting local instance setup repairs the environment; editing files that are part of the change's tracked deliverable does not, and once you have done it, the thing you can report on is no longer the thing you were asked to verify. If a flow can only be driven by touching the change, that *is* the finding: stop, report what was observed up to that point, and hand off. Same for the borderline — a local setup file that the change itself also modifies — treat it as part of the change and stop. `(basis: verify's stated boundary — its deliverable is the per-flow verdict plus reproductions, and it hands off rather than repairing.)`

## The confusable pairs

- **defect vs environment fault** — *the residual test.* Not "was the environment involved" but "would a change that declared and guarded its preconditions have behaved acceptably in this instance". An unstated precondition, or an outcome that was silent, wrong, or destructive ⇒ defect. A stated precondition unmet, with a clear immediate failure ⇒ environment. (ownership of the named fact + the acceptable-behaviour bar)
- **caused by the change vs pre-existing** — *the baseline drive.* Both are genuine defects and both get reported; the tag decides whether this change is answerable for it, and both answer the verdict scale's fault question the same way, since a level tracks whether the unit behaved as claimed. With no standable baseline, locate by reach and label the conclusion as reach-located. (comparison, or reach as the degraded form)
- **environment fault vs unstable behaviour** — *hold the named environment fact constant and re-drive.* Constant fact with mixed results ⇒ the instability is in the change or its dependencies. If the fact *cannot* be held constant, that instability is itself an environment fact and is recorded as one, not as a flaky application.
- **unstable behaviour vs a varying drive** — *did the drive vary?* A different input, a step that did not land, a different pace: a varying drive is no evidence about the application. Re-drive from the written reproduction, which is what holds the drive constant; only then is a mixed result a fact about the flow.

## When the classification cannot be reached

- **Nothing misbehaved** — this rule does not fire and there is nothing to attribute; it is not an absence to report on.
- **The flow cannot be re-driven** — a one-shot or irreversible flow, state the failure consumed, an instance that is gone. Reset to fresh state and re-drive if the run can (standing the instance up disposably is the cheap way to buy that). If it cannot, the observation stands as explicitly **single-drive**, and it supports a defect only when the failure left independently inspectable evidence a second party can examine without re-driving — a captured error surface, a persisted wrong artifact — which then *is* the reproduction, with the single-drive limitation stated on it. Otherwise carry it forward as not established.
- **The environment cannot be repaired** — the missing precondition is outside what the run may touch or knows how to supply. The attribution still stands as *environment fault*; what it carries in addition is that the fault is unrepairable within this run, with the specific precondition named, so the flow goes forward unobserved rather than judged. Do not substitute a drive that bypasses the real entry point in order to get a result, and do not soften an unobserved flow into a pass on the grounds that nothing was seen failing.
- **A disposable, isolated instance** — when the run provisioned the environment itself, an absent fact is the provisioning's gap first: repair the provisioning, record it, re-drive. It becomes the change's defect only when the missing fact is one the project's own setup contract says the change must handle, which is test 4 applied to a setup you built.
- **Several failures in one flow, or one fault across several flows** — attribute per *failure*, not per flow: one flow can carry an environment fault and a defect at once, and collapsing them buries the defect behind the fault. Conversely, one environment fault can void the observations of many flows (or, where the report is keyed per requirement rather than per flow, many entries) — attribute it once and mark every entry that depended on it.

What this rule outputs, per failure, is one attribution and the evidence behind it: *reproducible defect caused by the change*, *pre-existing defect*, *environment fault*, or *not established*. Exactly one, and the tests make it so: stability is the precondition for the other three, so anything that failed test 1 is *not established* and nothing else; a reproducible failure then resolves to exactly one of the remaining three, because ownership of the named fact is a single decision and the case where no fact can be named is folded into defect by test 4. Turning an attribution into a per-flow verdict level is the reporting step's work, against the scale that step loads.
