# The code-identity test

Every verdict assumes the instance is serving the code under observation; a stale instance makes a genuine failure and a missing change look alike. This test sets when that is established.

Confirm the instance is running the code under observation before anything else — [real-defect-vs-environment](real-defect-vs-environment.md) makes this a precondition of all attribution — and treat it as a test with a bar rather than an intention. It is **confirmed** by either route: **(i) provenance** — you started the instance yourself, from the window [frame-the-observation](../phases/01-frame-the-observation.md) pinned, and nothing has restarted, rebuilt, or re-deployed it since; or **(ii) an observed marker** — for an instance you did not start, an observation taken through the same access path the flows will be driven through that carries something the change alters and the pre-change state does not (a served surface, response, or reported build identity that differs between the two). The marker may not be the framed claim itself: using the claimed behaviour as the evidence that the right code is loaded makes a stale instance and a genuine non-resolution indistinguishable, which is the one confusion this test exists to prevent. These do **not** confirm it either: reading the revision out of the tree without knowing what the instance was started from; a build or compile step that succeeded; a process that has been alive since before your window existed; the instance's own claim about its version where the change does not alter that claim. Where no route is available, record code identity as **unknown** per the environment record [stand-the-app-up](../phases/02-stand-the-app-up.md) keeps and carry that limitation into the verdict — never assume it. `(basis: maintainer, 2026-07-27)`
