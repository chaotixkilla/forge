A flow that misbehaved is not yet a finding. Two questions sit between the drive record and the verdict — *did it really do that*, and *is the change why* — and what each costs when it goes wrong in either direction is set out in [real-defect-vs-environment](../rules/real-defect-vs-environment.md), which owns both tests. This phase answers both for every failure the drive produced and hands forward an **attribution** per failure. It assigns no level; that is [report-the-verdict](05-report-the-verdict.md)'s work.

## Enumerate the failures that enter — per failure, not per flow

Start from the drive record's set of flows that did not behave as claimed, and expand it into a list of **failures**: one flow can carry more than one, and the attribution below runs on each independently, because a flow that carries both an environment fault and a defect will hide the defect behind the fault if the two are attributed as one thing. Conversely one fault can be responsible for failures in several flows — attribute it once and mark every entry that depended on it.

Two cases enter that produced no step-level observation at all, and they enter deliberately rather than being written off as setup trouble: a flow whose real entry point could not be reached, and a run where the instance never came up serving. An application that will not start, and a feature nothing resolves to, are among the commonest things a change actually breaks — deciding either without the tests below is the guess this phase exists to remove. What gets attributed in those cases is the reachability failure itself, and the fact that there is no step entry to quote is a limit on the evidence, not a reason to skip the attribution.

What does **not** enter: a flow that behaved as claimed passes straight through. A friction finding has no fault to locate — a flow that functioned while being confusing travels forward as its own verdict plus its finding, and pushing it through a fault attribution would either invent a defect or bury the finding. And a **gap in the observation is not a failure**: a step left unobserved because the drive was narrowed, stopped on budget, or blocked behind an earlier step is nothing to attribute — it travels forward as the recorded gap it is, and it constrains the level rather than the attribution. Only a *misbehaviour* — the running system did something other than what the claim says — is a failure here.

## Establish stability first, to the counts the rule pins

Stability is the first of the ordered tests and it gates every other one, so it happens before any attribution is written down. Re-drive each failing flow **from the reproduction steps as you have written them**, and take the drive counts from [real-defect-vs-environment](../rules/real-defect-vs-environment.md): the number of matching observations that makes a failure *reproducible*, the number of clean drives that makes a behaviour *unstable*, and the cap on characterising an intermittent one are all pinned there, and they are deliberately **asymmetric** — running this step from intuition gets one direction wrong every time. What carries forward from a mixed result is the ratio and what varied between drives, never the outcome of whichever drive happened to be last.

One procedural point the counts assume: a re-drive has to *start where the first drive started*. Return the data and configuration the flow touched to the recorded starting state before each attempt — where the instance was stood up disposably, re-provisioning is the cheapest reset — and record that you did, because a drive that begins from the state its predecessor left is a different drive and says nothing about stability. Where the flow cannot be re-driven at all — an irreversible effect, an input consumed by the first drive, an instance that is gone — take the cited rule's single-drive case as it stands rather than improvising a substitute: it fixes what a one-drive observation can and cannot support.

## Attribute each failure with the rule's ordered tests

Work the tests in [real-defect-vs-environment](../rules/real-defect-vs-environment.md) in the order that rule sets, on each failure, and record **which test decided the call**. Those tests are the attribution — there is no second house heuristic here, and a label attached without them is a guess in a lab coat. The order is load-bearing there, and the two ways it gets broken are worth knowing before you start: reading the failure surface for a setup signature and stopping (a signature the change itself can produce), and skipping the residual test because the environment was visibly *involved* — which resolves the interesting cases backwards.

Each failure leaves this phase with **exactly one of the four attributions that rule terminates in** — *reproducible defect caused by the change*, *pre-existing defect*, *environment fault*, or *not established* — chosen by running its tests, never by which name reads closest to the symptom. Carry the names as it gives them: both the report and the level assignment read them, and a paraphrase collapses distinctions someone downstream needs. [verdict-scale](../rules/verdict-scale.md)'s question (b) maps all four onto levels, so the name you write here is what decides the level; do not pre-empt that mapping by choosing a name that sounds like the level you expect. With each attribution, carry the evidence behind it: the deciding test, the drive ratio, and — where the fault was located by **reach** rather than by a baseline comparison — the fact that it was, since that is the weaker conclusion and the reader is entitled to know which one they were handed.

The attribution is an inference drawn over the drive record, as is any statement about which layer first diverged. Label both as inferences by the discriminator in [observation-over-inference](../rules/observation-over-inference.md) and keep them separate from the entries they rest on. Phase 5 quotes the observation into the reproduction and reports the attribution as this run's reading; it can only do that if you did not merge them here.

## Repairing the environment, and the line that ends the run

Repairing the setup to get a flow driven is legitimate and the cited rule pins both its obligations and the line it may not cross. Two things belong to this phase. **The checkpoint:** before touching anything, confirm that what you are about to change is the setup *around* the change and not part of the change's own tracked deliverable — including the borderline file the change also modifies. If a flow can only be driven by crossing that line, stop: report the attributions established so far plus the blocker, and hand off.

**The loop back:** discharging the rule's obligation to re-drive what a repair invalidated means returning to the drive itself, with each post-repair drive recorded as a fresh drive in the phase-3 record rather than as an amendment to the entries it supersedes — and with the environment record amended, since that record is what the verdict's scope is read from. Repairs also accumulate, and past some point the instance stops resembling anything a user would meet; when you judge that line crossed, prefer reporting a named blocker over a verdict scoped to a heavily doctored setup. *Deliberately open:* how much repair is too much turns on which facts were substituted and how central they are to the flows being driven — context the executor holds at run time and this file cannot.

## Hand the attributions forward

Per failure: the attribution, the test that decided it, how it was located, the drive ratio with what varied, the observation quoted from the drive record, and every repair with the amended environment record. Per flow: which failures it carried. Assign **no** level — keeping attribution and level apart is what stops a level being picked on a hunch and an attribution then chosen to match it.

Stop at the attribution, too. verify localizes only far enough to tell a defect in the change from noise around it; the causal chain below that line is not pursued here, it is handed off in [report-the-verdict](05-report-the-verdict.md), which is also where these attributions become levels. Open [verdict-scale](../rules/verdict-scale.md) at this point only in one case: an attribution that looks as though it will not map onto any level. That mismatch means either the attribution is wrong or the scale is missing a case, and it is far cheaper to resolve here than inside the report.
