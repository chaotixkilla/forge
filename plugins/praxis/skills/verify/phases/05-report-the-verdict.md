Two failure modes pull in opposite directions, and this phase is written against both: a verdict that claims more than the drives support (*"it works"*, from four flows out of thirty), and a finding nobody can act on without standing the application up again to find out what actually happened.

## Assign every graded unit exactly one result

Assign each unit **one of the four results [verdict-scale](../rules/verdict-scale.md) places**, by working that rule's ordered questions in their order and taking the first stop they produce. The words carry none of what makes this repeatable — the ordered questions, the adjacent-result discriminators, the tie-break direction, and the definition of the graded unit itself all live in that file, and an assignment made from the words alone is the divergence between two cold runs that the scale exists to close.

The inputs are already prepared. Phase 3's per-flow observation label answers the **coverage half** of the scale's observation question — *not observed* is "nothing was exercised", *fully observed* is "every framed step produced an observation entry" — while the **confirmation half**, whether each of those entries confirmed its step's claimed effect at its own layer, is read off the per-step entries and not off the label; and phase 4's per-failure attribution is what the fault question maps from. Close as they are, a label is not a result: run the scale's questions against them rather than translating labels into results by eye, since the interesting units are exactly the ones where the mapping is not one-to-one (a *fully observed* flow whose third step misbehaved, a *partly observed* flow that also carries a reproduced defect, a *not observed* flow whose unreachability **is** the fault). Every result is reported with the scope it holds within, in the form the scale requires, and in the words of [results-and-certainty](../../../craft/evidence/results-and-certainty.md).

Where the framed unit set came back **empty**, there is no unit for a result to attach to: the run's result is `not checked`, for one of the **two reasons** the scale defines for an empty set, chosen by the guards it sets there — *no reachable surface* under both guards, *reach untraced* where guard 1 fails. Check the guards rather than assuming the empty set qualifies, and report the result with its reason and no per-unit row, since there is no unit.

## Roll the results up into a headline that claims no more than the drives support

The run owes one headline above the per-unit results, and it is computed, not composed. Resolve in order: **any unit `fails` → the headline is `fails`**; else **every unit `holds` → `holds`**; else **every unit `not checked` → `not checked`**, with each unit's reason; else **`unsettled`**. A run that drove any unit has exercised the claim, so a mix of `not checked` with `holds` or `unsettled` heads as `unsettled`, never as `not checked`; the units not checked still lead the un-driven set below, each with its reason, because an obstacle someone can clear is what stops the next run. `(basis: maintainer, 2026-10-02)` An empty unit set skips the ladder entirely: check the scale's guards first, then report `not checked` with the reason they select as the headline in its own right. One reproduced fault refutes the claim outright and stays refuted, while no quantity of clean drives can settle the rest — so the headline follows the worst unit, never the average, never the majority, and never the flow the run happened to care most about.

The headline then carries three things without exception, because each is a way it silently overstates itself: the **units it covers**, named; the **environment** they were driven in, from the phase-2 record plus every repair phase 4 recorded; and the **units not driven or not settled**, named as such. That last set is never empty by omission — where an explicit flow list replaced the framed set, everything else is unobserved by construction, and saying so is the whole difference between a scoped result and a claim about the application. A headline that says *the application works* is wrong even when every unit came back `holds`; write it about the units. `(basis: maintainer, 2026-07-27)`

Report the tally alongside the headline — how many units at each result — so a `fails` headline over nineteen clean units and one over a single driven unit do not read identically.

## What a defect finding must carry to be actionable

The bar is that a reader who was not at the run can reproduce the failure without asking a question, and can start work without re-driving anything to find out what happened. Each finding carries: the unit and the step it broke at; the entry point and starting state it was driven from; the interaction sequence in order; **expected-versus-observed at the failing step, quoted from the drive record** rather than paraphrased; the layer the effect was checked at; the environment with its repairs; the attribution from phase 4 with the test that decided it, the drive ratio, and whether it was located by comparison or by reach; and, for a narrowed drive, what was not exercised. `(basis: derived from what the handoff below consumes)`

What a finding must **not** carry is a mechanism. This run established that a fault is real and where it lies, not why it happens — so quote the observation and label every causal reading with the certainty it reaches — traced, inferred or unverified, never observed — by the discriminator in [observation-over-inference](../../../craft/evidence/observation-over-inference.md). A plausible cause written as fact sends the next reader down your guess instead of the evidence, which is worse than offering nothing.

Three neighbours report in the same shape and the same place, each labelled, so that none of them is either lost or mistaken for the change's own defect: an **environment fault**, labelled as one, so nobody re-hunts it as a code bug; a **pre-existing defect**, labelled so the reader knows this change is not answerable for it — it is still a genuine defect, and it does move its unit's result, because the scale's fault question maps that attribution to a fault answer and the result tracks whether the unit behaved as claimed while the tag carries answerability; and a failure attributed as **unresolved**, given a prominent line saying what was missing that would have settled it, so the reader knows the label was forced by absent evidence rather than earned by it.

## Usability findings, in a section of their own

Friction findings report in their own section, never merged into a functional result and never modifying one — [ux-walkthrough](../modules/ux-walkthrough.md) owns why the two may not collapse in either direction. They arrive already filtered, each recorded against that module's reportability bar at the moment it was observed, so this phase neither re-litigates that bar nor admits a finding at report time that was never recorded against it. `(basis: derived from phase 3's record discipline)`

Friction findings are **not graded or ranked** here, and neither is the functional side — no severity, no priority, on a friction finding or on a unit that `fails` alike ([verdict-scale](../rules/verdict-scale.md) fixes what the scale does not grade). Each finding carries its step and its anchor; prioritisation belongs to whoever owns the change.

Where flows were driven as a named persona, every finding from that pass is scoped to that persona's path and says so; a claim about users in general drawn from one persona's drive is `inferred`, and labelled so. **Where an experiential pass could not be performed at all**, report it as not performed with the reason, as narrowing — never silently absent, and never substituted with a reading of the code. That is distinct from a flow-and-persona *unit* whose access path could not be exercised: that unit is graded, by the scale's degrade cases, and does not disappear into a footnote while the base unit's `holds` reads as *holds for everyone*.

## Under `--from-spec` — report per requirement

The graded unit becomes the requirement, so the report is keyed to the spec's requirements rather than to flows: each requirement takes its result from the flow or flows that exercised it, rolled up over that subset by the same rule as the headline, and a flow that exercised several requirements reports under each. A requirement that **no flow could reach** is a unit that exists and was not driven — it takes the result the scale gives that case: `fails`, with the non-resolution as its reproduction, or `not checked`, with the reason it could not be reached. Never as met, and above all never *missing from the report*: a requirement quietly absent from a per-requirement report reads as covered, which is the one failure mode this reporting mode exists to prevent.

The converse case arises only with `--flows` set as well, and it reports rather than vanishing: a **driven flow that exercises no requirement** takes its result like any unit and appears in a short section of its own, keyed by flow name and labelled as outside the spec's requirements, so it neither disappears from a per-requirement report nor gets filed under a requirement it did not exercise. It counts in the tally and in the headline ladder, because it is a unit the run graded. `(basis: derived from the per-requirement rule above)`

A partially exercised requirement splits rather than rounding, one result per part, as the standard requires: the reached part takes its result, the unreached part is `not checked` with its reason, and the requirement is not reported as met on the strength of the half that ran. And the headline in this mode may not read as *the spec holds* while any requirement is not checked — the honest form states how many requirements hold, how many fail, how many are unsettled, and how many were not checked.

## Hand off; do not fix

verify's deliverable is the verdict, and it repairs nothing: a run that turns its own finding green has checked a change nobody else has seen. Each finding leaves as a named hand-off the caller runs, not by work performed here.

- A defect whose **mechanism is not established** — the common case, since phase 4 stops at attribution — is handed to **[debug](../../debug/SKILL.md)**, with the reproduction as its seed. Name the hand-off; verify doesn't run it, and doesn't root-cause the defect here.
- A defect whose mechanism **is** established and whose fix is understood is handed to **[develop](../../develop/SKILL.md)**, with the finding as the work item. Name the hand-off; the act that ran verify runs it, since editing the change mid-verify would make the verdict about different code. The discriminator between these two is whether the mechanism is established — not how small the fix looks, which is exactly the judgment a run that has not diagnosed anything is worst placed to make.
- Getting the verdict **in front of people** is the caller's, through [communicate](../../communicate/SKILL.md) and the act's delivery. verify returns the verdict and routes nothing itself, and deliberately has no flag for it.
- An **environment fault** goes back to whoever owns that environment, with the repair — or the reason none was attempted — recorded. It is not a code change and does not become develop's work item.

The report names the hand-off against each specific finding and stops there, in every context. Naming it discharges the obligation; doing the other skill's work in its place does not.

## Before it goes out, read it as its reader

Put the finished report through [deliver-at-the-readers-register](../../../craft/writing/deliver-at-the-readers-register.md) before delivering it, applying its honesty floor item by item from the rule, not from memory.

## Output

The verdict, returned to the caller: the headline with its unit set, its environment, and its un-driven set — or, for an empty unit set, `not checked` with its reason in its place; the per-unit results with their scope, or per-requirement results under `--from-spec` with requirements not checked called out and any driven-but-unmapped flow in its own section; a reproduction-bearing finding for every defect, with environment faults, pre-existing defects, and unresolved failures labelled as such; usability findings in their own section; and the named handoff for each finding.
