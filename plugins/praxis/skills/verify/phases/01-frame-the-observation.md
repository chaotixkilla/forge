A run that starts driving before its flows are framed observes whatever happens to be easy to reach and then reports it as though it settled something. verify's evidence is expensive to produce — a real instance, standing up, driven by hand through the surface a user actually touches — so *what* gets driven is decided here, from the change or from a spec, and never from what is convenient once the app is up.

## Pin the change under observation, and where its claim is read from

Every later step says "the change" and one thing has to fix what that is, or two runs frame two different subjects. **The change under observation is the set of version-controlled differences between the project's integration line and the working tree** — the uncommitted edits plus the commits made on this line since it diverged from the integration line — never the task's documentation where it sits inside the working tree, which is the task's record, not the work — whose base is *derived* each run (the repository's own default integration branch, resolved from the repository rather than assumed by name) and never a hard-coded ref. Where that base cannot be derived — a detached or root state, no resolvable default — fall back to the uncommitted working-tree differences against the current commit. Either way, **state the window you settled on** in the framing output; it is what "nothing changed" and the pre-change **baseline drive** in [real-defect-vs-environment](../rules/real-defect-vs-environment.md) are both relative to. `(basis: derived from review's change window)`

**The claim material** is that window's own statement of intent — the messages recorded with the commits in the window, the branch's own description where the project keeps one, read locally — a hosted review request's description isn't read, since verify stays ambient — and any spec the change itself references — read *together with* the differences, which say what actually moved. The differences bound the claim: an intent stated in that material but absent from the window is not part of this run's claim (record it as stated-and-not-present); a difference the material never mentions still frames a claim, because unstated behaviour is exactly what a drive is for. `(basis: maintainer, 2026-07-27)`

## Name the claim in observable form

For each flow, write what the running system must be seen to do: at which step, what appears, changes, or arrives, and — per the derivation below — what must **not** happen. "The checkout handler is correct" is not a claim this skill can settle; "completing checkout from a cart with one item produces a confirmed order and a confirmation the user can see, and never charges twice" is. Claims come from the claim material above, or from the spec under `--from-spec`; they are never invented to fit what is easy to drive.

Each framed claim must be settleable by an **observation** in the sense [observation-over-inference](../../../craft/evidence/observation-over-inference.md) defines one. Run each candidate claim through that rule's discriminator before accepting it: a claim only an inference could settle ("the query is efficient", "the handler is wired up", "the state is consistent") is not yet framed. Restate it as the observable consequence you would watch for, or strike it and record that this claim is outside what a drive can establish. A claim left in inferential form silently becomes a code-reading conclusion once the driving starts.

**The negative half, derived rather than invented.** Take **one negative claim per guard the change introduces or alters** — every refusal, validation, limit, exclusion, or single-use condition visible in the window — plus every negative the claim material states in words. The set is **complete when every such guard has exactly one negative claim and every stated negative is written down**; there is no requirement to imagine others, and a negative with no guard behind it and no statement in the material is not framed. `(basis: maintainer, 2026-07-27)`

## Select the flow set — three sources in a fixed precedence

Exactly one source supplies the flow set, chosen by the first rule that matches:

1. **`--flows=<list>` is given** → the set is exactly the named flows, in the order given. The list is authoritative: it is not filtered by the in-scope bar below, not extended with flows the change also touches, and not silently trimmed. Anything the change touches that is not on the list stays unobserved and is reported as such. `(basis: derived from SKILL.md's --flows contract)`
2. **otherwise `--from-spec=<path>` is given** → derive one flow per requirement in the spec: for each requirement, the concrete path through the running system that would show that requirement met. The report is keyed per requirement rather than per flow, which is what makes a requirement **no flow could reach** surface as unobserved instead of vanishing; record such a requirement here, at framing time, with why nothing reachable satisfies it, and carry it forward. `(basis: derived from SKILL.md's --from-spec contract)`
3. **otherwise** → frame the set from the change under observation: the flows the change itself can alter, by the bar below. Never "all the flows in the application" — that is unbounded work for a pre-landing check, and it dilutes the run's attention away from the surface at risk. `(basis: derived from SKILL.md's step 1)`

A lower-precedence source never contributes flows to a higher one. **When both flags are present**, `--flows` supplies the set and `--from-spec` supplies the report key: drive exactly the listed flows, report per requirement, mark every requirement no listed flow reaches as unobserved — and, for the converse, carry every listed flow that exercises **no** requirement forward as its own keyed entry, so it is reported with its result rather than dropped for having no requirement to sit under ([report-the-verdict](05-report-the-verdict.md) holds the section it lands in). `(basis: maintainer, 2026-07-27)`

**Flow names are the project's own vocabulary** — whatever this codebase calls a flow is a valid name, and the domain is **open by design**, being a property of each project rather than of this file. What is *not* open is name resolution: resolve each given name to a concrete path through the running system, and a name that resolves to nothing is reported as **not found**, never quietly dropped and never substituted with the nearest-looking flow — a run that silently drives `password-recovery` when asked for `password-reset` reports a verdict about a flow nobody asked about. Drive the names that do resolve; report the ones that do not, with what you searched.

## The in-scope bar for change-framed flows

A flow enters the default (source 3) set when **both** hold:

- **It is user-reachable** — a path a user or an external caller can travel through an entry point the product exposes, rather than a code path only a harness or an internal caller can enter. `(basis: derived from SKILL.md's defining distinction)`
- **The change can alter what a user observes on it** — the changed code executes on that flow's path as the running system runs it, or on something the flow depends on at run time, or on the wiring and configuration that put the flow in reach. A flow the claim itself asserts is reachable is in the set even when no traced path reaches it: that unreachability is what the drive will show, graded by [verdict-scale](../rules/verdict-scale.md)'s guard 2. Establish the rest by tracing from the entry point inward, not by file adjacency: sharing a file with the change is not a relation, and being three modules away on the executed path is. **When tracing is inconclusive, include the flow** and record the uncertainty, so the report shows why it was in the set: driving one extra flow costs a few minutes, while missing the flow that broke costs the whole point of the run. `(basis: maintainer, 2026-07-27)`

The bar governs source 3 only. Under `--flows` the caller has already decided; under `--from-spec` the spec has.

## Enumerate each unit's framed steps

With the set fixed, the last thing framing owes is the **step list per unit** — because the scale's load-bearing cut, one unobserved framed step bars `holds` with no tolerance, is counted over a list only this phase can produce. Leave it implicit and the coarser framing wins the better verdict for free. So for each unit, **write the ordered steps**, at this granularity: **one step per user action whose claimed effect is separately observable at a layer of its own**, plus **one step per framed negative**, whose claimed effect is that the named thing does not happen. Two consecutive actions with one observable effect between them are one step; one action whose effect shows at two layers is still one step, with both layers named on it. Anchor the granularity against the five-step `holds` anchor in [verdict-scale](../rules/verdict-scale.md). `(basis: derived from the scale's no-tolerance cut being counted over these steps)`

**The unit boundary.** A step belongs to *this* unit when the claim under check names its outcome as part of the same outcome; a step whose outcome is a claim of its own is a unit of its own. Signing in with a newly reset credential is a *step* of the reset unit where the claim is "the user can reset and then get in", and a *unit* where the claim material treats sign-in as its own asserted behaviour. Decide it from the claim material, record which you chose, and do not let both readings run — the tally and the headline scope differ between them. `(basis: maintainer, 2026-07-27)`

The list is not sealed here: [exercise-the-flows](03-exercise-the-flows.md) appends an unhappy path its own firing conditions required it to drive, recorded as an amendment to this list, and the amended list is what the verdict counts.

## When there is nothing to frame

**The empty case — no user-reachable behavior changed.** A change can be real and touch nothing a user can reach: an internal refactor with no observable delta, a configuration or documentation change, a code path nothing yet points at. The flow set is then empty, and that is a **real outcome of this run**, not an error and not a quiet pass. Two states must not collapse into each other, because a later reader cannot tell them apart from the flow set alone:

- **Traced empty** — you traced every surface the change touches and can name, per surface, why nothing user-reachable is affected: an absence claim, `traced` in the sense of [results-and-certainty](../../../craft/evidence/results-and-certainty.md)'s absence claims, because the search covered every place the behaviour could be. Record the traced surfaces and those reasons; this is a finding with evidence behind it.
- **Untraced** — anything short of that, such as a change whose reach you could not trace (an opaque surface, a build step you cannot follow, a dependency you cannot resolve). Record what blocked the trace. An empty set you could not trace is *not* a shown nothing-to-verify, and writing it as one manufactures a clean result out of a failed framing.

`(basis: maintainer, 2026-07-27)`

Either way the run stops here rather than standing an app up to observe zero flows, and the framing — which state, with its evidence — is carried to [report-the-verdict](05-report-the-verdict.md), which resolves it to the `not checked` reason [verdict-scale](../rules/verdict-scale.md) gives that state. Do not invent a flow to have something to drive, and do not fall back to driving unrelated flows so the run has output.

**The reject case — no source and nothing to derive from.** With no source flag *and* no change to frame from — not a version-controlled tree, no derivable window and no uncommitted differences either, or a working state you cannot diff — the run has no scope and cannot manufacture one. "Nothing changed" means the window pinned above is empty, not that the working tree is clean while committed work sits in the window. Stop and route back to the caller for an explicit `--flows` list or a spec, stating the window you resolved and what you looked for.

**The unreadable-spec case.** If `--from-spec` names a path that is missing or unreadable, stop and report that — do not silently fall back to change-framing. A readable spec with no running-behaviour requirement is an empty set, by the scale's guard 1; a requirement that exists but that no flow can reach is a unit of its own, graded by the scale. `(basis: derived from verdict-scale's empty-set guards)` The caller asked for a report keyed to that spec's requirements.

## Output

The framed observation: the **window** the change was resolved to; the claim per flow in observable form with its derived negatives; **the ordered framed steps per unit**, and the unit boundary chosen where one was in question; the flow set with its source named; the in-scope reasoning for change-framed flows; any unresolved flow name or unreachable requirement recorded as unobserved; and — in the empty case — the traced-or-untraced framing carried straight to the verdict. This is what [stand-the-app-up](02-stand-the-app-up.md) provisions for.
