The observation happens here, and it happens once. Every later phase consumes what this phase writes down: the classification works from it, the verdict is assigned off it, the reproduction is written out of it. So the discipline is not *drive the flows* — driving is the easy part — it is **writing down what the running system actually did, step by step, as it does it**, at a fidelity someone who was not in the room can replay. Anything reconstructed afterwards, from memory or from what the code was supposed to do, is not an observation, and everything this skill delivers rests on that difference.

## Drive one flow at a time, recording each step as you take it

Drive one flow to completion — or to its first stopping point — before starting the next, entering each through the entry point established when the instance was stood up. Write the record entry for a step *before* you take the next one: the flow, the step, the action taken with its input, what the system did as perceived through the surface you are driving, and whether that matched the claim under check `(basis: ratified by the maintainer 2026-07-27, on the build's recommendation — those five fields as the minimum entry — derived here, because an entry missing any one of them cannot be replayed by someone who was not present, and replay is exactly what the classification and reproduction phases consume)`. A narrative composed at the end of a drive is memory: it smooths over the step you half-watched and fills the gap with what you expected. Recording as you go also means an interrupted drive still leaves a usable partial record instead of nothing.

**The order is fixed, because a narrowed drive makes it matter.** Under `--flows` it is the order given. For a set derived from a spec or from the change, order it: **(1)** any flow another framed flow needs as a precondition comes before that flow; **(2)** then the flows whose own path the changed code executes on, before the flows the change reaches only through a run-time dependency or through wiring and configuration — the same three-way distinction the in-scope bar drew when the set was framed; **(3)** ties in the order the framing recorded them. And **there is no budget the executor invents**: a drive stops short only on a limit the caller stated for this run, or on an obstacle these phases name (an unreachable surface, an irreversible step, a dead instance). Record which of the two stopped it. `(basis: ratified by the maintainer 2026-07-27, on the build's recommendation — that three-step order, and no self-set budget. Because "stopped on budget" is a recorded narrowing below, and with neither an order nor a budget source two runs on identical inputs drive a different subset and report a different un-driven set; ordering preconditions first is forced by the drive itself, and putting the change's own new behaviour next is the proposal — the surface at risk is what a truncated run should have observed.)`

Two shapes need deciding before you start. A flow that branches or loops is driven along **one named path**, and the path belongs in the record — a flow name with no path is not reproducible, and a second path is a second flow. A flow of a single step still gets an entry and an effect to confirm, not a glance. And when the framed set is **empty** — a change with no user-reachable behaviour, or given flow names this instance has no such flow for — drive nothing, record the empty set with its reason (a named flow that does not exist is recorded as not found, never mapped onto the nearest similar-looking flow), and hand that record on. Where an empty set lands is the verdict's business; inventing a flow so there is something to drive corrupts the record instead.

## Check the effect, not the signal

A step is confirmed when the **effect it claims** is observed at the layer where that effect becomes visible — not when a signal that usually accompanies the effect appears. Which signals are not effects, and why the two come apart, is [observation-over-inference](../rules/observation-over-inference.md)'s success-surface section; the procedural move is this phase's: for every framed step, **name the effect the step claims and the layer at which it is visible, then go and look there** — read the created thing back through the surface that displays it, re-enter the flow and see the state persist, observe the downstream consequence at the boundary it crosses. Then class every entry in the record by that rule's discriminator and label it with the class it falls in: an entry resting on a signal alone lands on the inference side, and it may be reported as one, but it has not confirmed its step.

## Label each flow by how completely it was observed

These labels track **coverage of the observation only** — how much of the flow was watched — and not whether what was watched was correct. A flow every step of which was watched and which plainly misbehaved is *fully observed*, and it travels forward as a failure to be attributed; conformance to the claim is question (b) and (c)'s confirmation half in [verdict-scale](../rules/verdict-scale.md), never a label here. Assign each flow exactly one:

- **fully observed** — every framed step of the flow produced an observation-classed entry recording what the system did at that step.
- **partly observed** — at least one framed step produced one, and at least one did not: unreached, skipped, held back, or resting on a signal alone with nothing read at the effect's own layer.
- **not observed** — no framed step of the flow produced one at all.

The *fully* / *partly* line is a count, not a feeling: one framed step short of an observation entry drops the whole flow to *partly observed*, however healthy every other step looked `(basis: this skill's own contract, which fixes that an unobserved step is unobserved rather than passing and that a flow containing one is not a clean pass — so the label may not round a gap up)`. The *partly* / *not observed* line is whether the flow produced any observation-classed entry at all. An entry counts here only where the step was driven **through the real entry point** — a substitute move leaves the step it replaced unobserved, per the fidelity section below — which is what keeps this cut and [verdict-scale](../rules/verdict-scale.md)'s question (a) counting the same steps rather than two similar-sounding things. This phase's own half of it: a flow that failed at its very first step is *partly observed*, because that failure was itself observed, and filing it alongside "we never looked" loses the most report-worthy thing a drive can produce. Anchor the top with a flow driven from its real entry point through its last step, each step's result read back at the layer that shows it; anchor the bottom with a flow named for the run that this instance has no reachable entry point for — zero entries, label *not observed*, reason recorded. Every *partly* and *not observed* flow names its missing steps and why each is missing; every entry resting on a signal alone is named too, since the verdict's confirmation half reads those.

## Keep entry-point fidelity live for every step

Choosing the real entry point happened when the app was stood up; *holding* it is this phase's problem, because the pressure to reach behind the surface arrives mid-drive — a step you cannot get past, a state that takes four screens to arrange, a guard you would rather flip than satisfy. Before making any such move, re-apply the skipped-layers test defined in [reach-the-real-entry-point](../rules/reach-the-real-entry-point.md) to the move itself: which layers does it skip, and would a defect living in one of them now be invisible? The line to hold is this — arranging **preconditions the flow assumes** (an account that exists, data already there, a starting state the user would arrive with) is setup and stays legitimate; the moment a move *performs a framed step of the flow itself*, it has stopped being setup and become a substitute drive, and the step it replaced is not observed regardless of what happened after `(basis: the contract's boundary against test — verify's evidence is an observation of the running system reached the way a user reaches it, and a seam that genuinely cannot be driven is narrowed scope, never a substitute drive)`. A substitution taken by reflex is recoverable if you record it; unrecorded, it converts every remaining step of that drive into a harness run that reads as a pass.

## Drive the unhappy paths a suite structurally cannot see

Do not drive every failure branch, and do not drive none. **A path that fires a condition below is not an extra observation with no home: append it to its unit's framed step list as an added step, with its claim (what the user should see, or what must not happen) and the note that framing was amended mid-drive.** From that point it is a framed step like any other — it counts in the flow's label, its misbehaviour is a failure the next phase attributes on that unit, and it can move that unit's level. A fault found on a required unhappy path and filed as a loose note outside the framed unit is a fault that clears a change. `(basis: ratified by the maintainer 2026-07-27, on the build's recommendation — a fired unhappy path becomes an added framed step of its unit rather than a note beside it, with the amendment recorded. Because the four conditions below *require* the drive to take these paths while framing never created them, so nothing graded them: one run filed such a fault on the unit and reported `defective`, another filed it as a note and reported `works`, on the same observed leak.)`

An unhappy path belongs in *this* drive when at least one of these fires: it **surfaces something to the user** — an error state, a message, a redirect, a half-filled form — so the half that matters exists only in the running system; it **crosses a boundary a suite substitutes** — an unavailable dependency, a refused credential, a rejected charge, a timeout — so the harness's version of it is a fake; the change itself **introduced or altered the branch** — a new guard, a new validation, a new failure mode — so nothing yet establishes that it is reachable at all; or the question is **recovery**, whether a user who hits it can get back and still finish, which needs a live session to ask. When none fires, the path is a case for the automated suite rather than for this drive: enumerated input combinatorics, boundary values, and internal error branches with no user-visible surface are cheaper and stricter there, and driving them here buys nothing the suite does not already own `(basis: ratified by the maintainer 2026-07-27, on the build's recommendation — those four firing conditions, with "not driven here" as the default — derived from what a real drive buys over a harness, and proposed over the two nearby alternatives, since "drive every failure branch" makes each run unbounded and re-buys the suite's coverage, while "happy paths only" leaves a change's brand-new guard as the one thing nobody has established is reachable)`.

## When a flow fails mid-way

Finish the record entry for the failing step first — what you did, what was claimed, what you observed instead — while it is still in front of you; that entry is what the next phase classifies and what the reproduction is written from. Then decide continuation by **reachability**: if the flow's remaining steps can be entered without the failed step's effect, keep driving and recording them; if they cannot, stop the flow there and mark the remaining steps unobserved-because-blocked, naming the step that blocked them. Apply the same test across flows — a flow that needs the failed flow's effect as a precondition is marked *not observed* with the dependence named, and a flow that does not is driven `(basis: ratified by the maintainer 2026-07-27, on the build's recommendation — continue-by-reachability — derived, and proposed over halting the whole drive at the first failure, which discards independent observations that cost almost nothing to collect and are what let a report close in one round)`. What you may never do is infer an unreached step's outcome in either direction: it did not pass and it did not fail, and a step recorded as failing "because the earlier one did" is an inference wearing an observation's clothes.

One failure is not flow-level at all. If the instance stops serving — died, hung, no longer reachable — stop the drive, record every un-driven flow as *not observed* with that reason, and hand over what you have; standing it back up and driving again is a fresh drive recorded as one, and the fact that a restart cleared the failure is itself an observation worth writing down. Re-driving to find out whether a failure is *stable* is not this phase's move either: record it once, faithfully, and leave the re-drives to the phase that classifies it.

## Record a narrowed drive as narrowing, not as a smaller success

A drive is narrowed whenever less was exercised than the framing asked for, and each source has a required move. Given flow names replaced the framed set: the rest are *not observed*, not absent from the report. A step could not be reached through the real surface: narrowed scope, no substitute. An **irreversible** step — one that charges, sends, or destroys real state — with no isolation in place: stop short of performing it, record it as not driven with the reason, and note that observing it needs an isolated instance, which is a fresh run under `--sandbox` rather than a mid-drive improvisation. The only available access path to the surface skips layers a user's path would not (the **degraded** drive): exercise what that path does reach, record which layers it skipped, mark the rest unobserved — and do not fall back to reading the code, because a reading is not an observation and cannot enter this record at all. A framed step's claimed effect depends on a fact the environment record holds as **substituted or unknown**: drive the step, record that the effect could not be confirmed against a real fact, and name the dependence — the cap is [verdict-scale](../rules/verdict-scale.md)'s substitution-or-unknown cell, not this phase's call. Or the drive was **stopped short** — by the caller's stated limit or by a named obstacle, per the order section above, never by a budget the run invented. Every narrowing is recorded with three things: what was not driven, why, and what it would take to drive it.

What narrowing does to the verdict follows from *where* it falls. Narrowing **between** flows changes what the run is about: the un-driven flows report as *not observed*, and the flows that were driven are untouched and can still come back clean. Narrowing **inside** a framed flow caps that flow — it is *partly observed*, so the verdict phase cannot read it as a clean pass however well the driven steps went `(basis: the contract's two scoping rules — a pass is scoped to the flows actually driven in the recorded environment, and a flow containing an unobserved step is not a clean pass; between them, the between-versus-inside split is fixed rather than chosen here)`.

## Under `--ux`

Fires only when `--ux` is set; without it there is no experiential pass, and its absence is not a claim that the flows were pleasant. Once a flow's functional pass is recorded and closed, walk that same flow again as someone meeting it for the first time and record each point of friction against the bar defined in [ux-walkthrough](../modules/ux-walkthrough.md) — friction that does not clear that bar is not recorded. Keep it a second pass rather than something done while driving, so an experiential note can never edit the functional record; the findings ride alongside the flow's label and never by themselves turn a functioning flow into a defect.

## Under `--as-user=<persona>`

Fires only when `--as-user=<persona>` is set: re-drive the flows in that persona's shoes and report what *that* user encounters, stating each finding in the form [as-user](../modules/as-user.md) defines for one — including, where the persona names a user of assistive technology, exercising the flow through that access path and reporting what is perceivable and operable through it. Findings stay scoped to the named persona. If that access path cannot be exercised at all, the pass is recorded as not performed and named as narrowing per the section above; a statement about a user whose path you did not walk is an inference about this run, not an observation of it. Both flags may be set together, in which case each flow carries both extra passes — and neither substitutes for the functional pass the later phases read.

## Output

The drive record, handed to [separate-defect-from-environment](04-separate-defect-from-environment.md): per flow, the ordered step entries with each classed as observation or inference; the flow's observation label with every missing step named; the narrowing record; and the set of flows that did not behave as claimed, which is what the next phase classifies — flows that behaved as claimed pass through it untouched. No verdict is assigned here, and nothing is repaired here: a fix attempted mid-drive silently changes the system this record describes.
