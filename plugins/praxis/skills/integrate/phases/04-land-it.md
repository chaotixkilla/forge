This is where the change enters the shared line. The gate is green ([run-the-gate](03-run-the-gate.md)), the increment is reconciled ([prepare-the-increment](02-prepare-the-increment.md)); now it lands — either merged directly or opened as a review request — into the **integration target** resolved in [assess-the-change](01-assess-the-change.md) (an epic/`develop` branch, or the trunk), through the host, in the way the team actually works. The two things this phase must not get wrong: landing on anything less than green, and imposing a merge style the team doesn't use. Both are pinned below.

## Hosted actions go through the vcs capability

Landing touches the *host platform*, so delegate every hosted action — open a review request, merge, set a status — to the [vcs](../../vcs/SKILL.md) capability; the dispatch resolves to whichever provider is configured, and integrate names the capability, never the provider. (Routine local git — the commits and reconcile — was ambient in [prepare-the-increment](02-prepare-the-increment.md); this phase is the platform-mediated part.) integrate declares no vcs prerequisite — the `vcs` skill owns `tools.vcs` (doer-owns-prerequisites).

## Choose the landing path

The path follows the team's flow and what the **target** permits ([match-the-team-flow](../rules/match-the-team-flow.md)), with the merge strategy (merge-commit / squash / rebase) taken from the detected convention, not a house default. **Resolve what the target permits *up front*, don't discover it by failing:** read the target's landing constraint — does it require a review request (branch protection / required review) or allow a direct merge? — through the vcs capability before attempting to land, rather than attempting a direct merge and reacting to a rejection (a rejected merge attempt can leave a side effect and is a different question than the caller asked). This constraint is a team-flow fact, detected alongside the merge strategy in [match-the-team-flow](../rules/match-the-team-flow.md), and it is read for the *resolved target* — an epic branch may be unprotected where the trunk is protected, or vice versa.

**When the landing constraint can't be read (`tools.vcs` unavailable), degrade to the safe side, never the risky one.** The constraint read goes through the vcs capability, so if that backend is unconfigured the constraint is unknown. Do **not** assume direct-merge is safe — the target may be protected. Instead: if the target is **purely local** (no remote configured), a direct merge is ambient local git and proceeds normally (there is no shared/protected line to endanger); if a **remote exists** but the constraint can't be read, degrade to `--commit` semantics — record the coherent local commits, stop at *committed-only*, and report that the change was committed locally but not landed upstream because the landing constraint could not be determined (the `vcs` skill owns guiding through `init:vcs`). Never push an unreviewed change to a possibly-protected shared target on a guess. `(basis: safe-degrade — a missing vcs backend makes the protection state unknowable, and the unsafe assumption (blind direct push) risks bypassing a required review, while the safe one (stop at local commits) is fully recoverable; surfaced by the dogfood run against an unconfigured repo. USING-ANVIL §2 per-capability degrade.)`

- **Default (no landing flag): open a review request for a collaboration repo; ask a solo dev.** Alongside the landing constraint, detect the repo's **collaboration posture** — more than one contributor in recent history, a configured team roster of more than one, an existing PR/review practice, or branch protection all signal *collaboration*; a single contributor with none of these signals *solo*. Then:
  - **Collaboration repo → open a review request.** A shared line is never direct-merged by default — review-before-merge is the norm for work others depend on, whether or not protection enforces it.
  - **Solo repo → ask** whether to push directly to the target or open a review request. A solo dev's landing is often side-work they may not want to merge right now, so integrate does not assume — it asks. When a solo run **cannot be asked** (unattended), default to opening a review request (landable when the dev chooses, never force-merging not-yet-ready work) rather than a direct merge. `(basis: the unattended-solo fallback is the safe side of the maintainer's ask — a PR loses no work and forces no merge; derived, 2026-07-11.)`
  - **Branch protection always wins:** where the platform requires a review request on the target, open one regardless of posture.

  `(basis: ratified by the maintainer, 2026-07-11 — a collaboration repo requires a PR (a shared line is never direct-merged by default, even where protection doesn't enforce it); a solo repo is asked (direct-push vs PR) because solo landings are often not-yet-merge-ready side-work; branch protection always mandates a PR.)`
- **`--pr`** ([open-for-review](../modules/open-for-review.md)) forces the review-request path even where a direct merge is allowed — to get review on *this* change — and terminates the run at *opened-for-review* (a human merges later).
- **`--commit`** ([commit-only](../modules/commit-only.md)) never reaches this phase — it terminated the run at *committed-only* in [prepare-the-increment](02-prepare-the-increment.md).

## Never land on red

Re-affirm the gate at the moment of landing: land only on green ([green-before-land](../rules/green-before-land.md)). If the target moved since the gate ran, the gate is stale — re-reconcile and re-gate before merging ([integrate-against-current-target](../rules/integrate-against-current-target.md)), rather than merging a base the gate never vetted. Attach the context a reader needs: the merge/PR carries the why-and-shape message ([commits-tell-the-why](../rules/commits-tell-the-why.md)), scoped to one coherent concern ([one-coherent-change-per-unit](../rules/one-coherent-change-per-unit.md)).

## The run's terminal outcomes — the partition

Every **executing, run-to-completion** integrate run resolves to **exactly one** terminal outcome; this is the whole-skill outcome set, produced across the phases and reported in [confirm-and-report](06-confirm-and-report.md). The outcome is read off the change's **resting physical state** — *is the change merged into its integration target? is a deploy of it physically live on a requested environment?* — not off which failure the run hit and **not off the post-ship health verdict**; `--on-fail` ([failure-policy](../modules/failure-policy.md)) determines the resting state, it does not add outcomes, and the health verdict is a **separate reported axis** (below).

**Two non-member carve-outs** (states that are not a completed run):
- **`--dry-run`** → not a member: a preview mutates nothing, so it reaches no resting state. It reports its *would-be* outcome — **computed by evaluating the members below as if `--dry-run` were unset**, resolving the target's landing constraint read-only, never by attempting a mutation (e.g. "would-be: shipped"). `(basis: the preview flag plans without mutating — a planned outcome is not a reached one.)`
- **`--on-fail=ask`, paused** → not a member *yet*: an `ask` policy at a failure is a non-terminal pause awaiting a human decision; the run has no terminal outcome until the human acts, at which point it resolves to whichever member its resolved action reaches — **retry** → re-enters the flow (to a terminus); **stop** → abort's resting state; **roll back** → the resting state after the reversal; **continue** (advisory failures only) → proceeds to the normal terminus. Every decision `ask` offers ([failure-policy](../modules/failure-policy.md)) maps onto a member. `(basis: ask is interactive and non-terminal by construction — failure-policy.md; like dry-run, it is carved out rather than forced onto a member it hasn't reached.)`

**The five members** (the resting physical state of a completed run). A landed/shipped change carries three **orthogonal reported axes that never move the member** — *exposure* (dark behind an off-switch / partial canary / full), *health* (healthy / needs-rollback / indeterminate), and any *pending `--on-fail` action* — reported alongside like fields on a record, none of them a determinant of which member the run reached:
- **committed-only** — the change is committed **locally only**, not pushed or landed (`--commit`).
- **opened-for-review** — the change is landed as a **review request against the target awaiting a human merge** (`--pr`, or branch protection required it). A supplied `--target` is reported *deferred* (per the close section below), not a separate outcome.
- **stopped-on-failure** — the change is **not merged into its target**: a failed required gate, an unresolvable conflict, or a backend unavailable for the *core landing* (e.g. `--pr` with no vcs) halted it before merge, **or** a *landing* failure's `rollback` reversed the merge back out. The target line does not carry the change.
- **shipped** — the change **is merged into its target and a deploy of it is in place on a requested environment** ([ship-to-target](05-ship-to-target.md)), not reversed. This is reachable **only when the requested `--target` env deploys from the resolved target branch** (the per-(target, env) lookup phase 05 makes) — trunk→production, or a Git Flow `develop`→staging; a land where no env deploys from the target never reaches it (see *merged*). *A deploy exists on the environment* is the whole test — **how exposed** it is (dark / 5% canary / full) and **how healthy** it is (the post-ship verdict) are the orthogonal axes above, reported and pending their own follow-up, never folded into shipped-vs-merged. A change deployed at 5% and judged *needs-rollback* is still *shipped* (a deploy of it is on the environment); it becomes *merged* only if the deploy is **reversed** (removed).
- **merged** — the change **is merged into its target but no deploy of it is in place on any environment**: no ship was requested (no `--target`), **or** the requested `<env>` **does not deploy from the target** (e.g. `--target=production` on a `develop`/epic land — production deploys from `main`), **or** the ship degraded (`tools.ci` unavailable or the env→source mapping unreadable), **or** the ship was attempted and *nothing deployed* (it failed before promoting any stage), **or** a deploy was **reversed** (a `rollback` removed it, including after a *needs-rollback* verdict). A note carries which; the change is in the target line, nothing of it on an environment.

**A run rests at the deploy state its strategy reached.** integrate is a single land-and-ship pass, not a long-running ramp driver: for a staged/canary or behind-a-switch strategy it promotes to the stage its strategy — and its `--watch` window — reaches, and rests there as *shipped*, reporting the exposure reached and the stages or flag-flip that remain for a follow-up. It does not block to drive a multi-stage ramp to full exposure. `(basis: ratified by the maintainer, 2026-07-11 — a run rests at the promoted stage (partial exposure counts as *shipped*, the remainder tracked for a follow-up), not driving every staged rollout to full before returning, because a progressive ramp's bake times outlast a single invocation.)`

**Determination (read top-down, first match wins):** `--dry-run` → carve-out · a `--on-fail=ask` pause → carve-out until resolved · `--commit` → committed-only · landed as a review request → opened-for-review · else read the resting physical state: **not merged into the target** → stopped-on-failure; **merged into the target with a deploy in place on an environment** → shipped; **merged into the target, no deploy on an environment** → merged.

**Partition proof:** past the two carve-outs and the two early exits (`--commit`, review-request), the three remaining members partition on **two primitive binary physical facts** a cold executor reads off the world (not judgments) — *(a) is the change merged into its integration target?* and *(b) is there a deploy of it in place on a requested environment (not reversed)?* — exhaustive and mutually exclusive: **not-merged** → stopped-on-failure (b moot); **merged + a deploy in place** → shipped; **merged + no deploy in place** → merged. Fact (b) can only become true when a `--target` env **deploys from** the resolved target branch (the per-(target, env) lookup in phase 05); a land where no env deploys from the target never attempts a ship, so it rests at *merged* by fact (b) = no. This generalizes the old trunk-only partition without adding a member — an epic land, or a `develop` land with `--target=production` (production deploys from `main`, not `develop`), is just a *merged* with fact (b) false. Fact (b) also cannot wobble because everything else that could color it is pulled onto the orthogonal axes: **exposure** does not move it (dark, 5%, and full are all "a deploy is in place" = shipped), **health** does not move it (healthy / needs-rollback / indeterminate are all shipped until a reversal removes the deploy), and **`--watch`** does not move it (it only decides whether health is observed). Each `--on-fail` action lands the change in one fact by reversing — or not — **the failing stage's own applied effect**: `abort` reverses nothing (rests where it stopped); `rollback` undoes the effect of *the stage that failed* — a *ship* failure's deploy (→ no deploy in place = merged) or a *landing* failure's merge (→ not-merged = stopped-on-failure) — and where that stage applied **nothing** to reverse (a ship that failed before deploying) it is a **no-op that leaves the prior good step**, resting as *merged*, never collaterally reverting the good merge; `continue` proceeds to the normal terminus; `ask` is the carved-out pause resolving to one of these. No completed run is in two facts or none, and no axis, verdict, or observation flag moves it — the crack a per-policy, per-verdict, or per-exposure guard would leave is closed by reading the two primitive physical facts.

## Close the phase

Under `--dry-run`, report the landing path (merge vs. request), the resolved target, the strategy, and the message that *would* be used, without performing the merge. On a direct merge, hand to [ship-to-target](05-ship-to-target.md) with the resolved target and any `--target` — it makes the per-(target, env) ship decision and rests the run at *shipped* or *merged* accordingly (a land whose target no env ships from, or with no `--target`, rests at *merged*). On the review-request path, the terminus is *opened-for-review* → report and stop. (Routing every direct merge through [ship-to-target](05-ship-to-target.md) keeps the ship/no-ship decision in one place — phase 05 owns it — rather than pre-deciding it here.)

**A supplied `--target` on the review-request path is deferred, never dropped.** When the run opens a review request — whether by `--pr` or because branch protection forced it on the default path — the change awaits a human merge, so it cannot ship now. Report the `--target` as **deferred**, in a **deliberately generic** form: state that the change was opened for review and that the ship to `<env>` follows in a later run once the change reaches the branch `<env>` deploys from — **do not compute that hop here.** Resolving *which* branch `<env>` deploys from (and how many merges away it is) is the env→source lookup [ship-to-target](05-ship-to-target.md) makes on the actual shipping run; this path is not shipping, so it states the deferral, not a hop count, and two cold runs write the same message rather than one reading the mapping and one not. `(basis: pin the deferred message generic — the review-request path performs no ship, so it must not depend on a phase-05 mapping read it never does; surfaced by a re-verify cold walk that split on report content. Never silently omit the target the caller asked for.)` This is the same fail-loud discipline `--commit` applies to the downstream flags it forbids ([commit-only](../modules/commit-only.md)) — an unfulfilled ship intent must be surfaced, not swallowed.
