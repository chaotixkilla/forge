Landing put the change into its integration target; shipping puts it in front of users. This phase promotes the merged change to a requested environment — and its one non-negotiable is that *how* it ships is sized to the change's risk, not shipped all-at-once by habit. A reversible rollout is the difference between "flip it off" and "scramble to redeploy while users are down." This phase runs only when there is something to ship to.

## Ship only when a `--target` env is named AND it deploys from the resolved target branch

Two conditions must both hold, or the run rests at *merged* and hands straight to [confirm-and-report](06-confirm-and-report.md) — never inventing an environment:

- **A target environment is named.** `(basis: ratified by the maintainer, 2026-07-11 — shipping requires an explicit `--target`; with none, the run terminates at *merged* and does not promote. Auto-shipping an unnamed environment on every land is the unsafe surprise, and the config model carries no default deploy env.)`
- **That environment deploys *from* the resolved integration target.** Resolve, per (target, env), whether `<env>` is configured to deploy from the branch [assess-the-change](01-assess-the-change.md) landed into — read the environment→source-branch mapping through the [ci](../../ci/SKILL.md) capability (the same deploy config that resolves the promotion path). Route by these outcomes, in order (first match wins), so a cold run lands on exactly one:
  - **`<env>` deploys from the target** → promote (below). (Trunk→production; a Git Flow `develop`→staging.)
  - **`<env>` resolves to a *known* deploy branch that is *not* the target** (e.g. `--target=production` on a `develop`/epic land, where production is known to deploy from `main`) → do **not** promote; report that the change **landed into `<target>`** and that shipping `<env>` follows when the change reaches `<env>`'s known deploy branch. The `--target` is surfaced, never silently dropped.
  - **`<env>` cannot be resolved to a deploy source** — the mapping is unreadable (`tools.ci` unavailable, no env→source config), **or** `<env>` is absent from a readable mapping (an unknown / unconfigured / mistyped env with no known deploy branch) → **degrade**: report *merged*, that `<env>` could not be resolved to a deploy source, and that the ship was not attempted — never promote, and never name a deploy branch that doesn't exist. `(basis: ratified by the maintainer, 2026-07-11 (release-line gate), corrected to a per-(target, env) deploy-source lookup — a branch is a ship source for the environments configured to deploy from it, not by a global "release line" label; a Git Flow `develop` ships to staging but not production. The middle outcome requires a *known* other branch (so its report can name it); an env with no known deploy branch — unmapped or unresolvable — routes to this "could not resolve" degrade, not the middle one. Closes the re-verify contradiction where "deploys-from" and "merges-onward" both matched one branch, and the follow-up split where an unmapped env pulled between the middle and degrade outcomes.)`

With either condition unmet, hand straight to [confirm-and-report](06-confirm-and-report.md) to report *merged* (with the reason — no `--target`, or `<env>` doesn't deploy from the target); do not invent an environment.

## Promote, at a pace sized to risk

When `--target=<env>` is given ([promote-to-environment](../modules/promote-to-environment.md)):

- **Resolve and promote through the ci capability.** Resolve the environment's promotion path and any environment gating, and promote through the [ci](../../ci/SKILL.md) capability's *promote to an environment* operation. Honor environment protection (a required approval or wait timer comes back as a *pending* promotion — surface it and wait, do not force past it).
- **Choose the strategy by risk tier, not by target.** The *how* — all-at-once / small increment / staged exposure / behind a switch — comes from [make-rollout-reversible](../rules/make-rollout-reversible.md), keyed to the risk tier assigned in [assess-the-change](01-assess-the-change.md) (raised, never lowered, for a hotfix). A production target does not force all-at-once; a staging target does not excuse skipping a switch for an irreversible change.
- **For an irreversible-if-wrong change, verify the switch actually reverses without a redeploy.** A rollout is only "behind a switch" if turning it off is a config flip — a flag that still needs a redeploy to disable does not give fast rollback, and a flag/kill-switch identifier must never be one repurposed from older behavior. `(basis: community incident lore — a flag that requires a redeploy to flip is not fast rollback (post-ship postmortems), and reusing a dormant flag's switch for new behavior is the Knight Capital failure class (~$460M, 2012) where a missed-server deploy flipped on repurposed dead code. So the readiness test is "can this be turned off without a redeploy?", distinct from "is it behind a flag?")`

## Confirm the rollout reached the target

A promotion that was *accepted* is not a promotion that *arrived*: confirm the change actually rolled out to **the scope this run promotes to** — for an all-at-once strategy the full target; for a staged/canary or behind-a-switch strategy **the stage this run reaches** (the run rests there per the land phase's "rests at the deploy state its strategy reached," reporting the exposure and what remains) — with the promotion's state came back success for that scope, before handing to [confirm-and-report](06-confirm-and-report.md). A promotion accepted but not actually in place is reported as such (no deploy in place → *merged*), never assumed to have arrived or to be healthy.

## Degrade and fail-policy

- **No pipeline backend:** promotion goes through the [ci](../../ci/SKILL.md) capability. If it is unavailable (`tools.ci` unconfigured), **degrade**: the change is already landed, so the promotion is skipped, not the run — **hand to [confirm-and-report](06-confirm-and-report.md) exactly as the no-target and success paths do**, carrying the *merged* (not-promoted) terminal outcome so P06 emits the canonical report through the communication capability (noting the promotion could not run — the `ci` skill owns guiding through `init:ci`). Never undo the land, and never stop short of the report — the degrade narrows the outcome to *merged*, it does not skip confirm-and-report. `(basis: per-capability degrade; a missing ship backend narrows to land-only but the run still owes its report, USING-ANVIL §2 + confirm-and-report always runs.)`
- **Rollout failure:** apply `--on-fail` ([failure-policy](../modules/failure-policy.md)) — default abort (stop and report, leave recoverable); `rollback` undoes the *deployment* (the merge stays intact — a rollout failure never reverts the merge; where nothing deployed, rollback is a no-op leaving the good merge); `ask` waits for a human. A failed rollout never silently proceeds — and, exactly as the degrade branch above, it does **not** skip the report: hand to [confirm-and-report](06-confirm-and-report.md) with the resting-state terminal outcome (**merged** — the merge stands, no deploy in place), so P06 emits the report through the communication capability.

## Close the phase

Under `--dry-run`, report the resolved target, the chosen strategy (and the risk tier that set it), and the promotion that *would* run — without promoting. On success the terminus is *shipped* → hand to [confirm-and-report](06-confirm-and-report.md) with the rollout result and the risk tier, so the watch and report know what shipped and how.
