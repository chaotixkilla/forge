# notion — project_mgmt adapter

Implements the **project_mgmt** capability for Notion, over the transport configured in `tools.project_mgmt.transport` (mcp or api). The [project-mgmt](../SKILL.md) skill names the operation and dispatches here; each operation below is one of the project_mgmt capability's requests, translated to Notion's concrete surface. In Notion a tracker is a **database** (data source) and each work-item is a **page** with typed **properties**; the target database is `tools.project_mgmt.project_key`. Resolve exact property/tool/endpoint names against the live tool at call time (below) — the names here are not frozen.

## Operations

1. **Fetch a work-item** — given a reference (normally a direct page id or URL; where the caller has only a human-facing key, resolve it by querying the database's identifying property — which property carries that key is per-database, confirmed at call time), retrieve the page and read the fields the caller needs: its title, description (page body and/or a rich-text property), acceptance criteria (a dedicated property or a section of the body), labels (a multi-select property), and status (a status/select property).
   - *mcp:* the Notion connector's fetch/retrieve-page call to read the page by id/URL, plus a data-source query when the reference is an item key rather than a direct id. *api:* the retrieve-a-page endpoint (plus retrieve-block-children for body content), or a data-source query to resolve the reference first.
2. **Create work-items** — create one page per unit under the configured database (`project_key`), setting each page's title, description, labels, and status from the caller's unit, and encoding the caller-supplied **dependencies and sequence**. Dependencies map to the database's relation property (page→page) and sequence to its order/number property; because a relation's targets are the pages being created, linking is **two-phase regardless of transport** — create all pages first, then set the relations by the ids the creates returned. Fall back **per field, whenever the database has no property for it**: record dependencies in the page body when there is no relation property, sequence when there is no order/number property, labels when there is no label property — each preserved independently, whichever properties the database happens to define. Recording a field in the body because its property is *absent* is faithful preservation the adapter does on its own — *not* a schema mismatch; the Failure surface below is only for a field whose property exists but *rejects* the value, or a required property the schema won't accept. Creating a set is non-atomic and **two-phase** — one create per page (no transaction), then the relation-linking pass — so a failure can land in either phase. Report per unit against one invariant: **once a page exists, always return its reference.** A page created but not yet linked (e.g. the linking pass was throttled) is returned with its reference *and* its unset dependency links flagged, so the caller completes the linking; a unit whose page was never created is reported by cause — a *transient* failure (e.g. a throttle) to re-attempt, or, where the schema itself blocked creation, the permanent property/schema mismatch below for the caller to reconcile rather than blindly retry. A re-run then never duplicates an existing page, and no dependency is silently dropped.
   - *mcp:* the connector's create-pages call with the parent data source and per-page properties, then a second call to set the relation properties. *api:* create-a-page with `parent` set to the database and a `properties` map per page, then a second pass to set the relations.

## Failure surface

Report failures upward in capability terms — the caller hears an outcome, never a raw HTTP code:

- **Connector not authorized / token missing or lacking access** → report as "project_mgmt backend unavailable," which the caller's degrade path handles (and which the [project-mgmt](../SKILL.md) skill maps to guiding the user through `init:project_mgmt`).
- **Page or database not found / wrong workspace or database** → report "the requested work-item was not found on the configured provider" rather than a 404; do not fall back to a different item or database.
- **Rate-limited or transient network failure** (Notion throttles writes) → report as a *retryable* project_mgmt failure, distinct from a permanent one, so the caller can back off or degrade.
- **Property/schema mismatch** (a property the create needs *exists but rejects* the caller's value — e.g. no status option matching it — or the schema *requires* a property the caller can't supply) → report per unit what the schema refused — whether a field that couldn't be set on a created item, or a required property that blocked the item's creation entirely — as a *permanent* mismatch for the caller to reconcile (not a retry, since a re-attempt hits the same wall), rather than silently dropping the field or the item. (A field whose property is simply *absent* is not this case: the create operation above records it in the page body.)

## Call-time discovery

Notion's surface shifts (MCP tool names, API endpoint shapes, and — most of all — the *per-database property schema*), so name the operation and its purpose here and resolve the exact parameters when you call: confirm the current retrieve-vs-query call, the target database's actual property keys (the title property, the status and label properties, any dependency relation), and the create-page payload shape (`parent` as data-source vs database id, the `properties` map) against the live connector/API at call time. An adapter that pins today's property keys ages into a confident wrong write; one that names the operation and re-derives the arguments ages gracefully.
