# Mine the sources

Work picked up mid-flight comes with more than its request: a tracker item and its children, threads, earlier records, review requests already opened or merged. Summarizing them loses what they settled. A decision already taken gets proposed again as if open. A dispute two people left unresolved never reaches anyone who could settle it. A stream already live is planned as if unbuilt.

**Which sources.** Every source the intent names, and every source those link, one hop and no further, that names a part the work changes or a choice the work needs. Intent is read first, as always. Threads, earlier records and requests' descriptions are rationale, read only once the step has formed its own view ([form-your-own-view-first](form-your-own-view-first.md)). Sources are read oldest first, so a later one is read as later. A source in that set is read to its end, and skipped only when it can't be reached, meaning its fetch fails or no port this run has reads it; its size, its cost or a guess that it's out of scope is no reason, since only reading it says what it holds. (basis: benchmark, 2026-11-13, a linked source skipped for scope held the measured baselines)

Read each for these six things, and carry each where it goes:

1. **Decisions already taken.** A source that records a choice as made by one named person is carried as that agreement event, on the item it settles: a requirement or a criterion in a spec, a decision in a plan ([items-and-agreements](../../skills/document/rules/items-and-agreements.md), whose trail and no-decider rule apply as written). A later agreement that changes it settles a new item that `supersedes` it. A later statement against it with no decider, or this run's own evidence against it, leaves it agreed and files a question `opened-by` it.
2. **Questions still open, and points in dispute.** A question a source asks that no later source answers, and a point two sources or two people state differently by [surface-disagreement](surface-disagreement.md)'s conflict test, are each filed as a question, both positions in it. Only a later agreement event settles one. A later statement without one is another position.
3. **What already exists.** A request a source shows merged is named as the review request the units it shipped land through, so their state reads from it; a spec carries it as evidence on the requirements it serves. A job, setting or flag a source shows running tells which gate has passed ([documentation-plan](../writing/documentation-plan.md)). A check a source reports as run, such as a production run's result or a staging test, is filed as a verification on the item it checks, with its outcome and date ([items-and-agreements](../../skills/document/rules/items-and-agreements.md)), so what has been shown to hold is visible. Neither is written into an item or a page as the system's status, which is live state. When the documentation plan owes a runbook, an alert a source shows set up, in the alerting tool or in merged code, not merely proposed, is filed as an alert ([runbook](../../skills/document/rules/types/runbook.md)), its condition as the source states it, a query verbatim, in `condition`. When the documentation plan owes a runbook, a procedure a source writes out for this system, such as turning a feature off or rotating a secret, whether in use or only proposed, is filed as a procedure with its steps and commands as the source gives them. A figure a source shows read from a named system over stated dates, such as a failure rate or a weekly count, is the `baseline` of the metric with the same definition and unit, with those dates as its `baseline window` ([cutover-plan](../../skills/document/rules/types/cutover-plan.md)), the latest window winning; with no such metric, it is evidence on the earliest gate whose `touches` names the component the figure measures, and with no such gate it is named in the developer's report instead. (basis: benchmark, 2026-11-13, live alerts and measured baselines in the sources left the runbook empty and the metrics without a baseline)
4. **Claims carried from earlier records.** A figure or behaviour an earlier record states is a pointer to its own source ([prefer-primary-sources](prefer-primary-sources.md)). It is re-read there when this run can reach it, and otherwise carried graded `unverified` ([results-and-certainty](results-and-certainty.md)), naming what would check it; when the record reports someone's reading of a system, it is carried as a reported reading.
5. **How an outside service behaves**, such as what a setting does and how fast a change takes effect, by the same rule.
6. **What reviews found.** A review request's review comments are part of it. A comment saying the change does something wrong or fails a requirement is a defect, and one naming a way it could fail is a risk; a suggestion or a style remark is neither, and a question is item 2's. A defect or risk that no later commit or reviewer's comment shows fixed, a thread marked resolved not counting, is filed with the comment cited, as the first that fits: a threat ([threat-model](../../skills/document/rules/types/threat-model.md)) when an attacker drives it, an issue ([raid-log](../../skills/document/rules/types/raid-log.md)) when the change has it now, else a risk in the raid log; a kind whose type the documentation plan doesn't owe is skipped for the next that fits, and with none owed it is the evidence only. Each is also evidence on the requirement it bears on, and one a later commit fixed is that evidence only, citing the commit. A filed item whose claim an unfixed finding contradicts, such as a mitigation saying what a failure does, one filed later this run included and checked when it is filed, is refiled stating what the finding says the change does now, what it was meant to do kept in its body as the intent the finding breaks, and the finding's issue, threat or risk names it; when `agreed`, it gets a question `opened-by` it instead, as item 1 says. (basis: benchmark, 2026-11-13, a review's finding contradicted a filed mitigation and was never filed)

A source's own ids, such as its decision numbers or ticket keys, are written with the source named and linked, "the lane note's DEC-10", never bare: a bare id reads as this task's item of that prefix, which is another item.

A source this run can't reach, or reads only in part, is named in the developer's report as unread or partly read, with why and what it might hold. Nothing is inferred to fill it.

(basis: benchmark, 2026-11-12)
