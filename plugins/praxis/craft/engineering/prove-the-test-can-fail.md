# Prove the test can fail

A test that has only ever been green proves nothing — it may assert nothing, assert against the wrong thing, or never reach the code it claims to exercise. Confirm a new or changed test actually catches the behavior by watching it go **red** for the right reason before its green is trusted. Reach for the methods in this order, preferring the ones that touch no production code:

1. **Run the test against the pre-change code** — for a test guarding a behavior the change *alters*, the pre-change revision computes the old behavior, so a correct test reddens there on the *value*. This is the fail-before / pass-after check, and it mutates nothing. Caveat for a behavior the change *introduces* (a new function or parameter): the pre-change code reddens merely because the signature/behavior is *absent* (e.g. a `TypeError` on the new argument) — that proves the test *runs*, not that its assertion *discriminates the value* (an assertion of the wrong expected value would redden pre-change too). For an introduced behavior, method 1 is inconclusive for value-discrimination — fall through to method 2.
2. **Feed a deliberately-wrong expectation or input** — assert against a known-bad value, or drive the case with an input the behavior must reject, and confirm the case reddens. This exercises the test, not production code.
3. **A transient, self-reverting break** — only when neither method above can produce red (typically a regression-guard test for behavior that *predates* the change, so the pre-change code is already green): briefly break the behavior under test, observe the red, and immediately restore. This is a **verification probe, not a modification** — it leaves a net-zero diff and never appears in what's delivered, so it stays inside any boundary that forbids *delivering* a production change, which is not the same as transiently observing a red. When even this is infeasible, record the test as **not proven-red** — a residual risk reported with the result, never a silent green.

This is the operational core of a *discriminating* case: a case discriminates only if some plausible wrong implementation makes it fail. A new test's green is trusted as evidence only after it has been seen red, and a suite of never-red tests is inadequate whatever its line percentage. `(basis: Beck's TDD rule 1, tightened to a hard check; Just et al. 2014)`
