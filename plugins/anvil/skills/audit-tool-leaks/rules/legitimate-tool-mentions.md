The rule is "the skill layer names only capabilities," not "the string never appears in the repository." A tool name is legitimate or a leak by its **role**, never its spelling: it is a leak the moment a skill *acts on it as instruction*, and legitimate when it sits somewhere whose job is to *hold, declare, or illustrate* tool detail, or to *cite an accountable source*, without instructing. This rule is the counterweight to [what-counts-as-a-tool-name](what-counts-as-a-tool-name.md) — that one tells you what a leak is; this one tells you where a tool name is *supposed* to appear so you don't false-positive on it. An audit that flags the legitimate places is worse than no audit: it trains maintainers to ignore the findings, and it pressures them to mangle the very files whose job is to hold tool detail.

## The one test: judge the token's role

The unifying question is always the token's **role**; for a token sitting in *instruction*, the instrument is the **swap test** — replace the concrete token with another of its kind. If the surrounding instruction survives (the step still makes sense against the capability), the token was decoration on a capability sentence, and it is legitimate; if it collapses into something only that named tool can satisfy, a cold executor would *act on* it, and it is a leak. Same string, different role; the role is the whole judgment.

Everything below is that role test applied to where a tool name commonly appears — but two surfaces are **not** settled by a swap-test pass, so check them by name rather than trusting the instrument:

- a **platform primitive** in an agent's `tools:` field is *looser* — legitimate by location, outside the swap test entirely (next paragraph);
- a **`usage.md` Example** is *stricter* — a swap-test pass does not clear a provider-qualified value there (its own section below).

The platform-primitive case, first, since it sits outside the test: a **platform primitive** granted in the harness's mandated place — an agent's frontmatter `tools:` field. There is no adapter seam beneath a platform primitive to push it down into, and you cannot rephrase a harness primitive into a capability, so it is legitimate by that location, full stop. The HARD RULE fires on a concrete **product** — a vendor, a CLI, a named service — which always has a seam beneath it; a platform primitive has none, and the two must never be conflated.

## Inside an adapter — its home

An adapter exists to wrap one tool over one transport; naming that tool is its entire reason to exist. A tool name in `adapters/` is not a leak, it is the design working. The collection phase already excludes `adapters/` from the audit set for exactly this reason, so in practice you should never be adjudicating an adapter's contents — but if one ever reaches you (a stray read, a misfiled file), the answer is the same: tool-intrinsic detail belongs there, and finding it there is confirmation, not a finding. The rule pushes tools *down* into adapters; punishing them for arriving would defeat the push.

## In a config template's provider list — it's data

When a config template enumerates the providers a capability can bind to, the names in that list are *data*, not instruction — the menu of what a maintainer may configure, sitting in a data file the skill layer reads, not steps a skill performs. A skill that says "dispatch to the configured provider" is clean even though the configured provider's name lives, as a value, in the config. (This file isn't part of the skill layer the collection phase gathers anyway; it's noted here so that if you meet a provider name while reasoning about config, you recognize it as legitimate rather than chase it.)

The same holds for the schema's **other enum values**, not only its provider lists: the capability keys it defines, and any *kind* or *transport* enums it declares, are the config's own vocabulary — a skill that reasons in those terms (deciding what a capability needs *by kind*) is naming schema vocabulary, not leaking a tool. Watch one boundary, which is the role test in miniature: a *kind* named as a schema enum is vocabulary, but the same token used to mean a specific live product or connection the step acts on is a leak.

## In an agent's frontmatter `tools:` line — the platform-primitive case

This is the platform-primitive category named in the lead. An agent declares the primitives it may use in its frontmatter `tools:` field — the harness's *mandated* place to grant them, not instruction the skill layer acts on. A name there is legitimate **by location**, exactly like a name inside an adapter, and the collection phase excludes the field from the sweep for the same reason it excludes `adapters/`. The discriminator: a platform primitive in the `tools:` field is a grant; a concrete product named in the agent's *prose* and acted on as instruction is a leak — so scan the body, never the `tools:` grant.

## A clearly-marked illustrative example — judge intent

This is the hard one, because it's where leaks disguise themselves as examples. The test is the same one — is the text *instruction that depends on the tool* or an *illustration that happens to name one*? — but the swap test gains a counterpart for examples, the **deletion test**:

- **Legitimate mention** — the example is unmistakably fenced as illustrative, the surrounding instruction is phrased as a capability, and removing the example leaves the instruction fully intact (the deletion test). The tool name is decoration on a capability sentence.
- **Leak in disguise** — a cold executor reading the step would *act on* the named tool; strip the "example" framing and the instruction collapses into a tool-specific command. The "for instance" was cover for a dependency.
- **Canonical enumeration in disguise** — the *same* set of concrete providers recurs across the definitional prose (the description, the body, a so-called example) with no `e.g.`/`for instance` fence on any of them. Recurrence in definitional text entrenches the *canonical-set* reading — this is the menu the skill is built around, not decoration on one sentence — however illustrative any single occurrence looks in isolation. The illustrative carve-out is for a **single, genuinely-fenced** mention; a provider list that appears two or three times across the prose is canon, and the fix is to rephrase every occurrence to the capability (the concrete set stays only in the config template's provider list, where enumeration is legitimate data). Recurrence-without-a-fence is itself the tell — you don't need to adjudicate each occurrence's intent once the list repeats.

When the marking is ambiguous — you can't tell whether a reader would treat it as illustration or as a step — resolve toward leak. The fix is cheap (fence the example unmistakably, or rephrase to the configured-X form), and an "example" a reader might execute literally is one of the most common ways tools sneak back into a clean skill layer.

## In a `usage.md` Example — the stricter no-vendor bar

The illustrative-example carve-out above specifically does **not** reach a **representative invocation in a caller-facing `usage.md` Example**, and here a swap-test pass does *not* clear the token. An Example is not fenced instruction prose illustrating a capability — it is a sample of *how the skill is called*, and a caller scanning Examples reads a concrete value there as the real argument to type, the same way a vendor in the `description` would misdirect. So a `usage.md` Example is held to the same no-vendor bar as the description: a bare identifier with no provider in it is fine (`--pr=142`, `--id=<n>`), but a **provider-qualified value** (`--from-x=<vendor>:issue/991`) names a tool and is a leak — write the capability placeholder instead (`--from-x=<x-ref>`). The lone exception is an input whose entire purpose is to name a tool — the sanctioned adapter seam — legitimate wherever it appears. This settles the recurring split where one critic reads an Example's vendor token as a leak while another clears it as a "fenced example": in a `usage.md` Example the leak read is right — the fenced-example carve-out is for instruction prose that illustrates a capability, never for the invocations a caller copies.

## In a sourcing marker — the citation, not the product

A pinned bar carries a `(basis: <what it rests on>)` marker naming its source (and a `(routed to maintainer: …)` sibling for a proposal awaiting the maintainer's call). An **authority** named inside one — a standard, a paper, a book, a named methodology, the design record — is legitimate: it is the accountable source the bar answers to, not a tool the skill acts on, and there is no adapter seam beneath a citation to push a source down into. But the marker is **not** a blanket exemption for every string inside its parentheses. A concrete **product** named in a basis as *evidence-of-practice* — justifying a bar by pointing at one named tool that happens to exhibit the behavior — still fails the swap test: swap the product and the justification must survive, because the bar rests on the *capability* (that such tools behave this way), not on that one product having it. Name the capability in the basis ("the runner's own error-vs-failure reporting"), never the product ("<tool>'s error-vs-failure split"). It is the role test applied to a marker: a citation of an accountable authority is the basis doing its job; a product doing the evidentiary work the *capability* should be doing is a leak wearing a basis marker.
