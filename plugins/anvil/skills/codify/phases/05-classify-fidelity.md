A codified step carries an implicit promise about *how firmly it's specified*, and you phrase it from that promise as you write it. A step the executor must follow to the letter reads differently from one where it should use judgment, which reads differently again from a gate it must not pass until something is confirmed. There is no separate rendering pass that picks this up later — the classification is a decision you make *here* and apply in the words you choose. Get it wrong and the step either over-constrains a judgment call (turning latitude the executor needs into a brittle command) or under-constrains a hard rule (inviting a wrong move where there was only one right one). This phase makes the promise explicit: classify each step's fidelity, and phrase it at that fidelity — as a capability, never a concrete tool.

## Classify each step's fidelity, and phrase it accordingly

Every step is one of three kinds. The kind decides how you word the step and tells the executor how much latitude it actually has:

- **Rule** — deterministic. The same inputs always produce the same action; there is one right move and the executor's job is to make it. *"Reject inputs over the configured size limit"* is a rule — no latitude, phrased imperatively. These are mostly the forks you hard-resolved in phase 04.
- **Judgment** — latitude-requiring. The executor must weigh the specifics and decide, and pinning it would make the procedure brittle. Guide it — give the considerations, the trade-off, the thing to optimize for — but leave the call to the executor. *"Weigh how widely the craft will be reused against the cost of another file when deciding whether it earns its own rule"* is judgment: phrased as guidance, not a command. These are the decisions phase 04 consciously left open.
- **Checkpoint** — verify-before-proceeding. A gate where something must be confirmed before the procedure continues, because passing it on a wrong assumption is expensive to undo. *"Confirm the source material is complete before drafting"* is a checkpoint: phrased as a gate that halts the flow until satisfied. A gate is earned only when a wrong assumption crossing it forces rework beyond the gated step itself — downstream steps inheriting the error. If the error would stay local, use a rule or judgment step; a gate guarding a cheap mistake just slows every run.

When a step seems to be two kinds at once, it's usually two steps — split it. A single line that's both a hard rule and a judgment call hides the seam from the executor; separating them makes each promise clean and lets you phrase each at its own fidelity.

## Cite every rule from the phase that relies on it

A rule the procedure depends on — a piece of reusable craft sitting in `rules/` — is invisible to the runtime until a phase body references it by relative path; **citation is a rule's only registration.** There is no manifest, no list in `SKILL.md`; a rule that no phase cites is dead weight the executor never loads. So as you phrase each step, name the rule it leans on inline, from the phase where it applies — and the citation's form is pinned, because only one form loads: **a resolvable relative markdown link**. From inside `phases/`, a rule is cited as `[altitude-of-a-step](../rules/altitude-of-a-step.md)`; a flag-activated module, cited from its activating phase, is `[name](../modules/name.md)`; an agent whose method a fallback stands in for is a cross-layer link out of the skill, `[name](../../../agents/<kind>/name.md)`; and a phase or module that **delegates a capability to a sibling skill** cites that skill's `SKILL.md` — `[name](../../<skill>/SKILL.md)` — when the sibling exists, or names it in prose flagged *proposed, not yet built* with **no link** when the target skill isn't built yet (a link to a nonexistent file would dangle). A bare name in backticks looks like wiring but resolves to nothing — the file never loads and the executor runs without the craft, worse than no citation because it passes a skim. Exit bar: every `rules/` file cited from at least one phase, zero links dangling. Cite where it's load-bearing, not in a roster: the same rule may be cited from more than one phase if more than one step relies on it, and a rule cited from nowhere is either unwired or unneeded — resolve which before leaving the phase.

## State the inline fallback in every delegating step

A step that **delegates a capability to a sibling skill or port** must read as *invoke it and use what it returns* — name the sibling to call and treat its returned result as this step's input — never as a *description* of the work to perform in place. "Delegates to X" that reads as "do the thing X does" licenses a raw hand-rolled substitute at runtime (the delegation-bypass); "invoke X; its return is the input to the next step" does not. This is the load-bearing half of the citation above, and the contract audit's `skip-resistance` check flags a delegation phrased as work-to-do with no named invocation.

A step that fans work out — recruiting sub-agents such as explorers, critics, or parallel executors — must state, in the same step, what a lone executor does when fan-out is unavailable: apply the same lens inline, in sequence, before moving on. One clause is the right size (*"or, without fan-out, apply the lens yourself before proceeding"*) — the fallback is a degraded mode, not a second procedure. Without it, a cold executor in a constrained context either stalls or silently skips the delegated work, and the skip is invisible in the output. When the delegated work is a **named agent**, the fallback stands in for *that agent's method*, and that method must be **reachable to a lone executor** — by one of two forms, the defect being providing neither. Either **link the agent** by a resolvable relative path so the executor can read its method — a cross-layer hop out of the skill: from inside `phases/` it is `[name](../../../agents/<kind>/name.md)` (up past `phases/`, the skill, and `skills/`, then into the plugin's `agents/`) — **or restate the lens inline** in the fallback itself, self-sufficiently enough that a cold executor can apply it from the fallback text alone (*"or, without fan-out, apply the <lens> yourself: <the method in a sentence or two>"*). Both make the method reachable; which you use is a house-convention call — **mirror how the plugin's existing skills recruit agents** rather than imposing one form, since some plugins link and some inline-restate, and a new skill should read as native (this is the same mirror-the-siblings discipline scaffolding follows). Restate the *method* — the stable lens — never volatile facts about the agent's other consumers, which staleify. The real defect is a fallback that **names an agent and provides neither**: a bare "apply the adversary lens" whose only definition of that lens lives in an unlinked file passes a skim and loads none of the method it promises, exactly like an uncited rule.

## Phrase every step at the right altitude

Altitude is granularity *and* abstraction (the full craft is [altitude-of-a-step](../rules/altitude-of-a-step.md)). On granularity: a phase is a step — not a single throwaway sentence, and not a sub-project that should itself decompose. If a "step" needs its own ordered sub-steps to be runnable, it's really a phase of its own; if it's too slight to stand alone, fold it into its neighbor.

On abstraction, the hard rule: **never name a concrete tool, vendor, CLI, or service in a step.** A step names the *capability* it needs; the concrete implementation lives in an adapter below the skill layer. *"Publish the result to the configured artifacts backend"* is right; naming the specific backend is a tool-leak the kit's own audits exist to catch. The test that catches a leak: if a step can only be expressed by naming a tool, the tool belongs in an adapter, and the step should name what it *needs that tool for*. This is the same rule anvil enforces on every plugin it audits, so codify's own output must obey it without exception — a codified procedure that leaks a tool fails the standard it was built to uphold. It also covers a **harness command-id or dispatch syntax** the design seed's `primitives` list may name (an orchestration command, a subagent-invocation form): those are design-time orientation, not skill-layer vocabulary — name the *capability* ("fan out across parallel workers"), never the command that effects it. A specific dispatch syntax pinned as canon is the invented-mechanism form of a tool-leak; the harness owns the mechanism, the step names what it is for.
