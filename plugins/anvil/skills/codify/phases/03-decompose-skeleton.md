With the goal split and the knowledge sourced, the temptation is to start writing polished prose for step one. Resist it. A procedure written front-to-back tends to over-invest in the early steps and discover its true shape only near the end, by which point the early steps need rewriting to fit. Instead, get the *structural shape* down first — the spine — and lock it before polishing any single part. This phase produces that spine: trigger, inputs, ordered steps, output and boundaries. It's the breadth-first pass; phases 04–05 are the depth.

## Capture the four structural elements

A runnable procedure needs four things pinned before its steps can be filled:

1. **The trigger** — the intrinsic condition that *starts* the process. What state of the world means "now run this"? A spec procedure triggers on *"a piece of work is scoped enough to build but not yet specified"*, not on a clock or a person's whim. The trigger is what tells a cold executor whether this skill even applies to the situation in front of it.
2. **The inputs** — what must be on hand before the first step can run. Name each at the capability level (*"the source material for the spec"*), not by the tool that holds it. Missing inputs are the most common reason a procedure stalls mid-run; surfacing them here is cheaper than discovering them in validation.
3. **The ordered steps** — the procedure itself, in sequence. Each is a step, not a sentence and not a sub-project (the granularity craft is [altitude-of-a-step](../rules/altitude-of-a-step.md)). At this stage they can be one-line stubs; the point is the *order and the count*, the joints of the procedure, not the flesh.
4. **The output and scope boundaries** — what it produces, *and* what it deliberately doesn't cover. The boundary is as load-bearing as the output: a procedure that doesn't say where it stops invites a cold executor to wander past its mandate. State the negative explicitly — *"produces the spec; does not choose the implementation approach, that's the implementer's call."*

## Write the spine into the target skill's slots

The decomposed shape is written into the named skill's `phases/` — one phase file per ordered step, each a stub for now. Here you must hold the seam: **scaffold-skill owns structure, codify owns method.** In the normal flow, scaffold-skill has already laid out the skill's directory and seeded empty phase (and rule) stubs; codify *fills* those slots and does not invent new structure. When the slot count you've decomposed differs from what was scaffolded, that's a signal to reconcile with the maintainer, not a license to silently restructure another skill's skeleton.

The spine lives in `SKILL.md` as the ordered list of steps, and it is the only part of the skill the runtime loads on trigger — sibling files load *only* when the body references them by path. So the wiring is load-bearing, not cosmetic: **each numbered step in the spine must link its phase file by relative path** (`phases/03-decompose-skeleton.md`), or the body never loads and the executor runs a one-line stub with the method missing. A spine whose steps don't resolve to their phase files isn't a thin procedure — it's a broken one. Write the link as you write the step; an unlinked step is an unfinished step.

The exception is the standalone invocation: codify called directly on a skill with no skeleton yet. There, scaffold the structure first — create the `phases/` directory and the per-step stubs — *then* fill them. You're temporarily doing scaffold-skill's job because nothing else has; you are not redefining the seam. The default assumption remains: a skeleton exists and codify pours method into it.

A third case is the **regenerate**: the named skill already has *filled* phase bodies — thin and below the bar, but real content, not empty stubs. Treat those existing bodies as the skeleton — read the existing structure as the spine and preserve it; do not re-decompose or discard it. The shape is given; the lift happens in phases 04–06 over the existing files, raising each body to the bar without churning what already conforms. But **actively vet the given decomposition** before lifting it — the seed (or the old skill's shape) is a *candidate, not a spec*: run the **phase-earns-its-place test** over each existing or seeded phase — a step earns its own phase only when its honest procedure owes more than its one-line gloss (a method of its own, a judgment made inside it, or a distinct done-state to verify); one whose complete procedure *is* its gloss is thin. Cut or refile the ones that fail rather than lifting them in place. A precondition step with no decision folds into its neighbour or the preamble; a cross-cutting invariant misfiled as an ordered position becomes a `rules/` file cited where it applies. Record each phase cut and where its content went. Reconcile with the maintainer if the *decomposition itself* is wrong — a missing phase, a mis-split step — but a conformant phase that merely reads thin stays.

One thing the spine is *not*: the `usage.md` pointer. Above the numbered steps, the body carries a non-spine pointer to the skill's caller-facing `usage.md` — how a caller invokes the skill, seeded by scaffold-skill, not part of the procedure. Preserve it exactly where it sits: don't fold it into a numbered step, don't renumber around it, and don't treat `usage.md` as a phase. The seam again — scaffold-skill owns `usage.md` (the caller's view), codify owns the spine and phases (the method). When you write or refine the spine, leave that pointer standing above it.

## Don't polish yet

Leave the steps as stubs. The decisions inside them — the branches, the thresholds, the edge cases — are phase 04's work, and the fidelity tags are phase 05's. If you find yourself resolving an *"it depends"* here, you've slipped a phase ahead; note the fork in the stub and move on. A locked, complete skeleton with thin steps is the right output of this phase. Filling a step before the spine is stable means rewriting it when the spine shifts — the exact waste breadth-first ordering exists to avoid.
