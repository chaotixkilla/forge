This is the actual work of codification. Everything before it gathered material and laid out a spine; this phase converts intent into *rules* — it takes every place the human process says *"well, it depends"* or *"use your judgment"* and forces it into something a cold executor can execute without being in the room. A human reader fills gaps from shared context and good sense; a fresh agent fills them by guessing, and a guess is a bug. The whole value of a codified procedure over a prose description is that the decisions are *resolved in advance*. Skip this phase and you've written documentation, not a runnable skill.

## Resolve every "it depends" into explicit branches

Hunt down each fork the description leaves implicit and enumerate it: for every branch, the **condition** that selects it and the **outcome** it produces. *"Audit more deeply if the plugin is complex"* is not codified — it's a hole. Resolved: *"if the plugin declares config requirements, ships hooks, or bundles agents, take the deep audit path; otherwise the standard path."* The cold executor must be able to look at the input, evaluate each condition mechanically, and land on exactly one branch. If two conditions can both be true, say which wins; if none match, say what the default is.

## Quantify every vague adjective

*Fast, large, thorough, recent, important* — these are placeholders for a number or a rule that the human knew and the prose didn't say. Codifying them means replacing each with something an executor can evaluate: not *"reject large inputs"* but *"reject inputs over the configured size limit"*; not *"only recent activity"* but *"activity within the lookback window the run is configured for."* Where the right threshold is genuinely the team's contingent choice rather than an invariant, don't hard-code a number — parameterize it (a flag or config value) and name the *rule* for setting it. The bar: an adjective that hasn't become a number or a rule has not been codified.

## Close every standard-point

A **standard-point** is any place the procedure makes or demands a judgment that two competent cold executors could resolve differently — a bar for "good", a threshold, a grade, a selection criterion, a quality call. Vague adjectives are the visible subclass; most standard-points hide inside respectable verbs — *assess, prioritize, rank, pick the strongest, keep the good ones* — and such a verb is closed only when its **discriminator** (the test that separates what it keeps from what it drops, what ranks above from below) is reachable, stated inline or in a cited rule. Inventory them, then close every one in exactly one of two ways. **Pin it**: state the bar precisely enough that two cold runs converge, *and write its source inline as exactly one marker* — **(basis: <the authority or derivation it rests on>)** when an accountable source reached the bar, or **(routed to maintainer: <your derived candidate + why>)** when none did and you're handing the call up with your best proposal (phase 02's flip; the craft is [source-weighting](../rules/source-weighting.md)). The marker is load-bearing, not a footnote: a bar comes from an accountable source or the maintainer, never from your own default, and a pinned bar written with neither marker is a **fiat assertion** — not closed, no matter how confident the sentence sounds. Or leave it **open by design**: the latitude is deliberate, and the procedure text records the reason inline — *"deliberately open: pinning this would be false precision because the right call varies with the input in ways no condition here can enumerate."* An unpinned bar with no recorded reason is **open by omission** — the same defect class as an unresolved "it depends". Phase 06's gate blocks on every one of these: a verb with no reachable discriminator, a pinned bar with no marker, a bar neither pinned nor open-by-design.

One trigger is mechanical, and it fires on the *output*, not the phrasing: **the moment the skill's output carries a grade, rating, severity, confidence, or rank at all, a defined scale is mandatory** — the named scale itself (rating the output while naming no scale, e.g. "assign by impact," is not a way out; it just hides the ladder every executor then invents); **a one-clause definition inline on every named level** (or a cited rule that defines it); the assignment discriminators (the test separating adjacent levels, so the same case can't land on either side depending on who runs it); and anchors (a concrete calibration case for at least the top and bottom). A scale named but not defined — bare-label rungs — is decoration; two executors grade the same output differently, exactly the divergence validation exists to catch. And a scale built to grade something *asserted* usually carries no rung for the honest **negative** — a well-founded absence, a none-found, a confirmed-clean result — even though that is a foreseeable output wherever the skill can truthfully report *nothing*: decide before a cold run has to guess whether the negative is a level on this scale, a distinct terminal outcome (the partition below), or the empty case (the sweep below), because otherwise a *confirmed* absence and a merely *unestablished* nothing collapse into the bottom positive rung, and two runs split on grading the negative high (definitively established) or low (unverified).

A companion trigger fires on the skill's **terminal outcome**: when the procedure resolves each run to one of an enumerated set of verdicts or dispositions, that enum owes a **partition proof** on top of the per-value rubric — every reachable run lands in exactly one value (the set is exhaustive, its values mutually exclusive). Prove it by construction: walk the outcome space and confirm no run falls outside the set or satisfies two values at once. Treat a **two-value** verdict as suspect until you have tried to place the run that is *neither* — a green result that nonetheless establishes nothing, an input the procedure genuinely cannot decide — because "can't tell / not established" is usually a real third outcome, and a binary that omits it forces those runs silently onto the wrong side. A per-value test proves each value is reachable; only the partition proves the enum is complete. Do not conflate this with a graded scale: the outcome enum may be unordered, and the obligation it adds is completeness of the set, not a rung ladder.

When the run carries flags, degrade postures, and policy inputs, "walk the outcome space" means walk the **matrix**, not one happy path: the partition must hold across every flag combination, each capability's degrade posture, and each policy value — a happy-path proof will be wrong in exactly the dimensions it skipped (a partial, degraded, or policy-variant run that lands in *no* branch is the classic miss). And when one determining fact keeps **re-opening across rounds** — each fix peeling off another case it had conflated — stop adding guard clauses and **decompose the determinant into primitive facts**: reduce the outcome to the one or two physical primitives that actually decide it, then hang every other dimension (an exposure level, a health verdict, a pending action, a flag) off as a **named orthogonal axis** that *colors* the outcome without moving which primitive-defined member it is. A partition proven on primitives-plus-orthogonal-axes converges; one proven on a single fat classification keeps fracturing round after round. (This is the "same point re-opens across 2+ rounds → decompose, don't patch" rule, applied to a partition's determinant.)

A further trigger fires when the skill **aggregates** — when its output *relays* a grade or label produced by a sub-agent or sub-skill rather than minting its own: the pinned output shape must **reproduce that component's full defined vocabulary**, or state the normalization rule that collapses it. Enumerate a subset — three of the source's six grades — and a cold executor handling a dropped value either emits one the shape never listed or silently coerces it to a listed neighbor, overstating (or understating) exactly what the source reported. The check is mechanical: for every relayed graded or labelled field, diff the shape's enumerated values against the source component's defined scale; a gap is a finding unless a collapse rule is pinned inline.

## Enumerate the edge, empty, error, and degraded cases

Most process descriptions cover the happy path and nothing else, because that's the path the human walks ninety percent of the time. The codified procedure has to handle the other ten, where a cold executor has no instinct to fall back on. Sweep for the cases the description skipped: the **empty** case (no input, an empty result set — a real outcome, not an error), the **edge** case (exactly at a threshold, a single item, the maximum), the **error** case (a required input absent, a precondition violated, a downstream step failing), and the **degraded** case (a capability a step delegates to — sub-agent fan-out, an external backend — is unavailable; every delegating step states what the executor does inline instead, the convention phase 05 pins). For each, say what the procedure does — proceed, branch, or stop with a specific report. A procedure that only describes success is half-written.

## Mark the inputs the process should reject

Some inputs the procedure should refuse outright — and refusing well means saying *what to do instead*, not just stopping. Enumerate the excluded cases and pair each with its redirect: *"if the work isn't scoped enough to spec yet, stop and route back to scoping — don't spec a moving target."* An explicit rejection with a redirect turns a dead end into a useful signal; a silent acceptance of out-of-scope input produces confident garbage, which is worse than a clean refusal.

## When a decision is genuinely the executor's to make

Not every fork should be hard-resolved here. Some decisions legitimately require latitude — a fresh agent with good judgment *should* be trusted to make them, because pinning them would make the procedure brittle or absurdly long. The test for legitimate latitude: the right answer varies with runtime specifics the author cannot enumerate now, and the executor at run time will hold more of the deciding context than the author does — pinning would be false precision. When the test passes, the step gets *guidance plus room* — phase 05 tags it **judgment** rather than **rule** — and the text still records that the openness is deliberate and why; that recorded reason is what separates it from open-by-omission. When the test fails, go back and pin. The discrimination is the work: resolve what can be resolved, and consciously leave room only where leaving room is correct — never where you simply ran out of energy to enumerate.

This phase iterates, because each pass's resolutions create new forks (a branch you enumerate introduces conditions that themselves need thresholds). Without `--rounds`, keep making refine passes until a pass surfaces no new output-affecting fork — that's the converged state. `--rounds=<n>` fixes the count instead: for time-boxing, or when the maintainer wants to steer between passes.
