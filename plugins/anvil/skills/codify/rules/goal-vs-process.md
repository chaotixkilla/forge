Behind every process a team describes are two different things wearing the same clothes: the **invariant goal** — what good looks like for anyone doing this well — and the **contingent process** — the particular way *this* team gets there. They feel identical when the team describes them, because the team only knows their own way. But they have opposite fates in a codified skill: the goal should be hardened into the procedure's reason for existing, and the process should be parameterized so a different team can swap in their own without rewriting the skill. Confuse them and you get one of two failures — a skill that enshrines one team's habits as universal law, or a skill so generic it encodes nothing.

The goal is durable and shared. *"A spec a cold implementer can build from with no further questions"* is what good looks like for anyone writing a spec — no team that does this well wants the opposite. Harden it: make it the skill's purpose, the thing every step serves, the bar validation checks against. The process is the team's route, and routes are interchangeable. *"We seed every spec from the item in our work tracker"* is how this team starts; another good team might start from a design doc or a recorded conversation. Parameterize it — express it as a swappable input named at the capability level (*"seed from the source of record"*), a flag, or a documented assumption — so swapping the route doesn't touch the goal.

The test that separates them in one question: **would another team, also doing this well, do this step differently?** If yes, it's process — parameterize it. If no, it's the invariant goal — harden it. Run the test on each piece, not on the description as a whole, because a single sentence often braids both: *"write a thorough spec from the tracked work item"* hardens to *"write a spec a cold implementer can build from"* and parameterizes to *"seeded from the tracked work item."*

The anti-pattern is hardening a process as if it were a goal — baking *"start from the item in our work tracker"* into the procedure's spine, tracker and workflow and all. Now the skill only works for teams that use that exact tracker and that workflow, and it can't be reused without surgery. The mirror anti-pattern is parameterizing a goal as if it were process — making *"the spec should be buildable without follow-up questions"* an optional, swappable choice, which hollows out the skill's reason to exist. Harden what's invariant; parameterize what's contingent; and when a piece resists the test, lean on the why — a goal is a *want*, a process is a *way*.
