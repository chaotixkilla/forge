Frontmatter is the skill's contract surface — the part the harness reads to know the skill exists, and the part the contract audit reads to judge it well-formed. Everything below it is prose a human or a cold executor consumes; frontmatter is machine-load-bearing. So its shape is not a matter of taste: some fields are the skill format's own recognized keys (the harness acts on them directly), and our additions live under `metadata` precisely because that is the format-blessed place to hang our own contract without colliding with the format's reserved fields. Put a flag where the format expects a description and the harness ignores it; the audit then flags it; the maintainer then re-does it. Shape it right once.

## The recognized fields: name and description

Write `name` and `description` as the skill format's own top-level fields. The `name` is the one settled in phase 1 — a capability verb-phrase, matching the directory, and valid against the format's charset: `^[a-z0-9]+(-[a-z0-9]+)*$` — lowercase alphanumeric with single hyphens, and **no underscores, uppercase, or leading/trailing/doubled hyphens** (an invalid `name` fails to register at load, silently). A capability or config lane that carries an underscore does **not** carry it into the skill name: the skill is hyphen-case (`project-mgmt`) while it owns `tools.project_mgmt` (a JSON key, where underscores are legal), exactly as `publish-artifact` owns `tools.artifacts`. Don't mirror a lane's underscore into the skill name. The `description` is one line stating the single responsibility in capability phrasing: *what* the skill does and *when* it's the right skill to reach for, with no tool, provider, or vendor names. This line is doing double duty — it's how a reader (and the harness's own skill-selection) decides whether to invoke this skill, and it's a line the tool-leak audit scans. The bar for "good enough" is the sibling-disambiguation test: a caller holding only the pool's one-line descriptions must be able to pick between this skill and its nearest neighbor — if both descriptions could claim the same invocation, sharpen this one's when-clause until they can't (the harness routes on descriptions, so an ambiguous one misroutes invocations). A description that names a backend is a leak in the most visible possible place. Keep it a clean *what*; the *how-with-which-tool* lives down in adapters and is none of the description's business.

## The flags: draw from the shared axes, don't invent

Under `metadata.flags`, declare the flags this skill answers to, each with a one-line meaning. The discipline here is to reach for the kit's shared flag axes before minting a per-skill flag, because a vocabulary that's consistent across skills is one a user can learn once. The recurring axes are:

- **target** — which thing the skill operates on (the plugin/skill/subject it acts inside).
- **depth / rounds** — how many passes or how hard it works before returning.
- **scope** — which subset of the work to do (a list of checks, slots, or areas).
- **provenance** — where input comes from (live interrogation vs. a captured transcript/notes).
- **output** — how results come back (prose inline vs. a rendered structured page).
- **write-mode / safety** — whether it writes, previews, or hard-stops (the preview flag that plans without mutating).

A new flag earns its place only when no shared axis fits. Two declarations are owed by shape, not by taste: a skill that *writes files* declares the preview flag (plan-and-report without mutating) unless it already carries another pre-mutation checkpoint flag — every file-laying skill in this kit does one or the other; and a skill that *chains to another* declares the handoff flag. Don't declare a flag with no behavior behind it — a flag the body never reads is dead, and a flag that *activates a module* must have that module present, which the contract audit's flags↔modules check enforces. If you declare an activating flag here, the module is owed in phase 3 — but first check it *is* activating: a flag that merely names a phase's default (a default scope, window, branch, or mode the phase consumes anyway) is a phase input and owes no module; the default-selector test is in [choosing-slots](../rules/choosing-slots.md).

## config_requires: only for config-bearing plugins

Under `metadata.config_requires` declare the skill's external-capability prerequisites — but *only* if the target plugin is config-bearing. Recruit the plugin explorer to detect the posture: a config-bearing plugin has a config template enumerating pluggable backends and its skills touch them; a config-less plugin (the authoring kit itself is the type case — it runs in the workshop repo against files, with version control ambient) has no such template and its skills carry no `config_requires` at all. If the posture is genuinely unclear, default to config-less and add nothing — a missing prerequisite is easy to add when a real need appears; a spurious one makes a skill demand configuration it never uses, and the contract audit will flag a `config_requires` key with no backing template entry.

When the plugin *is* config-bearing, type each entry as `{key: tools.<capability>, if_missing: <posture>}` — one entry per external capability the skill genuinely needs, where `<posture>` is guide, degrade, or block (and `guide` may be compound: `guide via <the plugin's config-setup skill>, else degrade|block`). The full craft of choosing the capability key and the right posture is [shaping-config-requires](../rules/shaping-config-requires.md); at scaffold time you're declaring the *shape*, not resolving the runtime behavior.

Cross-check the seed for consistency before you commit the entries — it's a candidate, not a spec. A seed names a skill's capabilities in more than one place — a `config_requires` list, an explorer list, phase steps that read a backend — and those places can disagree: one design file names an explorer that reads a backend the other file's `config_requires` never provisions. Reconcile them against what the skill's steps *actually touch*: every backend a seeded phase or explorer reads must be covered by exactly one of — a `config_requires` entry the skill owns, or a delegation to another skill (a port, or a shared skill that owns that capability) — and no `config_requires` may name a capability no step uses. One arm of that reconciliation is mechanical, run per key: for **each** capability the seed proposes to own as `config_requires: tools.<cap>`, have the explorer already recruited above scan `skills/` for an existing port that owns `<cap>` — a thin skill carrying that key over an `adapters/` seam. If one exists, the seed declared wrongly: the honest coverage is *delegation, not ownership* — drop the `tools.<cap>` key and route the touching step through the port, rather than declaring a local dependency the port already carries and forking the capability into two homes. An internally-consistent seed — a step that reads the backend plus a `config_requires` that provisions it — can still be wrong this way, because the port it should defer to lives in the tree, not the seed; the per-key scan is what catches what the consistency check above passes. A backend-touching step with no provisioning, and a `config_requires` with no touching step, are the two halves of one seed inconsistency; resolve it here — drop the step, delegate it, or add the provisioning — rather than scaffolding a skill whose declared dependencies and actual reads don't match. This is the completeness counterpart to the minimality rule below: doer-owns-prerequisites stops you over-declaring; this check stops you under-declaring or declaring the wrong capability.

## Doer-owns-prerequisites

Declare only what *this* skill needs to run — never a prerequisite that belongs to a skill it hands off to, and never one a caller is expected to satisfy. If this skill chains to another that needs version control, that prerequisite is the other skill's to declare, not this one's to pre-satisfy on its behalf. The rule keeps each skill's contract honest: read a skill's `config_requires` and you know exactly what *it* touches, with no inherited obligations smuggled in from its neighbors. A skill that over-declares is one that fails to run in a project that could have run it fine. The corollary is a third posture beyond the plugin-level two: a skill in a config-*bearing* plugin can itself declare **no `config_requires` at all** when it delegates every capability wholesale to a port and resolves the rest locally — it sheds all of them, exactly as `spec` does. Config-bearing is the *plugin's* posture, not an obligation on each skill; don't add a token `config_requires` to "match the plugin." Mark such a skill with the prose note the delegating skills carry ("owns no backend of its own … so it declares no `config_requires`").

## What the frontmatter looks like at this stage

Everything declared, nothing filled with procedure: a clean `name`, a capability `description`, the `metadata.flags` block with one-line meanings, and `metadata.config_requires` either present-and-typed (config-bearing) or absent (config-less). The flags and config keys are *declarations awaiting content* — the body that reads a flag or honors a prerequisite is written in the content pass (codify), not here. Under `--dry-run`, this is the frontmatter you show without writing. Leave the seam clean: structure now, method later.
