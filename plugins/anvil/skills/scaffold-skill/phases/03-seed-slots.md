The slots are where a skill's body lives, and each slot has one meaning: `phases/` is the ordered procedure, `usage.md` is the caller-facing docs, `rules/` is reusable a-la-carte craft, `modules/` is flag-activated behavior. One of these is *always present* — every skill owes its callers a usage doc (`usage.md`); the other three are *earned*, seeded only when the skill genuinely carries a multi-step procedure, craft, or flag-gated behavior. Seeding the earned slots is where premature structure creeps in, because empty folders are free to create and tempting to create "just in case". They aren't free: every slot file is something codify must later fill or delete, something the contract audit checks for placement, and something the next maintainer reads as a promise that there's content here. So the governing principle for the earned slots is *create only what is earned*; seed every slot at the granularity of a stub — a named placeholder, not prose — except `usage.md`, which is seeded with its four sections populated from what phase 1 already established.

## Create the home

Write into `plugins/<plugin>/skills/<name>/`: the SKILL.md from phase 2, the always-present `usage.md`, plus whichever earned slot directories this skill needs (the always-present/earned split is the opening frame above; it is not re-argued here). *Which* earned slots this skill carries is decided by [choosing-slots](../rules/choosing-slots.md) — the depth, default-selector, and empty-is-valid tests all live there and are invoked by pointer, never paraphrased in this phase. This phase is *how to seed* the slots you've decided on.

## One phase per ordered step — when the procedure has depth

`phases/` is earned by procedural depth; the test that decides it (the per-step stub test, with the step count only as a suspicion trigger) is pinned in [choosing-slots](../rules/choosing-slots.md). When the interrogated capability passes it, decompose: each ordered, must-run-in-sequence step becomes `phases/NN-name.md`, where `NN` is the run order — the numbering is not cosmetic, it's the procedure's spine, and it maps one-to-one onto the numbered lines in SKILL.md. Number consecutively with two digits (`01`, `02`, …) — the convention every skill in this kit follows; when a step is later inserted, renumber the tail and update the spine in the same edit. (Consecutive-then-renumber over gap-numbering, by house convention: the lockstep between spine and filenames is the invariant worth a mechanical renumber, and gapped sequences read as missing files against all prior art.) Name each file for what the step *does* as a capability — `02-shape-frontmatter`, not `02-write-yaml`. Seed each as a stub — the one-line gloss of what the step accomplishes, and no more, never the procedure itself (the stub/content seam is defined once under *Granularity* below).

A *thin* skill gets no phases. When phase 1's interrogation surfaces a capability that fails the depth test in [choosing-slots](../rules/choosing-slots.md) — the shape of a port or dispatch skill, where every step's complete procedure is its one-line gloss — do not manufacture thin phase stubs that each hold a single line. Instead lay the short procedure **inline** in the SKILL.md body: the numbered steps live directly in the spine, pointing at no phase files, and `phases/` is not created. This is the same skepticism [choosing-slots](../rules/choosing-slots.md) applies to the earned slots — thin phase files that exist only to satisfy a "every skill has phases/" reflex are the bloat the scaffolding-skeptic kills.

## Under `--kind=port` — the port shape, made explicit

`--kind=port` declares the thin/dispatch shape up front instead of leaving it to the depth test: the skill is a tool-layer **port** (the type case of thin), so seed exactly — a `SKILL.md` whose numbered spine is the dispatch procedure written **inline** (resolve the configured provider → take the caller's requested operation → dispatch to the matching `adapters/<provider>` → return the result, or a capability-level failure the caller can react to), the always-present `usage.md`, and an **empty `adapters/` directory**. That empty `adapters/` is the one slot a port seeds beyond `usage.md`, and it is seeded *empty* because the first adapter is `add-component`'s job (`--kind=adapter`), not scaffold's. Seed **no** `phases/`, `rules/`, or `modules/` — a port is definitionally thin. The port **owns its capability's `config_requires`** (it is the doer that consumers delegate to and shed the prerequisite for; phase 2 declared it). Keep the dispatch capability-only: `adapters/<provider>` names the seam, never a concrete provider. This is the kit-blessed way to birth a port — reach for it rather than hand-copying an existing port skill.

## Wire the spine to its phase files — if there are phase files

This wiring applies only when the skill has phases. If it does, the numbered line in SKILL.md is not just the step's gloss — it is the *link* that loads the phase. The harness loads only the SKILL.md body on trigger and pulls in a sibling file only when the body references it by relative path, so a spine line that names a step without pointing at its phase file leaves that phase orphaned: written, but never loaded at runtime. So seed each spine line with an explicit reference to its phase — the step's one-line gloss followed by a relative-path link to `phases/NN-name.md` (the established form is a trailing `— see [phases/NN-name.md](phases/NN-name.md)`). Seed the gloss as a **pointer, not an instruction**: it names *what* the step achieves and points at the phase, and must not carry the method to *do* it — if a cold executor could complete the step from the spine line alone, the method has leaked up into the spine and the phase file will be skipped at runtime (the contract audit's `skip-resistance` check flags exactly this; the phase, not the spine, holds the method codify fills). Every phase file you seed earns exactly one referencing line in the spine; the lockstep is not only same-order-same-number but same-line-points-at-same-file. A seeded phase with no spine reference is dead weight codify will fill and the runtime will never reach.

The inverse is *not* a defect. A thin skill has no phase files, so its numbered spine lines carry the short procedure inline and point at nothing — nothing is stranded, because there is nothing to strand. A spine step with no phase link is a fault only when a phase file exists that it should have pointed at; for a phase-less skill, an inline, link-free procedure is the correct and complete form. Rules and modules get *no* spine line either way — they are not loaded by the spine but registered where they're cited or activated (see [choosing-slots](../rules/choosing-slots.md), and the wiring section below).

## Wire the modules and rules — where the reference lives, and when

Phases are not the only slot files that must be reachable: the same loads-only-what's-referenced rule governs `rules/` and `modules/`, and their wiring differs from the spine's in both *place* and *time*.

- **A module is referenced from its activating phase** — the phase where the flagged behavior kicks in — as a relative link: from inside `phases/`, `[name](../modules/name.md)`. When no single phase is the activation site (the flag changes the whole run), reference it from the SKILL.md body instead: a non-spine line pairing the flag with its module, placed like the usage pointer — above or outside the numbered procedure, never as a numbered step. This reference is *structural* — the flag↔module pair is fully known at scaffold time — so scaffold lays it now, into the phase stub or the body.
- **A rule is cited from each phase where it applies** — from inside `phases/`, `[name](../rules/name.md)` — and citation is its only registration. But *which* phase applies which rule is a method decision, so the citations themselves are codify's to write while filling the phases. Scaffold's job is the wiring *plan*: each rule stub records its intended citing phase(s), so codify inherits where to wire instead of a blank.

The citation form is pinned, not stylistic: a resolvable relative markdown link. From inside `phases/`, a sibling slot file is `../rules/name.md` or `../modules/name.md`; a bare backticked `rules/name` is not a link — it resolves to nothing and never loads. A reference the loader can't resolve is the same defect as no reference: a written slot the runtime never reaches.

## Seed usage.md — mandatory, and already fillable

`usage.md` is the always-present slot (the opening frame): the caller-facing doc that tells a reader deciding whether to reach for this skill *when to use it*, *what to reach for instead when it's the wrong fit*, *what invoking it looks like*, and *what bites*. There is no "does it need one" question — seed it for every skill.

And unlike the other slots, you don't seed `usage.md` as an empty stub — phase 1 already gathered what it needs. Seed it with its four sections, populated from the intent, flags, and sibling-scan you have in hand:

- **When to use** — from the single-capability statement: the situations where this skill is the right reach.
- **Not for — use instead** — from the sibling-scan: the neighboring skills a caller might confuse this with, and which to reach for instead (the overlaps phase 1 mapped are exactly this section's content).
- **Examples** — from the flags: representative invocations, including the flag combinations phase 2 declared (the preview flag, the handoff flag, and any scope/target flags), each with a one-line "what it does".
- **Gotchas** — the sharp edges intent surfaced: the altitude boundary (what this skill deliberately does *not* own), and any prerequisite or ordering a caller must know.

Keep it caller-facing and capability-phrased — `usage.md` describes *what* to reach for and *when*, never *how-with-which-tool*; it is read by the leak audit the same as the description. What you seed here is genuine content, not a placeholder codify must fill: this is the one slot scaffold-skill leaves populated.

## Point the SKILL.md body at usage.md — above the spine, not in it

The seeded SKILL.md must carry a usage pointer, and its placement is load-bearing. `usage.md` is a slot file, so the wiring rule applies — a slot the body never references is orphaned, never loaded. But `usage.md` is *caller-facing*, not an executor instruction, so it must **not** be a numbered spine step: the numbered lines are the procedure a cold executor runs in order, and a doc that says "here's when a caller should pick this skill" has no place in that sequence. Wire it as a **non-spine, top-of-body pointer** — one line above the numbered procedure, of the form `Usage & examples … see [usage.md](usage.md).` This honors the wiring rule (the reference exists, the slot loads) without lying about how `usage.md` runs (it doesn't run; it's read). A usage pointer smuggled in as step 0 or an appended numbered line is the placement error to avoid.

## One rule per reusable craft judgment

Each piece of reusable judgment that the phases apply *but that isn't itself a sequenced step* becomes `rules/name.md` — unordered, named for the craft it carries (`altitude-of-phrasing`, `choosing-slots`). A rule is a-la-carte: phases cite it where it applies, and citation is its only registration — no number, no flag. Seed it as a stub naming the judgment it will hold and recording its intended citing phase(s) — the wiring plan codify fulfills (see the wiring section above). The test for whether something is a rule versus a phase is in [choosing-slots](../rules/choosing-slots.md); if you find yourself wanting to give a rule a number or an activating flag, it's mis-classified.

## When the rule slot is a large library

Most skills carry a handful of rules, seeded one honest stub at a time as above. A few are built *around* a large a-la-carte library — a domain-craft skill whose whole value is a broad set of reusable judgments, often dozens of rules grouped into families by concern. Stubbing that many files by hand and filling them one at a time doesn't scale, and — worse — lets voice and depth drift across the set, when the whole point is that the rules read as siblings. Seed a large library as a **mirrored family**, not stub-by-stub:

- **Lock the skeleton and a manifest first.** Decide the families (the concern-groups the library divides into) and the shared rule shape — the section skeleton every rule mirrors (the opening, the discriminator with its tell, the sourced `(basis:)`, the anchors — or whatever shape the plugin's rule family already uses). The manifest is the roster: family → the rules under it, each with its one-line intent and its citing phase(s). This manifest replaces the per-file stubs; it *is* the wiring plan for the whole slot.
- **Author a few exemplars by hand.** Write two to four real rules across different families to fix the skeleton and voice — enough that a filler has an unambiguous model to mirror. Gate these like any authored content before fanning out against them.
- **Fan out the fill against the exemplars.** Draft the remaining rules as a mirrored family — the same discipline `add-component` applies to a same-kind set that must read as siblings: each new rule mirrors the exemplars' shape rather than a shape re-derived per file. Then gate the whole set *against the exemplars* (same case, same verdict?), so a bar shared verbatim across rules reads as house convention, not a per-file open standard.

Defer per-file stubbing: the manifest is the plan, the exemplars are the model, and the fill is one mirrored pass, not N hand-seeded blanks. A large family library MAY be organized into **subdirectories** — `rules/<family>/name.md` — to make the grouping visible. The citation is still just a resolvable relative link carrying the subpath (`[name](../rules/<family>/name.md)` from a phase); the slot is still `rules/`, and every nesting-agnostic rule of this phase (one citing phase per rule, no orphans, no dangling links) applies unchanged. Subdivision is organization, not a new slot kind.

## One module per flag-activated behavior

Each optional behavior toggled by a flag becomes `modules/name.md`, named for the flag that turns it on (a `--security` flag activates `modules/security.md`). The module and its flag are a pair — and the flag must already be declared in phase 2's `metadata.flags`, or the module is unreachable dead code that the contract audit's flags↔modules check will flag. So seeding a module is really confirming the loop is closed: flag declared above, behavior stubbed here, the two named consistently. Seed the body as a stub describing the behavior the flag activates. The seed's proposed module list is a **candidate, not a spec** — run the default-selector test from [choosing-slots](../rules/choosing-slots.md) over *each* module the seed names, the same active vetting you give seeded phases; don't trust the seed's classification and leave the cut to the gate. If the test comes back "phase input" for one, declare the flag and seed no module. If you reach for a module and there's no flag for it, go back and declare the flag — a module with no on-switch can never fire.

## Seed the standard-points as explicit stubs

Phase 1's sweep listed where the skill will grade, select, accept, or default. Each entry lands in the skeleton as an **explicit stub in the slot where it will be closed**: a bar used across steps (a grading scale, a shared selection threshold) → its own `rules/` stub; a bar local to one step → a demand line inside that phase's stub; a bar that lives behind a flag → in that module's stub. The stub states the *demand*, not the content, in three parts: what is judged, what must be pinned there (the scale with its rubric and anchors / the threshold / the acceptance test / the named default), and where the bar should come from (the authority to consult, or the maintainer). For a skill that grades its output, the seeded `rules/` stub reads like: *"the grading scale is owed here — levels, assignment rubric, and top/bottom anchors; source: <authority or maintainer>; cited from: <the grading phase>"*. Do not draft a plausible-looking scale to fill it — that crosses the stub/content seam (defined under *Granularity* below): content invented by the structure pass reads as done, so the sourced bar never gets written. A skeleton that carries its standard-points as demands hands codify a checklist of bars to close; one that doesn't hands codify a blank that gets filled from a generic executor's priors.

One standard-point class hides because it looks structural rather than graded: a skill that resolves each run to one of a set of **terminal outcomes** — a verdict, a disposition, the result the run lands on. That outcome enum is a standard-point too; seed it as one, with a demand line that owes not just a per-value assignment test but a **partition proof** (every run lands in exactly one value — the set is exhaustive and mutually exclusive). Flag a *two*-value outcome as owing that proof most: "indeterminate / can't-tell" is the third value a binary verdict most often drops, so seed the demand to make the producer prove no run falls between the two. Seeding it as a plain binary — treating the verdict as obvious rather than as a standard-point to close — is exactly how the missing third value survives to the gate.

## Granularity: a stub, not prose

Every seeded file is a *stub* — the one-line gloss of what the slot will hold, plus any standard-point demand lines and wiring-plan notes that belong to it, written so the content pass knows its job. The seam test, line by line: a stub line may say *what* the slot must accomplish or *what bar* must be closed there; the moment a line says *how* — an executable action, a resolved threshold, a drafted scale — it has crossed into codify's half. Resist writing real procedure, real craft, or real module behavior here: that's codify's work, and content written by the wrong pass tends to be content nobody revisits. The skeleton's value is that it locks the *structure* — the slots, their names, their order — so the content pass fills a fixed shape rather than improvising one. Breadth-first: stub the whole skeleton, then let codify fill it.

## Honor --slots, but default to need

`--slots` governs only the *earned* slots (`usage.md` is not up for override — it is always seeded). When `--slots=<list>` is given, seed those earned slots — the maintainer is overriding the default derivation, usually because they already know the skill carries a procedure (`phases`), craft (`rules`), or flag-gated behavior (`modules`). The override wins — the maintainer is the authority on their own skill — but when the interrogation says a listed slot is unearned or an omitted one is owed, honor the flag and record the disagreement in the phase-4 report; a silent override hides a design call the maintainer should see. When it's absent, *derive* the earned slots from need, per [choosing-slots](../rules/choosing-slots.md): seed `phases/` where phase 1 surfaced real procedural depth and `rules/`/`modules/` where that interrogation and phase 2's flags established a genuine call, and leave the rest unseeded. An empty *earned* slot is the speculative scaffolding the scaffolding-skeptic kills — the empty-is-valid test that governs this lives in [choosing-slots](../rules/choosing-slots.md).

## Match the plugin's conventions, don't impose a template

Recruit the plugin explorer to read how the target plugin's *existing* skills seed their slots — their phase-naming style, their numbering convention, how dense their stubs are. Mirror it. The kit has no single frozen skeleton it stamps onto every plugin; a plugin develops local conventions and a new skill should read as a native of its plugin, not an import from a generic mold. Where the target plugin is brand-new and has no siblings to mirror, fall back to the kit's defaults — but the moment there's prior art in the plugin, prior art wins.

Mirroring has a hard scope limit: it governs *voice, naming, and density* — never *which slots exist*. Which slots this skill carries comes from the skill's own seed, the interrogated need, and the documented contract, and those beat sibling precedent whenever the two point apart. Siblings can be known-incomplete — built before a convention landed, or missing slots their own design calls for — and an incomplete sibling is a backlog to fix, not prior art to copy: a pool where no skill yet carries rules or modules is no argument against seeding the first one that earns them.

## Under --dry-run

Produce the exact tree that *would* be created — every directory, every stub file with its one-line intent and any standard-point demands, and `usage.md` with its four populated sections — and write nothing. For a thin skill with no phases, show the inline procedure that would live in the SKILL.md body instead of a `phases/` directory. The maintainer reviews the whole skeleton as a unit before it touches the disk; a faithful preview lists every path including the always-present `usage.md`, never a half-seeded subset.
