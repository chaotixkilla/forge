A skeleton is half a skill: the structure is laid, but no step has a procedure, no rule has its craft, no module has its behavior. This phase decides what happens to that half — return it for the maintainer to fill, or hand it to codify to fill from the maintainer's process — and it does the one thing that keeps the two-skill split honest: it refuses to write procedure here. scaffold-skill and codify are deliberately two halves of authoring a skill, structure then method, mirroring the build discipline of skeleton-across-files before content-within-files. The seam between them lives in this phase, and crossing it — sneaking a "first draft" of the procedure into the freshly-seeded phases — is the failure mode this phase exists to prevent.

## Default — return the skeleton

Absent a handoff flag, the skill is done when the skeleton is laid: return it and report every path created — the SKILL.md, each `phases/NN-name.md`, each seeded `rules/` and `modules/` file. The report is the deliverable, not an afterthought: the maintainer reviews the structure as a whole and decides what fills it, so a complete path list is the thing that lets them see the shape at a glance and steer before any content goes in. List the slots that were *deliberately left empty* too (no rules, no modules) — absence is a design decision the maintainer should see confirmed, not a gap they have to wonder about — along with the standard-point stubs seeded (what bar each demands and where it lives) and any recorded disagreement with a `--slots` override, so every judgment call the scaffold made is on the table.

## With the handoff flag — hand to codify

When the handoff flag is set, pass the laid-out skeleton to codify to fill its procedure from the maintainer's process. The handoff is structural: codify receives a fixed skeleton — known phases in known order, known rules and modules to populate — and its job is to fill that shape, not redesign it. This is the bootstrap pairing working as intended: scaffold-skill produced the slots, codify produces the method that goes in them. Pass along the per-slot intent you stubbed in phase 3 — the standard-point stubs above all — so codify fills each slot toward the purpose it was created for rather than re-deriving it, and treats each standard-point as a bar it must close from an authority or the maintainer, never from a generic executor's defaults.

## Hold the seam — structure here, method there

This is the load-bearing rule of the phase, stated as a hard line: scaffold-skill owns *structure*, codify owns *method*; never write procedure in this skill. The seam test that decides borderline lines: a stub line may say *what* a slot must accomplish or *what bar* must be closed there (a standard-point demand is structure); the moment a line says *how* — an executable action, a resolved threshold, a drafted scale — it is method and belongs to codify. The temptation is real — you've just interrogated the intent and named every phase, so you know roughly what each step does, and it feels efficient to draft it. Resist. Procedure written by the scaffolding pass is procedure written without the source-knowledge, fidelity-classification, and cold-executor validation that codify brings — it reads as done while being unsourced and unvalidated, which is worse than an honest empty stub because nobody re-opens a phase that looks finished. A stub invites filling; a fake-finished phase repels it. The clean handoff is a skeleton whose stubs are honestly empty of method.

## Leave declared contract in place, unfilled

The frontmatter declared flags and (for config-bearing plugins) `config_requires` in phase 2. Leave those declarations exactly as they are — present and typed, awaiting the content pass that writes the body which reads a flag or honors a prerequisite. Do not strip a flag because its module is still a stub, and do not fill in a `config_requires` posture's runtime behavior — both are content-pass work. The contract is *declared* by scaffold-skill and *fulfilled* by codify; this phase hands off a contract that is complete in its declaration and honest in its emptiness of implementation. An audit run on the handed-off skeleton should find the contract well-shaped (flags present, config keys typed, slots placed) even though the method is not yet written — that's the proof the structural half was done right.

## Under --dry-run

A dry run never reaches a real handoff: produce the report of exactly what *would* be created — every path, every declared flag and config key, every deliberately-empty slot — and write nothing. If the handoff flag is also set, state that codify *would* be handed the skeleton, but do not invoke it: a preview previews, it does not chain into a mutating downstream pass.
