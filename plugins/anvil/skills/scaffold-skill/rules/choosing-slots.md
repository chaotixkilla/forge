A skill's slots split two ways. One is **always present** — `usage.md`, the caller-facing doc every skill owes — seeded uniformly regardless of what the skill does. Three are **earned** — `phases/`, `rules/`, and `modules/` — seeded only when the skill genuinely carries a multi-step procedure, reusable craft, or flag-gated behavior. This rule is mostly about the earned three, because that's where the judgment lives: `usage.md` is not a decision, it's a given.

For the executor-facing slots, the slot you put a piece in is a claim about *how it runs*: a phase runs in sequence, a rule runs when something cites it, a module runs when a flag turns it on. Misfile a piece and you've lied about how it runs — a craft judgment numbered as a phase forces an order that doesn't exist; a flag-gated behavior dropped into phases runs unconditionally; an optional lens written as a rule can never be switched off. The contract audit's slot-placement check catches the gross cases, but the right time to get this right is at authoring time, when the piece is still a thought and not yet a file. This rule is the decision procedure.

## The always-present slot — usage.md

`usage.md` is not chosen; it is seeded for every skill, because a skill always has callers, and callers are always owed the same four things: when to use it, what to reach for instead when it's the wrong fit, what invoking it looks like, and what bites. This is not "earned by content that exists" the way phases, rules, and modules are — the content always exists, because every skill has an answer to all four. So the scaffolding-skeptic framing below does *not* apply to it: `usage.md` is never speculative structure, it is uniform structure. It is wired differently too — it is caller-facing, not an executor instruction, so it is referenced from the SKILL.md body as a non-spine top-of-body pointer, never as a numbered spine step.

## Phase — ordered, must run in sequence, earned by procedural depth

If a piece *must run*, and *must run in a particular position relative to the others*, it's a phase. The test is dependency: does this step consume what an earlier step produced, and produce what a later step consumes? Interrogating intent must precede shaping frontmatter must precede seeding slots — each needs the prior one's output. That dependency chain *is* the procedure spine, and it lives in `phases/NN-name.md` with the number carrying the order. If you can run two pieces in either order without anything breaking, at least one of them isn't really a phase — it's a rule the phases happen to cite.

But `phases/` is earned, not automatic. It is earned by *procedural depth*, and depth is a testable bar, not a vibe. The bar is the per-step stub test; step count is only a symptom that tells you which way to look, never the thing that decides.

- **Per-step depth — the stub test (this is the bar).** For each step, ask what its honest stub would say *beyond* its one-line spine gloss. A step earns its own file when the stub already owes more than the gloss: a method of its own (sub-actions or a worked decision the gloss can't carry), a judgment made inside it (a discriminator to apply, a bar to check), or a distinct done-state an executor must verify before moving on. If a step's *complete* procedure IS its gloss, that step is thin.
- **Step count — a suspicion trigger, not a floor.** A one- or two-step procedure is *usually* inline and three-plus *usually* earns `phases/`, so the count flags which outcome to expect and tells you to look harder — but it never settles the call. The stub test settles it: a genuinely deep two-step (each step owing its own method, judgment, or done-state) earns `phases/`; three shallow steps whose complete procedure is their gloss stay inline. When the count and the stub test disagree, the stub test wins.

The skill-level call follows: when most steps pass the stub test, seed `phases/` — a thin step among deep ones folds into the neighboring phase it serves rather than getting its own file. When no step (or only one) passes, the skill is thin: keep the short procedure **inline** in the SKILL.md body, and `phases/` is not created. Anchors for the scale: a full authoring skill — interrogate, shape, seed, hand off, each step carrying its own method, judgment, and done-state — is the deep end; a port or dispatch skill — receive the capability call, resolve the configured adapter, invoke it, relay the result, where every step's full procedure is its gloss — is the thin end. (Basis: the kit's design record pins `phases/` to procedural depth and names the port/dispatch shape as the type case of thin.) Forcing phases onto a thin skill is exactly the speculative structure the scaffolding-skeptic hunts — thin phase files that exist only to satisfy a "every skill has phases/" reflex. The phase-1 intent interrogation supplies the inputs for the test: the steps the capability implies and what each would have to carry.

## Rule — reusable judgment, applied a-la-carte

If a piece is *judgment or craft* that several phases reach for, but that isn't itself a sequenced step, it's a rule. A rule has no position and no on-switch — it lives in `rules/name.md` and the phases that need it *cite* it. "How to phrase a capability without naming a tool" is craft applied during intent, during frontmatter, during seeding — it's not a step you do *once at position three*, it's a discipline you apply repeatedly. That's the signature of a rule: cited from many places, ordered by none. The test: if removing the piece from the sequence and citing it where needed loses nothing, it was a rule wearing a phase's number. Reuse-count is not the only door to a rule file: a single-citer piece — even one a port cites once from its inline body — still earns `rules/name.md` when it carries a **defined vocabulary, a scale, or several discriminators a cold executor must reach** (a failure taxonomy with per-term assignment tests and confusable-pair discriminators earns a file; a bare three-term list stays inline). The tell for promotion is *depth* — a defined vocabulary or multiple reachable discriminators — not reuse alone.

A rule is registered by being cited from the phase where it applies — and *only* that way. It gets no line in the SKILL.md spine, because the spine loads phases and a rule is reached through the phase that cites it, not directly from the body. Listing a rule in the spine is a placement error in the other direction: it dresses cited craft as a sequenced step. So the wiring split is clean — phases are referenced from the spine (the harness loads them on trigger), rules are referenced from their citing phase (loaded only when that phase pulls them in).

## Module — optional behavior, toggled by a flag

If a piece is behavior that runs *only when explicitly turned on*, it's a module, and it comes as a pair with the flag that activates it. A `--security` flag and `modules/security.md` are two halves of one thing — the flag is the on-switch, the module is the behavior. The signature is optionality with a switch: the base procedure is complete without it, and a per-invocation choice brings it in. Two consequences follow. First, a module without a declared flag is unreachable dead code — the flags↔modules check exists precisely to catch a module nobody can turn on. Second, the inverse: if something *seems* to need activation wiring but you can't name the flag, it's not a module — reconsider whether it's a phase (always runs) or a rule (cited craft).

## The three confusions worth naming

**Rule vs. module.** Both are "not a phase", and they're easy to swap. The discriminator is the switch: a rule is *always available* and applied by judgment wherever it fits; a module is *off by default* and turned on by a flag. A rule needs no flag and must not get one — inventing a flag for a rule is how you end up with a flag that gates nothing. A module needs a flag and must have one. Ask: "is this on unless asked off, or off unless asked on?" Cited-craft is the former; flag-gated-behavior is the latter.

**Phase vs. rule.** Both are "runs as part of the normal flow", and the discriminator is position. A phase occupies a slot in the sequence and depends on its neighbors; a rule is timeless craft the phases invoke. If you can't decide, try to assign a number: if a defensible number exists (it must come after X and before Y), it's a phase; if any number is arbitrary, it's a rule. A **graded scale** (a severity/priority/scoring ladder) is placed by the same reuse test: a scale only one phase applies is inlined in that phase; a scale two or more phases — or a module — apply is reusable craft and belongs in a `rules/` file they cite. One consumer → inline; many → a rule.

**Module vs. phase input — the default-selector test.** A flag can look like an on-switch and be nothing but a value. Ask what the skill does when the flag is *absent*: if the answer is "the same step, with a default value" — the flag merely names a phase's default window, branch, scope, or mode, and the phase always consumes *some* value of that input — it's a **phase input**: declare the flag, seed no module. If the answer is "the base procedure, minus a behavior" — nothing in the base run does this thing until the flag adds it — it's a module. The tell: a default-selector's would-be module could only restate what its phase already does; a real module's behavior appears nowhere in the base phases. (A flag that selects how wide a window the first phase examines is a phase input, because the phase always needs *some* window; a flag that adds an extra lens no base phase ever applies is a module.)

## Empty is a valid answer — for the earned slots

Not every skill carries rules, most carry no modules, and a thin one carries no phases. A skill that is a shallow dispatch with no multi-step procedure, no reusable judgment, and no optional behavior is correctly skeletoned as `usage.md` alone plus an inline procedure in its SKILL.md — no `phases/`, no `rules/`, no `modules/`. Do not seed empty slots "for symmetry" or "in case it grows later": speculative slots are exactly the premature structure the scaffolding-skeptic critic hunts, and an empty `rules/` folder — or a `phases/` of one-line stubs — reads to the next maintainer as a missing-content promise rather than a deliberate absence. The *earned* slots are earned by content that exists, not anticipated by content that might. When in doubt, omit the earned slot; adding one later when a real phase, rule, or module appears is cheap, and far cleaner than deleting a slot that never earned its place. This skepticism is scoped to `phases/`, `rules/`, and `modules/` — it never argues away `usage.md`, which is seeded whether or not the skill is "big enough", because it is the uniform contract every skill meets.
