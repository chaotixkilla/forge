A skill that touches an external capability has a prerequisite: that capability must be configured before the skill can run. `config_requires` is how a skill *declares* that prerequisite as part of its contract, so the harness can resolve it — guide the user to set it up, run a reduced path, or hard-stop — before the skill stalls mid-run on a missing backend. Shaping it well is what makes a skill's prerequisites self-resolving instead of a surprise failure. This rule is the craft of writing those entries at the right altitude, with the right type, and the right failure posture — and, just as important, of knowing when there should be none at all.

## First gate: is the plugin config-bearing?

`config_requires` exists only for config-bearing plugins, so the first question is the posture of the *target plugin*, not of the skill. A config-bearing plugin runs inside a consuming project, touches pluggable backends, and carries a config template enumerating them; its skills declare which of those backends they need. A config-less plugin touches none of that — the type case is the authoring kit itself, which runs in the workshop repo against files with version control ambient, and whose skills carry *no* `config_requires` whatsoever. If the target plugin is config-less, the right number of entries is zero, full stop. If the posture is genuinely unclear, default to config-less and declare nothing: a real prerequisite is trivial to add when a concrete need appears, whereas a spurious one makes a skill demand setup it never uses, and the contract audit will flag a `config_requires` key that points at no template entry. Under-declaring is recoverable; over-declaring is a false contract.

## One entry per external capability

When the plugin is config-bearing, write one entry per external capability the skill *genuinely* needs to run — and name the *capability*, never the tool. Derive the capability from what the skill actually touches and what the target plugin's config template offers: the template enumerates the recognized set, so it — not a list memorized here — is the source of truth (you'll commonly see version control, knowledge, CI, artifacts, telemetry, communication, project management, but treat that as illustrative, not closed). The key is `tools.<capability>` — `tools.artifacts`, `tools.vcs` — pointing at the capability the skill depends on, which the config template then maps to a concrete provider. This is the same altitude discipline as everywhere else: the skill declares *"I need an artifacts backend"*, and the configuration decides *which one*. Never write a provider or product name into a `config_requires` key; that would be a tool-leak in the contract itself.

## Type each entry: key plus if_missing posture

Each entry is `{key: tools.<capability>, if_missing: <posture>}`, and the `if_missing` posture is the load-bearing choice — it tells the harness what to do when the capability isn't configured at invocation time. The three postures:

- **guide** — the capability is needed, and the right response to its absence is to walk the user through configuring it (hand off to the capability's setup path), then proceed. In frontmatter this is commonly written **compound** — `guide via <the plugin's config-setup skill>, else degrade` (or `, else block`) — naming the setup path to hand off to and the fallback if setup can't happen. Choose this when setup is reasonable to ask for inline and the skill can't meaningfully run without the capability, but a missing config is an expected first-run state rather than an error.
- **degrade** — the capability is nice-to-have, and its absence should *narrow* the skill, not stop it: run the reduced path that doesn't need it and tell the user what was skipped. Choose this when the skill has a meaningful core that stands without the capability — e.g. a skill that can return results inline but would *also* publish them to an artifacts backend if one were configured.
- **block** — the capability is essential and there is no honest reduced path; the right response to its absence is a hard stop with a clear message. Choose this only when running without the capability would produce a wrong or empty result, so failing fast is kinder than proceeding.

Pick the posture by asking two questions in order. First: *can the skill deliver an honest, useful reduced result without the capability?* Yes → **degrade** (and the reduced path is a promise codify must fulfill). Second, only if no: *is a missing config an expected first-run state, with a setup path to hand to?* Yes → **guide**, written compound with its fallback; no → **block**. The posture encodes *this skill's* dependence, not the capability's importance in general — two skills declaring the same capability can legitimately carry different postures. Get it wrong in the strict direction and you block a skill that could have degraded gracefully; get it wrong in the loose direction and a skill silently produces a degraded result the user expected to be complete.

## Doer-owns-prerequisites

Declare only what *this* skill needs to run — never a prerequisite that belongs to a skill it calls or hands off to, and never one propagated up from a caller. If this skill chains to another that needs version control, that prerequisite is the downstream skill's to declare and resolve when *it* runs; this skill does not pre-satisfy it. The rule keeps each skill's contract a true statement about that skill in isolation: read its `config_requires` and you know exactly what it touches, with nothing inherited and nothing borrowed. A skill that over-declares — listing prerequisites for capabilities only its callees use — fails to run in projects where it would have run fine, because the harness gates it on a backend it never actually reaches.

## At scaffold time, declare the shape — not the behavior

This rule runs while scaffolding, so what you produce is the *declaration*: the typed entries in `metadata.config_requires`, each with its key and its `if_missing` posture, sitting in well-formed frontmatter. The *behavior* behind a posture — the body that actually guides setup, runs the reduced path, or emits the block message — is content-pass work that codify writes into the procedure. Don't conflate the two: at this stage a `degrade` entry is a promise that the skill *will* have a reduced path, fulfilled later. The contract audit checks the declaration's shape (key exists in the template, the posture is in the guide/degrade/block vocabulary — the compound `guide via …, else …` form included); the procedure fulfills it. Hand off a contract that is complete in its declaration and honest about leaving the behavior to be written.
