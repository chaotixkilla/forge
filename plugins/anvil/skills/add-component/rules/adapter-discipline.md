The adapter is the kit's pressure-release valve. The skill layer is held to a hard rule — name only capabilities, never tools — and that rule is only livable because there's one place the concrete tool is *allowed* to live. The adapter is that place. Get its discipline right and the whole capability-not-tool boundary holds with zero friction; get it wrong and either the boundary leaks upward (a tool name escapes into a skill) or the adapter rots (frozen tool facts that no longer match the provider). Two rules keep an adapter honest.

## Hold tool-intrinsic info only

An adapter contains the things that are true *because of the tool* and would change if you swapped tools: the provider's actual calls, the parameters it expects, the shape of what it returns, its quirks and failure modes, and the translation from the capability's abstract request into this provider's concrete one. That — and only that — is an adapter's job.

What does *not* belong: orchestration (what order to do things), policy (whether to do them), and anything that would stay the same across providers. Those are skill-layer concerns. The test: *"if I swapped this provider for another, would this line have to change?"* If yes, it's tool-intrinsic and belongs here. If no, it's leaking down from the skill layer — push it back up. An adapter that decides *when* to publish, not just *how* to publish to one backend, has swallowed skill logic and will have to be untangled later.

## Discover exact params at call time; don't freeze them

Name the calls and their shape, but resolve the precise parameter names and current options when you actually call them — don't hardcode a parameter list into the adapter as if it were permanent. Providers change their surface; a frozen list is a fact with an expiry date, and a stale adapter fails in the most confusing way (it looks right and calls wrong). This is methods-over-facts applied inside the one place tools are permitted: even here, encode *how to make the call* and *what it's for*, and let the exact arguments be re-derived against the live tool. An adapter that says "request the change against this provider's change-request surface, supplying title and body as that surface currently names them" ages gracefully; one that pins specific field names ages into a bug.

## An operation's contract still owes convergence

Holding tool-intrinsic detail does not exempt an adapter from standard-closure. Each operation carries a *contract* — what it returns on partial success, how it disposes of an input the backend is missing versus one it rejects, whether a failure is retryable or permanent, the shape it hands back when a multi-step call half-completes — and every one of those is a place two cold executors diverge unless it is pinned. Those are standard-points, subject to the same closure discipline as any procedure. The trap is the "thin port" framing: *thin* bounds the **skill layer** (a port names capabilities and dispatches — no graded scales up there); it does **not** bound the adapter. An operation that mirrors a sibling adapter inherits that sibling's closure; an operation with **no sibling to inherit from** carries its convergence bar unaided, and its contract must be pinned here to the standard-closure bar or two runs of it will disagree. Name the calls loosely (params re-derived at call time), but pin the *contract* tightly.

Sweep this **per operation, reads included** — a read's own failure branch (an id that won't resolve, a member that's gone) carries the same convergence bar as a write's partial success; the sibling-less operation is the loudest case, not the only one. And the closure does not stop at the adapter: the **skill-layer return taxonomy** — the failure classes the port relays up to its callers (unavailable / not-found / retryable / permanent …) — must name **every class a provider-agnostic caller must mechanically distinguish**. Drop the *permanent* class the adapter defines and a caller coding to the skill layer folds a permanent rejection into *retryable* and spins forever. This is the relayed-vocabulary discipline — an output that relays a component's classes reproduces them all — applied to a port's failure taxonomy.

## Never leak the name upward

The cardinal rule: the tool/provider name lives in the adapter and stops there. The skill layer above names the *capability* and dispatches to whichever adapter is configured; it must never know which adapter that is. Concretely, the parent skill reads *"publish to the configured artifacts backend"* and the dispatch routes that to your adapter — the skill text contains no backend name, ever. If a provider name has crept into a phase, a rule, or a module, that's the exact leak `audit-tool-leaks` exists to catch, and the fix is to relocate the concrete detail down into the adapter and rephrase the skill line as a capability. The adapter is a one-way membrane: tool facts come in, capabilities go out, and nothing tool-shaped passes back up.
