Frontmatter is the part of a skill the harness reads before the body ever runs — it's the contract between the skill and the system that loads it. Get it wrong and the failure is silent and total: a `name` the format doesn't recognize means the skill never registers, a `description` in the wrong shape means it never gets recruited, a flag declared in the wrong place is a flag that doesn't exist. So this phase checks the shape of what the loader sees, against the contract in [frontmatter-contract](../rules/frontmatter-contract.md). It is a structural check — does each field exist, in the right place, in the right form — plus one reading check: does the description name a capability, not a tool. Run it per skill, against the inventory from phase 01; never re-walk the plugin here.

## Recognized fields exist and are well-formed

Every `SKILL.md` must carry `name` and `description` as the format's top-level recognized fields — the ones the loader keys on. Two failure modes to catch:

- **Missing or misplaced.** A skill with no `description`, or one that buried `description` under `metadata`, won't be recruited correctly. The field has to sit where the format expects it, at the recognized top level — not nested, not renamed. Check presence and position, not just presence.
- **Malformed.** A `name` that doesn't match the skill's directory, a `name` that violates the format charset (`^[a-z0-9]+(-[a-z0-9]+)*$` — no underscores, uppercase, or leading/trailing/doubled hyphens), or a `description` that's empty or a placeholder left over from scaffolding, is a defect even though the field is technically present. Check the charset **independently** of the name↔directory correspondence: the same invalid string sitting in *both* `name` and the directory passes a correspondence check while still failing to register at load — the exact load-breaking defect a correspondence-only check waves through. A config-lane underscore (`tools.project_mgmt`) is legal in the JSON key but illegal in the `name` (which is `project-mgmt`). The placeholder tell: text that describes the slot rather than the skill — a line that could sit unchanged in any other skill's frontmatter is scaffolding, not a description. The contract is a usable description, not a filled slot.

## The description reads as a capability

This is the one judgment call in the phase, and the one that distinguishes a contract audit from a syntax check. A description tells the recruiter *what the skill does* — and it must say so in capability terms, never by naming the concrete tool underneath. "Publish the report to the configured artifacts backend" is a capability; the same sentence with a named backend is a tool-leak. The reason is durability: descriptions are matched against user intent and they outlive any one provider, so a description pinned to a tool goes stale the moment the project swaps providers, and worse, it leaks the implementation into the layer that's supposed to be implementation-agnostic.

Flag a description that names a vendor, a CLI, an MCP tool id, or any concrete tool an adapter would wrap. The test that closes the borderline case: would the sentence survive the project swapping providers, unedited? A capability phrase does; a product, CLI, or vendor name doesn't. Note the boundary with the tool-leak audit: that audit hunts leaks across the whole skill body; here you check only the description field, because a malformed-or-leaky description is a *frontmatter* contract defect — the recruiter reads it. Don't expand this into a full-body leak scan; that's a different audit with its own slot-by-slot method.

## The contract lives under metadata

Everything the kit adds beyond the format's recognized fields lives under `metadata` — that's the convention this audit enforces, and it's where phase 03's cross-references go looking. Two things belong there:

- **`flags`** as a map of flag → one-line meaning. A flag declared anywhere else (loose at the top level, or in the body prose only) is not a declared flag as far as the contract is concerned — phase 03 will read it as undeclared, and the flags↔modules check will misfire. Check that every flag the skill actually honors is declared here, in the map, with a meaning.
- **`config_requires`** — for config-bearing plugins only — as typed entries under `metadata`. Each entry declares a capability the skill needs and what to do when it's absent. The shape the contract requires is `{key: tools.<capability>, if_missing: <posture>}`: a capability-keyed dependency plus a posture from the guide/degrade/block vocabulary — where `guide` may be **compound** (`guide via <the plugin's config-setup skill>, else degrade|block`) to name the setup hand-off and a fallback. Check each entry has both halves and that `if_missing` stays within that vocabulary; a missing half, or a posture outside guide/degrade/block, is a defect — but the compound `guide via …, else …` form is valid, not an invented fourth posture. A config-less plugin should carry no `config_requires` at all; its presence there is itself a finding (the plugin claims a dependency its posture says it doesn't have).

## Anti-patterns

- **Treating present-but-empty as conformant.** A `description:` with nothing after it, or a `flags:` map with placeholder entries, passes a naive "field exists" check and fails the contract. The contract is about usable content in the right place, not filled keys.
- **Auditing config shape on a config-less plugin.** If phase 01 recorded "config-less," skip `config_requires` entirely here — its absence is correct. Manufacturing "missing config_requires" findings on a plugin that rightly has none floods the report and buries the real findings.
- **Re-deriving the inventory.** You already have the skill list, the flags, and the config posture from phase 01. Read each `SKILL.md`'s frontmatter once more only to inspect field shape — don't re-walk the slots or re-enumerate components here.
