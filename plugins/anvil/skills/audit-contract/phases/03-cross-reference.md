Phase 02 checked each piece in isolation — is the field well-formed, is the flag declared. This phase checks whether the pieces *agree*. A flag is a promise that a behavior exists; a `config_requires` key is a promise that a config slot exists; a provider enum is a promise that an adapter exists. Each structural check here is a join between two lists from the phase-01 inventory, run in **both directions** — skip the both-directions discipline and you catch missing backings but miss orphans, half a contract check. The last check (standard-closure) is the one non-join: it reads body content, because contracts break in content too. When a join turns on *whether a declared thing obliges a backing thing at all*, that judgment is not re-derived here — it lives in [coverage-expectations](../rules/coverage-expectations.md); this phase states the mechanical check and points there for the "when."

Run only the checks named by `--checks`, or all of them by default. Each is independent; a subset run is a legitimate request (re-checking one dimension after a fix) and must not silently pull in the others. The tokens map one-to-one onto the sections below, in order: `flags-to-modules`, `config-keys`, `adapter-coverage`, `load-wiring`, `skip-resistance`, `usage-doc`, `slot-placement`, `standard-closure` (`frontmatter` is phase 02's token).

`--skill` scopes orthogonally to `--checks` and the two compose: `--checks` narrows *which dimensions* run, `--skill` narrows *which skill* they judge. Under `--skill` ([01-inventory](01-inventory.md) scoped the map), every check runs against that one skill and raises findings only for it; resolve the cross-skill joins against the siblings and config read as join context (per [01-inventory](01-inventory.md)) so a scoped run reports no phantom dangling reference, and don't raise a finding on a sibling's own contract. One check needs its plugin-wide nature spelled out: **adapter-coverage** attributes to the port skill that *owns* the `adapters/`, so under `--skill` it runs for the scoped skill's own adapters when that skill is the owning port, and is otherwise outside the single-skill scope — reported as a deliberate skip, exactly as the config-bearing checks are on a config-less plugin ([04-report](04-report.md)).

## Flags ↔ modules

A behavior-gating flag is an on-switch; the module is the behavior it switches on. Check the bijection both ways:

- **Flag → module.** Finding: a behavior-gating flag with no backing module in `modules/` — a dead switch the user passes to no effect.
- **Module → flag.** Finding: a module with no activating flag — unreachable dead code; the behavior exists but nothing fires it.

Whether a given flag *gates behavior* (module owed) or merely *parameterizes a phase* — a target selector, a format switch, a subset narrower owes none — is the coverage judgment, with its operational test, in [coverage-expectations](../rules/coverage-expectations.md). Name the discriminator, don't re-derive it: demand a module only where the flag toggles dormant behavior, or you file false findings against the parameterizing ones.

## config_requires ↔ config keys (config-bearing plugins only)

Each `config_requires` entry names a capability dependency that's only real if the config has a slot for it. Cross-reference every declared key against the config schema or template from phase 01. Finding: a declared dependency key with no matching template slot — at runtime it resolves to nothing and the `if_missing` posture never gets to fire. Skip this check on a config-less plugin (phase 01 recorded the posture); don't synthesize a phantom template to check against.

A second finding lives on this join: **over-declaration by delegation.** The dependency belongs to the *doer* — whichever skill directly resolves the backend and calls its adapter. A skill that declares `tools.<cap>` but never dispatches `<cap>` *itself* — every use is handed off to a port skill that owns the capability — is claiming a prerequisite it doesn't touch. Check by inspection: for each declared `tools.<cap>`, find where the body uses it; if every use is a delegation (a phase names the capability and hands the operation to a sibling port skill that itself declares `tools.<cap>`, and this skill owns no `<cap>` adapter of its own), the key is stale. Finding: a `config_requires` key for a capability the skill fully delegates — it gates its run on a backend only the port skill uses (the precedent that fixes it: a skill that delegates its `--publish` to a shared artifact skill declares no artifacts dependency; the port skill carries it). A skill that resolves the backend directly *anywhere* keeps the key, even if it also delegates elsewhere — the test is whether it ever touches the backend itself.

A companion finding on the same join is its inverse — **mis-delegation**. Over-declaration hands off a capability the skill shouldn't *declare*; mis-delegation hands off an operation the named port cannot *perform*. When a skill delegates an operation to a port, that operation must be in the **port's declared operation set** — read the port's `SKILL.md` and confirm it offers the specific operation the consumer hands it (fetch a hosted change, post a status), not merely that it owns the capability's config key. Routing an operation the port doesn't declare delegates into a void: at runtime nothing serves it, and a degrade posture may fire ("backend unconfigured") for an operation that never needed that backend. The frequent shape is a **local or ambient read mis-modeled as a delegation** — reading a local file, or the local working-tree state, needs no configured backend and is *not* a delegation; it is ambient, like reading the tree the audit itself runs in. Routing an ambient read through a host-oriented port both over-declares a dependency and answers a *different question* when that port degrades (a whole-subject fallback where the local read was right there). Finding: an operation delegated to a port that isn't in that port's declared operation set — including an ambient/local read dressed as a delegation. Check by inspection: match each delegated operation against the target port's declared operations, and name a local/ambient read as ambient, carrying no capability. Over-declaration and mis-delegation are the two ways a delegation goes wrong — declaring a backend you fully hand off, and handing off an operation the delegate can't do.

## Adapters ↔ providers (config-bearing plugins only)

Each provider a project can select needs a backing adapter, or the selection routes to nothing. Cross-reference the provider enums against the adapter inventory. Finding: a configured provider with no backing adapter — a runtime dispatch into nothing. Which providers *count as configured* — and why an enumerated-but-unselected provider missing an adapter is a note rather than a finding, except when a capability's *every* provider lacks one — is settled in [coverage-expectations](../rules/coverage-expectations.md).

## Spine ↔ phases, and phases ↔ rules (load wiring)

The other joins ask whether a declared thing has a backing thing; this one asks whether the backing thing is *reachable*, because the harness loads a skill body lazily — on trigger it reads only the `SKILL.md` body, and a sibling file loads only when an already-loaded file references it by a resolvable relative path. A file referenced by nothing never loads, and the skill silently runs without it. Both-directions joins against the phase-01 inventory:

- **Spine → phases (only when phases exist).** IF a skill has phases, its `SKILL.md` must reference each one by relative path. Finding: a `SKILL.md` whose spine doesn't reference one (or more) of its *existing* phases — that phase never loads and the skill runs on its summary, not its method. This is the highest-severity break in the audit. A skill with no `phases/` slot strands nothing and is not a finding — phases are earned (see [coverage-expectations](../rules/coverage-expectations.md)).
- **Phases → rules.** Finding: an orphaned rule (no citing phase — dead craft that never loads), or a phase citing a rule that isn't on disk (a dangling reference).

**A citation counts only if it resolves.** "Cited" means a resolvable relative markdown link from the citing file's directory — from inside `phases/`, a sibling rule is `[name](../rules/name.md)`. A bare backticked path is prose the loader never follows; a bare `rules/name` resolved from `phases/` points at the non-existent `phases/rules/name`. Check each mechanically: take the citing file's directory, apply the link target, confirm a file exists there. Finding: a non-resolving citation — bare path, missing `../`, missing `.md`, or target absent — in the same severity family as an orphaned rule. Modules are covered by the flags↔modules join above (reachability runs through the flag, not a body citation); where a module *is* cited from its activating phase, that citation must still resolve.

**A cross-skill delegation is cited like a rule; a delegation to a not-yet-built skill is not a citation at all.** A phase or module that delegates a capability to a *sibling skill* cites that skill's `SKILL.md` by a resolvable link, and that link must resolve, same as a rule's. But a delegation to a **skill not yet built** is named in prose and flagged *proposed* with no link — a link to a nonexistent file would dangle. That prose reference is legitimate: **do not file it as a dangling or orphaned reference.** Confirm the flag it activates is real (the flags↔modules join); the unbuilt target is future work the maintainer ratified, not a wiring defect.

## Spine glosses and delegations are load-bearing (skip-resistance)

Load-wiring confirmed the phase is *referenced*; this check asks whether the reference is *load-bearing* — whether the agent must open the phase (or invoke the sibling) to run the step, or can act on the spine/description alone and skip the method. The exempt cases and fuller rationale are in [skip-resistance](../rules/skip-resistance.md); the two mechanical flags:

- **Self-sufficient spine gloss.** Read each numbered SKILL.md line: could a cold executor complete the step from that line alone (does it carry the method, not just the capability + pointer)? Finding: a spine gloss carrying executable method — the phase it links is referenced but will be skipped. (Exempt: a thin/port skill whose spine is an inline procedure with no `phases/`.)
- **Descriptive delegation.** Read each phase/module that hands a capability to a sibling skill/port: does it name the sibling to *invoke* and consume its return, or describe the work as something to *do in place*? Finding: a delegation phrased as work to perform (no named sibling-invocation) — it licenses a raw hand-rolled substitute (the delegation-bypass). This is distinct from the mis-delegation join above (which checks the op is in the port's set); here the defect is that no invocation is named at all.

Both are static reads; the completion-trace property is not statically decidable and is not checked here (see the rule). Severity sits with the load-wiring family — a skipped method is the same damage class as an unreferenced phase.

## Usage doc ↔ SKILL.md (a non-spine pointer)

Every skill owes a caller-facing `usage.md`, referenced off the spine. Two things must both hold:

- **Present and referenced.** Finding: a missing `usage.md`, or one present but unreferenced (or referenced but absent) — caller docs no caller is routed to, or a dangling pointer.
- **Referenced as a non-spine pointer.** The reference sits in the top-of-body prose, not the numbered spine — `usage.md` is caller docs, not a step the executor runs. Finding: `usage.md` wired in as a numbered spine step (it mis-instructs the executor to run docs as a phase). A spine citation is the defect, not the pass.

Run this alongside the spine↔phase and phase↔rule joins, not folded into them. Coverage here is uniform — every skill owes one, with no "configured vs. theoretical" softening (see [coverage-expectations](../rules/coverage-expectations.md)); severity sits below the runtime breaks (see [04-report.md](04-report.md)).

## Body files ↔ slots

Every body file lives in a slot, and the slot encodes an altitude: `phases/` is ordered must-run procedure, `rules/` is reusable a-la-carte craft, `modules/` is flag-activated behavior. A file in the wrong slot is consumed at the wrong altitude — a scattered procedure loses its order, a reusable craft note buried in `phases/` runs once when it should be citable everywhere. Walk each body file and match its content-kind to its slot against [slot-placement](../rules/slot-placement.md), which carries the tells. Finding: a file whose content kind doesn't match its slot, named with the kind it should be.

This is the most judgment-heavy check in the phase — recruit the contract-skeptic critic. Hand it your placement calls (and any flags↔modules verdict you're unsure of) and let it argue the other side; a call that survives it is one you can state with confidence.

## Standard-points are closed

The joins above check wiring; this check reads content — the one question the phase-01 map can't answer. A skill's body makes and demands judgments, and a judgment left open silently diverges run to run: every executor fills the bar from its own priors. Three openings have a mechanical shape you check by inspection — **lead with them**; the full scan, the closed-state tests, and the marker forms live in [standard-closure](../rules/standard-closure.md). Walk every phase, rule, and module of each skill and apply, in order:

- **Defined scale.** The trigger is the *output*: if the skill's findings/candidates carry a grade, rating, severity, confidence, or rank at all, a named scale is mandatory and each level must carry a one-clause assignment test — inline or in a cited rule — with anchors on the top and bottom. Two dodges, one finding: rating the output while naming no scale ("assign by impact" — the ladder is invented per run), and naming rungs without an assignment test (bare labels — the lines are drawn per run). Finding: output is rated but carries no defined scale, or a named level with no assignment test.
- **Sourced bar.** Every bar the skill *pins* carries, inline, one visible marker: `(basis: …)` or `(routed to maintainer: …)`. Finding: a pinned bar carrying neither — a fiat assertion whose tightness the next editor can't trace or contest.
- **Discriminator-linked judgment.** Every grading, ranking, or selection verb ("grade," "prioritize," "pick the strongest," "keep the good ones," "filter," "rank by") has its discriminator — the property the judgment turns on — stated inline or in a cited rule it can reach. Finding: a judgment verb with no reachable discriminator; the executor invents the axis and two runs rank on different ones.

Each is near-mechanical: enumerate the levels / find the pins / find the verbs, then check for the definition / the marker / the discriminator. The missing thing is nameable, so a lazy auditor cannot wave it through.

The defined-output family runs deeper than the graded scale: when a skill's output *relays* a sub-component's grade, is a *ratio* or threshold, *classifies the whole run* into terminal outcomes, or must report an honest *absence*, the [standard-closure](../rules/standard-closure.md) defined-output checklist carries the matching check. Apply it whenever the output has one of those shapes.

Past these shapes, a judgment can still be open — a bare qualifier ("appropriate," "sufficient") standing where a bar should be, attached to no scale, no explicit pin, no grading verb. For that residue apply the **divergence pair**: write the two defensible cold readings of the same line. If you can write the second reading, it's open by omission — file it with the pair as proof. This residue is judgment-heavy and earns an adversarial pass — recruit the standards-skeptic critic (a sibling of the contract-skeptic, under `agents/critics/`) to presume every judgment word hides an unpinned bar and articulate the two readings. And keep the audit diagnostic: flag that a bar is open, never propose its value — a bar filled from the auditor's priors is the same defect this check exists to catch. Even the `(routed to maintainer: …)` marker's proposal is the *producer's*; the checker confirms a marker is present, it never authors the bar.

## Anti-patterns

- **One-directional joins.** Checking flag→module but not module→flag (or spine→phase but not phase→rule) leaves orphans uncaught. Each join runs both ways.
- **Trusting existence over reference.** A phase or rule file sitting in the right slot is not enough — if nothing references it with a resolving link, the harness never loads it. An unreferenced phase reads as a clean slot in a naive walk and is the audit's most damaging miss.
- **Counting a bare path as a citation.** A path in backticks is prose the loader never follows. Resolve every citation; don't satisfy a join by string-matching filenames against body text.
- **Collapsing the usage.md check into load-wiring.** Its point is precisely that the reference must *not* be a spine step — a spine citation is the defect, not the pass.
- **Filing every judgment word as an open standard.** Past the mechanical checks, the residue finding needs the divergence pair — two defensible cold readings. A qualifier whose readings collapse to one verdict is closed in practice; flagging it buries the genuinely open points.
