An audit that finds problems but reports them badly is an audit no one acts on. The findings are only useful if the maintainer can tell, for each one, *what's wrong, where, and how the contract says it should be* — and can tell the showstoppers from the nits at a glance. This phase turns the cross-reference results into that report. It writes nothing back to the plugin and fixes nothing — a contract audit is diagnostic; remediation is a separate, deliberate act the maintainer takes after reading. The report's whole job is to make that next act obvious.

## Honor the requested scope

Report exactly the checks that ran. If `--checks` named a subset, the report covers that subset and says so — a report that silently implies full coverage after a partial run is a lie of omission, because a maintainer reads "no findings" as "all clear" when really four of five dimensions were never looked at. State which checks ran and which were skipped (including the config-bearing checks skipped because the plugin is config-less — that's a deliberate skip, not a gap, and saying so pre-empts the "why didn't you check config?" question). Default is all checks; a subset is the explicit ask.

The same holds for `--skill`: a skill-scoped run names the skill it judged, so "no findings" reads as "this skill is clean" and never as a clean bill for the siblings that were only read as join context, not audited. Default is every skill; a single skill is the explicit ask.

## Each finding: what, where, expected

Every finding points at the responsible file and states what the contract expected versus what it found. Three parts, always:

- **Where** — the file (and the specific flag, key, or provider) the finding is about. A finding the maintainer can't locate is a finding they can't fix. "An orphaned module exists somewhere" is useless; "`modules/deep.md` has no activating flag" is actionable.
- **What's wrong** — the specific contract breach, in one line. "Declared `--deep` flag has no backing module," not "flag issue."
- **What the contract expects** — the fix direction, so the finding carries its own remedy. "Add a `modules/deep.md` or remove the flag" tells the maintainer the two legitimate resolutions without this phase choosing for them. For an open standard-point the expected state is the *closure*, not a value: define the undefined scale level, add the missing `(basis: …)` / `(routed to maintainer: …)` marker to the fiat pin, supply the discriminator-less verb its axis, or record inline why the bar stays open. The audit never proposes what the bar should be — a bar filled from the auditor's priors is the very defect the check catches; the value is the maintainer's to source from the plugin's design record.

## Rank by severity

Sort findings so the contract-breaking ones come first. The tier test — so a finding kind this list doesn't name still lands in the same place for any two executors — is *what does the defect break?* The skill's own method never loads → tier 1. A declared behavior or dependency is silently inert at runtime → tier 2. Callers are undocumented → tier 3. The runtime behaves correctly but the structure misleads a reader → tier 4. "Changes what executes" always outranks "changes what a reader understands"; that ordering, not the order the checks happened to run in, is the whole basis.

- **Tier 1 — method loss.** A `SKILL.md` whose spine doesn't reference one of its *existing* phases: the harness never loads that phase and the skill runs on its summary, not its method — the most total break the audit can find, worse than a dead switch since the affected behavior isn't just unreachable, it's the skill's own procedure gone missing. (A skill with no `phases/` slot is not this finding, or any finding — phases are earned by procedural depth, and a thin skill validly keeps its short procedure inline in `SKILL.md`; there is no stranded phase to rank.)
- **Tier 2 — behavior-breakers.** A dead flag (user passes it, nothing happens); a `config_requires` key that resolves to nothing (runtime dependency hole); an orphaned rule no phase loads; a dangling or non-resolving citation (a bare-path "citation" the loader can't follow loads nothing — same family as the orphan); and an open-by-omission standard-point — an undefined scale level, a missing absence/negative case, a fiat bar (a pin carrying no `(basis: …)` or `(routed to maintainer: …)` marker), a discriminator-less grading verb, or a bare judgment the divergence pair splits (see [standard-closure](../rules/standard-closure.md)). A standard-point never crashes a run, it silently degrades every run: the skill executes, but the judgment inside it is filled from each executor's priors, so the "same" skill returns different verdicts run to run. All of these sit below a spine→phase break because the method still loads — it's a declared behavior, or the bar inside the method, that's gone.
- **Tier 3 — caller docs.** A missing or unreferenced `usage.md`: a genuine contract gap — the skill owes caller-facing docs and either lacks them or routes no caller to them — but nothing that executes is degraded. Pinned below tier 2, not above it: a maintainer plugs runtime holes before docs holes, per the tier test.
- **Tier 4 — convention defects.** A misfiled slot, a `usage.md` wired in as a numbered spine step (a placement defect of the same kind — the reference exists but sits at the wrong altitude, mis-instructing the executor rather than breaking a behavior), a tool-flavored description: real, worth fixing, but the plugin runs correctly today.

Below all tiers, **notes**: observations carrying no action obligation — an enumerated-but-unselected provider with no adapter, for instance — render in a trailing section outside the finding count. Findings are triage items; padding the count with no-action items dulls the triage. Within a tier, group by skill, then by file within the skill — remediation happens one file at a time inside one skill at a time, so this order matches the fix path instead of ping-ponging the maintainer across the plugin. Severity isn't decoration; it's the maintainer's triage order, and getting it wrong buries a showstopper under three nits.

## Render per --report

- **Inline (default)** — return the findings directly, severity-ranked, in the conversation. This is the right default: a contract audit is usually run in flow, mid-edit, and an inline list is the fastest thing to act on.
- **Artifact** — when `--report=artifact`, write the findings to the configured artifacts backend instead and return the reference. Choose this for a report that outlives the conversation — a baseline to hand off, or a pre-release sign-off record someone else will read. The content is identical; only the destination differs. (The example names the *capability*, not a backend: which artifacts provider it resolves to is the project's config, not this phase's business.)

## Edge cases

- **A clean audit still reports.** Zero findings is a result, not silence. Say "all checks passed" and name the checks that ran — a maintainer needs to know the audit ran and found nothing, distinct from the audit not running. An empty report reads as a crash.
- **Findings that depend on judgment.** A slot-placement call the contract-skeptic flagged as arguable — or a standard-closure call whose divergence pair the standards critic judged thin — should be reported as such: state it as a finding but note it survived (or was softened by) the critic, so the maintainer weights it accordingly rather than treating a close call as a hard breach.
- **Don't fix here.** If the urge is to also rephrase the leaky description or move the misfiled file, resist it — this phase reports. Remediation belongs to the maintainer, or to whatever skill they invoke next with the report in hand.
