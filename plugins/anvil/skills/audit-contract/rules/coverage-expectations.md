Several of the cross-reference checks — flags↔modules, adapters↔providers, and the spine↔phases / phases↔rules load wiring — are really questions about *coverage*: when does a declared thing oblige a backing thing to exist, and when does a thing-on-disk oblige a reference that loads it. Answer too loosely and the audit under-reports (a dead flag slips through, an unreferenced phase reads as fine); answer too strictly and it over-reports (every selector flag and every theoretical provider becomes a false "missing" finding). This rule sets where the line sits, so each check demands backing where backing is genuinely required and nowhere it isn't. The governing principle all halves share: judge against what the plugin and its projects *actually use* and load, not against every shape the convention could theoretically take.

## Flags: a backing module is required only when the flag gates behavior

A flag obliges a module when, and only when, it turns a distinct behavior on. The test is what the flag *does*:

- **Gates behavior → module required.** A flag like "also run the exhaustive pass" activates a self-contained chunk of behavior that's dormant otherwise. That behavior must live somewhere — a `modules/` file — or the flag is a dead switch the user can pass to no effect. Missing module is a finding.
- **Parameterizes a phase → no module, and demanding one is a false finding.** A flag that names a target (`--plugin=<name>`), selects an output format (`--report=inline|artifact`), or narrows a run (`--checks=<list>`) doesn't activate dormant behavior — it tunes behavior the phases already run. There is no module to back it, correctly, and filing "missing module" against it is over-reporting.

And the reverse, which the both-directions check enforces: **a module with no flag is dead** regardless of this distinction. Behavior that nothing can activate is unreachable code; that's always a finding, because the only way to reach a module is through its flag.

The judgment is "dormant behavior toggled on" versus "running behavior tuned," and it has an operational test: run the skill in your head without the flag. If every behavior the skill can perform still occurs on some default path — the flag only picked the target, the format, the subset, the window — the flag parameterizes, and no module is owed. If some behavior now happens on *no* run at all, the flag gates it, and that dormant behavior needs a `modules/` home. A corollary that settles a recurring confusion: a flag whose no-flag default *is* one of its own values (a default selector — it merely names which branch runs when you don't pass it) parameterizes by definition; there is no dormant behavior to house. When a flag still won't land on either side of the test, that's a close call worth the contract-skeptic critic, not a mechanical rule-out.

## Adapters: cover the providers a project actually configures

A config-bearing plugin's config enumerates providers per capability, and each provider a project can *select* needs a backing adapter or the selection routes to nothing. The line here is about which providers count:

- **Judge against configured providers, not the universe of conceivable ones.** A capability could in principle support a dozen providers; what matters is the set a real project configures. A missing adapter for a provider no project selects is not a live defect — it's an unexercised branch, at most a note. A missing adapter for a provider a project *does* select is a runtime hole: the user picks it and the dispatch resolves to nothing.
- **Why not demand exhaustive coverage.** Requiring an adapter for every enumerable provider turns the audit into a checklist against a hypothetical, floods the report with findings no project will ever hit, and pressures the plugin to carry adapters it has no use for. Coverage is measured against use, not against the enum's outer bound.

In capability terms: the config routes an "artifacts backend" capability and a project configures one provider for it. That provider needs a backing adapter under `adapters/` — selecting it must resolve to a real implementation. A second provider the enum lists but no project configures doesn't oblige an adapter today; it's the configured selection that makes coverage load-bearing.

How "configured" is determined at audit time: the live set is whatever provider selections are *reachable from where the audit runs* — a consuming project's config file, when the audit runs inside one. A missing adapter for a reachable selection is a runtime hole and a behavior-breaker finding. When no project config is reachable (auditing the plugin in its marketplace repo, the common case), every enumerated provider is merely *selectable* — the enum is the plugin's offer, not evidence of anyone's use — so missing adapters there are reported as notes outside the finding count, not findings. Not enumerated at all obliges nothing; the audit doesn't invent providers. One exception stays a finding even with no config in reach: a capability whose *every* enumerated provider lacks an adapter — then no selection any project could make would resolve, which is a dead capability, not an unexercised branch. (Basis: this rule's own principle — coverage is measured against use, and the config in reach is the only evidence of use the audit has.)

## References: every file that must load needs something that loads it

The harness loads a skill body lazily — only the `SKILL.md` body is read on trigger, and a sibling file loads only when an already-loaded file references it by relative path. So a body file's reachability, not its mere existence, is what coverage measures here. The line is hard, not judgment-soft like the flag/adapter halves, because the load chain is mechanical:

- **A phase that exists obliges a reference from the spine.** `phases/` is earned by procedural depth — a skill with a real multi-step procedure decomposes it into ordered phases; a thin skill (a few shallow steps, no per-step depth) keeps that short procedure inline in `SKILL.md` and ships no phase files at all. So the obligation is conditional on the slot being populated: *if* a skill has phases, every file in `phases/` must be cited by its `SKILL.md`, because the spine is the only file loaded on trigger and an uncited phase never loads — the skill then runs on its summary instead of its method. (Whether a given skill *should* have decomposed — the depth bar itself — is the scaffolding skill's standard, not this audit's; here, absence is simply valid.) This is the most load-bearing coverage requirement in the audit when it applies — a missing module leaves the skill's method intact, but a stranded phase reference *is* the missing method. A `SKILL.md` that doesn't reference one of its *existing* phases is a high-severity finding, ranked above any dead-switch or orphaned-backing finding. But a skill with no `phases/` slot is not a finding: its procedure lives inline in `SKILL.md`, which is valid, and there is no file on disk left stranded.
- **A rule obliges at least one citing phase.** Citation is a rule's only registration. A rule in `rules/` that no phase cites never loads — it's dead craft, however good. Coverage is satisfied by *one* citing phase; a rule need not be cited by every phase, only reached by some. An orphaned rule (zero citing phases) is a finding; so is the reverse, a phase citing a rule that isn't on disk (a dangling reference that loads nothing). For a **phase-less skill** — a port or thin dispatch whose procedure is inline in `SKILL.md` with no `phases/` — the inline body *is* the citer: a rule reached by a resolvable link from that body is registered exactly as a phase citation would register it, so "citing phase" reads as "citing body" here. The rule is orphaned only when nothing links it — neither a phase nor the inline body. A rule may sit in a **subdirectory** of `rules/` (`rules/<family>/name.md`) when a large library groups its files into families; this changes nothing here — the citation is a resolvable relative link that carries the subpath (`../rules/<family>/name.md` from a phase), the slot is still `rules/`, and the one-citing-phase and link-resolves checks run exactly as they do for a top-level rule. Don't treat depth as a defect: a nested rule is orphaned only if nothing links it, dangling only if its link doesn't resolve — the same two tests, applied to the fuller path.
- **A citation counts only if it resolves.** "Cited" means a relative markdown link the loader can follow from the citing file's directory — from inside `phases/`, a sibling rule is `[name](../rules/name.md)`. A bare backticked path is prose, not a citation: the loader never follows it, and a bare `rules/name` resolved from `phases/` would point at the non-existent `phases/rules/name` regardless. So resolve every citation — take the citing file's directory, apply the link target, confirm the file exists — and never satisfy this check by string-matching filenames against body text. A rule reached only by bare mentions is orphaned in practice; a link whose target is absent is dangling. Both are findings of the same family.

Unlike the flag and adapter halves, once a phase or rule is *on disk* there is no "configured vs. theoretical" softening to apply: a phase or rule the plugin ships is a phase or rule that must be reachable. That hardness is about reachability, not about existence — whether a skill has phases at all is the separate, earned-by-depth question above (a thin skill validly ships none), and a skill without phases strands nothing. The only thing this reachability check doesn't reach is modules — a module's reachability runs through its activating flag (the flags↔modules half), not through a body citation, so it isn't double-judged here.

## Usage docs: every skill owes one, referenced off the spine

`usage.md` is caller-facing documentation, and coverage here is uniform and hard-edged — every skill owes exactly one, no exceptions and no "configured vs. theoretical" softening. Two conditions, both required:

- **Presence and a reference.** The skill ships a `usage.md` and its `SKILL.md` points at it by relative path. Missing docs, or docs nothing routes a caller to, is a gap either way.
- **A non-spine reference.** The pointer belongs in the top-of-body prose, not the numbered spine. `usage.md` documents how to *call* the skill; it is not a step the executor *runs*, so wiring it in as a numbered spine step is a placement error — it tells the executor to run caller docs as a phase. Coverage is satisfied only by a non-spine pointer; a spine-step citation fails the check even though a reference exists.

This differs from the phase/rule reachability above in what "reachable" means: a phase must be reachable *by the executor via the spine*, whereas `usage.md` must be reachable *by a caller via a non-spine pointer* — same lazy-load mechanism, opposite placement. Don't collapse the two; a `usage.md` in the spine is a defect, not a pass.
