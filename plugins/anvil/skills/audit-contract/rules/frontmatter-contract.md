This is the definition the frontmatter phase checks against and the cross-reference phase reads flags and config dependencies from. Frontmatter is the only part of a skill the harness parses before running the body, so its shape is load-bearing in a way prose isn't: the loader keys on it. The contract below is the convention the kit enforces — recognized fields where the format expects them, everything the kit adds nested under `metadata`. It is a *shape*, not a schema document — don't transcribe an exact field list here, where it would go stale the moment the format moves. Authority splits cleanly by layer: for the recognized top-level fields, the format's official documentation wins over kit practice when the two disagree (the loader implements the docs, not our habits); for everything under `metadata`, the kit's own convention is the authority — the format ignores that envelope by design, so there is no external schema to defer to.

## Recognized fields, at the top level

`name` and `description` are the format's recognized fields and must sit where the loader looks — at the recognized top level, not nested under `metadata`, not renamed. Both are required; both must carry real content, not a scaffolding placeholder.

- **`name`** identifies the skill to the loader and should correspond to the skill's directory. A mismatch is a defect even when both halves exist — and so is a `name` that violates the format charset `^[a-z0-9]+(-[a-z0-9]+)*$` (lowercase alphanumeric, single hyphens; no underscores, uppercase, or leading/trailing/doubled hyphens): an invalid `name` fails to register at load. Check the charset *independently* of the correspondence — the same invalid string in both `name` and the directory passes a correspondence check yet is still load-invalid. A config lane's underscore (`tools.project_mgmt`) is legal in that JSON key but never in the `name` (which is `project-mgmt`).
- **`description`** is what the recruiter matches against intent, and it must read as a **capability** — what the skill does, never the concrete tool it does it with. "Open a change request against the configured review backend" is a capability; the same line naming a vendor or CLI is a tool-leak in the one field the recruiter reads. The borderline test: would the sentence survive the project swapping providers, unedited? A capability phrase does; a product, CLI, or vendor name doesn't. The reason is durability and layering: the description outlives any provider and lives in the implementation-agnostic layer, so a tool name there both goes stale on a provider swap and leaks the implementation upward.

## The kit's additions live under metadata

Everything beyond the recognized fields is the kit's own convention, and it nests under `metadata`. Two kinds of entry belong there:

- **`flags`** — a map of flag → one-line meaning. The map is the *declaration*: a flag honored by the body but absent from this map is undeclared as far as the contract is concerned, and the flags↔modules cross-reference will read it as missing. Every flag the skill actually honors appears here, each with a meaning terse enough to render in a help listing.

- **`config_requires`** — *config-bearing plugins only* — typed entries declaring the capabilities the skill depends on and what to do when one is absent. Each entry takes the shape `{key: tools.<capability>, if_missing: guide | degrade | block}`:
  - **`key`** is capability-keyed (`tools.<capability>`), never a named provider — the dependency is on "an artifacts backend," not on a specific one.
  - **`if_missing`** is built from three recognized postures — **`guide`** (walk the user through configuring the missing capability, then proceed), **`degrade`** (continue with reduced function, skipping the part that needed it), or **`block`** (stop; the capability is load-bearing and there's no sensible partial run). `guide` is commonly written **compound**, naming the config-setup skill to hand off to and a fallback if setup can't happen: `guide via <the plugin's config-setup skill>, else degrade` (or `, else block`). That compound form is well-formed — it is a qualified `guide`, not a fourth posture.

  An entry missing either half, or carrying a posture outside the guide/degrade/block vocabulary, is malformed. Whether the *chosen* posture is wise for its capability is deliberately open: that's a per-capability design call the author makes, unauditable by shape — the contract checks vocabulary membership and completeness, nothing more. A config-less plugin should carry no `config_requires` at all — its presence there is itself a finding, because the plugin is claiming a runtime dependency its config posture says it doesn't have. And the dependency belongs to the *doer* — the skill that directly resolves the backend and calls its adapter. A skill that delegates a capability wholesale to a port skill (naming the capability and handing the operation off, the way one skill hands its publish step to a shared artifact skill) declares no `config_requires` for it; the port skill, as the doer, owns it. Declaring a prerequisite you fully delegate is over-declaration — a dependency the skill never directly touches — and the cross-reference phase checks for it.

## What this rule is not

It is not a full-body tool-leak scan — that's a separate audit with its own slot-by-slot method. Here the only reading check is on the `description` field, because the recruiter reads that field specifically; the rest of this rule is structural. And it is not the place to assert which fields the format recognizes as gospel — that set belongs to the format and can move. Check shape against the convention and the kit's living examples, not against a hardcoded field list memorized here.
