A static audit proves a plugin is *shaped* right — frontmatter well-formed, no tool leaks, every flag backed. It cannot prove the plugin *works*. Dogfooding is the behavioral counterpart: actually run the plugin's skills and watch where they stall, guess, or drift from what their frontmatter promised. But a dogfood run is only as good as its scenarios — exercise the happy path and you prove nothing the audits didn't already. This phase chooses the invocations worth running, and it is the phase that decides whether the whole run finds anything.

## Resolve the subject — and refuse to guess it

Dogfood needs two things named before it can pick anything: *which plugin's skills* are the tool, and *what they run against* as the subject. Resolve them in this order:

- `--self` sets both at once: the kit is the tool **and** the subject. This is the self-hosting proof — the kit running its own skills on its own tree. Equivalent to targeting the kit's own plugin root as the subject.
- `--plugin=<name>` names the tool. By default the subject is that same plugin — a plugin proving its skills work by turning them on itself.
- `--subject=<path>` overrides the default subject: run the tool's skills against a *different* tree. It composes with `--self` the same way — the subject half is overridden, the kit stays the tool — because the flag's declared meaning is "override the subject," not "pick a tool." Reach for it when the plugin under test has no meaningful self, and the test for that is the operand class: a plugin has a meaningful self when its skills operate on the class of thing it itself is (an authoring kit operates on plugins, and is one); it has none when its skills' operand class excludes its own tree — and then an external subject is required, not optional.

If neither `--plugin` nor `--self` is given, **stop and ask** — do not pick a subject for the maintainer. Defaulting the subject silently is the one thing this phase must never do: a dogfood run against the wrong tree produces findings that look real and aren't, which is worse than no run. The subject is load-bearing; an unstated subject is an unresolved decision, not a default.

## Choose scenarios that exercise real craft

A scenario is one concrete invocation of one skill against the subject — a flag combination plus enough of a starting state that the skill has real work to do. The selection craft — including the load-bearing test that separates a stress from a smoke test, and the sufficiency floor the finished set must clear — lives in [picking-scenarios](../rules/picking-scenarios.md); the short version is: **pick the invocations most likely to break.** Three signals point at them:

- **Decision forks.** A skill whose phases case-split — "if the capability is new to the skill, do A; if it already exists, do B" — has at least two scenarios hiding in it, and the interesting one is rarely the first branch. Pick the branch that gets the least hand-running, which is reliably the non-default one: the error path, the empty-input path, the already-exists path, the second configured provider. The default branch was exercised every time the maintainer touched the skill; the non-default branch may never have run at all.
- **Surface area.** The skills with the most flags, the most slots, or the most external touches have the most ways to drift. A skill that dispatches a capability to a configured backend, gates a module behind a flag, *and* takes a subject path has three independent things that can be wired wrong; one scenario each beats three scenarios of the simplest skill.
- **Reflexive reach.** Under `--self`, prefer the kit skills that operate *on skills* — the authoring and audit skills — because those are exactly the ones whose correctness the kit's whole premise rests on. If the kit's own component-adder can't add a component to the kit, self-hosting is a fiction.

For example, dogfooding a kit's component-adder: a weak scenario is "add a rule to some skill" — it touches no wiring and proves only that a file gets written. A strong scenario is "add a flag-activated module to a skill that has no flags yet," because that forces the skill to create *both* the module body and the activating flag declaration, and a downstream contract check will immediately catch it if only one half landed. The strong scenario passes the rule's load-bearing test — a nameable defect, an observable failure, beyond the static audits' reach; the weak one fails its first question, because "the file didn't get written" is a defect any invocation would catch.

## Size the set — sufficient, bounded, closed

Pick a small, fixed set — enough to clear the sufficiency floor in [picking-scenarios](../rules/picking-scenarios.md), few enough to actually run and read end-to-end. Sufficiency is relative to the claim the report will make: a set licenses "this plugin works end-to-end" only if it chains the plugin's primary workflow start to finish *and* hits the highest-risk fork of each high-surface skill; anything narrower, and the verdict must name the paths it walked instead of claiming the plugin. The scenario *count* is deliberately open — plugin pools vary by an order of magnitude, so a pinned number would be false precision — but the working anchor is three to six for a single-plugin pass: below the floor the run can't conclude anything, and much past six the challenge phase's end-to-end read of every log degrades to skimming, which quietly blinds the critics.

Bound the set explicitly before running, especially under `--self`. The kit auditing the kit can recurse — a dogfood scenario that invokes a skill which itself invokes dogfood — and an unbounded reflexive run never terminates. Fix the scenario list now and treat it as closed; later phases run *these* and only these. Discovering a new scenario mid-run is a finding to record, not a scenario to add to the current pass.

Anti-pattern: choosing scenarios by what's easy to set up rather than what's likely to break. The skill with no flags and no external touches is the easiest to invoke and the least worth dogfooding — its static audit already told you everything a run would. Spend the run on the skills the audits *can't* fully judge.

The output of this phase is a written, closed list: for each scenario, the skill, the flags, the starting state it runs against, and **the defect it hunts**. The rule requires naming each scenario's defect before the run; writing it into the list is what makes that requirement checkable, and it is what the report phase later uses to tell a skill bug from a thin scenario. Carry the list into the run phase unchanged.
