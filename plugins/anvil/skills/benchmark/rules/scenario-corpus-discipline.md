A comparison is only as honest as the scenarios it runs on. Every other bar in this skill — the repeats, the delta against spread, the regressions-first ranking — assumes the two arms were asked the same, fair questions; if the questions were chosen to flatter the change, the machinery downstream just launders a rigged input into a confident verdict. The craft of choosing scenarios that are representative, real-path, and not smoke tests is not restated here — it is [picking-scenarios](../../dogfood/rules/picking-scenarios.md), and it applies unchanged, because a benchmark scenario is first a good dogfood scenario. This rule adds only the disciplines that appear the moment there are *two* arms and a result to be tempted by. The frame-the-comparison phase applies it when it freezes the set and when it reuses a curated corpus as a yardstick; the run-both-arms phase applies it when it holds that identical corpus across both arms; and the aggregate-and-decide phase applies it when a scenario that discriminates nothing is routed back for a corpus fix.

## Freeze the set before you run, and before you look

Both arms see the identical set, and the set is fixed before a single run of either arm — this is the non-negotiable core. The instant the scenarios can differ between the changed tree and the baseline, the per-scenario delta stops being attributable to the change: a difference you can't pin on the code is not evidence, it's an artifact of asking the two versions different questions. Identical inputs are what make the subtraction mean anything.

But identical-across-arms is only half of it. The set must also be fixed *before any result is seen* — closed and written down before the first arm runs, and never edited in light of how a run turned out. The reason is human, not mechanical: once you have watched the change win on some scenarios and stumble on others, you can no longer choose the corpus innocently. Dropping the scenario where the change regressed, or adding one you already suspect it aces, feels like tidying and is actually rigging — and the tell is that you only ever discover these "improvements" to the corpus *after* seeing the score. A scenario that looks worth adding mid-run is a finding for the report and a candidate for the *next* frozen set, exactly as a mid-run discovery is in a dogfood pass — never a live edit to the set being scored now.

## The corpus is a signed artifact, not a target to optimize against

When the caller reuses a curated set via the scenario-reuse flag, that set is a human-signed-off artifact with standing of its own — a fixed yardstick successive iterations of a change are measured against so the numbers stay comparable across passes. Treat it as a yardstick, never as a target. The distinction is the whole game: a change that improves the specific handful of scenarios in the corpus has demonstrated nothing until you believe that handful stands in for the behavior at large. Optimize blindly against a frozen set and you get a change that has learned the test, not the task — so when a reused corpus is carried into a fresh pass, curate it to keep representing the space the skill faces, never to chase the score.

## A benchmark predicts the invocations you did not run

Hold the purpose in view, because it is what every discipline above protects. You will run the skill over a handful of scenarios; it will be invoked, in the field, thousands of times over inputs no one in this pass ever typed. The benchmark has exactly one job — to let the tested handful *predict* the untested multitude — and it can only do that job if the corpus is an unbiased sample of the space the skill actually faces. Every quiet act of tuning the corpus to the change severs that link: a set you have curved toward the thing you're measuring no longer stands in for anything but itself, and the verdict, however green, stops forecasting the field and starts describing a closed loop. Curate the corpus to represent the world, then measure the change against it honestly — never the reverse.
