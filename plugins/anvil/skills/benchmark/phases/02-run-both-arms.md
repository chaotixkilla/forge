Phase 01 framed *what* the comparison is — which change, which baseline reference, which scenarios, how many repeats. This phase produces the raw evidence that comparison will rest on: the paired run logs, one set per version under test. Everything the verdict later claims traces back to what gets recorded here, so the discipline of this phase is not cleverness in running — it is fidelity in *holding two runs identical except for the one thing being measured*.

## Drive dogfood's run-and-observe procedure — and only that

Do not reinvent running a skill from cold. Driving a skill as a fresh executor — the cold-executor stance, the mutation-disposition decisions, the honest per-scenario log of what fired, where it stalled, what it assumed — is already written down as [dogfood](../../dogfood/SKILL.md)'s [run-and-observe procedure](../../dogfood/phases/02-run-and-observe.md), built and hardened for exactly this. That single phase is what benchmark reuses, and *only* that phase. benchmark is **not** a second whole dogfood run: dogfood's contract exposes no seam to hand it a caller-frozen scenario set, no repeat concept, and no knob for which version of the skills to execute, so do not pretend one exists or invoke dogfood end to end hoping to parameterize it — that warm assumption is exactly what breaks a cold executor here. Instead, benchmark drives dogfood's run-and-observe procedure *directly* and supplies from its own phases everything that procedure would otherwise get from dogfood's neighbours.

Concretely, benchmark stands in for the phases on either side of run-and-observe and keeps only the middle one:

- **Scenario selection is benchmark's, not dogfood's.** dogfood's own scenario-pick phase always chooses scenarios afresh; letting it run would give each arm a separately-picked set and silently void the identical-corpus invariant this whole comparison rests on. Bypass it entirely: feed the run-and-observe procedure the closed scenario list phase 01 froze, in place of anything it would pick, unchanged and identical for both arms.
- **Run-and-observe is what benchmark keeps.** For each scenario in the frozen list, run the skill as a cold executor and record what it did, where it stalled, what it assumed — dogfood's run-and-observe procedure followed verbatim, including its mutation-disposition and simulated-capability rules. This is the one dogfood phase benchmark executes.
- **Grading is benchmark's, not dogfood's.** dogfood's challenge and report phases grade and rank its own run; benchmark does not use them. Grading each arm's logs is [03-grade-outcomes](03-grade-outcomes.md)'s job and the verdict is [04-aggregate-and-decide](04-aggregate-and-decide.md)'s, so stop at the end of run-and-observe and hand the raw logs onward untouched. benchmark's job in this phase is to produce evidence twice, in strict correspondence — not to reach a per-run verdict dogfood-style.

Let dogfood's run-and-observe carry the running; benchmark carries the pairing.

## Materialize the baseline arm — and root the run in it

The changed tree is present — it is the working tree you are standing in, and the changed arm's run-and-observe simply runs there. The baseline tree is not present; it must be reconstructed at the reference phase 01 pinned (the last release, the pre-change tree, or whatever `--baseline` overrode it to). Materialize that tree through the configured **version-control capability** — the same capability [release](../../release/SKILL.md) uses to mark a released version — as a clean, isolated checkout of exactly that reference. Name the act at that altitude only: *materialize the baseline tree at the pinned reference.* The concrete commands belong to the version-control adapter, never inlined here; a named tool in this phase is the exact leak the kit's own audits flag.

A checkout on disk is not yet a baseline *run*. dogfood's run-and-observe reads and executes the skill files it finds under the plugin in the working context it is driven from — so the lever that decides *which version of the skills runs* is the execution root, not any dogfood flag. In particular, dogfood's `--subject` overrides the *operand the skills run against*, not *which version of the skills executes*; pointing `--subject` at the checkout would run the **changed** skills against the baseline tree as their subject — the exact inverse of what the baseline arm needs, so do not reach for it. The correct mechanism is the root: drive the baseline arm's run-and-observe with the working directory rooted at the materialized checkout, so every skill file it reads and runs is the baseline version and nothing of the change leaks in. Root the changed arm in the working tree and the baseline arm in the checkout; that difference in execution root — never a `--subject` swap — is the single thing that differs between the arms.

If the baseline cannot be materialized — no version control available, or the reference is ambiguous — stop and say so, because a comparison with only one arm is not a comparison, and a fabricated or approximated baseline produces a delta that measures nothing.

## Run each arm N times — the repeat is benchmark's to orchestrate

dogfood's run-and-observe runs each scenario once; the repeat concept lives nowhere in dogfood — it is benchmark's, carried from [signal-vs-noise](../rules/signal-vs-noise.md). So benchmark drives that single-pass procedure **N times per arm**, where N is the repeat count phase 01 fixed (signal-vs-noise's pinned default of 3, unless `--repeats` overrode it), producing N independent cold runs — and thus N logs — for every scenario on each arm. More than one pass is not optional and not a budget dial you may quietly turn to one: a cold executor is nondeterministic, so a single run of a scenario is one draw from a distribution of possible outcomes, and one draw cannot distinguish a real improvement from a lucky roll or a real regression from an unlucky one. That is why signal-vs-noise mandates repeats and defines how many; a single run is an anecdote, not a measurement, and a verdict built on anecdotes is the failure this whole tier exists to prevent. Each pass must be a genuinely fresh cold execution, reset to the frozen scenario's declared starting state rather than reusing the prior pass's residue, or the N draws collapse into one draw wearing N hats and the spread they exist to measure vanishes. Complete the full N passes on *both* arms before moving on, so phase 04 receives a distribution per scenario per arm, not a point.

## Repeats and mutation: reset, don't accrete

When the skill under test mutates its subject, the fresh-reset the previous section demands needs a concrete mechanism, and it overrides dogfood's default disposition menu. dogfood run once lets a mutation be kept as an attributable commit, reverted after observing, or aimed at a throwaway subject; under benchmark's repeats none of those is right as-is — keeping N×2 mutation commits litters the tree with runs no one will read, and the throwaway-subject route is already ruled out above because `--subject` would misroot the arm. So pin the disposition for repeats: before the first pass of a scenario, snapshot its declared starting state; before each later pass, restore the subject to that snapshot, so every pass is a genuinely fresh draw and not the prior pass's residue graded again. Keep the snapshot-and-restore at capability altitude — restore the subject to its recorded starting state through the version-control capability, or run each pass against a fresh isolated copy of that state — never a named command. A skill that mutates nothing needs none of this: its starting state and the next pass are identical by default.

## Symmetry is load-bearing

The delta between the arms is only meaningful if the arms differ in **exactly one thing**: which version is under test. Every other variable must be held equal, and holding it equal is this phase's core obligation, not an afterthought. Concretely, both arms must run the *same* scenarios, with the *same* inputs and flags, at the *same* repeat count N, under the *same* conditions — the frozen, identical corpus that [scenario-corpus-discipline](../rules/scenario-corpus-discipline.md) requires — and must differ *only* in the execution root that selects the skill version. Any asymmetry silently invalidates the comparison, and the traps are ordinary: giving one arm a richer scenario set than the other; feeding a scenario different inputs between arms; running more repeats on the arm you expect to win; letting a simulated capability return drift between arms so the two versions answer different questions. If a variable cannot be observed to be equal across the arms, make it equal by fixing it — the same seed, the same declared assumptions, the same simulated returns — rather than letting it float. An asymmetric benchmark is worse than none: it launders a difference in *conditions* into an apparent difference in *quality*, and the crisp per-scenario delta hides that it was never earned.

## Record every run attributably

Capture each run's outcome and its full run-and-observe log — what the skill did, where it stalled, what it assumed — and key every one to the triple **(scenario, arm, repeat)**. This addressing is what makes the later phases possible: [03-grade-outcomes](03-grade-outcomes.md) grades each log on its own, and [04-aggregate-and-decide](04-aggregate-and-decide.md) can only line up scenario A's changed-arm distribution against scenario A's baseline-arm distribution if every run says plainly which scenario, which version, and which repeat it was. Preserve the logs intact — do not average, summarize, or collapse them here; aggregation is phase 04's job and needs the individual runs to compute variance. This per-scenario, per-arm pairing is precisely what surfaces the killer case a single dogfood pass and every static critic miss: a change that *fixes* scenario A while silently *breaking* scenario B nets out to "looks fine" in any summary, and only shows itself when A's pair and B's pair are held side by side with their repeats. Losing the attribution loses the regression.
