A benchmark is an A/B, and an A/B is only honest if both arms and the scenarios that judge them are fixed *before* any run. The whole reason to pay for two arms instead of one dogfood pass is regression detection — catching a change that fixes scenario A while quietly breaking scenario B — and that only holds if the two arms are the same skill on the same scenarios, differing in nothing but the diff under test. Move any of those inputs after results appear and the comparison can be made to say anything, and the regression it was built to catch is exactly the one you'd be tempted to define away. This phase pins the comparison so the later phases measure a real delta rather than a rigged one. It runs and writes nothing.

## Resolve the two arms

Name both things being compared before touching anything downstream:

- **The change.** The working-tree diff for the `--plugin`, narrowed to the paths of any `--skill` given. This arm is the plugin's skills *as they stand now* — the edit whose worth is in question.
- **The baseline.** The pre-change tree: what the skill was before this diff. By default that is the last recorded state, fetched through the configured version-control capability — the same capability release leans on to name and pin a released tree. `--baseline` overrides the default when the maintainer wants to measure against a specific prior tree rather than the immediate predecessor. Keep this at capability altitude: the *act* is "retrieve the pre-change tree from version control." The commands that do the retrieval belong to the version-control adapter, never inlined here — naming a concrete tool in a phase is the exact tool-leak the kit's own audits flag.

If no baseline is resolvable — nothing to fetch, no override given — **stop and ask**; do not fabricate one. A delta is a difference against a prior, and there is no difference against nothing. Model this on how release refuses to derive a bump with no history: measuring a change against an unknowable prior produces a verdict that looks like evidence and isn't, which is worse than no verdict. Require an explicit `--baseline` or a version-controlled predecessor before going further.

## Determine the target skills

Default the target to whatever the diff touches — the set of skills with changed files under the `--plugin`. `--skill` narrows that set to one when the maintainer wants a focused comparison even though the diff ranges wider. If the diff touches no skill under the plugin, there is no change to benchmark; say so and stop rather than manufacturing a comparison of a tree against itself.

## Curate the scenario set

Both arms run the *same* scenarios — a scenario is one concrete invocation of a target skill, a flag combination plus enough starting state that the skill has real work to do, and it must be identical across arms or the delta measures the scenario drift instead of the diff. Pick invocations that exercise the skill's real paths, especially the ones the change plausibly disturbs: happy-path smoke tests prove a change is *no worse on the easy cases*, which is not the claim a benchmark exists to make. And the set must **cover the change**: every file the diff touches must be exercised by at least one scenario. A changed file no scenario runs cannot be benchmarked at all — there is no run of that path to observe or grade — so an uncovered changed file is a framing failure to fix *now* (add a scenario that exercises it), never a defect to be discovered downstream where the pipeline has no run to attach it to. `--scenarios` reuses a curated set when one exists — preferred, because a stable corpus makes runs comparable over time; otherwise pick fresh.

The corpus bar this set must clear — representativeness, coverage of the disturbed paths, and how a curated set is kept honest across reuse — lives in [scenario-corpus-discipline](../rules/scenario-corpus-discipline.md). The selection craft for spotting the invocations most likely to break is dogfood's job and is already written down; lean on [picking-scenarios](../../dogfood/rules/picking-scenarios.md) rather than duplicating it here, since benchmark's execution is dogfood run twice and its scenarios are dogfood scenarios.

Fix the scenario set now, before any run, and treat it as closed. Choosing scenarios after seeing results is gaming the benchmark: you would keep the ones that flatter the change and drop the ones that expose its regression, and the regression-detection premise the whole skill rests on collapses. Write the set down — for each scenario, the skill, the flags, and the starting state — and carry that list unchanged into the run phase. A scenario discovered mid-run is a finding to record for a future pass, not an addition to this one.

## Under --dry-run

Stop here and show the framed comparison without writing or running anything: the resolved change (plugin, touched skills, narrowing), the resolved baseline (the prior tree and how it was reached — default predecessor or explicit `--baseline`), the target skills, the closed scenario set, and the planned repeat count (from `--repeats`, else the default pinned in [signal-vs-noise](../rules/signal-vs-noise.md)). The dry run's job is to let the maintainer veto a mis-scoped or mis-baselined comparison *before* it costs the heavyweight two-arm run — so name the exact arms, scenarios, and repeats that would execute, never a vague "will benchmark."
