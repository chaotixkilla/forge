The boundary check in phase 3 is only as good as the classification feeding it: every file under a published source path must carry a verdict — *ships* or *authoring-only* — because phase 3's whole job is to find authoring-only files that ended up on the ships side of the line. A file left unclassified is a file the audit silently passed. So this phase is exhaustive by design: walk the tree, label every file.

The reason the labels matter so much is the install mechanic. **Install copies a published plugin's entire source directory verbatim — there is no per-file exclude and no ignore-list filter at publish time.** Whatever sits under that source path at publish time lands on the consumer's disk. There is no second chance to strip a file out downstream. That single fact is why classification is the heart of this skill: the only thing standing between maintainer tooling and a consumer's machine is whether someone correctly labeled it authoring-only and kept it outside the shipping tree.

## Walk the tree

Enumerate every file under each published source path from phase 1, and every file in the repo's authoring planes (the design/notes plane, the kit's own tree, repo-root maintainer files). Read enough of each file — or rely on its location and kind — to assign a verdict. Location and kind decide alone only where the location's job already fixes the verdict: files under a skill's slot directories (`phases/`, `rules/`, `modules/`, its `usage.md`), `agents/`, `adapters/`, hooks, the plugin manifest, and the config template ship by construction; files under the design/notes plane are authoring-only by construction. Everything else — repo root, a plugin root outside the slot directories, anything whose name merely suggests docs, config, or data — gets opened before it gets a verdict. The plugin explorer reads structure read-only; lean on it to enumerate and characterize rather than guessing from names alone, because a misleading filename ("notes.md" that is actually shipped user docs, or "config" that is actually a maintainer fixture) is exactly the kind of trap a name-only pass walks into.

## Assign the verdict

Apply the classification craft in [ships-vs-authoring](../rules/ships-vs-authoring.md). The durable test that decides every case: **would a consumer who installed this plugin need this file to use it?** If yes, it ships. If no — if the file exists only to *build, audit, document-for-maintainers, or release* the plugin — it is authoring-only.

- **Ships** (consumer-facing, belongs inside a published source path): the skill bodies and frontmatter, the agents the skills recruit, the adapters that resolve capabilities to concrete tools, lifecycle hooks, the plugin manifest, and the config template/schema a consumer fills in. These are the runtime surface of the plugin.
- **Authoring-only** (must live *outside* every published source path): design and decision notes, the authoring kit itself, maintainer scripts and generators, internal contributor docs, scratch and fixture material. None of it is needed to *use* the plugin; all of it exists to *make* the plugin.

## The cases that are easy to get wrong

- **A README or docs file.** Split by audience, not by being documentation. A usage README that tells a consumer how to invoke the plugin ships. A contributor/architecture doc aimed at maintainers is authoring-only — and if it sits at repo root rather than inside a plugin, it is outside every source path anyway, so it ships to no one. Judge by who needs to read it.
- **Config artifacts.** The *template/schema* a consumer fills in to wire the plugin to their environment ships. A *populated* config holding a maintainer's own backend choices or secrets is authoring-only and must never sit inside a source path — flag it hard.
- **Tests and fixtures.** A consumer does not run the plugin's authoring tests, so test suites and their fixtures are authoring-only. The one exception is material the plugin loads at *runtime* (an adapter's data table, a hook's payload) — that ships because the running plugin reads it.
- **A file that is genuinely ambiguous.** Do not force a verdict you cannot defend — and "defensible" has a test: you can name the moment the file gets used. For *ships*, the runtime moment a consumer's session reads it; for *authoring-only*, the making activity it serves (the full form is in [ships-vs-authoring](../rules/ships-vs-authoring.md)). One nameable moment → the verdict stands. Both → genuinely dual-use: mark it *uncertain* and carry it to phase 3 for the boundary-keeper critic to challenge. Neither → you don't know what the file is yet; read it, and if reading doesn't resolve it, *uncertain*. Guessing is worse than either: a wrong "ships" verdict leaks tooling, a wrong "authoring-only" verdict could strip something a consumer needs.

## What you hand to the next phase

A complete verdict map: every walked file tagged ships / authoring-only / uncertain, with its path and which source path (if any) it sits under. Phase 3 needs only to ask, file by file, whether the verdict and the location agree — an authoring-only file inside a published source path is the violation this skill exists to catch.
